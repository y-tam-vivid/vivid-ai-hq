**統合は「消す側に統合済みマークを付ける」だけでは終わっていない。** 消す側の全列と残す側を突き合わせ、残す側が空の項目を移すところまでが統合。備考への退避は記録であって移送ではない。

2026-08-12の実地で確立した手順（`~/data/houjin_bangou/` の `merge_paiti_into_pasti.gs` `delete_merged_rows.gs` が実装）。

```
① 消す側の全項目をログへ出す      ← 行を消すと戻らない。これが唯一の記録になる
② 全列を突き合わせる
     消す側に値あり × 残す側が空       → 移す
     消す側に値あり × 残す側にも値あり  → 残す側を正とする（値が違っても）
     プレースホルダ（入力ガイド文）      → 無視
     捨てると決めた列                  → 移さず備考へ記録
     チェックボックス列                → どちらかが true なら true
③ 集計に効く列（流入経路など）を空にする  ← 忘れると二重計上になる
④ 備考に経緯と捨てた値を書く
⑤ 行を削除する（行番号の大きい順・消す直前にIDを再確認）
```

**注意点**

- **統合で行を残すと、ステータスや注記は直しても集計に効く列を空にし忘れる。** 2026-08-03に統合したB-0370が `流入経路=コミュニティ` を残したまま、統合先にも同じ値があり、8/11まで二重に数えられていた
- **突き合わせ検査は「残す側が空でないこと」しか見ない。値が一致するかは人の目が要る。** 統合先に別人の代表者名が入っていても素通りする
- **重複の発見は電話番号・住所が効く。** 社名の1文字違い（PASTI/PAITI）は文字列比較では拾えない。住所まで一致すれば同一法人の裏付けとして十分
- **正本側（kintone）の削除を先に。** シート行を先に消すとレコード番号の対応が失われる
- IDは欠番になるが、採番は最大値+1なので再利用されない

**廃止した選択肢の後始末はリネームでなく上書きに任せる。** リネームが使えるのは旧値と新値が1対1で対応するときだけ。2026-08-12の実例：kintoneの「イベント」4件は、上書き後に コミュニティ2件／出展・出店2件 へ割れた。「イベント→出展・出店」とリネームしていたら2件が誤った値で固定されていた。**選択肢を消すのは値の移行が終わってから**（先に消すとレコードの値が選択不可のまま宙に浮く）。
