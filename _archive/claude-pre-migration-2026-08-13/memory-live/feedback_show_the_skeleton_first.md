**文書・図・レイアウト・構成を作る前に、完成形の骨組みを3〜5行で見せてから作る。** スクリプトに必ずドライランを付けているのと同じことを、成果物にも適用する。

**Why**：2026-08-12、「登録から受注までの流れを1つの図として書く」と言って、実際には長文10行を書いた。田村さんの言う「図」は矢印と枠の絵で、私の解釈は「構造化された記述」だった。**合意した瞬間には両方とも合意できたと思っている。** 完成品を見るまで発覚せず、そこまでの作業が無駄になった。

自分のメモリ [[feedback_design_diagram_first_minimal_emoji]] に「流れ・関係・階層は図式で見せる。図を1行に潰すのは改悪」と書いてあったのに、それを破っている。**規則を持っていても、着手前に形を見せる一手が無いと守られない。**

**ズレが起きる語**（中身を指さない言葉。これが出たら骨組みを見せる合図）

```
図 / 整理する / まとめる / 分かりやすく / きれいに / ちゃんと / 使いやすく
```

**How to apply**：

- 「〜を作ります」と言った直後、実装に入る前に骨組みを出す。**実装10分でも骨組みは30秒。** 30秒で「違う」と言ってもらえれば、10分が無駄にならない
- 骨組みには「どこに」「何列使って」「どういう並びで」を含める。完成イメージが目に浮かぶ粒度にする
- 決定を記録するときは「何を」だけでなく **「どういう形で」** も書く。形が無い決定は、次のセッションで別の形に作り直される
- 田村さん側の負担は「抽象語に具体例を1つ添える」だけ。これがあると骨組みを外さない

**ズレの型を混同しない**（対処が別）

```
語の解像度が違う   → 骨組みを先に見せる（この項目）
実物を見ずに書いた → [[feedback_read_the_artifact_not_the_copy]]
既決を読まずに提案 → [[project_sales_workbook_read_first]]／③決定・論点ログDB
勝手にスコープ拡大 → 依頼された作業を先に終える。広げるなら先に断る
```
