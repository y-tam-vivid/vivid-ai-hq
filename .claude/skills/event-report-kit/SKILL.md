# Event Report Kit

実施報告書を、次回に使える資産として残すスキル。

原則は2つ。**記載内容はスキーマで固定し、デザインだけを案件ごとに変える。**
そして**企画書のKPIを引き継ぐ**。同じフォーマットで実績を蓄積すれば年次で横比較でき、
次回の予算議論や広報計画の根拠になる。

報告書の価値は「やったことの記録」ではなく「次回の判断材料」にある。
その基準で書く。

---

## Step 0: 材料を集める

報告書に必要な実績は、当日その場でしか取れないものが多い。
不足している場合は、無理に埋めず「未取得」と明記する。推測値を書かない。

| 材料 | 取得元 | 欠けたときの扱い |
|---|---|---|
| 来場者数 | 受付カウント | 概算なら「概算」と明記 |
| 写真 | 記録担当 | 肖像権処理を経てから使う |
| アンケート | 会場回収・QRフォーム | 回収数と回答率を併記 |
| 収支実績 | 経理・領収書 | 確定前なら「速報値」と明記 |
| メディア掲載 | 掲載モニタリング | 掲載日・媒体名・URLを控える |
| SNS実績 | 各プラットフォームのインサイト | リーチ・保存数 |
| 現場の気づき | 撤収後の簡易振り返り | 記憶が薄れる前に拾う |

企画書とKPI目標値は `event-plan-kit` の成果物、または `event-db-sync` の台帳から取得する。
**目標値がない状態で報告書を書かない。** 比較対象がないと達成度を示せない。

---

## Step 1: 構造化する

`assets/report-schema.json` に落とし込む。章立ては `references/report-structure.md` を読む。

KPIは企画書と同じ形式で持つ。

```json
{"指標": "来場者数", "目標値": "200", "実績値": "243", "測定方法": "受付カウント", "未達要因": ""}
```

達成率は自動算出されるので手で書かない。

---

## Step 2: 検証する

```bash
python3 scripts/validate_report.py <報告書>.json
```

機械が判定するのは次の4点。

- **必須項目の充足** — イベント名・開催日・会場・主催者・目的・実施内容・総括
- **KPI対比の成立** — 目標値と実績値が揃っているか。達成率80%未満で未達要因が空なら警告
- **収支の整合** — 収入 − 支出 = 収支 が合っているか。1来場者あたりコストも自動算出
- **主観表現の検出** — 「盛況だった」「成功だった」が数値を伴わずに使われていないか

最後の判定は特に重要。**主観的な感想にとどまる報告書は次回の判断材料にならない。**

| 悪い例 | よい例 |
|---|---|
| 多くの来場者が集まり、成功だった | 来場者は目標200名に対し243名（達成率122%）。事前のSNS告知が寄与したとみられ、特に親子層の比率が高かった |

---

## Step 3: 課題と改善策を書く

**ここが報告書で最も価値のある章。** 数値は記録だが、課題は資産になる。

観点を分けて棚卸しする。

| 段階 | 問い |
|---|---|
| 企画 | 目的とターゲット設定は適切だったか |
| 準備 | スケジュール管理と役割分担に問題はなかったか |
| 集客・広報 | どの媒体が効いたか。効かなかったのはなぜか |
| 当日運営 | スタッフ間・協力先との連携に課題はなかったか |
| 事後 | 回収すべきものを回収できたか |

各課題に**具体的な改善策**を対で書く。「次回は改善する」は改善策ではない。
「受付の待機列が最大15分発生したため、次回は受付を2列にし、事前申込者用のレーンを分ける」まで書く。

未達だったKPIは、原因を分析して残す。未達そのものより、原因不明のほうが問題になる。

---

## Step 4: 出力する

**内容はスキーマ、デザインは案件ごと。**

| 提出先 | 形式 | 使うもの |
|---|---|---|
| 社内共有・行政提出・補助金報告 | Word | `docx` スキル |
| 協力先・協賛への報告、社外プレゼン | PowerPoint | `pptx` スキル |
| ふくち。グループのブランド資料 | PowerPoint/PDF | `fukuchi-deck-builder` スキル |
| 台帳への記録のみ | Markdown | そのまま |

**ブランド指定のある資料は既存のブランドスキルを使う。** 独自に配色を決めない。

写真を掲載する場合、**肖像権の処理を必ず経る**。
報告書は社外へ配布され、回収が難しい。判断基準は `event-social-kit` の
`references/privacy-checklist.md` に従い、迷えば使わない。

---

## Step 5: 台帳へ書き戻す

報告書が完成したら、`event-db-sync` 経由で台帳へ実績を反映する。

- 来場実績、メディア掲載数、SNS実績
- 振り返り（次回に効く気づきを1〜3点）
- ステータスを「振り返り済」へ

**ここまでやって1件が閉じる。** 報告書を作っただけで台帳が更新されていないと、
次回の企画時に前回実績を引けず、同じ調査を繰り返すことになる。

---

## オーケストレーションでの位置づけ

```
event-plan-kit ── KPI目標値を設定
        ↓
event-comms-orchestrator ── 広報を実行、実績を収集
        ↓
event-report-kit（本スキル）── 目標と実績を突き合わせ、課題を残す
        ↓
event-db-sync ── 台帳へ書き戻して1件を閉じる
        ↓
次回の event-plan-kit が前回実績を根拠として引く
```

---

## バンドルされているファイル

- `scripts/validate_report.py` … 必須項目・KPI対比・収支整合・主観表現の検証
- `assets/report-schema.json` … 報告書の統一スキーマ（企画書と共通のKPI形式）
- `references/report-structure.md` … 章立てと各章の書き方、KPIの分類

## 動作要件

Python 3 標準ライブラリのみ。出力形式に応じて `docx` / `pptx` / `fukuchi-deck-builder` を併用する。
