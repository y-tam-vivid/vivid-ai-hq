# 顧客DB反映（kintone反映CSV ＋ Notion顧客DBミラー）

## これは何か
顧客情報を **kintone(正本/SSOT)** と **Notion🏢顧客DB(中間ミラー・法人番号キー)** の2層に反映する定型作業。
- **kintone側**：Claudeは直接書けない。→ **取込用の61列フォーマット(CSV/xlsx)を出力**し、人がkintoneへCSV取込する（重複判定はkintone側の法人番号キーで）。
- **Notion側**：コネクタで直接 upsert する。既存は**空欄のみ補完（非破壊）**、新規のみ作成。

入口は3パターンでも、**難所と出口は同じ**（61列化 → 突合 → kintoneファイル出力 → Notion upsert → 検証）。まず入力タイプを見極め、共通処理へ合流させる。

固定の参照（DB ID・61列・スキーマ・担当者ID）は必ず `references/targets.md` を読むこと。地雷の詳細チェックリストは `references/gotchas.md`。

---

## Step 0-前提. 入れ先の判定 ― toB か toC か（最初に確定）
- **toB（法人・事業者）** → 🏢顧客DB（kintoneミラー・法人番号キー `collection://f506787d-4e72-4c7f-a1f4-0c657f54afc8`）＝**本スキルの対象**。
- **toC（個人・資産形成/投資商材の顧客）** → 📇toC顧客台帳 ①個人顧客マスター（`collection://5758448f-778d-4eb1-ba76-81f4e4de4634`）。手順は [[project_toc_customer_ledger]]。本スキルでは作成せず交通整理のみ。
- **判定ルール**：フォルダ/ファイル名の `_toB`（法人）/`_toC`（個人・投資商材）で明示。無ければ内容で自動判定＝**法人格・事業者として関わる相手=toB／個人が資産形成・保険・投資商材の顧客=toC**。確信不可のみ確認。
- toBで関わった経営者個人へtoC商材（クロスセル）は両方に登録し、toB×toC を関連法人relで橋渡し（toC側の運用）。

## Step 0. 入力タイプを見極める（分岐はここだけ）
- **①名刺**：画像/OCR(raw.csv)。1社1レコードへ統合(表裏/EN併記マージ)＋WEB補完が必要。新規取得＝多くは「見込み客」。
- **②共有データCSV**：kintoneエクスポートや企業リスト。ほぼ構造化済み→列マッピング＋WEB補完。
- **③既存顧客の更新**：既存レコードへ項目追加/補完。差分だけ抽出し、**必ず既存に突合してUPDATE**（新規作成しない）。
- **④コミュニケーションログ**：LINEトーク履歴(txt)、Facebook Messengerエクスポート(html)、メール等の会話ログ。→ 相手を①〜③の要領で顧客DBに用意しつつ、**会話は下の「コミュニケーションログの取り込み」節**で📨ログDBへ格納。

どのパターンも以降の Step は共通（④はログ格納節も併走）。

## Step 1. 61列フォーマットへ整形
`references/targets.md` の61列に機械転記（python推奨）。
- ①名刺：raw.csvを法人番号/社名で1社統合。表裏/EN/ひらがな重複を畳む。住所から郵便番号分離。役職・URLはプロフィールへ。
- ②③：ソース列を61列へ名寄せマッピング。
- **カナ3列**(顧客名/代表者/先方担当)は自動確定せず空欄＋黄色フラグ（人手確定）。
- 自社取引担当者は**案件ごとに指定**を確認（既定で埋めない）。

## Step 2. 法人番号・企業属性をWEB補完
法人番号(13桁)・資本金・従業員・設立・事業所数・インボイス番号を、**general-purposeエージェントを10〜14社刻みで並列**起動して取得。
- 主力：国税庁法人番号(houjin-bangou.nta.go.jp) → GBizINFO(info.gbiz.go.jp) → インボイス公表(invoice-kohyo) → 各社HP。
- **名寄せの鉄則**：社名だけで決めず、住所・URL(ドメイン)・代表者のいずれかと突合。確信不可は空＋conf=low＋理由。**推測で数値を埋めない**。
- 個人事業主・士業の共同事務所・海外法人は**法人番号なしが正常**（空が正）。

## Step 3. 既存Notion顧客DBと突合（重複防止の核）
Notionの現DBを `SELECT url,Name,法人番号,カスタマーID` で取得し、各社を突合：
- **一致キー**：①法人番号(13桁) → ②正規化した社名(株式会社/合同会社等・英語括弧・空白を除去しNFKC)。
- **英語⇔日本語の表記差はnorm正規化で漏れる**（GLOBAL NET↔グローバルネット / AtoX Directions↔AtoXディレクションズ / NMarketing↔ラクラクAI 等）→ **手動エイリアスで同一判定**して二重登録を防ぐ。ここは毎回目視で create リストを走査すること。
- 表/裏ペアや広告面など**連絡先も代表者も無い空シェル**は裏面/非企業の疑い→ドロップ判断。
- 分類：`enrich`(既存に法人番号が無く今回取得→補完) / `create`(新規) / `skip`(一致済)。

## Step 4. kintone取込用ファイルを出力（kintone反映）＝**担当者マスターに日付タブ追記方式**（2026-07-31変更）
取り込みごとに別名ファイルを作らず、**担当者ごとの1マスターファイルに `追記_YYYYMMDD` シート（タブ）を増やしていく**。マスターの単位＝名刺の出所/担当者別（既定）。
- **出力先マスター**：`…/11_取引先・人物別/顧客情報kintone反映csv/[担当者]顧客情報kintone反映csv.xlsx`（例 `[松本]…` `[有璽]…`）。無ければ新規作成し、先頭に61列の空マスターシート＋READMEシートを置く。
- **手順（python/openpyxl）**：
  1. **クラウド実体化**：Google Driveのオンライン専用ファイルは openpyxl で開けず `File is not a zip file` になる。先に `cat "<file>" >/dev/null` 等でローカルDLをトリガーしてから開く。`~$xxx` はExcelロック中の一時ファイル→対象外。
  2. **必ずバックアップ**：同一ファイル上書きになるため、追記前に `_backups/[担当者]…_YYYYMMDD_HHMM.xlsx` へ `cp`（md5照合）。これで旧「元ファイルは上書きしない」＝非破壊原則をバックアップで担保する。
  3. `load_workbook` で開き、**既存シートは保持したまま** `追記_YYYYMMDD` シートを新規追加（61列・黄色フラグ・コメントは従来どおり）。同日再取込は `追記_YYYYMMDD_2` 等で衝突回避。READMEシートは1枚に集約し末尾へ処理ログを追記。
  4. `save` で同名上書き（＝タブが1枚増える）。ローカル同期パス上で保存すればDriveへ自動反映。
- 黄色セル＝要確認（カナ／WEB確度low・mid）。法人番号セルに確度・名寄せ注意・出典をコメント。
- **大容量(100KB級)を新規に別配置する場合のみ**ローカル同期で `cp`（md5照合）。MCPのcreate_fileは内容インライン必須で法人番号/電話が化けるため使わない。
- この後、**人がkintoneへCSV取込**（重複判定はkintone側で法人番号を重複禁止フィールドに）。取込対象は最新の `追記_YYYYMMDD` タブのみを指定する。

## Step 5. Notion顧客DBへ upsert
`references/targets.md` のミラースキーマへマッピングして反映：
- **create**：新規ページ作成。名刺のみ由来の未登録リードは `種別=見込み客`・`kintone反映=未`、既にkintone顧客なら `顧客=済`。`自社取引担当者` は担当者マスターへのrelation。
- **enrich（既存更新）**：**空欄のみ補完（非破壊）**。既存の値・人手メモは上書きしない。法人番号など未入力キーを埋めるのが主目的。
- **流入経路/紹介者**：kintoneの `流入経路`＋`顧客紹介者名`＋`流入経路詳細` を、Notion `流入経路` プロパティに「経路 / 紹介:◯◯」と**併記**して一目で見えるように。

## Step 6. 反映後の必須検証（手転記化けを潰す）
create/update はプロパティをインライン記述するため、**特定漢字が稀な異体字に化ける**（畠→畑、袋→裋、門→隀、田→異、坂→坐、地→圠、道→逓、軒→軍、木→杩 等）。
- 反映後に `SELECT Name,法人番号,カスタマーID,代表者,メモ` を取得し、原本(python側の正データ)と突合。**Name/法人番号/カスタマーIDは完全一致を必須**、本文の化けを洗い出す。
- 修正は `update_properties`。**修正時も同じ化けを繰り返す**ので、化けやすい漢字は\u エスケープでなく直接日本語で書き、再検証する。
- 最後に `SELECT COUNT(*), COUNT(法人番号), COUNT(DISTINCT 法人番号)` で **法人番号の重複ゼロ**を確認。

## コミュニケーションログの取り込み（LINE / Messenger / メール等）＝④入口
やり取りログを **📨コミュニケーションログDB**（ID・スキーマは `references/targets.md`）へ1スレッド=1レコードで格納し、相手を🏢顧客DBへRelationする。どのClaude(別タブ)でもこの手順で横断的に処理できる。

1. **相手を特定して顧客DBに用意**：ログの相手企業/人物を突合。🏢顧客DBに無ければ先に顧客レコードを作成（見込み客・Step2〜5）。ログのRelation先にする。1スレッドに複数社が絡む時は主たる相手を選ぶ。
2. **ログを1レコード作成**：`スレッド名 / チャネル(LINE/Messenger/メール/電話/Chatwork/Slack…) / ステータス(進行中/完了/保留) / 参加者 / 期間 / 最終やり取り日 / 相手（顧客）→🏢顧客DB(relation) / 自社担当→👤担当者マスター(relation)`。
3. **本文の型**：`📌最新サマリ(日付つき・最上部)` → `🧭経緯タイムライン(表)` → `💬主要往復(抜粋)`。最新サマリは追記のたび更新（[[feedback_notion_latest_version_top]] 最新版を最上部）。パイロット1本目のみ原ログ全文をコードブロックで可、以降はサマリ＋主要往復で十分。
4. **原ログ全文はDrive原本で保管**（byte正確・DL可・化け回避）：`…/マイドライブ/Downloads書類アーカイブ/11_取引先・人物別/コミュニケーションログ原本/` へ判別可能名でcp（md5照合）。Messenger等のhtmlはpythonでタグ除去し参加者・本文を抽出してサマリ化。**原ログ全文をNotion本文へ逐語転記しない**（長文＋化け源）。
5. **自ページURLを埋める**：作成後、各ログの `本ページURL_kintone貼付用` に自ページURLを設定。
6. **kintone相互リンク**：kintone顧客レコードに「NotionログURL」列を用意し、`法人番号, 会社名, チャネル, NotionログURL` のCSVを出力→人が**法人番号キーで更新取込**（手貼りゼロ）。法人番号なし(個人事務所/NPO一部/個人)は会社名で手動照合と備考に明記。逆方向はkintoneの「法人番号＋レコードURL」をもらえばNotionの空`kintoneレコードURL`列を一括反映。
7. **商談/面談の議事録は分離**：🌐全社議事録DB（同思想＝相手Relation＋最上部サマリ）へ。ログDBと議事録DBは別、両者を🏢顧客DBにRelationして横断で後追い可能に。
8. **人材・除外の扱い**：複業/紹介の人材プロフィールは `種別=人材` で顧客DBへ（所属先企業は顧客化しない）。**自社の業務委託者は顧客DBに含めない**。
9. 化け検証は顧客と同じ（**日本語を直接記述**→SELECT突合）。
