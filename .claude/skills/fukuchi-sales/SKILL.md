## 判断軸

### 1. 営業の手数を増やす変更はしない

- **★営業が手で入れる項目を増やす提案は、原則として却下する。** 入れなければ台帳が埋まらず、埋まらなければ仕組み全体が死ぬ。「あると便利」で列を増やさない。
- **同じ情報を2度書かせない。** 案件シートに会社名を手打ちさせるような設計にしない。鍵（社内顧客ID）だけ入れさせて残りは自動で引く。
- **人がやっている移送・転記を見つけたら、残す理由を問う。** 理由が「まだ作っていないから」なら、それは仕様ではなく借金。自動化する。
- 入口は増やしてよいが、**行き先は1つに保つ**。入口が3つでも着地は `00_企業マスタ` / `02_個人マスタ`。

### 2. 層を並走させない

- **案件層（スプレッドシート）と確定層（kintone）を並走させない**（2026-08-02決定）。kintoneの案件をシートへ戻さない。シートの上流値をkintoneへ入れない。
- 同じものを2箇所に置いた瞬間、どちらが正か判定できなくなる。**語彙を揃えることより層の役割分担を優先する。**
- Notionは読む場所。**🏢顧客DBの事実列は編集しない**（次の同期で上書きされる）。

### 3. 誤ったIDは空欄より有害

- 法人番号は kintone の結合キーなので、誤ると**別法人に紐づく**。採用条件は「13桁＋検査数字＋国税庁の商号が社名と一致」。
- **推測でデータを埋めない・書き換えない。** 不明は空欄のまま残す。
- 社内顧客IDの分け目は「法人か個人か」ではなく **「請求書の宛先はどちらか」**（`B-####` / `C-####`）。同じ相手にIDが2つ付くのは正常。

### 4. 選択肢を変えるときは、リネームか上書きかを先に決める

```
意味は同じで名前だけ変える        → リネーム（既存の値はそのまま生きる）
意味が割れる・区分の定義が変わる  → 上書き（1件ずつ正しい値を入れ直す）
```

**混同すると、リネームで誤った値が固定される。** 2026-08-09に「イベント」を廃止したとき、上書きしたことで4件がコミュニティ2件／出展・出店2件に割れた。リネームしていたら2件が誤ったまま残っていた。

### 5. 正本の削除は人の手に残す

- **正本（kintone・マスタ）の行削除は当方では行わない。** 削除スクリプトを渡して人が実行する。
- 不要な行はステータスで表す。消さずに状態で表す。

### 6. 機微の置き場

- **銀行口座情報（金融機関名・コード・支店・口座種別・番号・名義・店番・通帳記号／番号）は kintone 留置。** 企業マスタ・顧客詳細・取込CSV・Notionに入れない。
- toCの資産・収支・保険は**内容と金額を Notion**、**決済情報は kintone**。提案に使う数字と、漏れたときの被害が大きい情報を分ける。
