# Event DB Sync

対外イベントの情報を整理し、NotionのイベントDBへ正確に反映するスキル。

広報の実務は担わない。**台帳を正しく保つこと**が役割で、広報は `event-comms-orchestrator` が
この台帳を読んで動く。台帳が汚れると下流の全てが狂うため、正確性を速度より優先する。

## 適用範囲

| 対象 | 扱い |
|---|---|
| 主催・共催・出展する対外イベント | 本スキル |
| 広報・集客を伴う催事、セミナー、展示会 | 本スキル |
| LIFE STAND UP の療育イベント（放デイの外出・施設内行事） | `standup-event-notion-importer` |
| 社内会議・研修 | 対象外。通常のカレンダー運用で足りる |

判断に迷ったら「外部に告知するか」で分ける。告知するなら本スキル。

---

## ワークフロー

```
1. 入力を集める      … メモ・口頭・資料から材料を拾う
2. 構造化する        … レコード形式へ正規化。推測項目を洗い出す
3. 検証する          … validate_record.py で機械チェック
4. 重複を照合する    … 必ず実データで確認
5. 起票・更新する    … 承認を得てからMCPで反映
6. 報告する          … 何を入れたか、何が未確定かを伝える
```

---

## Step 1: 入力を集める

企画情報は整った形では来ない。会話の断片、チラシの写真、見積書、口頭の決定事項が混ざる。
まず材料を並べ、**確定している事実と、まだ決まっていないことを分離する**。

「たぶん無料」「確か9月頃」といった曖昧な情報は、確定情報として扱わない。
その旨のまま次のステップへ持ち込む。

---

## Step 2: 構造化する

`assets/event-record-template.md` の項目へ落とし込む。プロパティの型と正式名称は
`references/notion-structure.md` を読む。

### 推測してはいけない5項目

以下が空欄のまま起票しない。**必ずユーザーに確認する。**

| 項目 | 誤ると何が起きるか |
|---|---|
| 会場（正式表記・階層・区画） | 来場者が辿り着けない |
| 参加費（無料／有料・金額） | 告知の信頼を失う |
| 予約（要否） | 当日トラブルになる |
| 自社の立場（主催／共催／出展／協力／後援） | 関係先に失礼になる |
| 主催者・共催者の名称と表記 | 併記漏れは関係悪化に直結する |

チラシや写真から読み取れた情報も裏取りではない。「◯◯と読めますが、正式表記を確認させてください」と返す。

情報の正規化ルール（日付表記の揺れ、時間の書式、会場名の階層表記）は
`references/intake-normalization.md` を読む。

---

## Step 3: 検証する

```bash
python3 scripts/validate_record.py <レコード>.json
```

機械的に判定できることは機械に任せる。出力は4種類。

- **エラー** … 必須項目の欠落、日付の逆転、値の不正。解消するまで起票しない
- **確認要求** … 推測してはいけない5項目の空欄。ユーザーに聞く
- **警告** … 開催日が過去、プレスのリードタイム割れ、書式の揺れ
- **重複照合クエリ候補** … 次のステップで使う固有語

日本語は空白で区切られないため固有語の自動抽出には限界がある。
候補が少ないときは警告が出るので、会場名や主催者名を手で足す。

---

## Step 4: 重複を照合する（省略しない）

**登録前に必ずイベントDBを検索する。** 会話の記憶や引き継ぎメモではなく、実データで確認する。
別セッション・別担当者が先に起票しているケースがあり、照合を怠ると重複が生まれる。

照合には**そのイベント固有の語**を使う。「夏祭り」「相談会」「体験会」のような汎用語は
複数年・複数拠点に登場するため照合に向かない。会場名、主催者名、開催年を組み合わせる。

ヒットした場合の判定。

| 状況 | 判断 |
|---|---|
| 同名かつ同一年月 | 真の重複。既存を更新する（新規作成しない） |
| 同名だが年が違う | 別イベント。新規作成してよい |
| 名称が近いが会場が違う | ユーザーに確認する |
| 0件 | 新規作成して安全 |

---

## Step 5: 起票・更新する

### 書き込み前に必ず確認する

応答の末尾で確認し、承認を得てから反映する。

> Notionへ最新情報を反映しますか？（対象DB：イベント管理DB）

新規作成・更新・ステータス変更のいずれも同じ。読み取りは確認不要。

### ステータスの遷移

```
企画中 → 開催決定 → 告知中 → 開催中 → 終了 → 振り返り済
```

**「開催決定」への遷移が広報の起点**になる。ここで `event-comms-orchestrator` へ引き継ぐ。
ステータスを更新したら、その旨をユーザーに伝えて広報計画の生成を促す。

### 更新時の原則

- 既存ページを特定してから更新する。迷ったら新規作成せず確認する
- 実績値（来場数・掲載数）は確定してから入れる。速報値を入れる場合はその旨を明記する
- 過去の記録を上書きしない。追記で残す

Notion MCP特有の入力形式（親IDの指定、日付の分解、リレーションの記法）は
`references/notion-structure.md` に落とし穴をまとめてある。**必ず読んでから書き込む。**

---

## Step 6: 報告する

反映後、次を簡潔に伝える。

1. 何件を新規作成／更新したか
2. 未確定のまま空欄にした項目
3. 推測で埋めた箇所があればその根拠
4. 次のアクション（ステータスが「開催決定」なら広報計画の生成を提案）

## オーケストレーションでの位置づけ

```
event-db-sync（本スキル）
   │ ステータス「開催決定」
   ▼
event-comms-orchestrator … 配信カレンダー生成
   ├─ event-social-kit    … SNS素材・キャプション
   ├─ event-press-kit     … プレスリリース（未実装）
   └─ event-report-kit    … 事後報告（未実装）
                              │ 実績値
                              ▼
                         event-db-sync（本スキル）へ戻す
```

台帳は起点であり終点でもある。会期終了後、実績を本スキルで書き戻して1件が閉じる。

---

## バンドルされているファイル

- `scripts/validate_record.py` … 起票前の検証と重複照合クエリ生成
- `assets/event-record-template.md` … レコードの項目一覧
- `references/notion-structure.md` … DBプロパティ設計とMCP入力形式の落とし穴
- `references/intake-normalization.md` … 断片情報の正規化ルール

## 動作要件

Python 3 標準ライブラリのみ。Notion MCP が必要。
