# Production Management

主催・共催イベントの実施体制と当日運営。Step 3 で読む。

---

## 1. 必須の4役割

規模の大小にかかわらず、この4つは必ず立てる。兼任は可、不在は不可。

| 役割 | 業務 | 不在だと何が起きるか |
|---|---|---|
| **総括** | 全体判断・来賓対応・変更時の決定 | 想定外が起きたとき判断が止まる |
| **受付** | 受付・配布物・**来場者数の実測** | KPIの根幹が測れず報告書が書けない |
| **記録** | 写真・動画撮影、SNS素材の確保 | 広報素材も報告書の写真も残らない |
| **安全** | 導線管理・救護連絡・緊急対応 | 事故時の一次対応が遅れる |

**受付と記録は後から取り返せない。** 当日その場でしか取得できないため、
最優先で人を割く。総括が兼任すると判断が遅れるので、可能なら分ける。

各担当の**連絡先を必ず記入する**。当日会場内で連絡が取れないと、判断も伝達も止まる。

## 2. 香盤表の作り方

`build_runsheet.py` が骨格を生成する。生成後、次を人が確認する。

- **設営時間は足りるか** — 初めての会場は想定の1.5倍を見る
- **リハーサルを入れたか** — 音響・映像・通信は必ず実機で確認する
- **開場前ブリーフィングを入れたか** — 当日変更の共有はここでしか行えない
- **休憩と余白があるか** — 分刻みで詰めると1つの遅れが全体を崩す
- **撤収後の簡易振り返り** — その場で3点だけ口頭共有する。記憶が新しいうちが最も濃い

プログラム合計が終了時刻を超過している場合はスクリプトが警告を出す。
超過したまま当日を迎えると、必ず最後のプログラムが削られる。

## 3. 当日フローの設計

来場者の動線を、入口から出口まで一本で書く。

```
到着 → 案内表示 → 受付 → 配布物 → 導線 → 体験/観覧 → アンケート → 出口
```

各接点で「誰が対応するか」を決める。決まっていない接点が事故の起点になる。

- **受付の滞留**が最も起きやすい。ピーク時の想定人数を捌けるか計算する
- **アンケートは出口で回収する**。会場内で配ると回収率が落ちる
- **子ども連れがいる場合**、ベビーカー動線とトイレ位置を事前に確認する

## 4. リスク管理

想定して書いておく。書いたリスクは起きても対応できる。

| リスク | 事前に決めておくこと |
|---|---|
| 雨天・荒天 | 実施可否の基準、判断時刻、決定権者、告知手段 |
| 集客未達 | 何人を下回ったらどう動くか（当日の追加告知など） |
| 機材・通信障害 | 代替手段の有無。オフラインで成立するか |
| 事故・急病 | 一次対応者、会場救護室の場所、救急連絡先 |
| 来場超過 | 入場制限の基準と方法 |
| 撮影トラブル | 撮影可否の掲示、許諾の取り方 |

**中止判断は基準と決定権者をセットで決める。** 誰が決めるか曖昧だと、
当日に責任の押し付け合いが起きる。

保険（イベント保険・賠償責任保険）の要否は、規模と会場の規定で変わる。
会場管理者に確認する。

## 5. 準備工程の逆算

開催日から逆算し、リードタイムのある工程を先に置く。

| タイミング | 工程 |
|---|---|
| D-90〜60 | 会場押さえ、企画確定、決裁 |
| D-45 | 協力先への依頼、見積確定 |
| D-30 | 印刷物入稿、備品発注、メディア招致 |
| D-21 | 広報素材の準備 |
| D-14 | プレスリリース配信、申込受付開始 |
| D-7 | 体制確定、香盤表配布、会場との最終確認 |
| D-3 | 備品搬入、リハ準備、最終リマインド |
| D-1 | 前日設営（可能なら）、全員へ最終共有 |

広報側の逆算は `event-comms-orchestrator` の `build_schedule.py` が担うので、
企画書には準備工程だけを書く。二重に管理しない。
