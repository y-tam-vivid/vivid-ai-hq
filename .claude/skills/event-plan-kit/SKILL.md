# Event Plan Kit

対外イベントの企画書を、決裁が通る粒度で作るスキル。

原則は2つ。**記載内容はスキーマで固定し、デザインは案件ごとに変える。**
そして**企画書のKPIは報告書の実績欄と対になる**。同じ器で目標と実績を持つから、
終了後に達成度が自動で成立し、年次で横比較できるようになる。

---

## Step 0: 粒度を決める

自社の立場によって必要な粒度が変わる。過剰な企画書は書く側も読む側も消耗する。

| 立場 | 必要な範囲 |
|---|---|
| **主催** | 全項目。特に実施体制・進行管理・リスク対応・予算は必須 |
| **共催** | 全項目だが、分担範囲を明記。相手方の担当領域は「◯◯社担当」と書く |
| **出展** | 目的・ターゲット・出展内容・KPI・予算・当日体制。会場運営は主催者に依存 |
| **協力・後援** | 目的・関与範囲・提供リソース・クレジット表記。進行管理は不要 |

立場が確定していない状態で書き始めない。`event-db-sync` の台帳から取得する。

---

## Step 1: 5W2Hで骨格を固める

先に骨格を固めると、目的・予算・スケジュールの一貫性が取れ、書き直しの手戻りが減る。
**Why（目的）から決める。** 目的が決まればWhom・Whatは自然に絞り込まれる。

| 観点 | 問い |
|---|---|
| Why | なぜやるのか。やらなかった場合に何が起きないのか |
| Whom | 誰に来てほしいのか。何人か |
| What | 何を提供するのか |
| When | いつか。なぜその時期か |
| Where | どこか。なぜその会場か |
| How | どう運営するか。誰が何を担うか |
| How much | いくらかかるか。財源は何か |

目的は「関わる人が、とるべき行動を決められる」水準まで具体化する。
「認知拡大」では現場が動けない。「◯◯層に◯◯を体験してもらい、後日の相談件数につなげる」まで書く。

章立てと各章の書き方は `references/plan-structure.md` を読む。

---

## Step 2: KPIを設計する

**ここが企画書の要。** 効果測定の指標を企画段階で決めておかないと、終了後に成果を評価できない。

指標は3〜5個に絞る。多すぎると誰も追わない。各指標に「目標値」と「測定方法」を必ず添える。
測定方法が書けない指標は、実際には測れないので採用しない。

| 分類 | 指標の例 | 測定方法の例 |
|---|---|---|
| 集客・認知 | 来場者数、新規比率、メディア掲載数、SNSリーチ | 受付カウント、掲載モニタリング、各SNSのインサイト |
| 満足・関与 | アンケート回答数、満足度、再来意向 | 会場配布・QRフォーム |
| 事業成果 | 相談件数、申込数、契約数 | 受付票、後日の追跡 |
| 運営品質 | 受付待ち時間、タイムテーブル遵守率 | 当日記録 |

KPI欄のスキーマは `assets/plan-schema.json` を使う。この形式で持てば、
`event-report-kit` がそのまま実績欄として引き継げる。

---

## Step 3: 実施体制と進行管理を組む（主催・共催のみ）

主催イベントは、当日「誰が・いつ・何をするか」が決まっていないと破綻する。

```bash
python3 scripts/build_runsheet.py --config <設定>.json \
  --out /mnt/user-data/outputs --prefix <識別子>
```

開催時間とプログラムから、設営・リハーサル・ブリーフィング・進行・撤収・簡易振り返りまでを
分単位で並べ、役割分担表と併せて出力する。

このスクリプトは次を自動で検出する。

- プログラムの合計時間が終了時刻を超過している場合の警告
- 必須役割（総括・受付・記録・安全）の未割り当て
- 担当者の連絡先未記入

**受付と記録は必ず置く。** 受付がないと来場者数の実測が取れず、報告書のKPIが埋まらない。
記録がないと広報素材も報告書の写真も残らない。後から取り返せない項目。

体制設計・緊急時対応・リスク項目の詳細は `references/production-management.md` を読む。

---

## Step 4: 予算を組む

- 収入（参加費・協賛・補助金）と支出（会場・機材・人件・広報・保険・予備費）を分けて書く
- **予備費を10%前後見込む。** 当日の想定外は必ず起きる
- 決裁者は費用対効果を見る。KPIの目標値と突き合わせ、1来場者あたりコストを示すと判断しやすい
- 過去に同種イベントがあれば、その実績を根拠として引く（`event-db-sync` の台帳から取得）

---

## Step 5: リスクと代替案を書く

決裁が通らない企画書は「決裁者の関心」「KPIの具体性」「リスク・代替案」のいずれかが
欠けていることが多い。リスクは書いたほうが通る。

最低限、次を想定する。

- 雨天・荒天（屋外・移動を伴う場合）
- 集客未達（何人を下回ったらどうするか）
- 機材・通信の障害（代替手段の有無）
- 事故・急病（一次対応と連絡先）
- 中止判断の基準と決定権者、告知手段

---

## Step 6: 出力する

**内容はスキーマ、デザインは案件ごと。**

| 用途 | 形式 | 使うもの |
|---|---|---|
| 社内決裁・行政提出 | Word | `docx` スキル |
| プレゼン・協力先提示 | PowerPoint | `pptx` スキル |
| ふくち。グループのブランド資料 | PowerPoint/PDF | `fukuchi-deck-builder` スキル |
| 概要共有のみ | Markdown | そのまま |

**ブランド指定のある資料は必ず既存のブランドスキルを使う。** 独自に配色を決めない。

出力後、企画内容を `event-db-sync` へ反映し、ステータスを「開催決定」へ進める提案をする。
そこから `event-comms-orchestrator` が広報計画を引く。

---

## バンドルされているファイル

- `scripts/build_runsheet.py` … 香盤表・役割分担表の生成
- `assets/plan-schema.json` … 企画書の統一スキーマ（報告書と共通のKPI形式）
- `references/plan-structure.md` … 章立てと各章の書き方、決裁を通す観点
- `references/production-management.md` … 実施体制・当日運営・リスク管理

## 動作要件

Python 3 標準ライブラリのみ。出力形式に応じて `docx` / `pptx` / `fukuchi-deck-builder` を併用する。
