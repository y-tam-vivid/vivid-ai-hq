# STAND UP イベント Notion 移行スキル

放課後等デイサービス「LIFE STAND UP」（株式会社ILIFE／大阪府藤井寺市）のイベント企画・報告書を、
Notion の 3 データベース構造へ移行・登録するための手順書。**1イベント = 1企画書 = 1報告書**（同一施設の
統一様式）を前提に、Google Drive のドキュメントから Notion レコードを生成する。

このスキルの肝は **(1) 登録前の重複照合を絶対に省略しないこと**、**(2) 報告書の収支内訳から学年構成を
復元するなどの抽出ルールを守ること**、**(3) NotionのMCP特有の入力形式を守ること** の3点。各詳細は
`references/` を参照する。

---

## 前提条件（最初に確認）

1. **コネクタ**: Notion MCP と Google Drive MCP の両方が接続されていること。どちらかが無ければ、その旨を
   伝えて接続を依頼する。
2. **固定リソースID**: 3つのコアDBの `data_source_id` と Google Drive 親フォルダIDは固定。
   `references/notion-structure.md` の冒頭に記載。**これらは毎回ハードコードで使ってよい。**
3. **可変リソース**: 訪問先（場所マスター）の各 `page_id` と、Driveの年度シーズンフォルダは増えていく。
   **ハードコードせず、毎回 検索・一覧取得で解決する**（手順は後述）。

---

## ワークフロー

本スキルは2つのモードを持つ。入力ソースで判断する。

- **モードA：過去報告書の移行**（Google Docs形式の企画書・報告書 → Notion）。既存の一括移行作業。
- **モードB：継続運用での新規起票**（統一Wordテンプレート＋Excel試算表 → Notion）。企画段階の登録と実施後の報告更新。

共通して **Step 2（既存照合）〜Step 5（登録）の考え方は同じ**。違いは入力の取得方法と、モードBでの
企画／報告の2段階（新規作成＋更新）。

---

## モードA：過去報告書の移行

処理は **新しい年度・シーズンから順に** 行うのが既定。1フォルダ（1シーズン）単位で Step 1〜5 を回す。

### Step 1. 対象フォルダの一覧取得

Google Drive 親フォルダ「イベント企画・報告書」配下の、対象シーズンフォルダの中身を取得する。
まずは**軽量な一覧**（スニペット無し）でファイル構成を把握する。

```
search_files(query="parentId = '<シーズンフォルダID>'", excludeContentSnippets=true, pageSize=100)
```

ファイル名から、その期に何イベントあるか（単発／複数日）と、各イベントの企画書・報告書ペアを把握する。
ファイル名の日付・イベント名がそのまま種別判定のヒントになる（例: `4.6 ... kidzania` → 外出、
`8.3~9 Summer festival` → 複数日）。

### Step 2. 既存照合（**絶対に省略しない**）

**過去のセッションが一部を登録済みのことがあり、照合を怠ると重複が発生する。** 登録前に必ず
イベントDBを検索し、対象シーズンのイベントが未登録であることを確認する。

```
notion-search(data_source_url="collection://<イベントDB data_source_id>",
              query="<そのシーズンに固有のイベント名を2〜4語>")
```

照合クエリには **そのシーズンに固有のキーワード** を選ぶ。例えば「プラネタリウム」「夏祭り」「映画」
「ボウリング」「いちご狩り」「クリスマス」は複数シーズンに登場するため照合に不向き。代わりに
「ガス科学館 NIFREL」「キッザニア 防災」「おにぎらず ナン パニーニ」のような、その期だけに出る固有名を使う。
**0件ヒット → 新規登録して安全。** 既存ヒットがあれば、日付（年）まで突き合わせて同名別年か真の重複かを判定する
(同名でも実施日の年が違えば別イベントであり、重複ではない)。

### Step 3. 報告書（report）の取得

各イベントの実数（参加者・収支・振り返り）は報告書から取る。報告書だけをスニペット付きで一括取得する。

```
search_files(query="parentId = '<フォルダID>' and title contains 'report'", pageSize=100)
```

- スニペットに収支・参加者・振り返りが含まれるので、**多くはこれだけで登録できる**。
- **巨大ファイル（夏祭りreport等、40KB超）はスニペットがコンテキストを圧迫する**ため、`title contains 'report'
  and not title contains 'festival'` で除外して一括取得し、巨大ファイルのみ個別に
  `read_file_content(fileId=...)` で読む。
- 報告書が無く企画書しか無いイベントは、企画書から登録し、振り返り欄にその旨を注記する。

抽出ルール（学年構成の復元、男女比、種別判定、収支の分離記録）は **必ず** `references/extraction-rules.md`
に従う。

### Step 4. 訪問先の照合・新規作成（外出イベントのみ）

外出イベントは場所マスターに紐付ける。**既存施設の再利用を最優先**し、無ければ新規作成する。

1. まず既知訪問先を `references/known-venues.md` で確認（page_id一覧あり）。リストに無い、または不確かなら
   場所マスターを検索して実在を確認する。
   ```
   notion-search(data_source_url="collection://<場所マスター data_source_id>", query="<施設名>")
   ```
2. **同一チェーンの別店舗仮定**: マクドナルド・ボウリング場・VS PARK等で報告書に店舗名の明記が無い場合は、
   既存の同名店舗と同一と仮定して紐付け、ユーザーへの報告時に「同一店舗と仮定」と必ず明記する。
3. 新規施設は場所マスターに先に作成して `page_id` を得てから、イベント側で紐付ける。
   施設名・エリア（select）・住所・電話・アクセス・料金減免・危険箇所注意点を埋める。住所/電話が報告書に
   無く一般知識で補う場合は、その不確かさを注記する。施設名が報告書に無いときは体験内容から推定し、
   推定であることを注意点欄に明記する。

### Step 5. イベントの一括登録

`notion-create-pages` で、そのシーズンのイベントをまとめて登録する。親は
`{"data_source_id": "<イベントDB data_source_id>"}`。各プロパティの正確な名前・型・入力形式は
`references/notion-structure.md` に従う。特に **日付の展開形式・リレーションのJSON配列文字列・
multi_selectのJSON配列文字列** は間違えやすいので必ず参照すること。

ステータスは原則「報告済」（報告書ベースで登録するため）。

## モードB：継続運用での新規起票

現場が統一Wordテンプレート（企画＝報告一体型）とExcel試算表で起票したイベントを登録・更新する。
テンプレートは「単発用」「複数日用」があり、Yu Gothicで作成された企画＝報告一体様式（青＝企画欄／緑＝報告欄）。
**運用フローは確立途上のため本セクションは暫定。確定したら詳細化する。**

### B-1. 入力の取得

- **Google Drive上のファイル**: Word(.docx)は `read_file_content(fileId=...)` で読める。Excel(.xlsx)も
  `read_file_content` で自然言語表現が得られる（数値が崩れる場合は `download_file_content` で取得）。
- **手元アップロード（/mnt/user-data/uploads）**: docxスキル・xlsxスキルを先に参照してから読む。

### B-2. 2段階運用（企画 → 報告）

継続運用では1イベントが2段階で登録・更新されることがある。

1. **企画段階（実施前）**: テンプレートの青＝企画欄から新規ページを作成。
   - ステータス＝`企画中` または `準備中`、予定人数、ねらい、種別、訪問先（下見情報があれば）を埋める。
   - 実績人数・振り返り・収支実績はこの時点では空。
2. **報告段階（実施後）**: 同一イベントのページを **更新**（新規作成しない）。
   - 既存ページを `notion-search`（イベント名＋実施日で照合）で特定し、`notion-update-page`（command=update_properties）で更新。
   - ステータスを `報告済` に変更し、実績人数・参加者構成・参加者名・収支メモ（実績）・振り返り・保護者向け抜粋を追記。

**企画段階を飛ばして報告のみ登録する場合**（実施済みイベントを後からまとめて入れる等）は、モードAと同じく
最初から `報告済` で新規作成すればよい。

### B-3. テンプレート欄 → Notionプロパティ 暫定マッピング

| テンプレート記入欄 | Notionプロパティ |
|---|---|
| 事業名 | イベント名 |
| 実施日 | 実施日 |
| 参加予定者／参加者 | 予定人数／実績人数・参加者（名前）・参加者構成 |
| ねらい・効果目的 | ねらい・効果目的 |
| 事業収支（Excel試算表） | 収支メモ |
| 訪問先（外出時） | 訪問先（場所マスター照合・Step 4と同じ） |
| 振り返りと今後に向けて | 振り返り |
| （保護者向け文面を作る場合） | 保護者向け抜粋（コンプライアンス順守） |

抽出ルール（学年復元・収支分離・種別判定・コンプライアンス）と Notion 入力形式の注意は、モードAと共通で
`references/extraction-rules.md` ・ `references/notion-structure.md` に従う。

### B-4. 確定待ちの論点（運用が固まったら詰める）

- 記入済みテンプレートの保管場所（Drive専用フォルダか、手元アップロードか）。
- 企画段階で登録するか、実施後の報告のみ登録するかの運用ルール。
- Excel試算表の列構成と収支メモへのマッピングの固定化。
- 写真（顔スタンプ済）・試算表PDFの添付運用。

## データ品質ルール（要点）

詳細は `references/extraction-rules.md`。要点のみ:

- **学年構成は収支の料金内訳から復元できる**（手帳有無 × 小中/高 の単価別人数）。男女比は名簿がある時のみ。
- **収支は kid's 負担分と会社負担分（スタッフ入場料・高速・駐車・ガソリン）を分離して記録**する。
- **保護者向け抜粋は、コンプライアンス上の禁止表現を避ける**（「英語特化型」「英語学習」「英検合格」等は
  保護者向け文言に使わない）。
- **複数日イベントは延べ参加人数**を予定/実績人数に入れ、参加者構成に日別内訳を書く。

---

## よくある落とし穴（要点）

詳細は `references/notion-structure.md`。要点のみ:

- 親は `data_source_id`（`page_id` ではない）。
- 日付は `date:実施日:start` / `date:実施日:end` / `date:実施日:is_datetime` に分解。
- リレーション値は **ページURLのJSON配列文字列**（例: `"[\"https://app.notion.com/p/<32桁hex>\"]"`）。
- multi_select も JSON配列文字列。数値は素のnumber。
- **ページ削除・ゴミ箱移動はこのMCPツールではできない**。重複を見つけても削除はせず、タイトルに
  `【重複・削除予定】` を付けてユーザーに手動削除を依頼する。
- **文字化けに注意**: 出力時に「梓→梣」「嵜→嵌」「阿倍野→阯倍野」等の変換崩れが起きやすい。固有名詞
  （特に子どもの氏名・地名）は正しい漢字で書く。崩れた場合は最後にまとめて修正する（辞書は
  `references/notion-structure.md`）。

---

## 保留・最終処理（移行プロジェクト全体の終盤に行う）

- **EV番号（イベントID）の振り直し**: 過去セッションの登録順で歯抜けがあるため、振り直しは全シーズン
  完了後にルールを定めて一括で行う。途中では触らない。
- **文字化けの最終クリーンアップ**: 各レコードに残った変換アーティファクトを最後にまとめて修正する。
- **在庫DBとの紐付け**: 夏祭り等で使う物品（スーパーボール・ポイ・文具玩具等）は在庫DBと共通。必要なら
  在庫DBを照合して使用品目リレーションを張る（移行段階では収支メモへの記録で代替可）。

## 報告スタイル

ユーザー（田村有璽氏）の既定: 結論ファースト・簡潔・段落ベース。1シーズン登録後は「登録件数・種別内訳・
新規訪問先・既存再利用・同一店舗仮定や日付の食い違い等の注記」を簡潔にまとめ、次シーズンへ進む確認を取る（モードBの報告更新時も同様に、更新内容を簡潔に報告する）。
