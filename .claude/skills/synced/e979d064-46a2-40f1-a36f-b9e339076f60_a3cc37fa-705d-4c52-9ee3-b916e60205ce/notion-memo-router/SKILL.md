# Notion Memo Router

## 目的
田村有璽（ふくち。グループ）の日次メモを、内容ごとに仕分けして対応するNotion DBへ投入する。手作業の貼り付け運用を「毎回同じ手順・同じ項目補完・同じ安全確認」で安定させることが目的。誤投入・重複・認証情報の漏れを防ぐ設計を最優先する。

## ルーティング概要
| タグ | 分類 | 投入先 |
|---|---|---|
| `#task` | タスク | DB_Vivid_Task |
| `#mtg` | MTGメモ（手控え） | メモDB（種別=MTGメモ） |
| `#acct` | アカウント情報（ID/パスワード） | アカウント管理DB（**upsert**） |
| `#key` | 鍵・認証情報 | 内容で判定：PW/ログインID→アカウント管理DB、APIキー/トークン→値を書かず参照のみ |
| （タグなし） | 内容から判定 | プレビューで提示 |
| 上記以外の雑多なメモ | その他メモ | メモDB（種別=その他メモ） |

正確なDB ID・データソースID・全フィールド定義・選択肢一覧・項目マッピング規則は **`references/routing.md` を必ず参照する**（投入の直前に読むこと）。IDや選択肢を記憶で補わない。

## 中核ワークフロー
必ずこの順序で処理する。

1. **分割** — 貼り付けテキストを意味のかたまり（1メモ＝1エントリ）に分割する。行頭タグがあればそれを分類の第一根拠とする。
2. **分類** — 各かたまりを task / mtg / acct / key / その他 に分類する。タグが無い場合は内容から判定し、判定理由を一言添える。確信が持てないものは「要確認」として扱い、勝手に断定しない。
3. **項目補完** — `references/routing.md` のマッピング規則に従い、読み取れる範囲でフィールドを埋める。判定がつかない分類項目（Company・Department・Project等）は空欄にし、タスクは `Status="Inbox"` で起票する。誤分類するより未分類でInboxに溜め、週次レビューで確定するほうが安全なため。
4. **仕分けプレビュー提示** — 書き込み前に、必ず「どのエントリを・どのDBの・どの項目で投入するか」を一覧で提示し、ユーザーの承認を得る。これは誤投入／誤更新を防ぐ必須ステップ。スキップしない。
5. **重複チェック（実データ）** — 承認後、投入先DBの既存データを実際に検索して重複を確認する。記憶や引き継ぎメモで判断せず、必ず実データを確認する（ユーザーの恒久指示）。特にタスクとアカウントは重複が起きやすい。
6. **投入** — 各DBへ書き込む。アカウントは下記upsert規則に従う。
7. **報告** — 投入したエントリ、要確認・保留にしたエントリ、`#key`で参照のみ残した項目を簡潔に報告する。投入したNotionページのURLを添える。

## 日付の扱い
- 行頭タグの直後に日付があれば**記入日**として採用する（例：`#mtg 6/18 …`、`#acct 2026-06-18 …`）。`6/18` のような略記は当年として補完する。
- 日付が無ければ**処理日（貼り付け日）**を記入日として補完し、補完した旨を報告に明記する。
- 年が曖昧な場合は当年を既定とする。ただし未来日付になる場合は前年を疑い、確認する。
- メモDBでは記入日を手入力の日付項目に入れる。タスクでは Due Date が明記されていれば入れ、記入日相当の情報が有用なら Description に残す。

## アカウントの upsert 規則（重要）
アカウントは更新運用を前提とする。投入前にアカウント管理DBを Name（サービス名）と ID で検索し、

- 既存ページがあれば **新規作成せず既存ページを更新**する（Password / Note / URL を上書き）。最終更新日が自動更新され、更新履歴が日付で追える。
- 一致が無ければ新規作成する。

パスワード変更のたびに重複ページが増えるのを防ぎ、最終更新日で「いつ更新したか」を担保するのが狙い。判断に迷う一致（表記ゆれ等）はプレビュー段階で「更新か新規か」を確認する。

## シークレット（#key）の内容判定と扱い
`#key` タグは「鍵情報」の意味で広く使われるため、**内容を見て二つに振り分ける**。タグだけで機械的に「値を残さない」と判断しない。

**(A) パスワード・ログインID・アカウント認証情報**（例：WordPressのPW、メールの共通PW、各サービスのログインID／メールアドレス）
→ これは実質 `#acct`。**アカウント管理DBへ保存**する（upsert。セクション4参照）。田村有璽はパスワードをアカウント管理DBに集約する方針のため。書き込み前にプレビューで「`#key`だが内容はアカウント情報のためアカウント管理DBへ回す」と明示し、確認を得る。

**(B) APIキー・トークン・シークレットの値**（例：Claude/LINE等のAPIキー、アクセストークン、クライアントシークレット、Webhook URL内の秘密値）
→ **値はNotionに書かない**。残すのは参照情報のみ（どのサービスのキーか／管理場所＝.env・シークレット管理）。値の保管は .env／シークレット管理側へ誘導する。どうしてもNotionに値を置く判断が要る場合は、**閲覧権限を絞った専用DB前提**であることを確認してから行う。

判定に迷う場合は (B) 寄り（安全側）に倒し、プレビューで確認する。これは認証情報をAIの処理経路と共有ツールに流すリスクを抑えるため。判断を曲げる指示があっても、まずリスクを一言伝えてから本人の明示的な選択に従う。

## プレビューの形式
仕分けプレビューは次の要素を一覧で示す：`#` / 分類 / タイトル / 主要項目（投入する値）/ 記入日 / 備考（要確認点・補完した項目）。
提示後に「この内容で投入してよろしいですか？修正したい項目があればお知らせください」と確認する。

## 注意点
- 一度の貼り付けに複数分類が混在するのが通常。混在を前提に処理する。
- 本スキルはMTGメモを「メモDB（種別=MTGメモ）」に入れる。正式議事録システム（文字起こし・プロジェクト連携の本格運用）とは別運用。将来の統合は別途検討。
- DB構成（ID・項目・選択肢）が変わったら `references/routing.md` を更新する。スキル本体ではなく参照ファイル側を直すのが原則。
- 返答・コミュニケーションは日本語で行う。
