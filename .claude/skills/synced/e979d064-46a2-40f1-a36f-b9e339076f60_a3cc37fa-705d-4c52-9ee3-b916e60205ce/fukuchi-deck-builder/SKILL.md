# fukuchi-deck-builder

ふくち。グループのブランドに完全準拠したスライド資料を、再利用可能なデザイン部品を組み合わせて生成する。
構成は固定しない。読者・目的・枚数に応じて部品を自由に並べ、トーンだけは絶対にぶらさない。

## 基本ワークフロー

1. **前提を確認する。** 構成を作る前に、最低限これだけは確認する（会話履歴で既に判明していれば再質問しない）:
   - 想定読者（企業／行政／福祉施設／投資家／求職者 等）
   - 成果物の形式（pptx＋PDF両方／いずれか）
   - 元ドラフトの有無（ある場合は内容整合の方針＝こちらの判断で整合してよいか）
   曖昧なまま進めると手戻りが大きい。1ターンに質問は絞り、ボタン選択式が望ましい。

2. **環境を整える。** 作業ディレクトリで `npm install pptxgenjs` を実行（未導入時）。日本語フォントは
   Noto Sans CJK JP を前提とする。`fc-list | grep "Noto Sans CJK JP"` で存在を確認。無ければ
   `scripts/fukuchi_components.js` の `FONT` を環境にあるフォント（例: Yu Gothic, IPAexGothic）に変更する。

3. **構成を設計する。** 読者に響く順序で部品を並べる。下の「部品カタログ」と「読者別の構成指針」を参照。
   元ドラフトがある場合は、内容の不整合（役割の矛盾・空欄・誤字）を洗い出し、確認した方針で整合させる。

4. **生成スクリプトを書く。** `scripts/fukuchi_components.js` を `require` し、部品関数を呼ぶだけ。
   ブランド定数（配色・フォント）は絶対に上書きしない。色を変えたい場合も部品の `color` 引数で
   `F.BRAND.*` のいずれかを渡す（独自カラーコードを混ぜない）。

5. **必ず視覚QAする。** 生成 → PDF変換 → 画像化 → 目視。特に循環図・カード・組織図・表は
   文字切れ・はみ出し・重なりが出やすい。1回の修正サイクルで直す。詳細は
   `references/qa_checklist.md` を読むこと。

6. **納品する。** `/mnt/user-data/outputs/` にコピーし `present_files` で提示。pptx（編集用）と
   PDF（配布用）の役割を一言添える。

## 部品カタログ

`scripts/fukuchi_components.js` が公開する関数。すべて第1引数に `pres`、描画系は第2引数に `slide`。

| 部品 | 関数 | 用途 |
|------|------|------|
| デッキ初期化 | `newDeck(meta)` | 16:9・著者情報を設定した pres を返す |
| 表紙 | `titleSlide(pres,{eyebrow,title,subtitle,tagline,footnote})` | 濃紺の表紙 |
| 本文枠 | `contentSlide(pres,kicker,title,onDark)` | kicker＋タイトル付きの空きスライドを返す |
| リード文 | `lead(slide,text,onDark)` | タイトル直下の説明段落 |
| 番号リスト | `bulletList(pres,slide,items,y0,onDark)` | 目的・要点の列挙（丸数字） |
| 強調バンド | `bandBox(pres,slide,lines,{y,h,fill})` | 結論・キーメッセージの帯 |
| カードグリッド | `cards(pres,slide,items,{y,h})` | 2〜4分割。`{head,sub?,body?,lines?,color?}` |
| 循環図 | `cycleDiagram(pres,slide,center,nodes,cx,cy)` | 4ノードのループ図（エコシステム/連携モデルの核） |
| 比較表 | `comparisonTable(pres,slide,rows,{colW,rowH,y})` | Before→After。先頭行ヘッダ |
| ロードマップ | `roadmap(pres,slide,phases,{y,h})` | フェーズ3カラム。`{tag,period,body,kpi,color?}` |
| 組織図 | `orgChart(pres,slide,top,depts,sub)` | トップ＋横並び部門＋任意の下段 |
| 締め＋会社概要 | `closingSlide(pres,concl,profile)` | 締めメッセージと会社概要カード |
| フッター | `pageNum(slide,n)` / `brandFoot(slide,onDark)` | ページ番号／ブランド表記 |

部品の引数の詳細は `scripts/fukuchi_components.js` 冒頭のコメントと各関数の直上コメントを読むこと。
動く実例は `references/example_build.js`（企業向け17ページ構成の完成例）を参照。

## 読者別の構成指針

固定構成ではないが、読者ごとに「効く順序」の型がある。下を出発点に、依頼内容で調整する。

- **企業向け**: 表紙→目的→ミッション→社会課題→解決アプローチ→エコシステム→各連携モデル→
  グループ会社→組織Before/After→ロードマップ→締め＋会社概要。連携可能性と事業の信頼性を強調。
- **行政向け**: 社会課題と地域連携モデルを前段で厚くする。エビデンス（研究連携＝SWELLSOCIETY）と
  政策提言の循環を強調。会社概要は早めに提示し公的信頼性を担保。
- **福祉施設向け**: 送り出し型福祉モデルと現場運営（ILIFE）を主役に。BPO・補助金支援など
  施設側の具体メリットをカードで明示。専門用語は噛み砕く。
- **投資家・金融機関向け**: ロードマップとKPI、社会的インパクト指標、組織のスケール設計を厚く。
  金融連携モデル（核＝ビビッド）と全国展開・FC計画を前面に。

## ブランド整合の鉄則（必読）

ふくち。グループには資料間で矛盾しやすい固有事情がある。清書・新規いずれでも下記を必ず守る。

- **会社の役割を取り違えない。** ビビッド＝資金調達・金融（補助金/融資/節税/金融教育）。
  ILIFE＝福祉現場運営（就労支援・生活再建・支援データ）。SWELLSOCIETY（リアンライフ）＝研究・
  効果検証・政策提言。ふくち。＝統括・相談支援・地域連携ハブ。元ドラフトでこれが逆転していたら
  実態に合わせて必ず修正する（過去ドラフトはビビッド/ILIFEの記述が逆転している例があった）。
- **金融連携モデルの核はビビッド**（ILIFEではない）。
- **SWELLSOCIETYは後継法人リアンライフへ移行中**。グループ構成表記は
  「SWELLSOCIETY（リアンライフ）」と併記する。
- **会社概要の所在地は推測で番地まで書かない。** 不明なら「大阪府藤井寺市（詳細は別途）」と
  プレースホルダにし、ユーザーに差し替えを促す。代表者は田村 有璽、設立2026年。
- **配色・フォントは BRAND/FONT 定数のみ。** 独自カラーやフォントを混ぜると一目でブランドが崩れる。

## 注意

- 構成・文言の判断材料はメリット/デメリットを添えて提示し、ユーザーが選べるようにする。
- 元ドラフトの不整合は黙って直さず、整合方針を一度確認してから反映する。
- 1スライドに情報を詰め込みすぎない。表は7行程度、カードは4枚程度、循環図は4ノードが上限の目安。
