# Event Comms Orchestrator

イベントの対外発信を、開催決定の瞬間から終了後の振り返りまで一本の計画として管理するハブ。

このスキル自体は投稿物を作らない。**計画を立て、状態を管理し、実制作を専門スキルへ渡す**のが役割。
実制作を担うスキル（スポーク）は次の通り。

| フェーズ | 委譲先 | 状態 |
|---|---|---|
| 台帳（起票・更新・照会） | `event-db-sync` | 稼働中 |
| 企画書・進行管理 | `event-plan-kit` | 稼働中 |
| SNS素材・キャプション全般 | `event-social-kit` | 稼働中 |
| 実施報告書・振り返り | `event-report-kit` | 稼働中 |
| プレスリリース・メディア対応 | `event-press-kit` | 稼働中 |

全スポークが稼働中。委譲先が明確なタスクは、ハブが自前で処理せず必ず該当スキルへ渡す。

## 全体の連鎖

```
イベント構想
   │
   ▼
event-plan-kit ── 企画書・KPI目標値・体制・香盤表・予算・リスク
   │
   ▼
event-db-sync ── 情報整理・検証・重複照合・イベントDBへ起票
   │              ステータス「開催決定」が広報の起点
   ▼
event-comms-orchestrator（本スキル）── 配信カレンダー生成・フェーズ判定
   ├─ event-press-kit   … D-30〜D-14  プレス（事前告知）／終了後（実施報告）
   └─ event-social-kit  … D-14〜会期〜終了+3日  SNS
   │
   ▼ 会期終了
event-report-kit ── KPI目標値を引き継ぎ、実績と対比。課題と改善策を残す
   │
   ▼ 実績値（来場数・掲載数・リーチ・収支）
event-db-sync ── 台帳へ書き戻して1件を閉じる
   │
   ▼
次回の event-plan-kit が前回実績を根拠として引く
```

台帳が起点であり終点。広報だけ走って台帳が更新されない状態を作らない。

**KPIは企画書と報告書で同じスキーマを共有する。** 企画段階で目標値と測定方法を決めるから、
終了後に達成率が自動で成立する。目標値のない企画は、成果を評価できない企画になる。

---

## なぜ計画層が要るのか

媒体ごとにリードタイムが逆方向だから。

報道機関に取材へ来てもらうには開催の1か月前には案内が要る。記者のスケジュールを押さえる必要があるためで、
直前に送っても企画枠に入らない。一般告知のプレスリリースも2週間以上前が目安になる。

一方SNSは直前ほど効く。1か月前の告知は流れて忘れられる。

この非対称性を記憶で管理すると必ず取りこぼす。だから開催が決まった時点で、
プレスからSNSまでを一枚のカレンダーに落とす。それが本スキルの主たる仕事。

---

## Step 0: プロファイルを確定する（`event-db-sync` へ委譲）

**SSOTはNotionのイベントDB。** プロファイルの作成・検証・起票は台帳スキルの仕事なので、
ハブは自前でヒアリングせず `event-db-sync` を呼ぶ。

1. `event-db-sync` でイベントDBを照会し、該当レコードを取得する
2. レコードが無い、または必須項目が欠けている場合は `event-db-sync` に起票・補完させる
3. ステータスが「開催決定」以上になっていることを確認する。「企画中」なら広報計画はまだ引かない

台帳から受け取るべき項目。これが揃わないと下流のスポークが再ヒアリングを始めてしまう。

- 会期（開催初日・最終日・開催時間）
- 会場の正式表記、所在地
- 参加条件（参加費・予約）
- 自社の立場、併記が必要な主催者・共催者
- 投稿先アカウントとその性格、ブランドカラー
- プレス配信・メディア招致の有無
- 掲載NG事項

**推測してはいけない5項目**（会場・参加費・予約・自社の立場・主催者共催者）が空欄のまま
下流へ渡さない。空欄なら `event-db-sync` の検証結果をユーザーに提示して確認を取る。

DBのプロパティ設計とMCP入力形式は `event-db-sync` の `references/notion-structure.md` が正。
ハブ側では二重管理しない。

---

## Step 1: 配信カレンダーを生成する

`scripts/build_schedule.py` で開催日から逆算する。

```bash
python3 scripts/build_schedule.py --name "<イベント名>" \
  --start 2026-09-12 --end 2026-09-13 \
  --open 10:00 --close 17:00 \
  --accounts "個人,主催公式" \
  --press --media-invite \
  --out /mnt/user-data/outputs --prefix <識別子>
```

- `--press` … プレスリリースを配信する場合に付ける
- `--media-invite` … 記者に取材へ来てほしい場合に付ける。D-30の招致案内とD-3のリマインドが入る
- `--accounts` … カンマ区切り。当日のライブ配信は先頭のアカウントに割り当てられる
- `--end` … 単日開催なら省略可

出力は2つ。人が読む `_schedule.md` と、Notionへ取り込む `_schedule.csv`。

生成される主な枠。

| タイミング | 内容 |
|---|---|
| D-30 | メディア招致案内（`--media-invite` 時） |
| D-21 | プレス素材準備。メイン画像候補3案以上 |
| D-14 | プレスリリース配信（火・水・木の午前に自動調整） |
| D-10 / D-7 | SNS告知1本目・2本目 |
| D-3 | 記者へリマインド |
| D-1 | 前日告知・当日準備 |
| 当日 | 開場前告知／開場／前半／混雑実況／成果物／ラストコール／御礼 |
| 終了+1日 | 実施報告投稿 |
| 終了+3日 | 総集編リール |
| 終了+7日 | 実施報告プレスリリース、振り返り |

**土日は自動回避するが祝日は判定していない。** 生成後、プレス配信日が祝日に当たらないか目視で確認し、
当たっていれば前倒しする。ここは必ずユーザーに確認を促す。

生成したカレンダーCSVは配信タスクDBへ取り込む。反映は `event-db-sync` に委譲し、
承認を得てから書き込ませる（ハブが直接Notionへ書かない）。

---

## Step 2: フェーズを判定し、委譲する

現在日と会期を突き合わせて、いまどのフェーズかを判定する。

```
企画段階           → 企画期            → event-plan-kit で企画書・体制・KPI設計
今日 < D-14        → 事前・プレス期    → プレス素材の準備、メディア招致
D-14 〜 D-1        → 事前・告知期      → event-social-kit で告知投稿
会期中             → 当日・ライブ期    → event-social-kit で反復運用
終了後             → 事後・報告期      → event-report-kit で実施報告、総集編、振り返り
```

委譲するときは、スポークが再ヒアリングしなくて済むよう**プロファイルの内容を引き渡す**。
特に会場表記・参加条件・立場・アカウントのトーン設定は必ず渡す。

`event-social-kit` を呼ぶ際は、そのスキルのStep 0（プロファイル確定）は済んでいる旨を明示し、
Step 1（肖像権チェック）から始めさせる。二重にヒアリングさせない。

---

## Step 3: プレスリリースを扱う（`event-press-kit` へ委譲）

原稿作成・検証・メディアアプローチは `event-press-kit` の担当。ハブは自前で書かない。

ハブが行うのはタイミング管理のみ。

- 事前告知：一般向けは開催2週間以上前、メディア招致を伴うなら1か月以上前
- 実施報告：終了後1週間以内。**来場実績が確定してから**渡す
- 配信曜日・時間帯の根拠は `references/channel-leadtimes.md`

委譲時は台帳から取得した会場表記・参加条件・立場・主催者名を引き渡す。
実績数値は `event-report-kit` の集計結果を使い、二重に集計しない。

---

## Step 4: 進行を管理する

会期が進むにつれ、実績が計画からずれる。ずれを記録して次回に活かすのがハブの最後の仕事。

- 実施済みタスクの状態を `event-db-sync` 経由で更新する（承認を得てから）
- 実績値（リーチ・保存・来場数・メディア掲載数）を `event-db-sync` で台帳へ書き戻す
- 計画になかった発信が生じたら、その事実も残す
- 会期終了後、次回の設計に効く気づきを1〜3点まとめる

同じイベントの次回開催時は、前回のプロファイルとカレンダーを複製して起点にする。
ゼロから組み直さない。

---

## ユーザーへの確認を挟むべき場面

自動で進めず、必ず一度止まる。

1. プロファイルの推測してはいけない5項目が埋まっていないとき
2. Notionへ書き込む直前（`event-db-sync` が確認を出す）
3. プレス配信日が祝日・大型連休・世間の大きなニュースと重なりそうなとき
4. 数値や実績を文面に入れるとき（根拠の所在を確認する）
5. 共催者・後援者の名称を出すとき（表記と掲載可否を確認する）

## バンドルされているファイル

- `scripts/build_schedule.py` … 配信カレンダー逆算生成。`--help` で全オプション
- `assets/event-profile-template.md` … 下流へ引き渡す項目の一覧（起票自体は `event-db-sync`）
- `references/channel-leadtimes.md` … 媒体別リードタイムとPR TIMES実務

## 動作要件

Python 3 標準ライブラリのみ。台帳連携は `event-db-sync`（Notion MCP）に依存する。
SNS素材の生成は `event-social-kit`（Pillow / OpenCV / ffmpeg）に依存する。
