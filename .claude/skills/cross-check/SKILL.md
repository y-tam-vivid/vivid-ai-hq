# 相互チェックの型 ── 一人の目で通さない

> **2026-08-20 有璽氏の指示**
> 「AIエージェント同士でチェックし合う構造を作りなさい。同じミスを繰り返さないような
>   設計にして、それぞれがちゃんとその目線で作り上げていって、
>   自分だけじゃなくて、何人かの目で見て」

## なぜ要るか（実証つき）

**一人で書いたコード7本に、3体を並列で当てたら24件の不備が出た。単独では1件も見つけられなかった。**（2026-08-20 実測）

```
ピタゴラス（システム）   設計と実装の穴   8件
検査役                 規範との突合     10件
ロビン（CKO）           決定と実態のズレ  6件
```

そのうち2件は**実害を出してからの発覚**だった。うち1件は取り返しがつかない
（Notionの408件を上書きし、上書き前の値がどこにも残っていない）。

規範は「検証は**作成者と別の主体**が行う（自己採点にしない）」と定めている。
**守っていなかったのが原因。**

## 型 ── 3つの役を必ず別の主体に分ける

```
          ┌──────────────┐
議題 ─────▶│ ビビ（窓口） │  受ける。担当を選ぶ。自分では作らない
          └──────┬───────┘
                 │
        ┌────────┴────────┐
        ▼                 ▼
   ┌─────────┐      ┌─────────┐
   │ 作る役   │      │ 別視点   │   ★同時に走らせる（会話させない）
   │         │      │ の作る役 │      同じ型で並べる。合意させない
   └────┬────┘      └────┬────┘
        └────────┬────────┘
                 ▼
          ┌──────────────┐
          │ 検査する役    │  ★作った本人ではない。領域ごとに置く
          │              │     データ→つる／コード→ステラ
          │              │     法務→センゴク／財務→ナミ
          └──────┬───────┘
                 │  通らなければ 作る役へ差し戻す（最大2周）
                 ▼
          ┌──────────────┐
          │ 束ねる役      │  ロビン（CKO）
          │ 合意点／対立点 │  ★対立は残してよい。合意させると視点が消える
          │ ／不明点      │
          └──────┬───────┘
                 ▼
              人は「承認」か「差し戻し（理由つき）」だけ
```

## 必ず守る5つ

### 1. ★自分が作ったものを自分で検査しない

作った本人の申告を検査役は信用しない。**実物を読む。**
2026-08-20、リリスが「直した」と申告した4点を つる が検査したら、
コードは直っていたが**データの後始末が残っていた**（メモ列の汚染78件）。

### 2. 書き込みの前に検査役を通す

```
台帳・DB・kintone へ書く    → つる（data-auditor）
コード                      → ステラ（dev-producer）配下
契約・法務                  → センゴク（legal）
数字・与信                  → ナミ（cfo）
```

**検査役が「止めろ」と言ったら止める。** 2026-08-20、つるが cron 登録を止めた
（「単発なら止めない。無人で回すのは止める」）。この判定に従った。

### 3. AI同士を会話させない

合意条件が無いので止まらず、残らず、高い。
**同じ型で並べて、束ねる役が対立点を洗い出す。** 対立が残ってよい ──
違う角度の材料が並ぶことに価値がある。合意させると誰かの視点が消える。

### 4. 最大2周で止める

2周して決まらなければ「**決められない理由**」（情報／判断／権限のどれが足りないか）を
書いて人に返す。止まる条件を先に決めないと永遠に回る。

### 5. 検査役は「指摘まで」。直さない

直すと検査にならない。修正は作る役へ差し戻す。
ただし**自分たちの仕組み自体の監査**（`self_audit.py`）だけは例外で、
可逆なものはその場で直してよい（対象は cron・レジスタ・設定であって、顧客データではない）。

## 検査役に必ず渡すもの

```
① 何を作ったか（ファイル・行番号）
② 作った本人が「直した」と申告している内容
   ★「申告を信用せず実物で確かめてください」と明記する
③ 特に見てほしい観点（過去に踏んだ地雷を具体的に）
④ 「最後に “進めてよいか” を一言で。止めるべきなら止めると言ってください」
```

**④が要。** 検査役に「通す／止める」の判定まで書かせる。
指摘だけ出して判断を作る役へ返すと、作る役が自分に有利に読む。

---

## 出し方（検査役の型）

```
① どこ        ファイル:行番号 / シート名:行番号 / DBのページ
② 何が問題か   一文で
③ どの規範に反するか
④ 起きる事故   具体的に
```

深刻な順に**最大10件**。多く出すより、止めるべきものを確実に止める。
問題が無ければ「**無い**」と明言する。ただし
**「読んでいない範囲」があれば必ず書く** ──「探した範囲では見つからなかった」と
「無い」は別物。

## ★検査役に「完璧でなければ不可」と言わせない（2026-08-20 実地）

Notion同期のガードで、検査役が**3周続けて★不可**を出した。毎回まっとうな穴だったが、
4周目に入るときに判定の出し方を変えたら、その回で収束した。

```
それまで   「載せてよい / ★不可」の2択で聞いた
           → 穴が1つでも残ると不可になる。穴は探せば必ず出る＝永久に終わらない
変えた     「載せてよい / 載せてよい（★条件つき・条件を明記） / ★不可」の3択にし、
           **残る穴が運用で受け止められる程度なら条件つきで通してよい**と明示した
           → 4周目で「載せてよい（条件：初回の本実行ログを人が1回目視する）」が出た
```

- **検査役は、判定の選択肢が2つだと不可へ倒れる。** 慎重であることが仕事だから正しい
- **「受け止められる穴」と「止めるべき穴」を分けさせる。**
  そのために **条件つきの判定を最初から用意しておく**
- **★ただし1周目から3択にはしない。** 最初の数周は穴を出し切らせる。
  収束させにいくのは、指摘が具体的で小さくなってからでよい
- 3周とも作る側は「実測しました」と申告していた。嘘ではなく、
  **試したパターンの外に穴があった** → [[reference_ran_is_not_succeeded]]
