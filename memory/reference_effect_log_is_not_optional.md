## 🔴2026-10-07 漏らした（有璽氏の指摘で気づいた）

営業台帳 02_個人マスタの構造を変え（段階6種へ畳む・検討時期列の新設・プルダウン998セル×2）、
intake_register.py も改修したのに、**効果記録をしなかった。**

- **★真因はトリガーが人（AI）の判定に依存していたこと。** ルールは MOC §1 の35行目で
  **毎ターン届いていた**。届かなかったのではなく、**「台帳の構造を変えた」を「仕組みの改修」と
  判定しなかった**。判定に任せる限り再発する
- **★スプレッドシートの台帳も、プルダウン（データ検証）も「仕組み」である。** コードだけが対象ではない
- 対処：`run_agent.sh` が担当を起動するとき、指示文に「改修／新規／列を足す／構造／プルダウン」等が
  あれば `effect_log_pending.jsonl` へ積み、`hook_session_writeback.py` の★検査5で
  ターン終了時に鳴らす（ピタゴラスが実装・2026-10-07）

```

- **★MCP の `notion-update-data-source` は、`schema_updates` 形式では効かない。**
  「Updated」と返るが★反映されない（fetch で5つのまま・ページ作成も選択肢エラーで弾かれた＝3経路で確認）。
  **★正しいのは `statements` に SQL DDL**：

  ★既存の選択肢を全部書く（options は置換されるため、落とすと既存行の値が壊れる）。
  ★書く前に現在の options を控えへ（`_backups/notion_ai_asset_kind_before_YYYYMMDD.json`）

## 🔴削減時間（h/月）では測れない改修がある

効果記録ルールの「削減時間（h/月）」は★人の作業時間を測るもの。ところが 2026-10-07 の改修2件は
**★人の作業時間を減らすものではなく、誤りを止めるもの**だった。

```
① 段階6種＋プルダウン   減ったのは★AIが「誰が既存顧客か」を数えるのに備考を1件ずつ読む手間。
                        ★人の入力時間ではない。効果は「10種に散るのを止めた＝数え間違いが起きない」
② intake_register.py    ★温度感が段階の列へ入るのを止めた。効果は★事故の予防

- **★0や推測値を入れない**（ルールどおり）。ただし「未計測」と書くと★後の週次振り返りで
  「まだ測れていないもの」として毎回出てくる。**★測れないものと、まだ測っていないものは別**
- ★提案（有璽氏の判断待ち）：業務削減効果の欄へ**「時間ではなく事故の予防（予防型）」**と書き、
  削減時間は空欄にする。★ルール本文（Core_Brain `03_作成物の効果記録ルール.md`）の改訂は
  ★規範の変更＝要承認なので、こちらからは書き換えない

## ✅2026-10-07 有璽氏 ── 未計測の扱い（★いつ測るか）

> 「こちらはまだ未計測です。★システムが確立してから計測します」

```
★仕組みが固まる前に測らない。★確立してから1回測る
  → 効果記録ルール「未計測の回収＝月曜の週次振り返りで1件ずつ聞く」から★一旦外す
  → 代わりに★「確立の条件」を書いておき、満たした回に測る
```

- **★「未計測」には2種類ある。**
  ① ★まだ測れない（仕組みが固まっていない）── 週次で毎回聞かない。確立の条件を書く
  ② ★測り忘れ ── 週次の回収対象
  **★区別せずに週次へ流すと、毎週同じものを聞くことになり、回収の仕組み自体が無視される**
- ★`intake_register.py`（受付シート→営業台帳）の確立の条件（2026-10-07 時点の現在地）：
  ```
  いま   改修済み・dry-run まで検証・★本実行なし・★cron未登録
         （ステラの条件＝初回に新規Cの行が出る回はログを人か検査役が目で確かめる）
  確立   ①本実行が通る ②cron/launchd に載る ③ドーベルマンの点検を通る ④1か月回る
  → ★④のあとに1問だけ聞く（誰が手でやっていたか・1件何分・月何件）
  ```
- ★予防型（時間では測れないもの）は、この「確立待ち」とも別。業務削減効果の欄へ
  「時間ではなく事故の予防（予防型）」と書く → 上の節
