**「警告が出ている」と「異常がある」は別。** 止めてあるもの・対応保留のものまで
警告に数えると、毎週同じ行が鳴り続け、**新しく増えた本物のズレが見分けられなくなる。**

2026-08-20 実測 ── `~/.vivid-relay/automation_inventory_check.py`（⚙️自動処理レジスタと
cron/launchd の突合・毎週月曜09:20）が「ズレ 4件」を出していた。中身を開くと：

```
本物の申告倒れ    2件   有効=True なのに cron に無い（notion_backfill / notion_customer_upsert）
止めてあるだけ    1件   有効=False（受付シート→台帳の登録。破壊的バグ修正中で意図的にOFF）
既に解消済み      1件   inbox_runner の登録漏れ（検査中に別経路で登録された）
```

**判定コードが `有効` も `既知（対応保留）` も読んでいなかった。** レジスタ側にはフラグが
あるのに、突合側が無視していた。＝**台帳に状態を持たせても、読む側が見なければ意味がない。**

## 監視は3つに分ける

```
① 本物のズレ      有効=True かつ 既知=False なのに実体が無い     → 警告に数える・Slackへ
② 止めてある      有効=False                                    → 参考表示のみ・数えない
③ 対応保留        既知（対応保留）=True                          → 参考表示のみ・数えない
```

②③を消さずに「参考」として出すのが要点。**消すと「そんな行があったこと」ごと忘れる。**

## ★④ 古い失敗 ── ログを走査する検知は「いつの失敗か」を見ていない（2026-08-21 実測）

2026-08-21朝の材料に「ログに出た失敗・警告」として
`watch_external.log ： 取得失敗 ビビ 朝ブリーフィング: <HTTPError 404>` が3件×2回、
計6行並んでいた。**前日の失敗ではなかった。**

```
実測（ログを行番号つきで読んだ）
   2〜10行目   404が3件×2回 ＝ ★このログの最初の2回の実行（2026-08-13頃・共有前）
   11〜35行目  以降7回はすべて「代理心拍 4件」＝正常
   今日トークンでGET   3ページとも 200（last_edited は 08-20 深夜）
→ ★404は8日前に解消済み。いまは1件も失敗していない
```

**真因は検知側。** `~/.vivid-relay/self_audit.py`（毎朝08:40）は各 `*.log` を
`tail -25` して `Traceback` `Error` `★失敗` `エラー` を含む行を数えるだけで、
**日付を一切見ていない**（66〜77行目）。ログは追記のみでローテートされないので、
**一度出た失敗は、直したあとも毎朝「今日の失敗」として報告され続ける。**

同じ走査で `inbox.log ： 【★本実行】📮 AI指示箱` のような**ただの見出し行**も
「失敗・警告」として並ぶ。★を含む行を拾っているため。

- **★ログから失敗を数えるなら、必ず「その行がいつのものか」で絞る。**
  時刻を持たない行しか無いログは、そもそも失敗の件数源にできない
- **★「N件失敗」を受け取ったら、ログを行番号つきで開いて位置を見る。**
  先頭に固まっていれば、それは初期不良の残骸であって現在の障害ではない
- 解消済みの失敗を数え続けると、②③と同じく**本物が埋もれる**
- **★2026-08-23 の朝も、同じ404が3件そのまま並んだ。**`self_audit.py` は未修正のまま
  （実体は `~/.vivid-relay/` ＝ git外なので放置すると両機で腐り続ける →
  [[reference_fix_where_git_reaches]]）。**毎朝この3行を調べ直す時間が繰り返し消えている**

## ★⑤ 期待間隔を実体のスケジュールから逆算していない（2026-08-22 実測）

⚙️レジスタ「有璽氏への進捗報告（progress_report.py）」は **期待間隔=8時間**で登録されていた。
実体は `daily_jobs.conf` の **12:00 と 18:00 の1日2回**。18:00→翌12:00 は **18時間**空く。

```
毎朝 08:40 の自己監査から見ると    経過14.7h > 8h ＝ 必ず🟡遅延
→ 正常に動いた翌朝ほど確実に鳴る。★異常の日と1文字も違わない見た目で
```

**1日N回の処理は「回数」ではなく「いちばん長い空き」で間隔を決める。**
`24 ÷ 回数` で入れると、実行が等間隔でない限り必ず慢性的な黄色になる。
2026-08-22 に 8 → **20**（18h＋余裕）へ是正した。

- **★レジスタに行を足すときは、実体の起動時刻を並べて最大の空きを数えてから間隔を書く。**
- 逆に**1件の遅れで間隔を緩めない**。同日、成果物ベースの外形監視
  （議事録の自動整理・35.5h）も🟡だったが、これは会議が無かっただけ ―― 履歴7日分を
  見てから判断し、**緩めなかった**（[[feedback_one_route_is_not_verification]]）。

## ★⑥ 心拍の宛先が行名の文字列一致 ── 名前がズレた瞬間、動いていても永久に🟡（2026-08-27 実測）

つるの毎朝の自己監査で見つけた。**2件とも「毎日 rc=0 で完走しているのに🟡遅延」だった。**

```
gas_outside_watch.py     PROC_NAME = '外形監視（自分で心拍を打てない処理の代理）'
                         ＝ watch_external.py と同じ名前（★相乗り）
                         専用行「GASの稼働を成果物から判定する（外形監視）」へは1度も届かず
                         実測：8/25・8/26 とも daily_jobs.log に「完了 rc=0」あり
build_landmine_index.py  ★beat を1行も持っていなかった（--quiet しか受けない）
                         landmines.json は毎朝08:25に再生成されている（mtime で実測）
                         レジスタの「最終実行」は人が手で書いた2日前の値だった
```

**心拍は「処理名」の文字列一致で宛先を決める。** 行名を1文字でも変えれば届かない。
そして**届かなかったことは、どこにもエラーとして出ない**（`try/except` で stderr へ流れ、
rc は 0 のまま）。＝ ①で書いた「動いているものを止まっていると誤判定する」の再発。

- **★新しいスクリプトを載せるときは、`PROC_NAME` をレジスタの行名からコピーして貼る。** 手で打たない
- **★`--beat` をフラグにしない。** cron 行が `--quiet` だけだった今回のように、
  フラグを付け忘れた経路が残る。**心拍は無条件で打つ**のが安全
- **★1本のスクリプトが2つの行を持つな。** 相乗りは `heartbeat_names_check.py` が
  検出する設計だが、今回は**検出されていた警告が読まれていなかった**（🟡警告のまま放置）
- 突合の作り方：`*.py` の `PROC_NAME` を全部集め、レジスタの「処理名」集合と
  ①レジスタにあって誰も打たない ②打つのに行が無い ③2本以上が同じ名前、の3方向で照合する

## 型として

- **フラグを足したら、そのフラグを読む側を必ず同時に直す。** 片方だけでは効かない
- **警告の件数を見たら、必ず中身を開く。** 4件のうち本物は2件だった
- **★「止めてある」「対応保留」「もう直った」は、どれも異常ではない。**
  監視が見るべきは「いま・有効なのに・動いていない」だけ
- 同じ話 → [[project_automation_register]] ／ [[project_browser_hygiene_check]]（🟡の慢性化）
  ／ [[reference_log_needs_an_exit]]（読まれない記録は無いのと同じ）

## ★検査役2体が違う数字を出したら、どちらかが嘘なのではなく、分類の基準が違う（2026-08-23 実測）

同じ自動処理の一覧を、別々の担当が同じ日に数えた。

```
ドーベルマン（番人）   申告倒れ 0件 ／ 止めてある 11件
                       ロビン週次・ステラ週次を「routine未着火＝意図的に止めてある」に入れた
リリス（実装）         ★申告倒れ 7件
                       同じものを「レジスタは有効と申告しているのに心拍が一度も来ていない」と判定
```

**どちらの観測も正しい。食い違っているのは分類の基準。**
そして真因は両者のどちらでもなく ── **⚙️レジスタの「有効」フラグが実態を反映していない**こと。

```
意図して止めている   → レジスタを「無効」にする。そうすれば誰が数えても「止めてある」になる
有効のままにする     → 心拍が来ないのは申告倒れ。直すべき対象になる
```

**★状態を人の記憶と文章に置くと、数える人ごとに違う答えが出る。データとして持つ。**

- **合意させない。** 対立が残ってよい ── 違う角度の材料が並ぶことに価値がある。
  合意させると誰かの視点が消える（→ fukuchi-core「AI同士を会話させない」）
- **★束ねる役が「なぜ違うか」を1行で言えるまで、どちらも採らない。**
  今回は「分類の基準が違う」まで降りて初めて、直すべき対象（レジスタのフラグ）が見えた

## ★「判断待ち」に積むと、こちらの停滞が人の判断のせいに見える（2026-08-23 実地）

申告倒れ7件を見つけたあと、当方は有璽氏へこう出した ──
「★このうち人の手が要るのは名刺フォルダの1件だけ。残り6件はこちらで進められます。
　止めるのか動かすのか、7件まとめてご判断ください」。

**そして着手しなかった。** 有璽氏から「ゼロのやつは全部やってくれた？」と聞かれるまで、
6件は「判断待ち」の欄に積まれたままだった。

```
実態      こちらが手を止めていた
見え方    有璽氏の判断待ちで止まっている
```

## ★監視スクリプトの「実体消失」は、まず自分の走査を疑う（2026-08-28 つる 実測）

`heartbeat_names_check.py` が5件警告を出していた。**うち4件が誤検知だった。**

```
実体消失「法人番号全国データ 月次更新」    → 実在。毎日09:35稼働・心拍🟢（11.9h前）
実体消失「地雷インデックスの再生成」       → 実在。毎朝08:25稼働・心拍🟢（0.3h前）
登録漏れ「警告」「失敗」                   → そんな処理は無い。beat()の第1引数を誤読
本物は1件だけ（intake_notify.py の登録漏れ）
```

**原因は走査側の正規表現2つ。どちらも「書き方の揺れ」を吸収していなかった。**

```
NAME_RX = ^PROC_NAME\s*=\s*['"](.+?)['"]\s*$
   ①変数名を PROC_NAME に固定    → BEAT_NAME を使う corp_number_monthly_update.py を拾えない
   ②行末に \s*$ を要求            → PROC_NAME = '…'  # コメント  が付くと落ちる
CALL_RX = \bbeat\(\s*['"](.+?)['"]
   ③自前ラッパ def beat(result, message) を持つファイル（routine_pickup.py）で、
     第1引数の「警告」「失敗」を処理名だと誤読する
```

- **★誤検知は本物を埋もれさせる。** 5件のうち4件が嘘だと、残る1件も読まれなくなる。
  「壊れた監視は無いより悪い」は、鳴らない監視だけでなく**鳴りすぎる監視**にも当てはまる。
- **★このファイルは同じ穴を4回踏んでいる**（2026-08-20 に2回、08-24 に1回、08-28 に1回）。
  いずれも「①定数で持つ ②直接渡す」以外の書き方が現れるたびに誤検知した。
  **正規表現ベースの走査は、書き方が1つ増えるたびに必ず落ちる。**
  次に落ちたら、正規表現を足すのではなく `ast` で読むか、
  **各スクリプトが `--print-name` で自分の処理名を名乗る**形へ変える。
- **★「実体消失」と出たら、消えたと決める前に `launchctl list` と心拍の最終実行を見る。**
  動いていて心拍も🟢のものを「消えた」と報告するのが、この誤検知のいちばん危険な形。

## ★毎朝の材料「ログの失敗 N件」の中身を数えた ── 6割が正常だった（2026-09-01 ロビン 実測）

④で「self_audit.py は未修正のまま」と書いた状態が **12日続いている**。
今日その中身を初めて数えた。**慢性の発生源は404ではなく Slack の disconnect だった。**

```
経路1  self_audit.py と同じ条件で全 *.log を走査
       （tail -25 → Traceback / Error / ★失敗 / エラー を含む行）
         corrections.log    1件
         intake_match.log   3件   ← 本物（8/31 07:20 の Sheets API 503 の traceback 3行）
         slack_socket.log   6件   ← ★全件が正常
       計 10件

経路2  slack_socket.log の該当6行を目視
       6行とも ConnectionError('サーバからdisconnect要求: warning')
       各行の直後2行が必ず「WebSocket接続完了」→「接続確立（hello受信）」＝復旧済み
       → 一致。★10件中6件（60%）は障害ではない
```

**★判定は済んでいる。読む側が知らないだけ。**
[[reference_slack_tokens_and_socket_mode]] に「disconnect は異常ではない（誤報の元）
＝ Slack 側が定期的に接続を張り直させる正常な挙動。見るのは down_since」と明記済み。
だが `self_audit.py` は memory を読まないので、**確定した判定が収集側へ一生届かない。**
文字列 `エラー` が `★接続が切れた/エラー:` に必ず当たるため、除外は1行で足りる。

- **★「正常だと判定した」で終えない。その事象を数えている仕組みを探して同時に直す。**
  ②③（止めてある・対応保留）と同じ根 ―― **状態を文章に持たせても、読む側が見なければ効かない。**
- **★件数そのものが指標にならない。** `tail -25` は窓が動く。同じログ・同じ日でも
  朝の材料は slack_socket 8件／intake_match 2件、数時間後の実測は 6件／3件だった。
  **増減を異常の兆候として読まない。**
- **★本物（intake_match の503）は、正常6件に挟まれて並ぶ。**
  つるが8/31に自力で捕まえたのは幸運で、埋もれる側の構造は何も変わっていない
  → [[reference_ran_is_not_succeeded]] ／ [[reference_heartbeat_proves_life_not_results]]
- 直す場所は `~/.vivid-relay/self_audit.py`（git外・両機で腐る → [[reference_fix_where_git_reaches]]）。
  **コード変更なので検査役では行わない。ピタゴラスへ回す。**

## ★★人の「保留する」という決定を、機械が持てる形にした（2026-09-05 実装）

**これまで「止めてある」を持てたのは自動処理レジスタ（有効=False）だけで、
指摘（findings）の側には保留の置き場が無かった。** その結果、有璽氏が 8/31 に
「既存台帳の掃除は置いといてよい」と決めたのに、毎朝08:10の点検は同じ3件を
**8日間 出し続けた**（決定は文章にしかなく、機械が読む場所に入っていなかった）。

```
2026-09-05 17:26  有璽氏が Slack のボタンで「期限なしで保留にする」（受付番号 #5bbcb0）
                  ★3案（A 外す／B 出し続ける／C 期限を切る）から A を選択。
                    ★日付での自動復活は入れない、というのが決定の中身
```

**clear（クリア）と park（保留）を分けた。混ぜると記録が化ける。**

```
clear   もう出なくてよい ＝ 直った／対応した
        cleared_by_human=True。再発したら streak を1から数え直す
park    ★問題は残っている。人が「いまは対応しない」と決めただけ
        警告からは外す ／ ★台帳からは消さない ／ ★連続日数を伸ばさない
        誰が・いつ・なぜ・どう戻すか を必ずレコードへ持たせる
```

**★保留にしたことが画面から消えないようにする（これが要点）。**
黙って警告から外すと、[[reference_a_warning_nobody_owns]] の
「警告が消えたとき、直ったのか検査側が拾えなくなったのか区別がつかない」を自分で作る。

```
毎朝の点検   「対応が要るものはありません」の下に ⏸保留中 3件 を必ず出す
             1件ごとに 理由／決めた人／日付／戻すコマンド を印字する
心拍         メッセージへ「⏸保留N件」を常に入れる（0件のときも）
稼働盤       findings.parked として別枠で出す。★慢性タイルの件数には足さない
track()      保留中のレコードは last_seen だけ更新する。
             ★更新しないと「今日は出なかった」に見え、保留と「直った」が同じ形になる
```

**実測（2026-09-05 17:5x）**

```
保留の前   ★対応が要る ： 3件（重複21組8日連続／法人番号空59件8日連続／受付放置9日7日連続）
保留の後   対応が要るものはありません ＋ ⏸保留中 3件（理由・決めた人・戻し方つき）
           findings_escalate.py ドライラン ： 対象 0件 ＝ 明朝08:15のSlack督促は出ない
```

**戻し方は1手** ── `python3 ~/.vivid-relay/findings_tracker.py --unpark "<key>"`。
`--list-parked` でキーが読める。**ledger_report.py 側は触らなくてよい**
（どれを保留にしているかの正本は `open_findings.json` の1か所だけ）。

実体 `bin/hooks/findings_tracker.py`（park/unpark/is_parked/parked_info/parked_findings）
／`~/.vivid-relay/{ledger_report.py, dashboard_data.py, dashboard_build.py}`
