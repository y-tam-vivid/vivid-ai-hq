**★心拍は生存確認であって、成果の確認ではない。** 2026-08-29 有璽氏
──「心拍とか作ってもなんかあんま意味ない気がつくんだけど。ほんまに」。**正しい。**

## 実際に起きたこと（2026-08-29 実測）

`build_landmine_index.py` は毎朝08:25に走り、**心拍を「成功」で打ち続けていた**。
その裏で起きていたこと：

```
memory 188本を走査 → 常設枠に載ったのは 19本（10%）
                     100本を上限で静かに落としていた
出す側は重い順の上位2本に固定 → 残り186本は一度も出ていない
さらに import time の抜けで NameError → ★それでも exit=0 → 心拍「成功」
```

**動いていた。成功と申告していた。効いていなかった。**
そして**こちらは気づかず、有璽氏の指摘で初めて分かった。**

## なぜ心拍では捕まらないか

```
心拍が見ているもの     プロセスが最後まで走ったか（生死）
心拍が見ていないもの   何件効いたか（成果の量）
                       その量が妥当か（期待値）
```

**中身が0件でも、空振りでも、心拍は緑になる。** だから
「毎朝ちゃんと動いています」という報告は、**何の保証にもならない**。

## 二度と起こさない形 ── 3点セットで持つ

心拍を捨てるのではなく、**心拍に数字を持たせ、数字に期待値を持たせる**。

| | 何を持つ | 例（地雷インデックス） |
|---|---|---|
| ① 生死 | 走ったか | 心拍「成功」 |
| ② 成果 | **何件効いたか（数字）** | 走査188本 / 載った59本 |
| ③ 期待 | **その数字が満たすべき条件** | 載った率 ≧ 50%／未提示の記憶 = 0本 |

**★③が無いと、①②が揃っても人が見て気づくしかない。**
「見れるものがない」のではなく、**見ても正常か異常か判定できない**のが問題。
条件を機械に持たせて初めて、人の指摘なしに🔴が立つ。

- 数字は**別々に数えない**。`dashboard_data.json` に集約し `facts.py` から読む
  （[[feedback_never_write_an_unmeasured_number]] の設計をそのまま使う）
- **★期待値を人の記憶や文章に置かない。データとして持つ**
  （fukuchi-core「稼働確認は最後にいつ動いたかと次はいつ動くはずかをセットで持つ」の
  成果版。間隔だけでなく**量**にも同じことが要る）

## ★申告と実物のズレは、作った本人の報告には出ない

「改善しました」と言った後に止まっている、が繰り返される理由は
**過剰修正・空振りが本人には成功に見えるから**。だから
[[feedback_never_write_an_unmeasured_number]] と同じく **別主体が数字で読む**しかない。
自己申告を検知の経路にしない。


## ★検査を作った本人が、同じ壊れ方を検査に入れた（2026-08-29・ドーベルマン指摘）

対策として `dashboard_data.py` に `build_effectiveness()`（4項目の不変条件）を入れた。
**その実装が、今日の事故と同じ形で壊れていた。**

```

   ＝ 何も数えていないのに緑。build_landmine_index が exit=0 を返したのと同じ型
   ★_errors に理由は残るが、health の判定には一切効いていなかった

② 閾値を、実測値を見てから決めた
   実測 55% を見て「50%以上なら🟢」とした ＝ 必ず緑になる基準
   本来向き合うべき事実は「memory 189本のうち45%が候補にすら載っていない」

③ カバレッジが memory・フック系だけ。intake_register や notion_backfill など
   金と時間が絡む業務側の停滞をゼロカバー ＝ 本丸を見ていない
```

- **★「判定不能」を「正常」に倒さない。** 数えられなかったものは緑ではなく**灰**にし、
  ng に数える。エラーを別枠へ逃がすと、全滅したときにいちばん静かになる。
- **★基準は測る前に決める。** 実測を見てから閾値を置くと、必ず自分に甘い数字になる
  （[[feedback_never_write_an_unmeasured_number]] の変種。数字を捏造しなくても、
  基準を後から合わせれば同じことが起きる）。
- **★検査を作った本人は、自分が想定した壊し方しか思いつかない。** 別主体を通す
  （[[feedback_use_the_team_not_alone]]）。今回は実際に、通して初めて4つ出た。

## ★裸の `main()` は、落ちたときに心拍を打たない（2026-08-31 つる 自己監査で実測）

これまでの節はすべて「動いたのに緑」の話だった。**今日出たのは逆側の穴。**

```
実測（2026-08-31 07:20 intake_match.py）
  経路1  intake_match.log ： Sheets API 503 → sh.read() で例外 → traceback で終了
  経路2  レジスタ「受付シートの照合」 最終実行=2026-08-30T07:20 のまま → 🟡遅延
  → 一致。★「失敗」の心拍は1つも打たれていない
```

**原因は構造。** `beat()` は `main()` の最後にしか無く、末尾は `main(...)` を裸で呼ぶだけ。
途中で落ちれば beat へ到達しない。結果、レジスタ上では

```
落ちた（例外で死んだ）        どちらも「最終実行が古い」だけ
遅れた（まだ走っていない）     ＝ 区別できない
```

**★同型が scheduled なもので計10本**（2026-08-31 実測・`tail -6` に except が無い）：
dashboard_build / gas_outside_watch / heartbeat_names_check / ledger_guard_extend /
ledger_report / memory_sweep / notion_minutes_duplicate_report / progress_report /
self_audit / watch_external。**intake_match を含め11本。**

- **★心拍は `try/finally` 側に置く。** 「成功で打つ」だけでは、いちばん知りたい
  「落ちた」が永久に届かない。落ちた瞬間こそ打つべき回。
- **★🟡遅延を見たら「まだ走っていない」と読まない。** ログを開いて traceback を探す。
  遅延と死亡が同じ色で出る間は、レジスタの色は原因を持っていない。
- 修正はコード変更なので検査役（つる）では行わず、ピタゴラスへ回した。

## ★2026-09-08 progress_report.py を修正・実測。残り10本は未着手

有璽氏「その構造を直す直す言ってて全然直っとらん」を受け、11本のうち1本を実際に直した。
`sys.exit(main())` の裸呼びを `try: main() / except: heartbeat.beat(失敗)` へ包む型
（`corp_number_monthly_update.py` と同じ）。実測：`build_report()` へ
`raise RuntimeError` を仕込み `--run --beat` で実行 → レジスタが🟢正常→🔴失敗→
（正常系を再実行して）🟢正常、と2回とも正しく遷移することを確認。

**★実測で踏んだ地雷（テスト方法そのものの罠）**：わざと失敗させるテストコピーを
`/tmp/xxx.py` へ置くと、`HERE = os.path.dirname(os.path.abspath(__file__))` が
`/tmp` になり `from heartbeat import beat` が `/tmp/heartbeat.py` を探して
`ModuleNotFoundError`＋`except Exception: pass` で**心拍そのものが握りつぶされる**
（レジスタが一切動かない＝テストが機能していないのに一見「何も起きない」だけに見える）。
**`sys.path.insert(0, HERE)` できょうだいモジュールを読む型のスクリプトを検証するときは、
テストコピーも同じディレクトリへ置くこと。** 別ディレクトリへ逃がすテストは、この型の
スクリプトでは検証にならない。

**残り9本（dashboard_build / gas_outside_watch / heartbeat_names_check /
ledger_guard_extend / ledger_report / memory_sweep / notion_minutes_duplicate_report /
self_audit / watch_external）と intake_match は依然未修正。** 依頼のスコープが

## ✅2026-09-13 外部調査で裏が取れた ── 「心拍は生死しか見ない」は★業界共通の結論だった

この記憶の見出しは 2026-08-29 に有璽氏の指摘から書いたものだが、**外にも同じ結論がある**
ことが分かった（クローバー調査・出典6本／`~/.vivid-relay/agent_console_research.md`）。

> 「The process keeps running. **The heartbeat continues.** But work stops happening.」
> （プロセスは動き続ける。**心拍も続く。**だが仕事は止まっている）

**★AIエージェント特有の失敗の形**。通常のソフトと違い**スタックトレースを吐いて落ちない**。
ループにハマる／レート制限で無期限に待つ／単に推論が止まる ＝ **静かに失敗する**。
**★Temporal のような耐障害性の基盤を使っても防げない**と複数の情報源が明言。

```
★対策として外が一致していたのは2つだけ
  ①タイムアウト監視   ★最後に「意味のある出力」を出してから何分経ったか
  ②完了の意味論を厳密にする
     ★「ツール呼び出しが成功した」≠「タスクが完了した」
     ★「プロセスが終了した」≠「依頼が果たされた」
```

**★②はうちが繰り返し踏んでいる型そのもの。**
- 2026-09-13 リリス：16分で **rc=0** 終了・`sweep_widths.py` は作ったが**出口の結果ファイルは無い**
- 2026-09-13 `build_running()`：`ps` が **rc=0** で壊れた出力を返し「0人」と言い続けた
→ **rc=0 も、心拍の着弾も、「仕事が終わった」の証拠にならない。**
→ [[reference_ran_is_not_succeeded]]（rc=0なのに出力が壊れていた実例）

**★だから心拍に「何をしているか」を載せる。**生死だけを送る心拍は、この失敗を検出できない。
外の最小の是正策も同じ ── `{updated_at, doing: "いま何をしているか"}` を書き続ける。
