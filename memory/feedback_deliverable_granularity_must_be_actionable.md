**「困りごと→担当職種」の1行止まりでは粗すぎる。「その職種が具体的に何をするか」まで分解し、価格帯（参考値でよい）まで添えて初めて使える成果物になる。**

**Why**：2026-09-08、福祉施設の困りごと119件×自社の手札のクロス判定（[[project_fukushi_needs_and_team_design]]）で、クローバー博士（researcher）が「#3 A型の廃業が急増 → 中小企業診断士」の粒度で外部専門家の割り当てを出したところ、有璽氏に差し戻された。

> 「チーム編成と書いてるけども、具体的にどの業務に対して人がいるのかとか、そういったものが全然わからないんだよ。それを全部洗い出せっつってんねん。だからまとめ方としてこれじゃちょっと弱すぎるで。中身がなくない？それぞれのサービスがどれぐらいの価格帯になるかも参考値として入れて。」

求められていたのは「困りごと→職種」の対応表ではなく、「困りごと→実行可能な業務（複数可）→誰が→資格の要否→価格帯」という設計図。**1つの困りごとに複数の業務がぶら下がるのが正しい形**（1対1に押し込めると粒度が落ちる）。

**How to apply**：

- **判定基準は「読んだ人が明日それを実行できるか」。** できないなら粒度が粗い。
- **「業務名」は必ず動詞で終える。**「中小企業診断士」のような職種名だけで止めない
  （例: ✕「中小企業診断士」→ ◎「生産活動の収支構造を分析し、赤字要因を特定する」＋担当職種）。
- **価格帯・料金は求められたら参考値でよいが、推測で数字を埋めない。** 出典があれば
  「公開料金(出典つき)」、無ければ「相場(推定)」、分からなければ空欄+「未確定」と明記する
  （数字の出どころを分ける手法は [[feedback_never_write_an_unmeasured_number]] と同型）。
- **士業がからむ業務は資格の要否（業務独占／推奨／不要）を明記する。** 「コンサル」
  「専門家」のような曖昧語で職種を書かない。
- **ズレの型としては [[feedback_show_the_skeleton_first]] の「語の解像度が違う」に近いが別物**：
  あちらは「作る前に骨組みを見せて形のズレを防ぐ」、こちらは「作った成果物そのものの
  分解の深さが足りない」。**量が多い列挙作業（100件超）ほど、1行の粒度を先に1〜2件で
  確認してから残りへ広げる**のが両方の教訓を満たす進め方。

**★続き（2026-09-08 同日2回目の差し戻し）**：粒度を動詞まで下げて68業務を再提出したが、
再び「本当の意味での網羅性」を求められた。今度は粒度の問題ではなく、**サービスの中の
「手続きの真ん中」しか拾えていなかった**こと。

> 「本当に網羅的にしてください。例えば、RPOの領域であれば、スカウト文を送るコンサル、
> 面接の練習や面接の代行、あと、RPO定着の領域で、研修、面談等の部分だったりもあると
> 思いますし」

実測：RPO(採用支援)は「求人原稿作成〜面接日程調整」の6業務のみで、面接の練習・代行・
内定フォロー・定着（研修・面談・離職予兆検知）が**丸ごと0件**だった。

**How to apply（技法として）**：1つのサービス名を見たら、時間軸で前後に伸ばす。
「その業務の**前**に誰かがやることは？　**後**に誰かがやることは？」を機械的に問う。

```
✕ いまの形   募集を出す 〜 面接を組む      ＝ 手続きの真ん中だけを拾いがち
◎ 要る形     母集団を作る → 惹きつける → 選ぶ → 入ってもらう → ★続けてもらう
```

- **「後」に伸ばした先（定着・アフターフォロー）ほど抜けやすい。** 手続きは「契約が
  成立するまで」で終わったように見えるが、依頼者が本当に求めているのは
  「その先も含めたサービス全体の設計図」であることが多い。
- 1メニューにつき最低5段階（前々／前／本体／後／さらに後）を自問してから件数を数える。
  それでも薄い段があれば、そこが本当の抜けである可能性が高い。
