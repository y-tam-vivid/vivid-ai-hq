**「止まらずに進めろ」（6文字）に対して「指示が大きすぎるかもしれません」と返した。** 指示は大きくない。
打ち切ったのは**こちら側の持ち時間**であって、相手の入力の長さではない。

```
実測（2026-08-20 02:50・ps で確認）
  claude -p が 3本 同時に生きていた（経過 11:40 / 6:40 / 1:40）
  うち2本は まったく同じ指示「止まらずに進めろ」
  Slack DM には「承りました。実行します」が 5分おきに 4回 届いていた

なぜ
  cron   */5 で slack_inbox.py が起動する
  実行   1回が最長900秒＝15分  → 5分ごとに新しい実行が重なる
  状態   last_ts をループの最後にしか保存しない
         → 打ち切られると「まだ読んでいない」ままなので、次の起動が同じ発言を拾い直す
  出力   capture_output は打ち切り時に出力が丸ごと消える＝15分の作業が0で返る
```

## 型（他の常駐スクリプトにも当てはまる）

- **周期より1回の実行が長い自動処理は、必ずロックを持たせる。** 持たないと積み上がる。
  積み上がったことは**ログにも心拍にも出ない**（どの1本も「成功」で終わるため）。
- **「読んだ」の確定は、実行の前に置く。** 実行の後に置くと、落ちた回だけ無限に再実行する。
- **★失敗の文言で相手を疑わない。** 原因が自分側にあるのに「指示が大きすぎるかも」と書くと、
  読んだ側は自分の書き方を直そうとする＝直らない方向へ人を動かす。
  書いてよいのは事実だけ ── 「持ち時間◯分を超えた」「途中まではここまで」。
- **打ち切っても途中経過を返す。** stdout をファイルへ流しておけば、殺しても残る。

## 直した実体（`~/.vivid-relay/slack_inbox.py`・2026-08-20）

```
ロック          slack_inbox.lock ＋ 生存確認（PIDへ signal 0）。走っていれば今回は何もしない
持ち時間        900 → 1800秒（ロックがあるので積み上がらない）
状態の確定      post('承りました') の直前に last_ts を保存
出力            Popen → slack_inbox_partial.txt へ流す。打ち切り時は末尾1200字を返す
文言            「指示が大きすぎるかもしれません」→「こちらの持ち時間の上限です。指示の長さは関係ありません」
```
