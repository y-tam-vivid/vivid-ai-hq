**つるのA分類「候補1件・9件」は、9件中5件しか decide() を通らなかった。**
残り4件（B-0327マーベリック／B-0372ジャパンネットワークグループ／

## ★★削除は指摘を減らさず、7組 増やした ── 消えたのは行ではなく判定材料（2026-09-05 ロビン実測）

**上の「3行を削除した」の結果を、5日後に数え直した。掃除にならず逆に増えていた。**

```
毎朝の点検ログを日付ごとに開いて数えた（ledger_report.log）
   08/26〜08/31  要判断 16組 ／ 別法人（対応不要）22組
   09/01 以降    要判断 21組 ／ 別法人（対応不要）18組
                 ↑ 削除は 8/31 09:12（その日の点検 08:10 より後）
```

**真因 ── `ledger_dupes.py` の「決着済み」判定は 00_企業マスタ の備考しか読まない。
だが突合の対象は 01_顧客詳細 からも作られる。**

```
削除前   00に行がある + 備考「B-0380へ統合済み」 → retired に入り集計から外れる
削除後   00の行ごと消えた ＝ 備考も消えた        → retired に入らない
         ★IDは 01_顧客詳細 に残ったまま         → 生きた行として復活し 7組が新出
```

**★消した3行の備考は、そのまま機械の判定材料だった。**
- B-0008「社内顧客ID 380 へ統合済み（2026-08-03）。**★行は記録として残す**」
  ＝ 消すなと自分で書いてあった行を消した。これで7組が復活
- B-0132「別法人と確認済み（B-0034 B-0145 B-0149 B-0380 と法人番号が異なる）」
  ＝ 4組ぶんの決着。別法人 22→18 の -4 はこれ

```
実測（2経路とも一致）
  経路1  01_顧客詳細を直読み → B-0008(行8)/B-0076(行75)/B-0132(行131) が実在。
         00にあって01に無いID 85件に対し、★01にあって00に無いIDはちょうど3件で
         削除した3件と完全一致（＝孤児は今回作ったものだけ）
  経路2  今日の21組のうち B-0008 を含む組は7組。21-7=14 ＝ 8/31の実測14組と一致
```

**How to apply:**

- **★正本の行を消す前に「その行の備考を、機械が読んでいないか」を確かめる。**
  備考は人が読むメモではなく、毎朝の判定に使われる列だった。
- **★消すなら関係する全シートを同時に消す。片側だけ消すと、判定材料だけが失われ
  判定対象は残る＝いちばん悪い形になる。** 00と01は別々に消す必要がある。
- **★「消す」で減るのは行であって、指摘ではない。** 削除の効果は実測で確かめる
  （このケースは翌朝のログ1行で分かった）→ [[reference_verify_outcome_not_mechanism]]
- 控え `~/.vivid-relay/deleted_rows_20260831-091220.json`（1,745バイト・3行の全内容）
  は実在する。**戻すこと自体は可能**（★戻すかどうかは有璽氏の判断。正本の変更）。
- ★同じ根 → [[reference_stale_copy_of_kintone_columns]]（状態を1か所にだけ書くと片方が腐る）

## ★8日連続の「8日」は、汚れの年齢ではない（2026-09-05 実測）
