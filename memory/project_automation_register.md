## 台帳と実体の突合（2026-08-19 新設）

**心拍とは見る角度が違う。心拍は「載っている処理が動いているか」、これは「そもそも載っているか」。**

```
① 実体にあるが台帳に無い   登録漏れ。誰も見ていない自動処理が動いている
② 台帳にあるが実体に無い   「稼働中」と書いてあるが cron も launchd も持っていない
                        ＝「自動と言っているのに自動になっていない」の正体
```

**②は心拍では絶対に見つからない** ―― 行が無ければ、心拍が来ないことすら分からない。
実際 2026-08-19 に部門名寄せ・重複検知を作ったとき、心拍を打つコードは書いたのに
レジスタの行を作り忘れ、心拍が空振りしていた。**作る側の規律に依存する限り再発する。**

**実体 = `crontab -l` と `~/Library/LaunchAgents/*.plist`。** 自前のもの
（`/.vivid-relay/` `/vivid-ai-hq/` `/bin/`）だけを数え、第三者製（Google更新等）は無視する。
台帳側は「実体」欄からスクリプト名を拾って突合する。

**★自分のマシンの分だけを見る。** 相手機へ ssh すると、閉じている日に検査が働かない
＝**「調べられなかった」が「異常なし」に見える**のが一番危ない。各機が自分を見る。

```
実体      ~/.vivid-relay/automation_inventory_check.py（両機・md5一致）
予定      毎週月曜 09:20（両機の cron）
通知      ズレがある日だけ Slack。読むだけで cron も Notion も変更しない
レジスタ   「台帳と実体の突合（Mac mini）」「同（MacBook）」の2行
初回実測   mini 実体7本⇄台帳7行 ／ MacBook 実体3本⇄台帳3行 ＝ どちらもズレ0
```

**この仕組みは自分自身を検知した。** レジスタに登録した直後、cronに載せる前の状態で
「申告倒れ1件」と出た。載せたら0に戻った。

**検知できないもの**: GAS（トリガー列挙APIが外から無い／GAS内に関数を置けば可能）、
クラウドroutine（列挙APIが存在しない＝外形監視の代理心拍でしか見られない）。

### ★心拍を打つコードを書いたら、レジスタの行を作るまでが1作業（2026-08-20 実地）

`inbox_runner.py`（📮AI指示箱・cron */5）は心拍を打つコードを持っていたが、
**レジスタの行を作っていなかった。** `heartbeat.py` は行を新規作成しない設計なので、
5分ごとに `[heartbeat] レジスタに「…」が無い。行を新規作成はしない` を
`inbox.log` へ書き続けていた。**ログは届く場所ではない**（→ [[reference_silent_sync_failure]]）ので、
有璽氏が「いれて」と言うまで誰も拾っていない。

```
心拍を打つコードを書いた      ← ここで終わると
   ↓                          ・🔴 すら立たない（監視対象ですらない）
レジスタの行を作る            ・気づけるのは週1の突合（月曜09:20）だけ＝最大6日
   ↓                          ・その間ログには毎回出ているが誰も読まない
1回走らせて着弾を実測          ★「行が無い」は失敗ではなく沈黙。だから見つからない
```

**②「台帳にあるが実体に無い」の実例が出た（2026-08-20・つる実測）。**
`台帳→Notion顧客DB の同期`（`notion_customer_upsert.py`）は
**有効=✓・最終結果=成功・最終実行=2026-08-19 15:57** と表示されているのに **cron に無い**。
成功の記録は手動テスト1回のもの。**「有効・成功」の3列だけを見ると自動稼働に見える。**
`notion_backfill.py` も同様に cron 無し（こちらは備考に保留と自己申告あり・意図的）。
→ **レジスタの表示で稼働を判定しない。実体（crontab）と突き合わせるまでが確認。**
→ [[feedback_one_route_is_not_verification]]

**③ なぜ②が起きるか ── 心拍は「誰が動かしたか」を区別しない（設計の穴・2026-08-20）。**
`heartbeat.py` は呼ばれれば書く。**人が手で叩いても、cron が叩いても、同じ1行が立つ。**
だから「一度も自動実行されていないのに🟢」が成立する。
実際 `notion_customer_upsert.py` は **cron に1行も入らないまま16回失敗し続けていた**のに、
手動実行1回の心拍だけでレジスタは「成功」を表示していた。

```
いまの心拍   処理名 ／ 最終実行 ／ 最終結果 ／ メッセージ
足りない列   起動元（cron / launchd / routine / 人の手）
             → 人の手しか無い行＝「作ったが自動化されていない」が機械的に見える
```

★実装は未了。**当面の判定手段は crontab / launchd / routine 一覧との突合ただ1つ**。
「台帳と実体の突合」（毎週月曜09:20）がその役だが、**クラウドroutineとGASトリガーは対象外**
（前者は RemoteTrigger がスクリプトから叩けず、後者はAPIで一覧が取れないため）。

## ★逆向きの食い違い ── 実体は動いているのにレジスタが「無効」（2026-08-20 実測）

これまで見ていたのは「申告倒れ」だった。**逆がある。**

```
申告倒れ    レジスタ「有効✓・成功」  実体が無い     → 動いていないのに気づけない
★逆向き    レジスタ「有効=False」    実体は動いている → **監視されていない**
                                                      止まっても🔴が立たない
```

実測（2026-08-20）
```
                          実体                        レジスタ
intake_register           daily_jobs.conf 07:25 稼働   有効=False
notion_customer_upsert    daily_jobs.conf 08:00 稼働   有効=False・最終実行=None
Manus watch               mini の crontab で稼働       実行機=MacBook（★実体はmini）
```

- **どちらの向きも「台帳と実体の突合」で見つかる。だが直す向きが違う。**
  申告倒れ → 実体を作るか、レジスタから外す
  ★逆向き → **レジスタを実体に合わせる**（実行行は正しい。止めてはいけない）
- **★どちらが正かは、判断の履歴で決める。** 今回は
  「有璽氏が毎朝に載せろと言った」「つるが載せてよいと判定した」＝**実行行が正**だった
- **検査役が食い違いを見つけても、直す向きまでは決められない。** 判断の履歴を持つ側が決める

### ★cron ではないものを「経路=cron」と書かない

crontab へは書けないので、いま日次で回っているものは `bin/daily_jobs.conf` にある。
レジスタや一覧ページに「cron」と書くと、**次に見る人が crontab を探して見つからず混乱する。**
「daily_jobs.sh 経由」と書く。

## ★既存行への相乗りは「行を作った」ことにならない（2026-08-20 当方のミス）

`gas_outside_watch.py` を新設したとき、心拍が「レジスタに行が無い」と言ったので
**既存の「外形監視（自分で心拍を打てない処理の代理）」に PROC_NAME を合わせた。**
＝ 行を作らず、**既存行に相乗りした。**

```
同じ行に心拍を打つ2本
   watch_external.py    crontab 09:00
   gas_outside_watch.py daily_jobs 08:30   ← 今日新設
→ ★どちらが動いたのか区別できない。片方が止まっても、もう片方の心拍で🟢に見える
```

**当方は同じ日に「心拍を打つコードを書いたら、同じ作業でレジスタの行を作るまでが1作業」と
書いておきながら、既存行に名前を合わせて済ませた。**

- **★「行が無い」と言われたら、行を作る。** 名前を既存に合わせるのは解決ではない
- **1行 = 1処理。** 相乗りすると、**片方の生存がもう片方を隠す**
- 統合してよいのは「同じ処理を1本にまとめた」ときだけ。**2本あるなら2行**

## ★化ける記号は、直すより使わない（2026-08-20）

Notion のページで `★` が `☦` `♦` へ**3回連続で化けた**。
担当は**★へ戻さず、記号を外して見出しの形を変えた**（「## 対応済み（2026-08-20）：…」）。

- **同じ場所で3回化けたら、その記号を使うのをやめる。** 直し続けても再発する
- **確かめ方は grep で数える。** 正規の記号と化け候補（`☦` `♦` `閘` 等）を両方数え、
  化け候補が0件であることを見る。**目視では拾えない**
