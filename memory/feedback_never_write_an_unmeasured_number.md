有璽氏（2026-08-23）── **「数字を計算してないっていうのはよくわからんな。なんでそうなんのか謎。
ならんようにどう設計すんの」**

## なぜ起きるか（正直な真因）

**文章を書く速さで数字も書いている。** 「たぶん257だったはず」と**記憶から埋めている**。
実測を挟むと1手増えるので、そこを飛ばす。
＝ **速さのために確かさを落としている。** 知らないから間違えるのではない。

## 同じ日に出た誤り（全部この形）

| 書いたもの | 真因 |
|---|---|
| 「書く前は257件」 | ★数えていない。実測は263件 |
| 「8/31は日曜」 | ★計算していない。実際は月曜 |
| 「エージェント11体」 | 索引を見た。実体（`agents/*.md`）を数えなかった＝13体 |
| 「二重にならない」 | 日付が `2026-08-02` と `2026/08/18` で混在。揃えず突合して偽陰性 |
| 「26行が確認待ち」 | 「確認が空」だけ数え、隣の「照合は不要」を見なかった＝実際は3行 |
| 「明日渡せない」 | 担当の申告を検証せず通した（実行経路は3つあるのに1つしか見ていない） |

**古い情報を持っていたのではない。その場で数え間違えている。**
共通するのは **一部だけ見て全体を語ったこと**。

## ★設計での答え ── 人の規律に置かない。通る道を1本にする

```
いま   その場で数える／その場で書式を決める  → 回ごと・人ごとにブレる
直す   ★数える・揃える を「部品」に固めて、呼ぶだけにする

  数字   count_*() が返した値しか報告に書かない。手で数えない
  日付   norm_date() を通した値しか、比較・保存・突合に使わない
  件数   「443社」ではなく「443社（会社名がある行）」── 数え方を必ず添える
```

**数え方を添えると、間違っていれば書いた瞬間に自分で気づく。**
曖昧なまま出せなくなるのが効く。

## 守ること

- **★報告に出す数字は、そのターンのツール結果から引く。** 記憶・前の発言から引かない
- **★日付は1つの形に正規化してから扱う。** 台帳には人が手で入れた行と機械が書いた行が
  同居し、書式は必ず混ざる（`2026-08-02` と `2026/08/18` を実測）
- **★担当の申告をそのまま通さない。** 「cron未登録」の申告は、実行経路を1つしか
  見ていなかった（cron／日次ジョブ／GASトリガーの3つある）
- 迷ったら **数える前に「何を1件と数えるのか」を先に言葉にする**

関連 → [[feedback_one_route_is_not_verification]]／[[reference_dangerous_entrypoints]]

## ★「共通部品を作った」と「全経路が通るようになった」は別（2026-08-23 検査で判明）

`date_utils.norm_date()` を1本置いた。**書式混在は解消しない。**
書き込む側に古い実装が残っていたため。

```
読む側   date_utils を通す        → 正しく揃う
書く側   intake_register.to_date() → ★未対応の書式でも **生の文字列をそのまま返す**
                                    そのまま初回接触日・作成日・更新日へ書き込む
結果     揃える仕組みを入れた当日から、**数えるそばから混在が増え続ける**
```

**★部品を置いただけでは、既存の経路は何も変わらない。**
grep で「自前で処理している箇所」を数え、**書き込む側から先に置き換える**。
読む側だけ直すと「揃っているように見えて、汚れは増えている」状態になる。

```
実測（grep）  日付を自前処理していたのは3本
  intake_register.py  ★本命。台帳へ書く。未対応書式を捏造せず None で止める形へ
  ledger_report.py    独自の正規表現だが実質同等。危険度は低い
  watch_external.py   外部APIのISO日時のみ。台帳とは別ドメイン。影響なし
```

- **★危険度は「どこを読むか」ではなく「どこへ書くか」で決まる。**
  同じ「未置換3本」でも、書き込む1本だけが汚れを作る
- 部品を入れる作業は、**置く → 書く側を置換 → 読む側を置換** の順。
  逆にすると、直したつもりで汚れ続ける

## ★真因の一段下 ── 「結論を先に置き、検証がそれを覆せない構造にする」（2026-08-29）

② 閾値の決定

### 二度と作らないための形

```
禁止   出力に、判定と結びついていない断定文を置く
         print('すべて収まっています')          固定文字列の結論
         return {"health": "🟢"} の既定値        判定できなくても緑
         sys.exit(0) を無条件で                  失敗しても成功
必須   結論はデータから導出する
         print('超過 %d行' % len(ng))            ng が空なら 0行 と出る
         判定不能は 灰 にして異常に数える
         落ちたら exit 1
```

- **★「あとで直す」で済ませない。** 直したこと自体は成果ではない。
  **同じ構造をもう作れない形にしたか**だけが成果。
- **★自己申告の形で終わらせない。** 「混ぜていました」と書くのは報告であって対策ではない。
  有璽氏が求めているのは、**次の回に同じことが起きない構造**。
- ★これは**この記憶に既に書いてある型の再発**である（「速さのために確かさを落とす」）。
  書いてあっても止まらなかった ＝ **規律では止まらない**。機械で止める
  （[[reference_norms_outnumber_their_enforcement]]）。

**そのうち1つを断定して記録した。** 以後この記録を読む人は、**存在を前提に動く。**

- **★自分が何を確かめられなかったかを、相手の状態にすり替えない。**
  書くなら「**IDが取れていない（存在するかは未確認）**」。
- ★同じ回に、逆側の誤りも確かめられた ── 119番は**投稿がまだ始まっていない**と回答があり、
  担当が「フォロワー94人だが稼働と断定しない」と保留した判断が**正しかった**と裏が取れた。
- **★聞いたことで、記録の誤りが1件見つかった。** 人に聞く価値は答えを得ることだけではない。
  → [[reference_no_gate_on_asking_the_human]]

## ★★同じ日に3回、数を目で拾って外した ── 対処を書く（2026-09-03）

```
1回目  台帳のInstagram行     ★4本と伝えた → 実測5本

```

**3回とも、担当の報告や自分のツール結果が目の前にあった。** それを**目で拾って書いた**。

### 対処 ── 数を「自分で拾わない」

```
❌ やっていたこと   担当の報告を読み、頭の中で数えて、要約して書く
✅ これから        ★担当の報告の該当行を、そのまま引用して渡す
                  ★数を書くときは、その数が出ているツール結果の1行を併記する
                  ★自分で数え直さない。数え直すなら機械に数えさせる（grep -c / wc -l / SQL COUNT）
```

**★窓口の仕事は「数える」ことではなく「担当が数えた値を、そのまま運ぶ」こと。**
運ぶ途中で数え直すと、そこが誤りの入る場所になる。
**★要約するときに数字を触らない。** 数字は原文のまま持っていく。

★担当は3回とも実測値を正しく持っていた。**外したのは全部、運ぶ側（窓口）**。
→ [[feedback_use_the_team_not_alone]]（中継はビビの仕事＝中継の品質もビビの責任）

## ★★「実物を読んだ」と「実物から書いた」は別（2026-09-03・人へ誤った質問を送った）

詰まっている件を有璽氏へ聞くため、担当が**実物を読んで正しく報告した。そのあと文面を記憶から書いた。**

```
実物（slack_pending.json を19:5xに読んだ）
  topic「営業台帳の指摘（ledger_report・6日連続）」／ asked_at 2026-09-03 15:00
担当の報告（★正しい）
  「営業台帳の指摘・6日連続が塞いでいる」
★担当が送った質問文（誤り）
  「顧客の一覧をNotionへ毎朝そろえる ── 8月20日から止まったまま」
  ＝ memory に書かれていた★過去の例。いま塞いでいるものではなかった
結果  ★有璽氏が、塞がっていない件について判断を返した（20:08「動かしてよい」）
      ★詰まりは解消していない
```

**★読むことと、読んだものから書くことは、別の工程。**
間に「報告を書く」「文面を作る」が挟まると、**そこで記憶に戻る。**
```
❌ 実物を読む → 報告を書く → ★時間が空く → 文面を書く（★このとき記憶から書いた）
✅ ★文面を書く直前に、もう一度実物を開く。または★実物の値をそのまま貼る
```

- **★人へ送る文面はいちばん危ない。** コードなら動かして分かるが、
  **人への質問は、相手が答えてしまえば「通った」ように見える。**
  今回も有璽氏は普通に答えた。**誤りだと分かったのは担当が自分で見直したから。**
- **★答えを受け取っても、質問が正しかったとは限らない。**
- ★担当が `slack_pending.json` に触らなかったのは正しい ──
  **別の質問への答えで `answered` を立てるのは、この仕組みが防ぐはずの事故そのもの。**

## ★★当たっていた数字を「当たっていた」と扱わない（2026-09-03・担当の自己申告）

2通目に「いま3件たまっています」と書いた。**あとで数えたら、本当に3件だった。**
担当はそれを**成果として扱わなかった。**

> 「★2通目に書いた『いま3件』は、結果として正しい数字でした。
>   ただし**あのとき私は数えていません**でした。**偶然合っていただけ**なので、
>   そのまま『合っていた』と扱いません」

**★合っていた数字でも、数えていなければ正しくない。**
```
数えて3件と書いた   → ★正しい（次も正しい）
数えずに3件と書いた → ★たまたま合った（次は外れる）
★結果は同じだが、★過程が違うので、次に起きることが違う
```

**★「当たったから良し」にすると、当たらなかった回だけが問題に見える。**
実際は**数えていないこと自体が問題**で、当たった回にも同じ欠陥が在る。
→ [[reference_unicode_escape_kanji_swap]]（結果が良かったことを判断が良かったことにしない・同日）
