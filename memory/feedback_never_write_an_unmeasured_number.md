有璽氏（2026-08-23）── **「数字を計算してないっていうのはよくわからんな。なんでそうなんのか謎。
ならんようにどう設計すんの」**

## なぜ起きるか（正直な真因）

**文章を書く速さで数字も書いている。** 「たぶん257だったはず」と**記憶から埋めている**。
実測を挟むと1手増えるので、そこを飛ばす。
＝ **速さのために確かさを落としている。** 知らないから間違えるのではない。

## 同じ日に出た誤り（全部この形）

| 書いたもの | 真因 |
|---|---|
| 「書く前は257件」 | ★数えていない。実測は263件 |
| 「8/31は日曜」 | ★計算していない。実際は月曜 |
| 「エージェント11体」 | 索引を見た。実体（`agents/*.md`）を数えなかった＝13体 |
| 「二重にならない」 | 日付が `2026-08-02` と `2026/08/18` で混在。揃えず突合して偽陰性 |
| 「26行が確認待ち」 | 「確認が空」だけ数え、隣の「照合は不要」を見なかった＝実際は3行 |
| 「明日渡せない」 | 担当の申告を検証せず通した（実行経路は3つあるのに1つしか見ていない） |

**古い情報を持っていたのではない。その場で数え間違えている。**
共通するのは **一部だけ見て全体を語ったこと**。

## ★設計での答え ── 人の規律に置かない。通る道を1本にする

```
いま   その場で数える／その場で書式を決める  → 回ごと・人ごとにブレる
直す   ★数える・揃える を「部品」に固めて、呼ぶだけにする

  数字   count_*() が返した値しか報告に書かない。手で数えない
  日付   norm_date() を通した値しか、比較・保存・突合に使わない
  件数   「443社」ではなく「443社（会社名がある行）」── 数え方を必ず添える
```

**数え方を添えると、間違っていれば書いた瞬間に自分で気づく。**
曖昧なまま出せなくなるのが効く。

## 守ること

- **★報告に出す数字は、そのターンのツール結果から引く。** 記憶・前の発言から引かない
- **★日付は1つの形に正規化してから扱う。** 台帳には人が手で入れた行と機械が書いた行が
  同居し、書式は必ず混ざる（`2026-08-02` と `2026/08/18` を実測）
- **★担当の申告をそのまま通さない。** 「cron未登録」の申告は、実行経路を1つしか
  見ていなかった（cron／日次ジョブ／GASトリガーの3つある）
- 迷ったら **数える前に「何を1件と数えるのか」を先に言葉にする**

## ★有璽氏の設計（2026-08-23）── 毎回数えない。1か所に集約して読むだけにする

> 「各エージェントが最新版の情報や数字を、どこか統一した場所に集約して、
>   それを読むだけにすればいいんじゃないの？ 1から全部数えたら、すごい時間かかるじゃん。
>   **ここを見るっていうものを定めていけばいい。** 全部を集約できないまでも、
>   このフォルダであればこの部分を見るとか、そういうふうな形で決め事として作って」

**「毎回数える」より優れている。** 理由は速さだけではない ──
**別々に数えると、数える人ごとに違う答えが出る**（2026-08-23 実測：
番人は「申告倒れ0件」、実装担当は「7件」。同じ日・同じ対象）。

```
① 集約できるもの      数字を1か所に持つ ＝ ★実装は `dashboard_data.json`（読み口が `facts.py`）
                      ★数え方も一緒に持つ（「443社（会社名がある行）」）
                      ★generated_at を必ず持つ（無いと古さが分からない）
② 集約できないもの    「どこを見るか」を決め事にする
                      台帳 → Skill `sheets-access` ／ Notion → 運用ルール正本
                      営業 → Skill `fukuchi-sales`
③ 読む側              ★規律に頼らない。フックが作業の直前に突きつける
```

**★新しい器を作らない。** 既にある `dashboard_data.json`（稼働盤用に実測を集約したもの）を
「数字の正本」へ格上げする。増やすと二重管理になる
（規範「新しい仕組みの採否は二重管理が増えないかで決める」）。

## ★同じ形の変種 ── 「エラーを見ずに、結果の数字だけ見た」（2026-08-23）

Slackのチャンネル一覧を取り、**「0件」だから権限が無い**と報告した。**誤り。**

```
叩いた   conversations.list?types=public_channel,private_channel
返り     {"ok": false, "error": "missing_scope", "channels": []}
             ↑ ここを見なかった              ↑ ここだけ見た
実測     public だけで叩くと **3件返る**。★権限はあった
影響     有璽氏へ「スコープを3つ追加してください」と過剰な作業を渡しかけた
```

**★API の返りは「数字」ではなく「ok と error」から読む。**
`ok:false` のときの空配列は「0件」ではない。**測れていない**という意味。

- **★空・ゼロ・見つからない を結論にする前に、エラーが出ていないかを見る**
- **★リクエストの条件を欲張らない。** 1回で全部取ろうとして
  （public と private を同時に指定して）、権限のある方まで巻き添えで落とした。
  **取れるものから1つずつ取る**
- 人へ作業を渡す前に、**その作業が本当に要るのか**をもう一度だけ実測する
  → [[feedback_verify_before_declining]]（押す場所まで特定してから渡す）

## ★この設計が効いた最初の実例（2026-08-23・実装当日）

同じ台帳を別々の担当が数え、**違う数字が出た。だが今度は原因が一撃で分かった。**

```
つる        443社   「00_企業マスタで会社名がある行」
ピタゴラス  437社   「社内顧客IDがある行（統合済みは除く）」
差 6件      ★全部「◯◯へ統合済み」の行だった（B-0008 / B-0141 / B-0214 /
                                              B-0222 / B-0310 / B-0374）
```

**どちらも正しい。目的が違うだけ。**

```
443社   全部の行を数えたいとき（履歴として残る統合済みを含む）
437社   いま生きている取引先を数えたいとき   ← 営業に見せるのはこちら
```

**★数え方が添えてあったから、食い違いが「謎」ではなく「差分」になった。**
添えていなければ、また「どちらが正しいのか」で1往復していた
（同じ日の午前に、番人0件 vs 実装担当7件でそれをやっている）。

## ★「共通部品を作った」と「全経路が通るようになった」は別（2026-08-23 検査で判明）

`date_utils.norm_date()` を1本置いた。**書式混在は解消しない。**
書き込む側に古い実装が残っていたため。

```
読む側   date_utils を通す        → 正しく揃う
書く側   intake_register.to_date() → ★未対応の書式でも **生の文字列をそのまま返す**
                                    そのまま初回接触日・作成日・更新日へ書き込む
結果     揃える仕組みを入れた当日から、**数えるそばから混在が増え続ける**
```

**★部品を置いただけでは、既存の経路は何も変わらない。**
grep で「自前で処理している箇所」を数え、**書き込む側から先に置き換える**。
読む側だけ直すと「揃っているように見えて、汚れは増えている」状態になる。

```
実測（grep）  日付を自前処理していたのは3本
  intake_register.py  ★本命。台帳へ書く。未対応書式を捏造せず None で止める形へ
  ledger_report.py    独自の正規表現だが実質同等。危険度は低い
  watch_external.py   外部APIのISO日時のみ。台帳とは別ドメイン。影響なし
```

- **★危険度は「どこを読むか」ではなく「どこへ書くか」で決まる。**
  同じ「未置換3本」でも、書き込む1本だけが汚れを作る
- 部品を入れる作業は、**置く → 書く側を置換 → 読む側を置換** の順。
  逆にすると、直したつもりで汚れ続ける
