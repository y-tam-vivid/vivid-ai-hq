# corrections.log は86%が有璽氏の発言でなかった（2026-09-19 ロビン発注・ピタゴラス対応）

## 何が起きていたか

`~/.vivid-relay/corrections.log` は「有璽氏の指摘を取りこぼさない」台帳（`hook_catch_correction.py`
がUserPromptSubmitで拾って書く）。**毎朝ロビン（記録役）とつる（検査役）の材料として
『有璽氏の発言』欄にそのまま流し込まれる。** ここに有璽氏の発言でないものが大量に混ざっていた。

**2026-08-25 から30日間・9回 memory に記録されながら、一度も担当へ投げられていなかった。**
2026-09-19 のロビンの棚卸しで初めて発注が出た。

## 実測（2026-09-19・全637行）

```
探針文字列「何回も言ってるやろ」（hook_selfcheck.pyの毎朝08:20/08:40点検）     101行（16%）
AI自身の起動プロンプト（"あなたは…です" + agents/*.md参照）                 273行（43%）
task-notification（バックグラウンドタスク完了通知・システム生成）           163行（26%）
run_agent.sh が毎回自動で挿入する定型警告文                                  9行（1%）
────────────────────────────────────────────
4パターンいずれかに該当（重複除去後）                                     546行（86%）
★真の有璽氏発言候補（残り）                                               91行（14%）
```

**★直近7日のうち5日は、有璽氏の実発言が0件なのに『有璽氏の発言』として毎朝配られていた**
（ロビンの実測。09-12/09-15/09-16/09-17/09-18が該当）。

## 直した2箇所（両方とも `bin/hooks/` にのみ書いた。既存637行は削除・書き換えしていない）

### ① hook_selfcheck.py の探針が本番ログを汚染していた（8/25から既知）

`CASES[1]`（`hook_catch_correction.py` を「何回も言ってるやろ」で叩く探針）が
毎朝2行ずつ本物の corrections.log を汚していた。

`hook_session_writeback.py` の探針は8/30に HOME差し替えで対策済みだったが、
**`hook_catch_correction.py` の `LOG` は `HERE`（`__file__` 基準）でパスを組んでおり、
HOME環境変数の差し替えでは効かない別の実装だった**（同じ「探針が本番を汚す」型でも、
実装が違えば対策も違う。過去の対策をそのまま流用できない）。

対処：`hook_catch_correction.py` に `VIVID_CORRECTIONS_LOG` 環境変数によるLOGパス上書きを
追加し、`hook_selfcheck.py` 側は `hook_catch_correction.py` を叩くときだけこの環境変数を
一時ディレクトリへ向けるようにした（`hook_session_writeback.py` の HOME差し替えと同じ発想、
実装だけ変えた）。

### ② UserPromptSubmit はキーボード入力以外でも発火する（自己参照ループ）

`hook_catch_correction.py` は UserPromptSubmit フックだが、これは有璽氏の入力だけでなく
①エージェント起動（`claude -p "あなたは◯◯です。…"`）②バックグラウンドタスク完了通知
（`<task-notification>` タグ）でも発火する。①の結果、**エージェントの起動プロンプト
（その中に規範の引用や過去の有璽氏発言の引用が含まれる）が『有璽氏の発言』として
記録され、翌朝の材料へ自己参照ループとして返っていた。**

対処：`_is_non_utterance(text)` を新設し、次の3条件のいずれかに一致すれば記録・
additionalContext注入をスキップする。

```
① エージェント起動プロンプト  冒頭に「あなたは」があり、かつ `.claude/agents/` パスを
                            含み、かつ「読んで」または「読み」を含む（3条件AND）。
                            ★単独条件では有璽氏の発言を誤って弾く恐れがあるため複合にした
② task-notification         先頭400文字以内に `<task-notification>` を含む
③ run_agent.sh定型文        「★機械が自動で付けた」と「run_agent.sh」の両方を含む
                            （実測で新たに発見。依頼の想定外だったが同じ汚染源として対処）
```

**★誤除外を避けるため、長さや語気の強さでは判定しない。** 有璽氏は長文で厳しい語を
使って指示することが日常的にある（実測サンプルにも「めんどくそ。B-0076は不要であれば
消していいです。…ちゃんと正しい情報持ってないやん全然。」のような発言が実在する）。
「有璽氏が絶対に書かない形」（自分の役割定義ファイルを名指しする・システムタグ・
機械の定型見出し）だけを条件にした。

## 直していないこと（正直に）

実測で「重要な制約：memory/…触れないでください」型（2行・検証用テスト指示文とみられる）

## task-notification の出どころ

`<task-notification>` タグはバックグラウンドタスクの完了通知で、Claude Code の
仕組み側がタスク完了時にその内容をUserPromptSubmitへ再注入していると見られる
（実測：全163行の先頭が `<task-notification>` タグで統一されている）。
②のエージェント起動プロンプトとは別経路（依頼どおり実測してから分けて判定した）。

## 🔴受け入れ基準「翌朝の材料から消えていれば完了」は、この器では成立しない（2026-09-20 ロビン）

**歴代の指定は「★明朝の材料で探針2件・起動プロンプトが消えていれば完了。消えていなければ
差し戻す」だった**（WORKING.md のピタゴラス宛ブロック）。翌朝（2026-09-20）の材料には
**2件とも出ている。** 基準を素直に当てれば「差し戻す」になる。**★それは誤判定。**

```
なぜ消えないか
  ① corrections.log は★追記型。過去の行は、修正が正しく効いても1行も消えない
  ② 材料は「前日ぶん」を切り出す。★修正が入ったのは同じ前日（9/19）の日中。
     修正前に書かれた 08:20（探針）と 08:30（起動プロンプト）は必ず混ざる
```

**★正しい判定軸は「修正が入った時刻以降に生成された行」。** 消えたかではなく、新しく
生まれるかを見る。→ [[reference_overwriting_containers_have_no_past]] の裏返し
（上書きの器に過去は無い ／ **追記の器に消滅は無い**）。

### 実測（2026-09-20・2経路）

```
経路1  grep  09-19 09時以降〜09-20 の行 = ★0件
経路2  mtime 2026-09-19 08:40:59（最終行 08:30:05）で停止
→ 一致。★修正後に生成された行は1行も無い
日付別  09-14=26 / 09-15=9 / 09-16=5 / 09-17=4 / 09-18=6 / 09-19=2（うち2件とも偽物）
```

**★この0件では、まだ「直った」と言えない。** 除外が正しく効いて偽物が0件なのか、
**誤除外で本物まで落としたのか**を区別できない。9/19 の日中は JFBI 協力団体の掲載・
ロゴ受領・特性分析の依頼など、有璽氏とのやりとりが実際にあった（commit で確認できる）。
沈黙を成立の証拠にしない → [[feedback_one_route_is_not_verification]]

### 次にこれを判定する人がやること

```
1  9/19 09時以降に有璽氏の実発言があったかを★別経路で数える（Slack DM・transcript）
2  あった  → corrections.log に0行なら★誤除外。_is_non_utterance() の条件を疑う
   無かった → 判定はさらに翌日以降へ持ち越す（材料がまだ無い）
★どちらとも言えないまま「消えていないので差し戻す」も「0件なので直った」も打たない
```

**★型として**：「○○が出なくなれば完了」という受け入れ基準を書くときは、**その器が
追記型か上書き型かを先に確かめる。** 追記型なら「出なくなる」は起こらず、基準が
永久に満たされない（＝正しく直しても毎朝差し戻される）。
→ [[reference_verify_outcome_not_mechanism]]
