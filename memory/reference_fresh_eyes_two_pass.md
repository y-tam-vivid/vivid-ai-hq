# fresh eyes 2パス方式 ── 検問インフラの検査は2段階で頼む

## 何を防ぐか（2026-08-29 ステラ設計）

検査役に「作った本人がこう申告している」「docstringにこう理由が書いてある」を
先に見せると、その説明に納得して穴を見落とすリスクがある（甘くなる）。
これは cross-check の原則「①自分が作ったものを自分で検査しない」の亜種で、
**検査役に渡す情報の量そのものが検査の厳しさを左右する**という問題。

## 型

```
Pass A（blind）   diff だけ渡す。作成者の申告・docstringの「なぜ」は見せない。
                  「このコードに欠陥があれば指摘してください」とだけ頼む。
Pass B（informed）通常の cross-check（従来どおり、申告・観点・docstringを渡す）。

A→Bで消えた指摘   ★「説明に納得して甘くなった」疑いとして残す。
                  消えた理由が正当（Aの誤解が晴れた）なのか、
                  それとも説明に丸め込まれたのかを、束ねる役（ロビン）が判定する。
```

## 対象

検問インフラ限定（.claude/skills/ ・ bin/hooks/ ・ ファイル名に guard/hook を含む .py）。
通常の機能実装（顧客DB連携・案件管理等）にはこの2段階は要らない
（cross-check の通常フローで十分。検問インフラだけ、防御が甘くなると
「検問が検問として機能しない」という自己言及的な事故になりやすいため特別扱いする）。

## 運用（次に検問インフラを検査依頼するときの手順）

1. まず diff だけを別の検査役（または同じ検査役の別セッション）へ渡し、Pass A の指摘を得る。
2. 次に通常どおり申告・観点・docstringを渡し、Pass B の指摘を得る。
3. Pass A にあって Pass B に無い指摘を洗い出す。
4. その差分を束ねる役（ロビン）へ渡し、「甘くなった」か「Aの誤解が晴れただけ」かを判定させる。

## ★初実演の結果（2026-08-29 夜・Layer1/2 実装の検査／検査役＝ステラ）

```
Pass A（blind・diffのみ）   疑義 10件
Pass B（informed）          ★消えたのは 2件だけ
                            消し方は「説明に納得」ではない。ステラが自分で
                            grep・diff・実行して1件ずつ裏取りして消した
                            ★Pass B で新規に 1件 発見
                            （action_catalog_check.py が実行元のコピーを import する構造。
                              Pass A の「読んで分かる診断」からは出てこない型）
判定                        「進めてよい（条件つき）」
```

**★2パスは二度手間ではない。A と B で見える種類が違う。**

```
Pass A が拾うもの   設計の矛盾（記述と実装の不整合・目的と手段の不一致）
Pass B が拾うもの   ★実行しないと分からない構造（どのファイルを実際に読むか・配布のズレ）
```

- **★Pass A が0件でも Pass B を省略しない。** 今回いちばん重い指摘は B でしか出なかった。
- **★A→B で消えた指摘は、消し方を必ず書かせる。** 「実測で消した」か「説明に納得した」かで
  意味が正反対になる。今回は前者だったので健全と判定した（手順4のロビン判定は不要だった）。
- **★依頼する側が依頼文で「Pass A から」と明記しないと使われない。**
  設計した本人（ステラ）が、設計した直後の検査で Pass B のみを実施した実例がある
  → [[feedback_use_the_team_not_alone]]。**型は規律ではなく依頼文で担保する。**

実演の詳細な経緯は [[feedback_use_the_team_not_alone]]、
Pass B で見つかった欠陥そのものは [[reference_heartbeat_proves_life_not_results]] にある。
