**2026-08-31、クローバー博士が外部の一次資料まで当たった。**
有璽氏「ネット上の最新情報で使えるものを使う。同じミスをどう改善したのかを見た上で提案しろ」。

## ★いちばん効く知見 ── 一度間違えると、二度と読まれない

```
「一度SOP通りにやって間違えた（＝手順が古かった）経験があると、
  以後そのSOPは懐疑的に一瞥するだけの対象になる」
                                          Ideagen（実務ブログ・単一ソース）
```

**★うちが実際に踏んだ失敗と一致する** ── 手順書に「Slackで聞かれます」と書いたが、
その機能が存在しなかった（実装より先行して書いた）。

- **★公開する前に、書いてあるとおりに実際に動くかを1回通す。** 例外なし。
- **★「まだ動いていない機能」は書かない。** 動いた日に1節足すほうが、信頼を落とさない。

## SOPが守られない主因

```
「その場でSOPを使う方が、いつものやり方より手間がかかる」（Ideagen）
★形骸化の3主因  更新ルール不在／更新作業が煩雑／重要性の軽視
★最重要は所有者制  1文書に1人の名前付きオーナー
                   「陳腐化はツールの問題ではなくオーナーシップの問題」（Glitter AI）
```

## 短いチェックリストは行動を変える（★唯一の査読済み一次研究）

```
WHO手術安全チェックリスト  合併症率 11.0% → 7.0%／院内死亡率 1.5% → 0.8%
                          Haynes AB et al., NEJM 2009
```
→ **網羅マニュアルではなく、その場で使う1枚（ジョブエイド）へ振り切る。**

## ★注意が要る逆説的な知見

```
「人にフィードバック（○×）を求めること自体が、
  ユーザーのAIへの信頼と精度への印象を下げる」  arXiv 2008.12735（単一研究）
```

**★うちの「迷ったときだけSlackで聞く」設計の前提を一部揺るがす。**
- **確認を増やすほど、営業はAIを信用しなくなる**という逆効果が起きうる。
- → **閾値を厳格にする。** 本当に迷ったときだけに絞る。良かれと思って確認を増やさない。
- → 聞くときは**「なぜ迷ったか」を一言添える**（GPSの比喩：
  「このルートに自信がありません。どう思いますか」）。

## うちの設計に裏付けが取れたもの

```
Stripe Radar   リスクスコアが閾値を超えた決済★だけをレビューキューへ投入し、
               人はキューに溜まった分だけ確認する
               ＝ うちの「迷ったときだけSlackへ」と同じ形
               docs.stripe.com/radar/reviews
```

## ★採らないと決めたもの（理由つき）

```
パイロット＋チャンピオン方式  エンタープライズ規模の事例。数名の営業チームでは
                             「チャンピオン」が実質1人になり形だけの制度になる
動画マニュアル               ★経験者には「遅い」と感じられ離脱要因になる（arXiv 2505.01939）
                             少人数・低頻度の作業では投資に見合わない
docs as code の自動通知      非エンジニア向けの転用実例が無い。営業はコードを読まない
○×を積極的に求める設計      上の逆説的知見のため。「迷ったとき」以上に増やさない
```

## ★エビデンスの質（クローバーの自己申告・そのまま残す）

```
査読済みの一次研究   NEJM 2009（医療）と arXiv 1本のみ
残り                 実務ブログ・SaaS企業の自社データ。多くが単一ソース
★うちの前提（数名の社内営業チーム）に直接当てはまる実証データは 1件も見つからなかった
日本語圏の実例       特に薄い。言い換えはこちらで作文するしかない
```

**★「見つからなかった」を書いた点が価値。** 数字を借りてきて根拠にしない。


## ★★警告された直後に、同じ型を踏んだ（2026-08-31・同日）

クローバーが「**一度手順書どおりにやって間違えると、以後その手順書は読まれない**」を
報告した。**その直後にこちらが書いた手順書に、実装の無い機能が入っていた。**

```
書いた   「名刺｜その場で撮って添付。★役職・住所・電話はこちらで読み取ります」
実装     ★名刺OCRの処理が存在しない（つるが2経路で確認）
           経路1  intake_register/match/notify/setup を grep → 名刺列を読む処理 0件
           経路2  customer-db-sync（OCRを持つスキル）との連携を grep → 0件
実データ  受付シート40行のうち★8行に名刺画像が添付済み。誰も読んでいない

★起きること  名刺を撮って送った営業は「読み取ってもらえる」と信じて何もしない
              実際には誰も読まない。★2026-08 の「Slackで聞かれる」と完全に同じ型
```

**★対策を記録した直後でも踏む。** 知識として持っていることと、書く手が止まることは別。
- **★手順書に「機械がやります」と書く前に、その処理が実在するかを grep で数える。**
  1機能につき2経路（処理本体／連携先）。**書いてから確かめない。**
- ★これが「一度間違えると二度と読まれない」の作られ方そのもの。**公開前に止まったのは
  検査役が居たから。** 自分では気づかなかった。
