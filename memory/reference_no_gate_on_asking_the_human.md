**同じ失敗が繰り返される理由は「忘れる」ではなく「その経路にだけ検問が無い」だった。**
2026-08-29 有璽氏 ──「散々書きますとかなんとかしますって言っててもそれ見ないんやったら
意味ないやん。根本的にどうやって解決すんのそういうの」。

## 実測した構造

```
ファイルを触る          PreToolUse が地雷を突きつける        効いている
ターンを終える          Stop フックが書き戻しを迫る          効いている
──────────────────────────────────────────────
★人へ作業を依頼する     何も鳴らない                        ここだけ素通り
★「無い/分からない」    何も鳴らない                        同上
```

**memory は「引きに行ったときだけ」来る。** ファイルを触らないターンではフックも鳴らない。
だから **探さずに人へ投げるターンは、どの安全網も通らない**。

## 「あとから記憶に書いてありました」が毎回起きる理由

指摘されて初めて検索するから。**書いてあることが届かないのではなく、探す前に止める検問が無い。**
「次からは必ず読みます」は規律に依存する対策＝規律が切れた回にだけ効かない
（[[reference_hooks_enforce_what_discipline_cannot]] と同じ型）。

## 直し（2026-08-29 実装・実測済み）

`bin/hooks/hook_session_writeback.py` に**検査2**を追加。器は増やさず既存の Stop フックへ足した。

```
このターンのこちらの発話に
  「いただけますか／書き出して／共有してください」等（人に手を動かさせる依頼）
  「見つかりません／存在しません／持っていません」等（無いという断定）
が出ていて、
  かつ memory / Drive / Notion を1度も検索していない
                                     → exit 2 で差し戻す
探していれば黙って通す。★探したうえで人へ渡すのは正しい行為
```

- 判定は**言葉ではなく行為**で見る（tool_use の入力に検索が現れたか）。「探しました」と
  書くだけでは通らない。
- 誤爆させない。**うるさいフックは読まれなくなり、無いのと同じになる**
  （[[reference_delivered_but_unread]]）。だから語を狭く取ってある。
- 実測4ケース（探さず依頼→2／探して依頼→0／無いと断定→2／通常報告→0）で確認。
  配布先は `~/.vivid-relay/hook_session_writeback.py`（settings.json が呼ぶ実体）。
  **★MacBook へは未配布。** git 経由で `bin/hooks/` は届くが、`~/.vivid-relay/` への
  コピーはそのマシンで1回要る。

## ★同じ日に、届ける側も2つ壊れていた（2026-08-29 実測）

対策を入れる過程で、**「memory に書けば次から効く」と言っていた仕組み自体が効いていなかった**
ことが分かった。書いても届かない状態が続いていた。

```
在庫（build_landmine_index.py）
   ★188本中100本を上限で落としていた。落ちていたのが
     reference_hooks_enforce_what_discipline_cannot ／ reference_delivered_but_unread
     ＝「書いても届かない」を止めるための記憶そのもの
   直し：直近7日以内のものは上限に関わらず先に確保する（FRESH_DAYS）
        → 常設枠 19本 → 59本

出す側（hook_inject_memory.py）
   ★語が一致しないとき順序が完全に安定で、上位2本だけが毎回出て残りは一生出ない
   直し：同点なら「まだ出していないもの」を先に出す（landmine_shown.json で回数を持つ）
        → 同じ入力5回で5回とも別の記憶が出ることを実測

★さらに build_landmine_index.py は `import time` の抜けで NameError を出しながら
  **exit=0 を返し、古い json をそのまま残していた**。cron からは「動いた」に見える。
  → 落ちたら exit 1 ＋ 心拍「失敗」（[[reference_ran_is_not_succeeded]] と同じ型）
```

**★対策を入れるときは、その対策が「届く経路」に載るところまで実測する。**
書いた・作った・入れた で止めると、今回のように何日も空振りする。

```

             → その後に探して、~/.claude/settings.json.backup_* に実在を確認
```

## ★良い形 ── 探したら、聞くべき質問そのものが変わった（2026-09-03）

担当から「フッターの Instagram のURLだけ有璽氏に聞けば埋まる」と上がってきた。
**聞く前に📱発信アカウント台帳を実測した（12行・全件）。**

```
実測  ILIFE の行は★「ILIFEブログ（活動風景）」1本だけ。Instagram の行が無い
      稼働中のInstagramは「個人・有璽」と「法人ビビッド」の2つだけ
      ★Instagram の行は4本ともあるが、発信先URLは全部 空
```

**聞くはずだった質問**：「Instagram のURLを教えてください」
**実際に聞くべき質問**：「**LIFE STAND UP の Instagram アカウントは存在しますか。**
台帳には ILIFE のブログしか登録がありません。無ければフッターのアイコンごと外します」

**★URLを聞く質問は「アカウントは在る」を前提にしていた。** その前提が確かめられていなかった。
**探すことで、答えが得られなくても質問が正しくなる。**

- **★「◯◯を教えてください」と書きそうになったら、その◯◯が存在する前提を先に確かめる。**
  存在しないものの値を聞かれた人は、答えようがないまま考え込むことになる。
- ★台帳を見たので、**聞くときに現状を添えられる**（何が登録済みで何が無いか）。
  人が判断する材料が増える。
