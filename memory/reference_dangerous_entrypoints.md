**規則はこれ1行。**

> **cron・メニュー・手順書に載せる前に、その1行が「書くのか、書かないのか、壊すのか」を実測で1回確かめる。名前からは判断しない。**

2026-08-13 に実際にやらかしかけた: `notion_meeting_customer_link.py` を毎朝の cron に載せる行を
提示したが、**`--apply` が無いため毎朝ログを吐くだけで1件も書かない**設定だった。
作成者本人の指摘で発覚。「登録したから動く」と思い込んだまま数週間過ぎうる形だった。

## 4つの型

**A. 呼んでも何も起きない**（安全側に倒れていて、動いていないことに気づかない）

| 入口 | 挙動 | 出典 |
|---|---|---|
| `notion_meeting_customer_link.py` | 既定 dry-run。`--apply` が無いと1件も書かない | **実測済み**（作成者が2026-08-13に確認） |
| `matchKintoneRun()` ほか計4入口 | **4入口のうち書くのは `matchKintoneRun` だけ**（`matchKintoneDryRun`/`matchKintoneReport`/`matchKintoneOrphans` は書かない）。危険の本体は関数名の違いではなく、**両者の出力ログが同形式で、違うのは1行目の `【ドライラン】`/`【本実行】` だけ**。件数も内訳も同じように出るのでログを上から読まない限り区別がつかない | **実測済み（2026-08-13・実ファイル読了）** |

**B. 呼ぶと取り返しがつかない**（危険なのに名前が普通）

| 入口 | 挙動 | 出典 |
|---|---|---|
| `build_sales_pipeline.gs` の `buildWorkbook` | **実行禁止**。下記4点 | **実測済み（2026-08-13・実ファイル読了）** |
| `apply_schema_v3.gs` の `applySchemaV3()` | **実行禁止**。下記3点 | **実測済み（2026-08-13・実ファイル読了）** |

### `buildWorkbook()` が壊すもの（実測）

本来は設置手順 step 4 の**セットアップ専用関数**。禁止なのは「もうデータが入っているから」であって
関数が邪悪なのではない。ただし現状では実行してはいけない。

1. 12シート全部に `buildSheet_()` を回し、その**1行目が `sh.clear()`**。
   値・書式・入力規則・条件付き書式・ノートを全部落とす。
2. さらに `deleteRows(1001〜)` `deleteColumns(ヘッダー数+1〜)` で**行・列ごと切り詰める**。
   **1000行を超えるデータは列ごと消える。**
3. `applyValidations_()` も**列番号ハードコード**（12/13/14/17/18/22…）。`apply_schema_v3` と同じ問題。
4. `CHOICES` の流入経路も**10値**。現行16値なら差分が消える。

> ⚠️ **いちばん危ないのは冒頭コメント。**「何度実行しても同じ結果になる（既存シートは中身を作り直す）」
> と書いてある。**冪等＝安全、と読める。実際の意味は「既存データごと作り直す」。**
> 名前ではなくコメントに騙される型。

### `applySchemaV3()` が壊すもの（実測）

1. `90_選択肢マスタ` を `clearContent()` してから、**スクリプト内のリテラル `CHOICES_V3` で敷き直す**。
   選択肢の正がシートではなく**このファイルの中**にある。
2. そのリテラルの `流入経路` は **10値**（フォーム営業/テレアポ/名刺/紹介/交流会/イベント/SNS/
   Web問い合わせ/セミナー/その他）。現行が16値なら**差分は消える**。
3. **いちばん危険なのはこれ。** `applyValidationsV3_()` が全シートに入力規則を貼り直すが、
   当て先が**列番号ハードコード**（`00_企業マスタ` の 12/13/14/17/18/22 等）。
   **列を動かしていると別の列に入力規則が当たる。**

> ⚠️ 3 は [[reference_sales_workbook_column_moves]]（「マスタ2枚は全GASが見出し名で引く」）と衝突する。
> **`apply_schema_v3.gs` は見出し名で引いていない。**「列移動してよい」はこのファイルには適用されない。

**C. 順序・選択肢の既定が罠**

| 罠 | 結果 | 出典 |
|---|---|---|
| 週次kintone同期で `matchKintoneRun()` を飛ばして `buildInsertCsvRun()` を流す | 対応が付いていないため更新CSVが0件で出て、**新規CSVが既存の会社をもう一度作る＝二重登録** | 一次（`match_kintone.gs` 冒頭に作者が機構を明記）。`buildInsertCsvRun()` の実物は未読 |
| kintone取込で「エラー行のみスキップ」を選ぶ | 一部だけ入り、次回が重複エラーになる | **コードでは検証不能**（kintone取込UIの挙動。`.gs` を読んでも確定できない。実地かkintone仕様に当たるしかない） |


**D. 動いたように見えて、静かに間違う**（エラーが出ず完走し、件数だけが違う）

| 罠 | 何が起きたか | 出典 |
|---|---|---|
| エクスポートを接頭辞 `顧客管理_` だけで拾う | 取り込みエラーログ `顧客管理_読み込まれなかった行.csv` も引っかかる。しかも**「読」の文字コードが数字より大きいため名前順で"最新"と判定される**。これを読んで**一致0件**になった。現在は `/^顧客管理_\d{8}T\d{6}/` で防いでいる | **実測済み**（`match_kintone.gs` に記録） |
| 鍵の強い順でなく行ごとに突合する | 弱い鍵が強い鍵を追い越す。`simcle.（222）` が会社名で先に掴み、社内顧客IDで確定できる293が弾かれた | **実測済み**（同上） |

A（呼んでも何も起きない）と紛らわしいが別物。**A は「動かない」、D は「動いた結果が違う」。**
D は完走してログも出るので、件数を突き合わせない限り気づけない。

## ★「載せる前に実測」が原理的にできない入口がある（2026-08-29 ステラ）

規範は「cron・メニュー・手順書に載せる前に、その1行が書くのか壊すのかを実測で1回確かめる」
と定めている。**だが、載せないと発火しない入口では、この手順が成立しない。**

```
実例  PreToolUse フック（hook_role_guard.py）
      メインセッションで agent_id が欠落するかを確かめたい
      → 本物の PreToolUse イベントでしか確かめられない
      → イベントは settings.json へ登録しないと発生しない
      → ★登録前に確かめる手段が存在しない（鶏と卵）

★フックを直接叩くテストは代用にならない。
  stdin へ payload を自分で作って流すので、**本物のイベントで何が入るかは分からない**。
  「実測した」と書くと、確かめていないものを確かめたことにする
```

### この場合の作法（fukuchi-core「先に復帰経路を作る」の応用）

```
1  戻せる状態を先に作る       settings.json をバックアップ（日時つきで別名保存）
2  未検証と明示して載せる      ★「実測済み」と書かない。「登録直後に確認する」と書く
3  ★登録直後の最初の1回で確認  本物のイベントで期待どおり動くかを見る
4  期待と違えば即座に戻す      バックアップから復元
```

- **★「載せる前に確かめられない」を「確かめなくてよい」にしない。**
  確かめる時点が後ろにずれるだけで、確かめる義務は消えない。
- **★載せる直前に、検査した版と載せる版の同一性を sha256 で突合する。**
  検査後に実装が進むと、**検査していないものが載る**（2026-08-29 ステラの要請）。
  更新時刻では判定できない（触っただけで変わる）。

関連: [[feedback_one_route_is_not_verification]]（同一性は時刻でなくハッシュで見る）


## ★`--help` が実データを書き換える（2026-08-31 実測）

```
dashboard_data.py に argparse は ★0件
  → 未知の引数（--help / --dry-run / --check など）は黙って無視され、
    ★本処理がそのまま走る
実際   ステラが `--help` を叩いたら、実データの再生成が始まった
```

**★「説明を出すだけ」に見える入口が、書き込みを走らせる。**
この記憶が挙げてきた4型（①既定dry-run ②名前は普通なのに全消去 ③順序を飛ばすと二重作成
④件数だけ静かに違う）に、**⑤未知の引数を無視して本処理が走る**を足す。

- **★`sys.argv` を手で見ているスクリプトは、全部この型を持つ。**
  `"--beat" in sys.argv` のような書き方は、**知らない引数を全部「無視」する**。
- **★新しく触るスクリプトは `--help` すら安全でないと思って扱う。**
  中身を読んでから叩く。読めないなら叩かない。
- ★見つかったのは、検査役が**自分の操作ミスを正直に申告したから**。
  隠していたら地雷のまま残っていた（[[feedback_use_the_team_not_alone]]）。

## ★止める判断が正しかったことを、止めたあとに実測で確かめる（2026-08-23 実地）

GAS 54v3 を無効化したあと、ドライランを1回通した。**そこで初めて実害の中身が見えた。**

```
54v3 が書こうとしていた   40_活動ログへ 23行
実測（日付を揃えて突合）  ★21件は既に台帳に在る ＝ 押していたら二重に入っていた
                          本当に新規は 2件だけ
```

**54v3 は「もう台帳に入っているか」を見ない。** 受付シートの「台帳登録」欄には
`登録済み16 / 既存と重複9` と印が付いているのに、それも見ずに全行を書こうとする。

- **止めたあとにドライランを1回通す。** 止める前は「危ないから」で止めてよいが、
  **止めたあとに「何が起きるはずだったか」を数えると、判断の根拠が事実になる**
- **無効化は `return;` を1行入れる。** 削除しない ── なぜ止めたかが分からなくなる

## ★Notion の select「名前を変えるだけ」は、実体としては作り直し（2026-09-03 実測）

予実管理DBの `法人` select を「個人（田村有璽）」→「個人」へ**リネームした**つもりだった。
**名前・色・並び順（6番目）は維持された。だが option の内部IDが変わっていた。**

```
実行前   ...MWFhZThkMDktNTFjNy00N2I0LTgyMWYtYTRhOWI5ZDgwYWNj
実行後   ...ZTlkNzQyMDAtYjUzMy00OTRlLTk2M2YtYmM1Mzc0MjkxMDZm   ★別のID
```

**＝ 内部的には「改名」ではなく「削除して新規作成」に近い挙動。**
[[reference_dangerous_entrypoints]] の②型（名前は普通なのに壊す）そのもの。

- **★データが1件でも入っていたら、その行の select 参照が外れた可能性がある。**
  今回は**実データ0件だったので実害ゼロ**。**選択肢の名前を変えるなら、中身が空のうちに。**
- **★「リネーム」という言葉から挙動を推測しない。**実行前後で**内部IDを実測して比べる**。
  名前・色・並び順が同じでも、同じものとは限らない。
- ★ナミが指示どおりに実行したうえで、**「指示の言葉と技術的な結果が違った」と自分から申告した**。
  この申告が無ければ、次にデータ入りのDBで同じことをして静かに壊していた。
