# 判断ハブ ── Slackのボタンで返す（2026-09-03 稼働）

**有璽氏「通知は届くけど、何に私は判断したらいいのかがわからない。営業で使っている
AI確認依頼はプッシュ通知になっているので、私とAI側とのやり取りも同じ設計にできないか。
押すだけでOKになるし、違う場合は記述するような形にしてくれたらいい」**

## 使い方（AI側）

```python
# ★必ず Mac mini から発行する（下の「踏むと痛い」参照）
import ask_hub
ask_hub.ask(
    subject='何についてか（案件名・成果物）',
    question='何を決めるのか（1文）',
    options=[('こうする', 'primary'), ('こうしない', None)],   # ★1〜4個
    detail='判断の材料',
    link='押せるリンク',           # 無ければ空。★意味の無いリンクは付けない
    asked_by='ピタゴラス', kind='開発')
```

`ask_hub.py --list` で一覧、`--show <受付番号>` で1件、`--preview`（引数なし）で投げずに中身を見る。
答えは `ask_hub.answer_of('受付番号')` で読む（未回答なら None）。

## 経路

```
AI ──ask_hub.ask()──▶ 有璽氏のDM(D0AT4NQ6X7D)
                      本文＝案件名／何を決めるか／材料／依頼元・種別・受付番号
                      [選択肢1][選択肢2][✍️ その他（書いて返す）]
  押した ──▶ slack_socket.py の interactive 経路（営業のボタンと同じ常駐）
             → 元メッセージが「✅ 受け取りました ── ◯◯」に変わる（ボタンが消える）
  その他 ──▶ Slackのモーダルが開く → 自由記述 → 同じ interactive 経路で戻る
             ★モーダルの送信も interactive なので、新しいスコープも購読も要らない
  開けない ─▶ 「DMに直接書いて」→ slack_inbox.py（cron */5）が拾う
```

## ★踏むと痛いところ

- **★発行は必ず Mac mini から。** 台帳 `ask_hub_queue.json` は受信側（mini）にしか無い。
  MacBook から投げると、押されたときに「受付番号が見つかりません」になる。
  `ask_hub.py` 自体は両機に在る（MacBook からは投げられるが**投げてはいけない**）。
- **★`notify.py` の `slack_pending.json` とは別物。混ぜない。** あちらは
  「答えが来るまで後続を一切進めない」設計で、実際に14日間パイプラインを塞いだ
  → [[reference_pending_decision_does_not_pause_the_pipeline]]。
  こちらは**誰も止めない**。止めたい処理は自分で `answer_of()` を見に来る。
- **★宛先は `ask_hub.ROUTES` の1か所だけ。** 2026-09-03 有璽氏「営業のやつ以外はDMで」。
  チャンネル分割は**許可であって指示ではない**（基準が未決）。分けるならこの表に足すだけ。
  種別（開発/営業/福祉/…）は1件ずつ記録してあるので、分けるときに数えて基準を決められる。
- **★選択肢は4個まで**（コードで止まる）。5個要るのは、こちらが決め切れていないだけ。
- **★リンクは押して意味のあるものだけ。** 1通目で「Slackのトップ画面」を入れかけたが、
  押しても同じ画面に戻るだけなので外した。

## ★出口が2本あると、翌日には記述式へ戻る（2026-09-04 有璽氏の指摘）

**有璽氏「選択式で依頼していたのに、記述式に変わってるよ」（08:54）。**
ボタンを作った翌朝には、判断依頼が文章に戻っていた。**仕組みを入れても、
古い出口が残っている限り、そちらが使われる。**

```
出口①  ask_hub.ask()   ボタン。押すだけ。★9/3 に3件だけ通った
出口②  notify.ask()    ★本文に「番号だけでOK」と書く記述式。ボタンを出さない
                       （_post() は text だけを送り blocks を使っていない）
出口③  notify.tell()   報告。★ここへ判断を紛れ込ませると、いちばん悪い形になる
```

**実測（2経路）** ── 経路1＝Slack DM の実物 ／ 経路2＝`notify.py` のソース直読・`ask_hub.log`。

```
9/3 15:00  出口② 「1 確認しました／2 いまは保留 … 番号だけでOK」＝記述式
9/3 19:59〜20:14  出口① ボタン3件。有璽氏はいずれもボタンで回答（ask_hub.log）
9/4 08:34  出口③ 棚卸し報告。冒頭に「報告です。返信は要りません」と書きながら、
           末尾で「検査＝規範側の変更なので判断を仰ぎます」と判断を求めていた
           ＝規範「報告と判断依頼を混ぜない」に正面から反する
```

- **★判断を求めるときは必ず `ask_hub.ask()`。** `notify.ask()` は使わない。
  報告 `tell()` の中に「どちらにしますか」を書かない。**判断は必ず別の1通に切り出す。**
- **★直った基準は部品の言葉で書かない** → [[reference_verify_outcome_not_mechanism]]。
  ここでの基準は **「有璽氏が判断を求められたとき、必ず押せるボタンが付いている。
  番号を打たされることが一度も無い」**。`blocks` の有無や関数名で合格を出さない。
- **★同じ型が別の場所でも起きる。** 新しい経路を足したら、古い経路を**塞ぐ**ところまでが
  ワンセット。残すと必ず戻る → [[reference_stale_premise_daily]]。

## 🔴 全AI・全担当への恒久ルール（2026-09-04 有璽氏・★2回目の指摘で規範化）

**有璽氏「ここで選択、クリックこちらがするような形の選択式にしてほしいって言ったんだけど、
また元に戻ってしまっている。これ、他のエージェント含めて全体に周知して。Slackの通知の仕方、
特に私の判断が要るものに関しては選択できるものにして。」**

```
★判断が要るもの   必ず ask_hub.ask()。ボタンを付ける。番号を打たせない
★報告            notify.tell()。冒頭に「返信は要りません」。★判断語を1つも入れない
★禁止            notify.ask()（記述式）を新しく呼ばない。tell()に判断を紛れ込ませない
```

- **★これは1担当の話ではない。ビビ・ピタゴラス・リリス・つる・ドーベルマン・ステラ・
  ロビン・ナミ・センゴク・フランキー・モルガンズ、全員に効く。**
  自分の担当領域から有璽氏へ何かを送るときは、**その1通が「判断」か「報告」かを先に決める。**
- **★2回言われた＝仕組みで止まっていない。** 1回目（9/4 08:54）は notify.ask() を
  ask_hub へ委譲する改修で直したが、**その改修は同日09:15に巻き戻った**
  → [[reference_two_sessions_built_the_same_thing]]。**直した記録があることと、
  いま直っていることは別。** 送る前に実物（`notify.py` に `ask_hub` があるか）を見る。
- **★「通知が来ない」も同じ回に言われている。** 押せる形にする前に、**まず届くこと。**
  届いていない原因を1経路で「送った」と断定しない → [[feedback_one_route_is_not_verification]]。

## 🔴 押されたことが、聞いた側へ返ってこない（2026-09-04 実地）

**有璽氏「Slackは返答してないかな？」** ── **押してあった。こちらが見ていなかった。**

```
10:58  ビビが #311115 を投稿
11:02  ★有璽氏が「付けない」を押す（4分で回答）
その後 ★こちらは気づかず、別の報告に答え続けていた
       ＝ 有璽氏から見ると「押したのに何も起きない」
```

**★ask_hub は投げっぱなし。** `answer_of()` を**誰かが見に行くまで、押されたことは誰も知らない。**
Slack上では元メッセージが「✅ 受け取りました」に変わるので**押した側は届いた気になる**が、
**聞いた側には何も飛ばない。**

```
いまの逃げ方（規律に依存する）  ★投げたら、次に自分が動く回で必ず answer_of() を見る
本当の直し方（仕組み）          ★回答が入った時点で、聞いた側へ知らせる経路を作る
                                → ピタゴラス領域。まだ作っていない
```

- **★「押すだけ」にしたのは有璽氏の手数を減らすため。** 押しても進まないなら、
  **記述式だった頃より悪い**（記述式なら少なくとも文章が目に入った）。
- **★2件以上を並行で投げているときほど落ちる。** 今回は #ec25ed の答え（10:57）には気づき、
  **その4分後の #311115 は見落とした。**「1回見たから大丈夫」にならない。
- **★有璽氏に催促させた時点で負け。** 待たせている側が確認しに行く。

## 🔴 予約した通知が、時間になって落ちた（2026-09-04）

有璽氏の「今日の15時に再度Slackで通知して」を、mini に `nohup sleep` で予約した。
**プロセスは生きていた。中身が落ちた。**

```
仕込んだとき  ★プロセスの生存を確認して「予約完了」と報告した
15:00        ValueError: 種別は 開発／営業／福祉／広報／財務／法務／個人／その他 のどれか
             （いま '経営'）  ← ★KINDS に無い種別を渡していた
気づいたのは  ★1時間40分後。別件で remind.log を覗いたとき
```

- **★`kind` は自由文字列ではない。** `ask_hub.KINDS` ＝
  **開発／営業／福祉／広報／財務／法務／個人／その他** の8つだけ。
  「経営」「開発部」などは通らない。**渡す前に KINDS を見る。**
- **★プロセスが生きていることは、仕事が成功したことを示さない。**
  → [[reference_ran_is_not_succeeded]]。予約型はここが特に外れやすい
  （仕込みの瞬間は成功して見え、失敗するのは誰も見ていない時刻）。
- **★予約したら、発火時刻の後に必ず結果を確かめる。** 見る場所は
  `~/.vivid-relay/remind.log`（標準エラーの落ち先）と `ask_hub.log`（投稿の記録）の2つ。
- **★仕込む前に1回、同じ引数で `--preview` を通す。** 今回は preview を挟んでいれば
  その場で ValueError が出て、15時を待たずに直せた。**時間のかかる検証ではない。**

### ★同じ日に2回目。今度は通信で落ちた（17:00の分）

```
15:00  ValueError（種別が KINDS に無い）        ← ★引数の誤り。previewで防げた
17:00  urllib.error.URLError: SSL handshake timed out  ← ★通信の一時不調。防げない
```

**★原因は毎回違う。だが結果は同じ ── 予約した通知が届かず、誰も気づかない。**

- **★真因は「1回きりで、失敗を誰も拾わない」構造。** 引数を直しても次は通信で落ちる。
  **潰すべきは個別の原因ではなく、失敗が黙って消える経路。**
  → [[reference_a_warning_nobody_owns]]
- **★入れるべきは再試行。** 送信は数秒で終わる処理なのに、1回失敗して終わっている。
  **3回・間隔を空けて試す**だけで、通信の一時不調はほぼ吸収できる。
  ★これはコード側＝ピタゴラス領域。ビビは仕込む側なので、依頼として出す。
- **★当面の逃げ方**：予約したら**発火時刻の直後に自分で結果を見る**。
  見る場所は `remind.log`（例外の落ち先）と `ask_hub.log`（投稿の記録）。
  **「プロセスが生きている」は結果の確認にならない**（15時の教訓と同じ）。

### ✅ 再試行を入れた（2026-09-04 夜・ピタゴラス）

```
実測  両機の ask_hub.py が sha256 一致（b6eba732…）／再試行の記述21箇所
      ★巻き戻っていない（今日5回巻き戻った notify.py とは別ファイル）
仕様  通信例外（URLError／socket timeout／5xx）のみ最大3回・2秒→4秒
      ★4xx と Slack の ok:false は再試行しない（何度やっても同じ・重複投稿の危険）
      3回とも失敗したら ask_hub.log へ「★送信に失敗した」を1行残す
      docstring の先頭に KINDS（8種）を明記
★未   実際にSlackへ通す通し確認はしていない（テスト投稿はノイズになるので、
      次の本番投稿で確かめる）。ステラの検査も未了
```

**★再試行してよい失敗の見分け方（一般に効く）**

```
◎ 再試行してよい  ★相手に届いていないと言い切れる失敗
                  urlopen() 自体が例外＝レスポンスのヘッダーすら受け取っていない
✕ 再試行しない    ★届いたかどうか分からない失敗
                  urlopen() は成功し、その後の読み取りで落ちた
                  ＝ HTTPの往復は完了しており、相手は処理済みかもしれない
                  → 再試行すると★二重投稿になる
✕ 再試行しない    ★何度やっても同じ失敗（4xx・権限エラー・ok:false）
```
**★「失敗したら3回やり直す」は雑すぎる。**外へ出る処理では、
**やり直すたびに相手側で1回起きているかもしれない**ことを先に考える。
