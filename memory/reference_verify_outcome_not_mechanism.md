**2026-09-03 実測（ロビン・毎朝の棚卸し）。**
Slack常駐の再接続バックオフを修正し、**検証はすべて合格した。そして障害は150倍長くなった。**

```
検証基準（修正時に自分で決めたもの）      結果
  ログの秒数が 1→2→4→…→300 と増えるか    ✅ 完全に増えた
  hello 受信でリセットされるか             ✅ そのとおり
  ステラの独立検査（diff・実読の2経路）    ✅ 一致

人が困っていた事実                        結果
  Slackのボタンが押せない時間              🔴 9秒 → 23分41秒（約150倍）
```

**★検証基準が、直したかった問題を一度も見ていない。**
測っていたのは「バックオフという部品が仕様どおり動くか」。
本当に守りたかったのは「営業がボタンを押したら反応すること」。
前者だけを検証したので、**後者が壊れたまま「直った」と report された。**

## なぜ起きるか

修正の直前は**部品の話をしている**（`backoff = 1` の位置、リセット条件、hello の分岐）。
その頭のまま検証基準を書くので、**基準まで部品の言葉になる。**
検査役（cross-check）も、渡された基準の中で正しく検査する。**基準の外は誰も見ない。**

```
壊れ方   仕様→実装→検査 が全部正しく繋がっている。どこにも誤りが無い
         ★誤っているのは「仕様が目的を代弁していなかった」の1点だけ
だから   バグ探しでは絶対に見つからない。検査を厚くしても出てこない
```

## どうするか

- **★修正に着手する前に「これが直ったと言える事実」を、部品の言葉を使わずに1行書く。**
  書けないなら、まだ何を直すのか分かっていない。
  ```
  ✕  backoff が 1→2→4 と伸びること
  ◯  ボタンを押してから反応するまでが、いつも○秒以内であること
  ```
- **★「悪化はしない」と書きたくなったら、そこが危ない。** 何と比べて悪化しないのかを
  数字で書く。書けないなら**修正前の値を先に測る**（今回は 9秒・19秒という修正前の実測が
  残っていたから比較できた。残っていなければ悪化に気づけなかった）。
- **★検査役へ渡すとき、目的の側の基準も一緒に渡す。** 部品の基準だけ渡すと、
  検査役の優秀さは基準の外側には届かない。→ [[cross-check]]
- **★トレードオフのある修正は、片側だけ測らない。** 「叩きすぎ」を直したなら
  「遅すぎ」も測る。上限・閾値・間隔を触る修正はほぼ全部これに当たる。

## 見分け方（自分の報告を読み返すとき）

**報告に出てくる名詞が、実装の名詞ばかりになっていたら黒。**
`backoff` `リセット位置` `hello` `単調増加` ── 一つも有璽氏や営業の言葉ではない。
**人が使う言葉の文が1つも無い報告は、目的を測っていない。**
→ [[feedback_write_for_the_reader]] と同根（あちらは配る文書、こちらは検証基準）

## ★いまここ ── 記録は書かれた。コードは直っていない（2026-09-03 つる）

**この学びを書いた当日、同じ障害がもう一度起きた。** 毎朝の自己監査で独立に実測した。

```
日別の最大断絶（slack_socket.log を hello受信⇄切断 で数え直した・2経路目）
  08-27〜09-01   0.0〜0.1分     ← 修正前。1秒リトライで即復帰していた
  09-02          0.3分         ← 修正の適用日（08:43）
  09-03 07:50    ★23.7分       ← 300秒上限へ張り付き、営業のボタンが24分死んだ
```

**★WORKING.md のピタゴラスのブロックは、いまも「✅実装・再起動・実測完了」のまま。**
悪化の実測は memory にしか無く、**作業の状態を持つ側（WORKING.md）へ戻っていない。**
＝ 次にこのブロックを読んだ人は「済んだもの」として素通りする。
→ [[reference_a_warning_nobody_owns]] [[reference_delivered_but_unread]] と同じ型。
**学びを書いた場所と、直す人が見る場所が違う。**

**★真因は backoff の伸び方ではない。** 切断理由は `warning`（Slackの定期的な接続入れ替え）で、
そこから即再接続すると古い接続が残ったまま新しい接続を開き `too_many_websockets` に当たる。
つまり**数秒で解ける一過性の混雑に、300秒の上限を当てている。** 直し方は上限を下げる
（例: 30秒）か、旧接続を閉じてから開く。**どちらもコード＝ピタゴラスの領域。**

## ★同じ型をもう1件（2026-09-03 ステラの検査）── 見た目は3経路で一致。でも起動しない

LIFE STAND UP サイトの試作。**再現度の検証は3経路のうち2経路で一致し、合格していた。**

```
経路2  JS実行後のDOM突合        差分は意図した2点のみ
経路3  計算後スタイル25要素      cmp 0バイト差・sha256一致・ページ全高も同一
報告   「見た目は変わっていません」  ← ここまでは正しい
```

**ステラが `find` と個別 `test -e` の2経路で見つけたもの：**
```
index.php        ★無い → WordPress はこのテーマを「壊れている」と判定し、有効化できない
wp_body_open()   ★無い → Site Kit(GA4)・Jetpack が挿入点を失う。既存サイトは両方稼働中
page.php / single.php / archive.php / search.php / 404.php  すべて無い
```

**★「実WordPressで動かしていない」以前に、いまの形では起動しない。**
検証していたのは「マークアップとCSSが原本を再現するか」。
確かめていなかったのは「**そもそもテーマとして成立しているか**」。

- **★再現度を測る前に「動くか」を1回通す。** 順序が逆だと、動かないものの見た目を精密に測る。
- **★検証の型が揃っていることは、検証の対象が正しいことを意味しない。**
  3経路そろえても、測っている軸が1本しかなければ、その軸の外は素通りする。
  → [[feedback_one_route_is_not_verification]] は「経路」の話。**こちらは「軸」の話。**
- **★代理環境は、代理できる範囲を書く。** 検証レンダラは実WordPressが必ず出す
  `global-styles-inline-css`・`wp-block-library`・`classic-themes` を1行も含んでいなかった。
  「実WPの代理」ではなく「テーマのマークアップの代理」。**名前が範囲を偽ると、読み手が広く信じる。**

## ★1本で得た結論を、数を確かめずに横展開しない（同日・同じ案件）

```
top-page で得た結論   「JSが注入していた実差分は headingFont の1点だけ」
20本を実際に読むと    applyTweaks は★8版に分岐していた
                     実差分あり 7本／うち★2本は本文の日本語が変わる
                       stand-up-top    静的「ことば と 体験 で 育つ」→ 注入「いま と これから に、伴走する」
                       recruit-values  静的「価値観で、選びあう。」  → 注入「互いを理解し、価値観を共有する」
```
**フォントの話だと思っていたものが、公開する文言の話だった。**
1本の結論を手順書にする前に、**残りが同じ形をしているかを機械で数える。**
