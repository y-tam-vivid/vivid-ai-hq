**2026-09-03 実測（ロビン・毎朝の棚卸し）。**
Slack常駐の再接続バックオフを修正し、**検証はすべて合格した。そして障害は150倍長くなった。**

```
検証基準（修正時に自分で決めたもの）      結果
  ログの秒数が 1→2→4→…→300 と増えるか    ✅ 完全に増えた
  hello 受信でリセットされるか             ✅ そのとおり
  ステラの独立検査（diff・実読の2経路）    ✅ 一致

人が困っていた事実                        結果
  Slackのボタンが押せない時間              🔴 9秒 → 23分41秒（約150倍）
```

**★検証基準が、直したかった問題を一度も見ていない。**
測っていたのは「バックオフという部品が仕様どおり動くか」。
本当に守りたかったのは「営業がボタンを押したら反応すること」。
前者だけを検証したので、**後者が壊れたまま「直った」と report された。**

## なぜ起きるか

修正の直前は**部品の話をしている**（`backoff = 1` の位置、リセット条件、hello の分岐）。
その頭のまま検証基準を書くので、**基準まで部品の言葉になる。**
検査役（cross-check）も、渡された基準の中で正しく検査する。**基準の外は誰も見ない。**

```
壊れ方   仕様→実装→検査 が全部正しく繋がっている。どこにも誤りが無い
         ★誤っているのは「仕様が目的を代弁していなかった」の1点だけ
だから   バグ探しでは絶対に見つからない。検査を厚くしても出てこない
```

## どうするか

- **★修正に着手する前に「これが直ったと言える事実」を、部品の言葉を使わずに1行書く。**
  書けないなら、まだ何を直すのか分かっていない。
  ```
  ✕  backoff が 1→2→4 と伸びること
  ◯  ボタンを押してから反応するまでが、いつも○秒以内であること
  ```
- **★「悪化はしない」と書きたくなったら、そこが危ない。** 何と比べて悪化しないのかを
  数字で書く。書けないなら**修正前の値を先に測る**（今回は 9秒・19秒という修正前の実測が
  残っていたから比較できた。残っていなければ悪化に気づけなかった）。
- **★検査役へ渡すとき、目的の側の基準も一緒に渡す。** 部品の基準だけ渡すと、
  検査役の優秀さは基準の外側には届かない。→ [[cross-check]]
- **★トレードオフのある修正は、片側だけ測らない。** 「叩きすぎ」を直したなら
  「遅すぎ」も測る。上限・閾値・間隔を触る修正はほぼ全部これに当たる。

## 見分け方（自分の報告を読み返すとき）

**報告に出てくる名詞が、実装の名詞ばかりになっていたら黒。**
`backoff` `リセット位置` `hello` `単調増加` ── 一つも有璽氏や営業の言葉ではない。
**人が使う言葉の文が1つも無い報告は、目的を測っていない。**
→ [[feedback_write_for_the_reader]] と同根（あちらは配る文書、こちらは検証基準）

## ★いまここ ── 記録は書かれた。コードは直っていない（2026-09-03 つる）

**この学びを書いた当日、同じ障害がもう一度起きた。** 毎朝の自己監査で独立に実測した。

```
日別の最大断絶（slack_socket.log を hello受信⇄切断 で数え直した・2経路目）
  08-27〜09-01   0.0〜0.1分     ← 修正前。1秒リトライで即復帰していた
  09-02          0.3分         ← 修正の適用日（08:43）
  09-03 07:50    ★23.7分       ← 300秒上限へ張り付き、営業のボタンが24分死んだ
```

**★WORKING.md のピタゴラスのブロックは、いまも「✅実装・再起動・実測完了」のまま。**
悪化の実測は memory にしか無く、**作業の状態を持つ側（WORKING.md）へ戻っていない。**
＝ 次にこのブロックを読んだ人は「済んだもの」として素通りする。
→ [[reference_a_warning_nobody_owns]] [[reference_delivered_but_unread]] と同じ型。
**学びを書いた場所と、直す人が見る場所が違う。**

**★真因は backoff の伸び方ではない。** 切断理由は `warning`（Slackの定期的な接続入れ替え）で、
そこから即再接続すると古い接続が残ったまま新しい接続を開き `too_many_websockets` に当たる。
つまり**数秒で解ける一過性の混雑に、300秒の上限を当てている。** 直し方は上限を下げる
（例: 30秒）か、旧接続を閉じてから開く。**どちらもコード＝ピタゴラスの領域。**

## ★同じ型をもう1件（2026-09-03 ステラの検査）── 見た目は3経路で一致。でも起動しない

LIFE STAND UP サイトの試作。**再現度の検証は3経路のうち2経路で一致し、合格していた。**

```
経路2  JS実行後のDOM突合        差分は意図した2点のみ
経路3  計算後スタイル25要素      cmp 0バイト差・sha256一致・ページ全高も同一
報告   「見た目は変わっていません」  ← ここまでは正しい
```

**ステラが `find` と個別 `test -e` の2経路で見つけたもの：**
```
index.php        ★無い → WordPress はこのテーマを「壊れている」と判定し、有効化できない
wp_body_open()   ★無い → Site Kit(GA4)・Jetpack が挿入点を失う。既存サイトは両方稼働中
page.php / single.php / archive.php / search.php / 404.php  すべて無い
```

**★「実WordPressで動かしていない」以前に、いまの形では起動しない。**
検証していたのは「マークアップとCSSが原本を再現するか」。
確かめていなかったのは「**そもそもテーマとして成立しているか**」。

- **★再現度を測る前に「動くか」を1回通す。** 順序が逆だと、動かないものの見た目を精密に測る。
- **★検証の型が揃っていることは、検証の対象が正しいことを意味しない。**
  3経路そろえても、測っている軸が1本しかなければ、その軸の外は素通りする。
  → [[feedback_one_route_is_not_verification]] は「経路」の話。**こちらは「軸」の話。**
- **★代理環境は、代理できる範囲を書く。** 検証レンダラは実WordPressが必ず出す
  `global-styles-inline-css`・`wp-block-library`・`classic-themes` を1行も含んでいなかった。
  「実WPの代理」ではなく「テーマのマークアップの代理」。**名前が範囲を偽ると、読み手が広く信じる。**

### ★ノイズは「消せないもの」ではなく「止められるもの」だった

  → ノイズ床 2,827px → ★0px
```
**★「測れない」で終える前に、揺らしている原因を1つずつ止めてみる。**
20本×PC/SPで240枚を見る工程では、この経路が使えるかどうかで作業量が変わる。

### ★「停止した」は一度きりの事実。あとで立て直せば嘘になる

リリスが前回「検証サーバは停止した（3経路で確認）」と報告した。**その報告は正しかった。**
だがその後の検証で立て直し、**止め忘れた。**
**★状態の報告には時刻が要る。** 「いま止まっている」と「もう二度と立たない」は別。
片付けは**セッションの最後にもう一度**やる。

### ★「止めました」を人が書くのをやめる（2026-09-03・3回目）

同じ案件で**検証サーバの止め忘れが3回**起きた。3回とも報告文には「停止を確認した」と書かれ、
**書いた時点では本当に止まっていた。**そのあと別の測定で立て直し、止め忘れる。

```
15:52  検査役が走査 → 0本（lsof / ps / netstat の3経路で一致）
15:56  再走査 → ★php 8750 ／ python 8757 ／ php 8758 が LISTEN
```

**★規律で直らないと3回で分かった。** 直し方は文章ではなく構造。
```

処理の最後に必ずポート走査を通し、結果を出力する
→ 「止めました」を人が書かない。機械が数えた結果を貼る
```
→ [[reference_hooks_enforce_what_discipline_cannot]]（規律に依存する対策は、規律が切れた回に効かない）

#### ★止め忘れの真因 ── SIGTERM では finally も atexit も走らない（2026-09-03 実測）

「try/finally に閉じた」と書いた**直後にもう一度残った。**原因が分かった。

```
finally / atexit  ★SIGTERM で殺されると走らない（Pythonが例外を上げずに落ちるため）
対処              signal.signal で SIGTERM/SIGINT を捕まえ、止めてから走査結果を出す
```
**★「try/finally に入れた」は対策の完了ではない。** 落とされ方によっては通らない経路がある。
**入れたあとに、実際にその殺し方で試す。**（今回はSIGTERMで殺してポートが残るのを実測した）
いまは `scan_ports()` がスクリプトの finally で必ず出るので、
**「止めました」を人が書く運用ではなくなった。**

### ★自分が足したものは、既存の検査軸の外で入る（2026-09-03）

390pxの横あふれを直す過程で、**犯人が2つ**見つかった。

```
① .programs-en「Communication & Bridge & Eiken」  ★原本にあったもの
② .recruit-band .rb-text{flex:1 1 420px}          ★★こちらが採用バナーで新しく入れたもの
                                                    狭い幅で420pxを要求していた
```

**②は、承認を得て足した機能そのものが作った不具合。**
既存の検査（原本との再現度・画素比較・DOM突合）は**「原本と同じか」を見る**ので、
**原本に無いものは、比べる相手がいない＝検査の外に落ちる。**

- **★足したものには、足した人が検査軸を1本用意する。**
  「原本どおりか」で守れるのは、原本にあるものだけ。
- ★今回は横あふれの測定を新設した副産物として見つかった。**新設しなければ公開まで残っていた。**
- ★同じ形 → [[reference_norms_outnumber_their_enforcement]]（規範は増えるが止める機械は増えない）

**なお ①の型は20本へ広がらなかった**（grepで実測：`&`連結の英字1行は front-page と
stand-up-top の2本のみ＝不合格だった2本と完全に一致）。**先に数えたので20回踏まずに済んだ。**

### ★軸を1本足すと、その1本だけが守られる（2026-09-03・実例）

スマホ幅の横あふれを測る検査を新設し、15通りを回して不合格を1件まで減らした。
**そのあと、同じ画面で「黄色い縦テープが見出しに重なって読めない」が見つかった。**

```

結果           390/360/320px すべてで重なっていたが、検査は全部「合格」を返した

**★検査は、測ると決めた軸の外を静かに通す。** 軸を足したこと自体は前進だが、
**「合格」の意味は「その軸で問題が無い」であって「問題が無い」ではない。**
報告に書くのは「合格」ではなく**「◯◯の軸で合格」**。

- ★この重なりは**元のHTMLにも在った**（実測）。実装が作った問題ではなく、
  デザインがSP幅で持っていた状態。**「作った側の検査」では原理的に出ない**種類でもある。
- ★有璽氏が最初に言った「見切れている」に、これが含まれていた可能性がある。
  **人の指摘を、こちらの分類（横あふれ）に翻訳した時点で、指摘の一部が落ちていた。**

#### ★「散見される」と言われたら、まず数える（2026-09-03）

重なりを1件報告したところ、有璽氏から**「他のページでも同様に散見されている」**と別の実例
（採用ページで「JOIN US」が見出しに重なる）が返った。

**★1件を直す話と、N件ある型を直す話は、選ぶ対処が違う。**
```
1件なら   その箇所を個別に直すのが安い
N件なら   ★一律に効く対処（重ね順を変える等）を探す方が安い。
          個別調整はN倍の作業になり、次に足すページでも再発する
```
**人が「散見される」と言った時点で、件数はまだ誰も知らない。**
対処を提案する前に**数える軸を作って数える。** 見積りも方針も、そこから決まる。

#### ★「一律に効く対処」があるかは、粒度を1段下げると変わる（2026-09-03）

装飾と見出しの重なりに対し、ビビが5案を出して**「E（重ね順を変えて文字を前面へ）を一律に
当てれば全件に効く可能性がある」**と見立てた。**実測で崩れた。**

```
同じ装飾（tape-vertical）でも、重なる相手の文字によって結論が変わる
  コントラスト比 9.88  ×「STAND UP・ネイティブスタッフによる英語療育」 → Eで読める
  コントラスト比 2.31  ×「ネイティブスタッフ」                        → ★Eでは読めない
  コントラスト比 9.88  ×「と過ごす、」                                 → Eで読める
```

**★「テープは全部A」でも「全部E」でもない。** 対処の単位は
「装飾の種類」ではなく**「装飾×重なる相手の組」**だった。

- **★一律の対処を提案するときは、その一律が成り立つ粒度を先に確かめる。**
  「同じ部品だから同じ対処でよい」は仮説であって、実測ではない。
- ★測り方の設計が良かった ── 交差を検出するだけでなく、
  **①文字を何%覆うか ②前面か背面か ③文字色と装飾の地の色のコントラスト比**まで出したので、
  「重なっているが読める」と「隠れている」を分けられた。
  **「重なりの有無」だけを測っていたら、また一律の対処を選んでいた。**
- ★重ね順は2経路で測っている（z-index と DOM順からの計算／交差内9点で
  elementFromPoint を呼ぶ実測）。**食い違ったら食い違いを残す**設計になっている。

##### ★数えた結果 ── 「散見される」は正しかったが、実態は「3ページに集中」（2026-09-03）

```
テーマ側60通り（20ページ×3幅）の確定値
  ★文字が隠れる 85件   390px:29 ／ 360px:29 ／ 320px:27

## ★★対処が、その対処を測る検査の前提を壊した（2026-09-03・この日の総まとめ）

重なりの検査は**「装飾が文字より前面にあるか」**で不合格を数えていた。
案1の対処は**「文字を前面に出す」**。**当てた瞬間、全件が判定の対象から外れた。**

```
測り直した結果  252件 → 63件（★大きく減ったように見える）
安定検査        ★不合格。既知の「JOIN US × RECRUIT｜採用情報」を2回とも検出できない
切り分け        recruit-top の移動だけを一時的に外して測り直す
                → ★外しても検出されない ＝「直したから消えた」のではない
結論            ★測り方が壊れている。63件は使えない
                ★「重なりが消えた」のではなく「重なりと数えなくなった」だけ
```

**★対処と検査が同じ性質を見ていると、対処が検査を無効化する。**
```
