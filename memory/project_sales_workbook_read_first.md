## 入口の設計（2026-08-19に降格を撤回した）

**受付フォームが主入口。「暫定だから降格」は実態と合わなかった。**
8/13時点では暫定扱いだったが、8/19に測ったところ**フォームには既に25行入り営業3名が使っている**一方、本体を営業が直接触る運用は始まっていなかった。実績のある側を正に据える。

```
📥受付フォーム（営業3名が使用中）
      ↓
   受付シート  ← 営業が書く場所。迷わない・壊せない
      ↓  移送GAS 54v3（Drive `1mmJiOYQ9ZxYtdCmjqInu9e7CTiCIQ7whz9AQFpx6i6Y`）
   00_企業マスタ / 02_個人マスタ  ← B-#### / C-#### を発番
      ↓
   40_活動ログ（接触の記録）
      ↓
   08_関係フォロー（A列にIDを入れるだけ。B/C/J/K/M は数式で埋まる）

   10/20/30 案件シート  ★自動で作らない（2026-08-14決定）
       接点があることと案件になることは別。案件は金額・確度・期日を持ち
       週次集計とkintone同期に乗るので、1件書いただけで見込みが膨らむ
```

- **書く場所（フォーム）と見る場所（本体）を分ける。** 二重管理ではなく役割の分離
- **判断できない行は自動で埋めない。** 事業ラインが決まらない・会社名と氏名が逆転している疑い・表記ゆれで既存へ寄せた、は受付シートの社内メモへアラートを出し、台帳登録欄を「未処理」で残す。人が直して再実行すれば既存を引くので二重にならない
- **フォームの選択肢は 90_選択肢マスタ と揃えた**（2026-08-19本実行）。寄せの層を構造的に消した。例外は入力者の「その他」1つだけ（名簿に無い人が送信を諦めるのを防ぐ。取り込み側は担当を空にする）
- **★移送の自動実行はまだ。** 初回は手で走らせた。SalesBreaker取り込み（毎朝7〜8時トリガー・稼働中）と同じプロジェクトにあるので同じトリガーへ相乗りできる
- **毎朝07:00 名刺バッチ ／ 毎朝07:30 Notion upsert は未実装**（Driveフォルダ設置とcronが残る）
- **00を開いて「入っていない」と見えるのは初期スクロール位置のせい。** 新しい行は795行目以降。Cmd+↓ で最終行へ飛ぶ。08のB列に社名が出ていれば00に入っている証拠（数式が00を引いている）
- 「問い合わせ営業」（旧称フォーム営業＝こちらから相手の問い合わせフォームへ送る流入経路）と「受付フォーム」は別物。2026-08-12に前者を改称して衝突を解消
- 社内顧客IDは `B-####`（法人名義）／`C-####`（個人名義）。分け目は法人か個人かではなく**請求書の宛先がどちらか**。同じ相手にIDが2つ付くのは正常

## 特に見落としやすい既決事項

- **層は並走させない**（2026-08-02）。スプレッドシート＝案件層（未着手〜見積提示）、kintone＝確定層（検討中以降）。**kintoneの案件をシートへ戻さない。シートの上流5値をkintoneへ入れない**
- `内定（契約前）` はkintone反映の対象外。`受注（契約締結）` だけがバッチに乗る
- 案件は 社内顧客ID を先に入れる。会社名は数式で自動。`★マスタ未登録` が出たら企業マスタへ追加

- 選択肢は `90_選択肢マスタ` を直す。セルにベタ書きしない
- kintoneは必ず中間CSVを経由。直接編集しない

## ★残件表そのものが規範と矛盾していることがある（2026-08-20）

「移送54v3の毎朝トリガー化」は残件表の**筆頭**にあり、「これを入れるまで有璽氏が手で実行する
運用が続く」と書かれていた。だが 54v3 は**会社名で突合して機械が「新規」と判定し台帳へ書く**
経路で、B-0050 と C-0072 を二重に作った事故そのものだった。
**毎朝自動で回すことは規範に正面から反する。**

```
やってはいけなかった   54v3 を自動化する
正しい後継             intake_match.py    照合だけ・書かない      cron 07:20 稼働中
                       intake_register.py 人が○を付けた行だけ登録
```

- **残件は「早くやる順」だけでなく「やってよいか」でも数え直す。**
  作った当時は正しくても、あとから規範が固まると**やってはいけない残件に変わる**。
- 表に残っている限り、誰かがいつか実行する。**⛔と理由を表の中に書いて消さない。**

## ★同じ事故が別の入口で再発しかけた ── 突合ロジックを2箇所で書かない（2026-08-20）

`notion_backfill.py`（Notion→台帳の取り込み）の検査で、
**2026-08-19 の B-0050／C-0072 二重登録と同型の穴**が見つかった。

```
すり抜けた例   「根本小百合」
               台帳 B-0017 の **代表者名として既に登録済み**
               しかもプロフィール欄に「Notion既存レコードあり」と明記されていた
               ★それでも会社名・法人番号だけの突合では引っかからない
```

**memory には「会社名1本で突合しない」と書いてあった。だがコードが守っていなかった。**
規範を書いても、**入口が増えるたびに同じ穴が開く**。

### 真因 ── 突合ロジックを入口ごとに書き直していた

```
既にあった   ledger_audit.py の norm_company / norm_person / norm_tel / norm_mail
新しい入口   notion_backfill.py が norm_name() を **自前で書き直していた**
             → 既存の堅牢な実装より弱いものが生まれた
```

- **★同じ判断をするコードを2箇所に持たない。** 既存の関数を再利用する
- **新しい入口を作るときは「この突合は既にどこかにあるか」を先に探す**
- 突合に使うキーは **会社名／人名／電話／メール／法人番号** の5つ。
  参照先は `01_顧客詳細`（代表者名・先方担当者名・電話・メール）／
  `00_企業マスタ`（電話）／`02_個人マスタ`（電話・メール）
- Notion側の**自由記述欄**（「先方担当・連絡先」）からも電話・メール・人名を抜き出す
  ── 構造化された列だけを見ると取りこぼす

## ★検査役が通しても、新規発番の承認は別（2026-08-20 当方のミス）

同じ日の午前に「54v3の自動化は⛔。**機械が新規と判定して書いてはいけない**」と判断したのに、
午後、当方の指示で `notion_backfill.py` の本実行を通し、**28件の新規IDを発番させた**
（B-0418〜B-0445）。**有璽氏に「28件を発番します」と出していない。**

```
何が正しかったか   実行そのものは技術的に正しい
                   ・つるの検査を2周通した（1周目で「根本小百合」のすり抜けを発見・修正）
                   ・重複疑い2件は正しく止めた（B-0017 / B-0325 は無傷を実測）
                   ・バックアップ 2,053,775バイト・突合28件全件一致
                   ・源はNotion側で **人が区分を決めた相手**（機械が新規と判定したのではない）
何を飛ばしたか     ★「何件を新規発番するか」を人へ出していない
                   つるの条件は「初回の本実行**結果**を目視」だった。
                   当方はそれを「実行してよい」と読み替えた
```

- **検査役の「載せてよい」は、実行の承認ではない。** 検査役が見るのは *正しく動くか*。
  **何件を、いつ、誰の台帳へ書くか** は別の判断
- **★件数が変わる操作は、件数を先に出す。** 「28件を新規発番します」と1行出せば済んだ
- 条件つき判定の条件は**文言どおりに読む。** 「結果を目視」を「実行してよい」に広げない
