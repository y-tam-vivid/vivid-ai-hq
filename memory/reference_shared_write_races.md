# 共有の置き場へ書く自動処理は、相手を巻き込む

**2026-09-13、別々の担当が別々の作業で、同じ型を3回踏んだ。** どれも「自分の書く分は正しい」。
壊れるのは**同じ場所を同時に使っている相手**の側なので、自分の検査では出てこない。

```
置き場              書き方                         巻き込むもの                       9/13の状態
────────────────────────────────────────────────────────────────────────────────────────────
Vercel Blob         読む → 足す → 書き戻す          ほぼ同時の別の書き込みを上書きで消す  ★実測で1回起きた
 (office_running_   ＋GETにCDNキャッシュ            （start の直後の done が埋もれた）    max-age 0 で減ったが
  ping.py)            → 古い値を読んで書き戻す                                             理論上は残る
git 管理下の theme/ git add <パス> → commit          ★他セッションの未コミットの書きかけ  起きていない。
 (editor_apply.py)   ＝ファイルの★今の全内容が載る   が★Cのcommitに混ざる                 構造として残る
                     （行単位では分けられない）
検証用WordPress     rrmdir → rcopy                  計測中の別プロセスが消えた瞬間を読む  停滞2本と同時期。
 (activate_theme.php)＝一瞬フォルダが空になる                                             因果は未確定
```

**Why**: 3つとも、作った人は「触るファイルが違う／自分の担当分しか書かない」と考えていた。
実際は置き場が1つで、書き方が**途中の状態を相手に見せる**か**相手の分ごと書く**形だった。

**How to apply**（共有の置き場へ書く処理を作る・レビューするとき）
- **先に「同じ置き場を他に誰が書くか／読むか」を数える。** 担当が違っても置き場が同じなら共有。
- **読んで書き戻す形は、同時に2本走ったら片方が消える前提で作る。**
  1件ずつ別の名前で書く（追記型）にすれば上書き競合そのものが起きない。
- **`git add <パス>` は安全な add ではない。** 書く直前にそのファイルが未コミットで変わっていないか
  `git status --porcelain <パス>` で見て、変わっていたら commit せず止めて知らせる。
- **丸ごと消して作り直す処理は、使用中のプロセスを先に数えてから叩く**
  （PID で見る。`pkill -f` は使わない → [[reference_two_sessions_built_the_same_thing]]）。
- ★どれも**正常系の単体テストでは必ず合格する**。確かめるなら2本同時に走らせる。
