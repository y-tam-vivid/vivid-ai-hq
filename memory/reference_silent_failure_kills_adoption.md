**★人が操作する仕組みは、成功より「失敗したときに何を返すか」で決まる。**

2026-08-23、Slackのボタンを初めて実地で押してもらった。押下は Mac mini まで届いた。
**だが値の検証で弾かれ、押した人には何も返らなかった。**

```
起きたこと   ログに「★valueの形式が不正」と出て終わり
押した人から  メッセージは元のまま。ボタンも残ったまま。**何も起きない**
本番なら     営業「押したのに動かない」→ もう一度押す → また無言
             → 「壊れている」と判断 → **二度と使わない**
```

**★仕組みは、落ちて死ぬのではない。無言で死ぬ。**

## 守ること

```
成功したとき   「✅ ◯◯さんが『△△』を選択（日時）」＋ボタンを消す
失敗したとき   「⚠️ 受け取れませんでした（理由）」
               ★必ず **逃げ道** を添える ──「受付シートで直接ご記入ください」
どちらでもない ★そんな状態を作らない。押したら必ず画面が変わる
```

- **★「何も返さない」を実装の初期状態にしない。** エラー処理を後回しにすると、
  最初に人が触った日がいちばん壊れて見える日になる
- **押した本人にだけ見える返し方**（Slackなら `response_url` の ephemeral）も使える。
  他の人の画面を汚さずに理由を伝えられる
- → [[reference_ran_is_not_succeeded]]（動いたと成功したは別）の人間側の版

## ★テストで実データを触らない経路を、最初から作る

このとき当方は `row=0`（存在しない行番号）を安全策としてテストに使い、
**その値が検証に弾かれた。** 安全にしようとした工夫が、そのまま不正値になった。

```
悪い   本番の value を少しずらしてテストにする → 検証に弾かれる／本番と紛れる
良い   ★テスト専用の印を value に持たせる（例 {"test": true}）
       → 書き込まずに「受け取りました」とだけ返す経路を通す
```

**人が押す仕組みを作ったら、「押しても何も起きない」パターンを必ず1回踏んでおく。**

## ★安全策は2つ重ねる ── 1つで足りると思った側が抜ける（2026-08-23 実測）

テストのとき、当方は安全策を2つ入れた。

```
① row=0            受付シートに存在しない行番号 → 書き込み先が無い
② candidate_id=BOTH 契約に無い値 → 弾かれるはず
```

**検査で分かったのは、②が弾かれていなかったこと。**
受信側は `candidate_id` を検証せず、**台帳のY列へそのまま書く実装**だった。
`row` が正しければ、台帳に `BOTH` という実在しない値が書かれていた。

```
助かった理由   ①が効いていたから（存在しない行なので書けなかった）
★もし①が無ければ   台帳に壊れた値が入っていた
```

- **★「これは弾かれるはず」を安全策に数えない。** 弾かれることを実測していない防御は、
  防御ではない（→ [[reference_ran_is_not_succeeded]]）
- **人が触るものを初めて通すときは、安全策を2つ重ねる。**
  1つは「書き込み先が無い」ような**構造的に不可能**なもの、
  もう1つは「値が不正」のような**検証に頼る**もの。
  ★検証に頼る側は、しばしば実装されていない
- 直し ── `^[BC]-\d+$` の形式検証を書き込み前に置いた。
  加えて `{"test": true}` の経路を最優先で分岐させ、書き込み関数を一切呼ばない形にした
