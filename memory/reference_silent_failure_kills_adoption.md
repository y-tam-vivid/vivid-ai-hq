**★人が操作する仕組みは、成功より「失敗したときに何を返すか」で決まる。**

2026-08-23、Slackのボタンを初めて実地で押してもらった。押下は Mac mini まで届いた。
**だが値の検証で弾かれ、押した人には何も返らなかった。**

```
起きたこと   ログに「★valueの形式が不正」と出て終わり
押した人から  メッセージは元のまま。ボタンも残ったまま。**何も起きない**
本番なら     営業「押したのに動かない」→ もう一度押す → また無言
             → 「壊れている」と判断 → **二度と使わない**
```

**★仕組みは、落ちて死ぬのではない。無言で死ぬ。**

## 守ること

```
成功したとき   「✅ ◯◯さんが『△△』を選択（日時）」＋ボタンを消す
失敗したとき   「⚠️ 受け取れませんでした（理由）」
               ★必ず **逃げ道** を添える ──「受付シートで直接ご記入ください」
どちらでもない ★そんな状態を作らない。押したら必ず画面が変わる
```

- **★「何も返さない」を実装の初期状態にしない。** エラー処理を後回しにすると、
  最初に人が触った日がいちばん壊れて見える日になる
- **押した本人にだけ見える返し方**（Slackなら `response_url` の ephemeral）も使える。
  他の人の画面を汚さずに理由を伝えられる
- → [[reference_ran_is_not_succeeded]]（動いたと成功したは別）の人間側の版

## ★テストで実データを触らない経路を、最初から作る

このとき当方は `row=0`（存在しない行番号）を安全策としてテストに使い、
**その値が検証に弾かれた。** 安全にしようとした工夫が、そのまま不正値になった。

```
悪い   本番の value を少しずらしてテストにする → 検証に弾かれる／本番と紛れる
良い   ★テスト専用の印を value に持たせる（例 {"test": true}）
       → 書き込まずに「受け取りました」とだけ返す経路を通す
```

**人が押す仕組みを作ったら、「押しても何も起きない」パターンを必ず1回踏んでおく。**

## ★安全策は2つ重ねる ── 1つで足りると思った側が抜ける（2026-08-23 実測）

テストのとき、当方は安全策を2つ入れた。

```
① row=0            受付シートに存在しない行番号 → 書き込み先が無い
② candidate_id=BOTH 契約に無い値 → 弾かれるはず
```

**検査で分かったのは、②が弾かれていなかったこと。**
受信側は `candidate_id` を検証せず、**台帳のY列へそのまま書く実装**だった。
`row` が正しければ、台帳に `BOTH` という実在しない値が書かれていた。

```
助かった理由   ①が効いていたから（存在しない行なので書けなかった）
★もし①が無ければ   台帳に壊れた値が入っていた
```

- **★「これは弾かれるはず」を安全策に数えない。** 弾かれることを実測していない防御は、
  防御ではない（→ [[reference_ran_is_not_succeeded]]）
- **人が触るものを初めて通すときは、安全策を2つ重ねる。**
  1つは「書き込み先が無い」ような**構造的に不可能**なもの、
  もう1つは「値が不正」のような**検証に頼る**もの。
  ★検証に頼る側は、しばしば実装されていない
- 直し ── `^[BC]-\d+$` の形式検証を書き込み前に置いた。
  加えて `{"test": true}` の経路を最優先で分岐させ、書き込み関数を一切呼ばない形にした

## ★「押した」と言われても、受け側に記録が無ければ判定できない（2026-08-23）

有璽氏から「2回目のボタンは押した」と伝えられた。**その結果を判定できない。**
検査役の実測 ── `slack_socket.py` は **launchd 未load、Claudeセッションの子プロセス**として
動いており、plist が指す `slack_socket.log` は**存在しない**。

```
押した側   押した（事実）
受け側     証跡が無い。セッションが終われば receiver ごと消える
結果       「届いた」も「弾かれた」も言えない。★無言の失敗と区別がつかない
```

- **★人が押す仕組みを「試してもらう」前に、押下が残る形にしておく。**
  順序は ①launchd load ②ログ出力先の実在確認 ③⚙️レジスタへ心拍 ④その後で人に押してもらう。
  これを飛ばすと、人の1回の操作が丸ごと無駄になり、**同じ検証を2度頼むことになる**
- 上の節と同じ構図 ── **無言なのは押した人の画面だけではない。こちら側も無言になる**
- → [[reference_ran_is_not_succeeded]] [[project_automation_register]]

## ★人が出した答えを、翌朝の処理が巻き戻す（2026-08-26 検査役が発見・書く前に停止）

受付シートの照合まわりで、**工程どうしが互いの出力を上書きする経路**が見つかった。
書き込みの直前に検査役が止めた。

```
① 人がボタンで候補を選ぶ     受信側（slack_socket.py）が Y列へ「選ばれたID」を単体で書く
② 翌朝07:20 の照合           ★Z列（確認）を一切見ず、社内顧客IDが空である限り
                             Y列を無条件で再計算し、多候補テキストへ**巻き戻す**
③ 登録（07:25）              巻き戻された Y列を読み「候補2件」と判断 → ★毎回 保留に落ちる
④ 通知                       Z列が埋まっているので**再通知しない**（対象から外す）
⑤ 結果                       ★人に何も知らせないまま、その行が永久に止まる
```

**★誰も失敗していない。全員が仕様どおり動いて、行だけが死ぬ。**

- **★「毎回作り直す」処理は、人が触った値を消す。**
  再計算する処理を書くときは、**人が触ったあとかどうか**を必ず見る
- **★工程を足したら、前の工程の出力を上書きしないかを数える。**
  今回は「受信側がY列へ書く」「照合がY列を作り直す」が、別々に正しく作られていた
- **★止まったことに気づける経路があるか。**
  ④で「再通知しない」条件が、そのまま「永久に黙る」条件になっていた。
  **除外条件は、同時に沈黙の条件でもある**
- 発見したのは検査役。**書いた本人の申告には無かった**
  → [[reference_ran_is_not_succeeded]]

### ★「触らない」という安全策が、別の盲点を作る（2026-08-26）

上の巻き戻しを直すとき、素直な答えは **「確認済みの行は触らない」** だった。
**それだけでは足りない。**

```
A 触らない だけ   人が選んだ答えは守られる
                  ★だが台帳が更新されて候補が増えても、**永久に気づけない**
                  （その行はもう再照合されないため）
A ＋ B            触らない ＋ 再照合した結果が変わったら **知らせる**
                  ★Y列は書き換えない。社内メモへ「確認は済んでいますが、
                    再照合すると結果が変わりました」と追記する
```

**★上書きを止めるだけでは、静かな取りこぼしに変わるだけ。**
止めた経路の分だけ、**知らせる経路を足す。**

### 通知は「決定を求めるもの」と「知らせるだけのもの」を分ける

```
決定を求める   ボタンつき。押されるまで残る
知らせるだけ   ★ボタン無し。「まだ登録は済んでいません。確認欄を選び直してください」
              ★state のキーも分ける（`alert:<行>`）
              → 二重通知と取りこぼしの両方を防ぐ
```

**★同じ経路で両方を流すと、片方の除外条件がもう片方を黙らせる。**
（今回まさに「Z列が非空なら通知しない」が、アラートまで止めていた）

### ★人が仕組みの外へ書いた答えを、仕組みが読まない（2026-08-26）

有璽氏は受付シートの**社内メモ**へ手で書かれた ── 「C-0049　上妻央育　と同じ」。
**答えは出ている。だが仕組みはそこを読まない。**

```
Z列（確認）   旧形式の「○ 同じ人」のまま（どのIDかを書く欄が無かったため）
登録側        候補2件を見て、機械的に ★保留 へ倒す
結果          ★その行は永久に登録できない
              しかも「まだ登録が済んでいません」という催促だけが届く
```

**★人が仕組みの外へ書いたということは、仕組みに受け皿が無かったということ。**
そこを読まずに催促すると、**答えた人にもう一度同じ問いを突きつける**ことになる。

- **★人が想定外の場所へ書き始めたら、それは仕様の穴の証拠。**
  「そこへ書かないでください」ではなく、**受け皿を作るか、そこを読む**
- **★答えを受け取れないまま催促を足すと、無視されるだけでなく信頼を失う。**
  「もう答えたのに」と思われた時点で、その仕組みは使われなくなる
- ★ただし**自由記述を機械が解釈して台帳へ書くのは別問題**。
  読んで**候補として先頭に出す**までにとどめ、確定は人の1クリックに残す

### ★「そこへ書かれた」を機械に読ませるのは、応急処置であって設計ではない（2026-08-26 有璽氏）

有璽氏が社内メモへ「C-0049 上妻央育 と同じ」と書かれたのを見て、
当方は **「社内メモを読む機能」を実装させた。** 方針として誤り。

> 「社内メモに書いたのは、**書く場所がなかったからです。**
>   積極的に社内メモに書くつもりはない。
>   **混ざってわけわかんなくなるんやったら、分けた方がいい**」

```
やったこと   人が外へ書いた答えを、機械が読みに行く
正しいこと   ★受け皿を作る。書く場所を用意する
違い         前者は「その場は通る」。だが自由記述を機械が解釈し続けることになり、
             否定文の誤検出など、別の危険を抱え込む
```

- **★人が想定外の場所へ書いたら、まず「なぜそこへ書いたか」を聞く。**
  受け皿が無かったのなら、**受け皿を作る**。読みに行くのは応急処置
- **★「機械が読めるようにする」と「人が書きやすくする」は別の問題。**
  今回は後者を解かずに前者だけ足そうとした
- 有璽氏の言葉 ── **「違っていた時のやり方を定めてくれたら、それに営業を含めて沿います」**
  ★人は決められた形に沿う。**決めていないから、外へ書かれる**

### 定めた形（2026-08-26・★③の実装は未着手）

```
① 候補が出て、どれかと同じ       ボタンを押す（★どのIDかまで選べる）
② 候補が出て、全部違う           「× 別人（新規でよい）」
③ 候補が出ないが台帳にいる       ★Slackのそのメッセージに**返信でIDを書く**
                                 → 機械が拾って確認欄へ入れる
                                 理由：営業は既にそこで押している。★欄を増やさない
④ 一度確認したあと間違いに気づいた ★確認欄を選び直すだけ
                                 （上書きしない設計なので、人が直したものは守られる）
                                 台帳へ載ったあとは台帳側の修正
```

**社内メモは、機械が一切読まない自由記述に戻す。**

### ★入力を信じて選択肢を消すと、入力ミスの行が詰む（2026-08-26 有璽氏）

「接触の種類が『継続』なら台帳に既にいるはずだから、
**『新規として発番してよいか』という文言自体を出さない**」── そう指示しかけた。

> 有璽氏「そこまでやってしまうと、例えば **営業側の記入ミス**とかでなった場合、**詰むじゃん**」

```
起きること   営業が接触の種類を選び間違えた行は、★新規にする手段が消える
             ＝ その行は永久に登録できない
正しい形     「継続」なら **台帳を先に確認する順序** を変えるだけ
             ★選択肢そのものは残す
```

- **★人の入力を信じて、選べる道を減らさない。**
  入力は間違う。間違った入力に対して**出口が無くなる**設計にしない
- **★優先順位を変えるのと、選択肢を消すのは別物。**
  前者は「どれを先に見せるか」。後者は「何ができるか」を狭める
- **★どんな入力ミスでも、必ずどこかへ抜けられる道を残す。**
  → 上の「逃げ道を必ず添える」と同じ原則。**選択肢を消すのは逃げ道を塞ぐこと**

### ★経路の最後の1行で、運んできた値が捨てられていた（2026-08-26 実測）

「どのIDと同じか」を受け取れるようにする改修で、**3つの工程を全部直した。**
それでも通らなかった。

```
投稿側    候補ごとにボタンを分ける         ✅ 直した
受け側    押下から candidate_id を受け取る  ✅ 届いている（ログに `candidate_id=C-0026`）
書く側    ★`OK = '○ 同じ人'` の固定文字列をそのまま書く
          `find_row_and_write(row, decision, candidate_id=None)` と
          **引数では受けているのに、書く値へ反映していない**
結果      受付シートには「○ 同じ人」だけが入り、★IDが消える
          → 登録側は「候補2件」と読んで、また保留に落ちる
```

**★運ぶ経路を全部直しても、最後に書く1行が古いままなら、何も変わらない。**

#### ★真因は「代入漏れ」ではなく、2本のスクリプトの契約ズレだった（訂正）

当方は「引数で受けているのに使っていない＝代入漏れ」と診断した。**症状であって原因ではない。**

```
受け側（slack_socket.py）    候補IDを **Y列（照合結果）へ分離して書く**【旧設計】
登録側（intake_register.py） **Z列（確認欄）へ直接IDが入っている**前提【新設計】
                             ＝ 片方だけ新しくなっていた
```

- **★2本のスクリプトが「どの列に何が入っているか」を別々に前提している状態は、
  どちらのコードを読んでも見つからない。** 繋いで初めて出る
- **★片方を新しい設計へ移したら、対になる相手も同じ日に移す。**
  移せないなら、**移していないことを両方のコードに書き残す**
- 直し方 ── 受け側がZ列へ直接 `○ 同じ人（C-0026）` を書く形へ統一。
  ★Y列への分離書き込みは廃止。**書き手を1本に減らした**

- **★値が「届いているか」と「使われているか」は別。**
  ログに出ていても、書く直前で捨てられていることがある
- **★引数で受け取っているのに使っていない箇所は、静かに壊れる。**
  受け取っている＝対応済み、と読めてしまう
- **★端から端まで1回通せば分かる。** 今回は有璽氏が実際にボタンを押して初めて出た。
  ドライランと単体テストは全部通っていた

**検証の設計** ── **入口で入れた値が、出口で同じ形で出てくるかを見る。**
途中の工程がそれぞれ正しくても、繋がっているとは限らない。
