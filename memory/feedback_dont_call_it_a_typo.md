**固有名詞が食い違っていたら、「誤記だ」と言う前に「どちらが新しいか」を確かめる。**

## 何が起きたか（2026-08-20）

有璽氏が Drive に作ったフォルダ名が `福祉施設の119番_IG_Manus MDファイル等` だった。
当方は**実測データを根拠に「119番は110番の誤記」と指摘した**。

```
根拠にしたもの   Manus のプロジェクト名   「福祉施設の110番 SNS・情報発信運用自動化」
                 Instagram ハンドル       @fukushi_110ban
                 （119番は消防・救急、という一般常識も足した）
```

**誤りだった。** 有璽氏「**名称は110番ではなく、119番が正式名称になった**」。
改称されており、Manus のプロジェクト名も Instagram ハンドルも**旧名のまま取り残されていた**。

## 何を間違えたか

**実測データを「現在の正」として扱った。** 実測できるのは「過去のある時点で誰かが書いた文字列」であって、
現在の正式名称ではない。システムに残っている表記は、**改称に追随していない可能性が常にある**。

```
×  システムの表記 A ≠ 人が書いた B  →  Bが誤記
○  システムの表記 A ≠ 人が書いた B  →  ★どちらが新しいかを確かめる
                                        人が書いた側が新しいことは普通にある
```

「実測で裏を取る」は正しい作法だが、**裏が取れるのは「そう書いてある」ことだけ**で、
「それが今も正しい」ことではない。日付の入らない固有名詞ではとくに危ない。

## どうするか

- **固有名詞の食い違いを見つけたら、指摘の形を変える。**
  「◯◯は誤記では」ではなく「**システム側は△△、こちらは◯◯。どちらが正ですか**」と両方を並べて聞く
- 一般常識（119番は消防）を根拠に足さない。**社名・サービス名は常識の外側で決まる**
- 新しい方が確定したら、**旧名を指している場所を全部洗って張り替える**
  → 規範「旧版を指す機械可読なリンクは見つけ次第すべて新版へ張り替える」

## ★逆向きもある ── 「あったよね」を確かめずに前提にしない（2026-08-27 実測）

上は「実測が正、人が誤り」と決めつけた失敗。**逆向きの失敗も同じ日に起きうる。**

有璽氏「**役職は別途あったよね**」──受付フォームの人名から役職を外す実装の話。
当方は「外した役職は既存の役職欄へ移す」前提で設計しかけた。

```
実測   受付シート ── 役職の欄は無い
       01_顧客詳細（42列）── 無い
       02_個人マスタ ── 無い
       ★3つとも無い。移す先が存在しなかった
```

**★どちらに倒すかを決めるのではなく、実物を見る。** 人の記憶も、システムの表記も、
どちらも「過去のある時点の写し」でしかない。

- **人が「あるはず」と言った器（欄・機能・ファイル・フォルダ）は、着手前に実在を1回確かめる。**
  無ければ「作るか／捨てるか」の判断が要る＝**設計の分岐が1つ増える**。黙って作らない
- 無かったときの返し方は上と同じ ── 「ありませんでした」ではなく
  「**3つとも見ましたが役職の欄はありません。作りますか、外して捨てますか**」
- **意味が特定できない指示は憶測で実装しない。** 同日「継承の部分はいらない」という指示が出たが、
  何を指すか特定できなかった。**分からないまま動かず、確かめる**
- 実例と実測の正本 → [[project_sales_workbook_read_first]]「役職の欄は、どこにも無かった」

## ★既存の器を「足りない」と決めつけない ── 運用が違うだけのことがある（2026-08-29 実地）

Notion 🗓️ イベント管理の「会場・地域」が **select 7択**（未定／河内町／オンライン／大阪市／
大東市／羽曳野市／梅田）だったのを見て、ビビは「**会場の正式表記が入らない＝致命的**」と
有璽氏へ報告した。スキル側が「会場＝正式表記・階層・区画まで」を要求していたため。

**有璽氏の返答** ──「**会場は具体的な場所ではなく、今はエリアだけを出しています。
会場名が必要ならその項目も入れてあったら、それはそれでいいと思います。**」

```
ビビの読み      「会場」列なのに正式表記が入らない → 設計の欠陥
実際            エリアを出すための列。★意図どおりに使われている
正しい対処      既存列を直すのではなく、★会場名の列を別に足すだけ
```

- **★スキル・手順書が要求する項目名と、実物の列名が同じでも、同じ意味とは限らない。**
  「会場」という名前が一致したので、同じものだと決めつけた。**列の中身（選択肢）を見れば
  エリアだと分かったのに、名前で判断した。** → [[reference_dangerous_entrypoints]] と同じ型
  （入口は名前で判断しない）が、**データの列にも当てはまる**。
- **★「足りない」と言う前に、いまどう使われているかを聞く。** 埋まっている値を見れば、
  設計者の意図はたいてい読める。7択が全部エリア名だった時点で気づけた。
- **★対処は「変える」ではなく「足す」に倒す。** 既存の運用が回っているなら、
  それを壊さずに横へ足す。**消さずに状態で表す**（fukuchi-core）と同じ判断。
- **★報告の言葉を強くしすぎない。**「致命的」と書いたことで、有璽氏に
  「直さないといけないのか」と余計な判断を負わせた。**事実（7択でエリアが入っている）を
  先に書き、評価は後ろに置く。**
