# 止まったことが伝わらないのは、黙りが2つ重なるから

**★2026-09-15 有璽氏「なぜかわからないが止まってるよ。なんで？」**

会議室の画面が今朝ずっと同じ数字のままだった。**本当に止まっていた。**

```
2026-09-15 00:42  Vercel Blob（画面が読むデータ置き場）が停止
                  Billing State: Inactive ／ 206KB・202ファイル＝★容量超過ではない
以後               /api/office が読めない → 画面は★初期値のまま固まる
09:48             有璽氏が気づいて指摘 ── ★9時間、誰も気づいていない
```

## ★なぜ9時間も気づけなかったか ── 黙りが2つ重なっている

**① cron の書き方で、出力がどこにも残らなかった**

```
3,33 * * * *  A && B && C && deploy.sh >> ログ 2>&1
                                          ↑ ★リダイレクトは最後の deploy.sh にしか掛からない
＝ A(office_data) B(office_realtime_push) C(office_build) の出力は★消える
＋ (cmd || true) なので★失敗しても止まらない
実測：ログ 17,233行のうち blob の文字列は★0件。手で叩けば1秒でエラーが出るのに。
```

**★直し方**：行全体を `{ ... ; } >> ログ 2>&1` で囲む。
**🔴ただし cron は生の `%` を改行に変える**（man cron）。
`date "+%Y-%m-%d"` のような書式つき date は cron の中で壊れる。
★一度これを入れて自分で事故を作りかけた。`date` は書式なしで呼ぶ。

**② 画面が、読めていないことを言わなかった**

```js
if (!j || !j.ok || !j.data) { return; }   // ★直前の表示のまま（画面を壊さない）
```

画面を壊さない配慮のつもりが、**「古い数字を、新しい顔のまま見せ続ける」**になっていた。
★人には「止まっている」としか見えない。**なぜ止まったかは画面のどこにも無い。**

**★直し方**：読めなかったら画面の一番上に必ず言う。

```
★新しいデータを読めていません。いま見えている数字は 09/15 09:54 時点のもので、
  それ以降は止まっています。
  理由：Vercel Blob: This store has been suspended. ／ この状態が 12分 続いています
```

★壊して確かめた（fetch を必ず失敗させた版で、この帯が実際に出ることを確認）。

## ★型として覚えること

```
「静かに失敗する」は1つの欠陥ではなく★2つの掛け算
   出す側が黙る（ログに残らない・失敗しても止まらない）
 × 受ける側が黙る（古いものを新しい顔で見せる）
 ＝ 人が目で見つけるまで誰も気づかない
★どちらか片方を直しても足りない。両方を直す。
```

- **★「画面が動いている」と「データが新しい」は別。** 画面は正常に描画されていた。
- **★時刻を焼くだけでは足りない。** 古いことを**赤で言う**まで人は気づかない。
- **★可逆な備えは先に入れる。** 課金の判断（不可逆・お金）は人へ渡し、
  ★「読めていないと言う」「ログに残す」は先に自分で入れてよい。
