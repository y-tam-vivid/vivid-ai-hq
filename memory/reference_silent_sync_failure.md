**`git pull --ff-only` を cron から直に呼んではいけない。** 作業をすればワーキングツリーは
必ず汚れ、ff-only は汚れていると必ず失敗する。つまり **「作業している間だけ受信が止まる」** ―― 
いちばん困るタイミングで止まる構造になる。2026-08-17 に **153回連続の失敗**（≒38時間）を実測した。

```
症状   規範・記憶・WORKING.md は毎ターン確かに届いていた。届いていたのが2日前の版だった
       読む側にそれを知る手段が無く、過去の状態を現在地として答えた
       エラーは ~/Library/Logs/… に463行。誰も見ていない
```

**ログは届く場所ではない。** 見に行かないと分からない場所は、届いていないのと同じ。
[[feedback_reading_list_is_not_a_map]] と同じ構図で、対策を「読む規律」に置くと、
規律が切れた回にだけ効かない。

## 直し方 ── 「取り込む」と「知る」を分ける

```
取り込み（merge）   失敗してよい。作業中に他機の変更が勝手に乗る方が危ない
知ること（fetch）   失敗してはいけない。マージしないので作業中でも必ず通る
```

`bin/vivid-sync.sh`（両機・cron */15）が ①fetch ②遅れ／進みを数える
③`~/.claude/SYNC_STATUS.md` へ書く（`~/.claude/CLAUDE.md` が @import ＝毎ターン届く）
④⚙️自動処理レジスタへ心拍（沈黙すれば🔴）。

- **ahead（自分の変更が他機へ届いていない）も同じ事故を起こす。** 受信だけでなく送信の滞留も出す。
- **🔴が出ている状態で現在地を答えない。** 先に取り込む。取り込めないなら古い版だと明示する。
- 心拍の処理名は完全一致で探されるため、**機械ごとに行を分ける**（同名2行あると更新されない）。

## ★🔴が一晩続く原因は、ほぼ「自分の未コミット」（2026-08-22 実測）

送信は `vivid-sync.sh` が自動でするが、**対象はコミット済みだけ**。書きかけを置いたまま
セッションを終えると、その機は ff-only できず**未取込6件のまま朝を迎える**。
2026-08-22 朝、前日の自己監査が作った memory 6ファイルが未コミットで残り、
mini は6件遅れの WORKING.md / MEMORY.md を「現在地」として読んでいた。

- **★作業の締めは「commit した」ではなく「`git status` が空になった」まで。**
  自己監査・バッチ処理のように無人で回るものほど、置き忘れを指摘する人がいない
- 直し方は捨てるのではなく**確定させて merge**する（[[reference_git_add_all_swallows_others]]
  ── `git add -A` ではなく触ったファイルを明示する）

## 一般化

**「自動で配っている」と「相手に届いている」は別。** 配送経路の存在は鮮度を保証しない。
自動処理レジスタに**その同期自身が登録されていなかった**のが根本 ―― 
他の全自動処理の土台なのに、監視の外にあった。→ [[project_automation_register]]

関連: [[reference_dangerous_entrypoints]] [[reference_silent_rejection_backlog]]

## ★枝分かれは `--ff-only` では絶対に解けない（2026-08-26 実害）

```
2026-08-25 夜  autocommit_stale.py が mini で発火し、放置1本を commit した（＝ahead=1）
その後         MacBook が先へ進み origin が伸びた（＝behind=11）
2026-08-26 朝  mini は behind=11 / ahead=1 の枝分かれ。
               merge --ff-only は失敗し、push も behind>0 で送れない
               ＝ ★11件遅れたまま孤立し、自力では永久に回復しない
```

**Why:** 「取り込みは失敗してよい」という設計は正しいが、**失敗し続ける状態**が生まれると別問題になる。
`--ff-only` は片方向にしか進めない。**自動確定（autocommit）を足したことで、
自分から枝分かれへ入る道ができていた**（commit はするが push は behind=0 のときだけ、という非対称）。

**How to apply:**

- **★汚れていない（未コミット0）ときに限り、通常の merge を試す。**
  衝突したら `merge --abort` して🔴のまま残す。**勝手に片方を捨てない。**
- **★「失敗してよい設計」には、必ず「失敗が固定化しないか」を確かめる。**
  1回の失敗は許容でも、**同じ理由で永久に失敗し続けるなら、それは設計の穴。**
- 枝分かれかどうかは `git rev-list --left-right --count origin/main...HEAD` の**両方の数**で見る。
  behind だけを見ていると「遅れている」としか分からず、**解けない遅れ**だと気づけない。

## 🔴★2回目 ── 機械は正しく止まった。誰も解かなかった（2026-09-05 実測）

**有璽氏「Mac miniが止まってないか確認して」で発覚。** マシンは止まっていない
（cron・launchd・毎朝ジョブは全部動いていた）。**止まっていたのは同期の1本だけ。**

```
実測  未コミット 0件 ／ behind 24 ／ ahead 19 ／ 共通祖先は同じ日の 4ed0551
      ＝ 9/5 の日中に分岐し、その後ずっと解けないまま複数セッションが作業を続けた
      衝突は8ファイル。全部「両側で末尾に別の節を足した」型（memory 配下だけ）
```

- **⛔当方の初見「自動mergeが未実装」は誤り。**`vivid-sync.sh:99` に実装されており、
  **衝突→abort→🔴のまま残す、という設計どおりに動いていた**（実測して訂正）。
  **機械の不具合ではない。人（AI）が解く前提の設計で、その人が来なかった。**
- **🔴★真の穴は「🔴の説明文が真因を決め打ちしていること」。**
  `SYNC_STATUS.md` は「原因はほぼ常に**ローカルに未コミットの変更があり**…」と書き、
  取り込み方として `git add -A && git commit` を案内する。
  **今回は未コミット0件。案内どおり叩いても何も起きない。**
  ＝ 読んだ側は「自分にできることは無い」と読み、🔴を見たまま素通りする。
- **★毎ターン🔴が届いていたのに、誰も解かなかった。**規範「🔴が出ている状態で現在地を
  答えない。先に取り込む」は、**解き方が案内されていないと守れない。**
  → [[reference_delivered_but_unread]]（届いていても読まれない／読めても動けない）

**How to apply:**

- **🔴を見たら、まず `git status --porcelain | wc -l` と上の rev-list を叩く。**
  未コミット0で behind>0 なら、それは**衝突が解かれるのを待っている状態**。
  `git merge origin/main` を自分で叩いて解く。**放置は「作業していない」と同じではない。**
- **衝突が memory / WORKING.md なら、ほぼ全部「両側の追記」。両方を残す**
  （マーカー3行を消すだけ）。**索引の1行が両側で書き換わっている場合だけ手で統合する**
  ── ここは重複させると同じリンクが2行並ぶので、機械的に両方残してはいけない。
- **★止まりを疑われたら「マシン」と「同期」を分けて測る。** 混ぜると、
  cron が動いているのを見て「止まっていません」と答えてしまう
  → [[feedback_one_route_is_not_verification]]

**★提案（未実施・有璽氏の判断待ち）**：`SYNC_STATUS.md` の🔴文面を、未コミット件数で
分岐させる（0件なら「衝突を解いてください」＋`git merge origin/main` を案内）。
毎ターン全AIへ届く文面なので、当方では書き換えていない。

## ★取り込めないときは、取り込まずに `origin/main` を読む（2026-09-07 ロビン・毎朝の棚卸し）

**🔴の日に「先に取り込む」ができない場面が実際にある。**
この朝、mini は **behind 34 / ahead 1**、かつ**別セッションが書きかけの memory 5本**が
未コミットで残っていた（mtime は 7〜30分前）。**commit も stash も他人の作業に手を入れる**ので
できず、merge も走らない。

**それでも重複は避けられる。読むだけなら、取り込まなくても origin は見える。**

```
git fetch -q origin                              作業ツリーに触れない
git rev-list --left-right --count HEAD...origin/main   1 34 ＝ 遅れの実数
git diff --name-only HEAD origin/main -- memory/       ★向こうで既に書かれたファイル
git show origin/main:memory/<file>.md | grep -n "…"    中身を直接読む
git grep -n "<語>" origin/main -- memory/              全ファイル横断で重複を探す
```

**実際に効いた** ── この朝に拾った候補のうち、
「申告なしの自動処理が本番稼働していた」「指示文の数字も測ってから書く」の2件は
**origin 側で既に記録済み**だった（`cca59ff`）。**取り込めていないので手元では0件に見える。**
grep しなければ、同じ内容を別ファイルへもう1本作っていた。

- **★遅れている機で記録を書くときは、先に `origin/main` を grep する。**
  手元の memory に無いことは「まだ誰も書いていない」の証拠にならない
  （[[feedback_one_route_is_not_verification]]「0件は別法で数え直す」の同型）。
- **★他セッションの書きかけを commit / stash して merge を通さない。**
  取り込みは失敗してよい（規範）。**失敗してはいけないのは「遅れていると知ること」の方。**
- ★この機（mini）は担当セッションが常時走るので、**ツリーは慢性的に汚れる＝behind が常態**。
  「今日は特別」ではない。**毎朝この手順を通る前提で書く。**

## ★汚れの1件は「書きかけ」とは限らない ── 機械が毎日置く未追跡ファイルで止まる（2026-09-12）

**★これが3回目**（9/5・9/7 に続く）。**3回とも🔴の理由が違う。** 今回は衝突でも通信断でも
枝分かれでもなく、**未追跡ファイルが1件あることだけ**で取り込みが閉じていた。

```
実測（08:4x・ロビン）
  behind 13 / ahead 1
  git status --porcelain      → ?? data/dashboard_history/2026-09-12.json.gz  ＝ ★1件
  git merge-tree --write-tree main origin/main  → rc=0・衝突出力なし ＝ ★通常mergeなら解ける
  git ls-tree origin/main -- data/dashboard_history/  → ★09-12.gz は origin に無い
                                                        ＝ merge がこの未追跡を踏むこともない
ソース側（bin/vivid-sync.sh）
  :71  DIRTY=$(git status --porcelain | wc -l)   ★未追跡も1件と数える
  :89  ② 取り込みのゲート = [ "$DIRTY" -eq 0 ]    ★1件でもあれば merge を1回も試さない
  :73  ①' 自動確定は「最終更新から60分以上」だけ ＝ ★書かれたばかりの生成物は拾わない
```

- **🔴既存の手順（この上の節・INDEX_仕組み）は「`wc -l` が0件なら自分で merge」と書いてある。
  今日はその判定が 1 を返す。** 手順どおりに読むと「汚れている＝触るな」で止まる。
  **★0か1かではなく、その1件が何かを見る。**

```
その1件の見分け方（先頭2文字で分かる）
  ?? で機械が毎日置く生成物（data/dashboard_history/*.gz 等）  ★merge を止める理由にならない
   M / A など 追跡下のファイル                                  ★誰かの書きかけ。触らない
```

- **★自動確定（①'）は救済策だが、60分ルールがあるので「今まさに書かれた生成物」は拾えない。
  拾えない間、②の取り込みは1回も試されない。** 救済策の穴が、そのまま受信の穴になっている。
- **★SYNC_STATUS.md が毎ターン全AIへ配る原因説明は今も「ローカルに未コミットの変更があり、
  ff-only マージができない」の決め打ち**（`bin/vivid-sync.sh:134` のベタ書き）。
  取り込み方として `git add -A && git commit` を勧めるが、**今日それをやると
  機械の生成物を人の意思で commit したことになる**。正しい一手は `git merge origin/main` だけ。
  → [[reference_stale_premise_daily]]「自動出力に前提を書くなら、判定を毎回やり直す形にする」
- ★直すなら2択 ── ①ゲートを「追跡下の変更だけ」で数える（`git status --porcelain -uno`）
  ②生成物を `.gitignore` へ入れて別経路で残す。**どちらも設計の分岐なので人の判断が要る。**
