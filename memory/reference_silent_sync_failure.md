**`git pull --ff-only` を cron から直に呼んではいけない。** 作業をすればワーキングツリーは
必ず汚れ、ff-only は汚れていると必ず失敗する。つまり **「作業している間だけ受信が止まる」** ―― 
いちばん困るタイミングで止まる構造になる。2026-08-17 に **153回連続の失敗**（≒38時間）を実測した。

```
症状   規範・記憶・WORKING.md は毎ターン確かに届いていた。届いていたのが2日前の版だった
       読む側にそれを知る手段が無く、過去の状態を現在地として答えた
       エラーは ~/Library/Logs/… に463行。誰も見ていない
```

**ログは届く場所ではない。** 見に行かないと分からない場所は、届いていないのと同じ。
[[feedback_reading_list_is_not_a_map]] と同じ構図で、対策を「読む規律」に置くと、
規律が切れた回にだけ効かない。

## 直し方 ── 「取り込む」と「知る」を分ける

```
取り込み（merge）   失敗してよい。作業中に他機の変更が勝手に乗る方が危ない
知ること（fetch）   失敗してはいけない。マージしないので作業中でも必ず通る
```

`bin/vivid-sync.sh`（両機・cron */15）が ①fetch ②遅れ／進みを数える
③`~/.claude/SYNC_STATUS.md` へ書く（`~/.claude/CLAUDE.md` が @import ＝毎ターン届く）
④⚙️自動処理レジスタへ心拍（沈黙すれば🔴）。

- **ahead（自分の変更が他機へ届いていない）も同じ事故を起こす。** 受信だけでなく送信の滞留も出す。
- **🔴が出ている状態で現在地を答えない。** 先に取り込む。取り込めないなら古い版だと明示する。
- 心拍の処理名は完全一致で探されるため、**機械ごとに行を分ける**（同名2行あると更新されない）。

## ★🔴が一晩続く原因は、ほぼ「自分の未コミット」（2026-08-22 実測）

送信は `vivid-sync.sh` が自動でするが、**対象はコミット済みだけ**。書きかけを置いたまま
セッションを終えると、その機は ff-only できず**未取込6件のまま朝を迎える**。
2026-08-22 朝、前日の自己監査が作った memory 6ファイルが未コミットで残り、
mini は6件遅れの WORKING.md / MEMORY.md を「現在地」として読んでいた。

- **★作業の締めは「commit した」ではなく「`git status` が空になった」まで。**
  自己監査・バッチ処理のように無人で回るものほど、置き忘れを指摘する人がいない
- 直し方は捨てるのではなく**確定させて merge**する（[[reference_git_add_all_swallows_others]]
  ── `git add -A` ではなく触ったファイルを明示する）

## 一般化

**「自動で配っている」と「相手に届いている」は別。** 配送経路の存在は鮮度を保証しない。
自動処理レジスタに**その同期自身が登録されていなかった**のが根本 ―― 
他の全自動処理の土台なのに、監視の外にあった。→ [[project_automation_register]]

## ★枝分かれは `--ff-only` では絶対に解けない（2026-08-26 実害）

```
2026-08-25 夜  autocommit_stale.py が mini で発火し、放置1本を commit した（＝ahead=1）
その後         MacBook が先へ進み origin が伸びた（＝behind=11）
2026-08-26 朝  mini は behind=11 / ahead=1 の枝分かれ。
               merge --ff-only は失敗し、push も behind>0 で送れない
               ＝ ★11件遅れたまま孤立し、自力では永久に回復しない
```

**Why:** 「取り込みは失敗してよい」という設計は正しいが、**失敗し続ける状態**が生まれると別問題になる。
`--ff-only` は片方向にしか進めない。**自動確定（autocommit）を足したことで、
自分から枝分かれへ入る道ができていた**（commit はするが push は behind=0 のときだけ、という非対称）。

**How to apply:**

- **★汚れていない（未コミット0）ときに限り、通常の merge を試す。**
  衝突したら `merge --abort` して🔴のまま残す。**勝手に片方を捨てない。**
- **★「失敗してよい設計」には、必ず「失敗が固定化しないか」を確かめる。**
  1回の失敗は許容でも、**同じ理由で永久に失敗し続けるなら、それは設計の穴。**
- 枝分かれかどうかは `git rev-list --left-right --count origin/main...HEAD` の**両方の数**で見る。
  behind だけを見ていると「遅れている」としか分からず、**解けない遅れ**だと気づけない。
