**繰り返す理由は「知らないから」ではない。知っているのに適用しないから。**

2026-08-20 の実例 ── `reference_sheets_number_format_order.md` に
「A列がキーとは限らない」と**自分で書いた2時間後**、40_活動ログをA列で数えて
「2行」と誤報告した（実際は25行）。

```
memory     毎ターン届くのは索引1行だけ。本文は関連しそうなときだけ引かれる
           → 作業中に該当する本文が引かれない
規範       毎ターン全文届く。だが量が多く、適用点で気づかない
```

**書くだけでも読むだけでも足りない。** 有璽氏の言葉：
「作業の時に記録してても、作業の時見てなかったら全く意味ないから」（2026-08-20）

## 3つの穴と、それぞれの機械（`~/.claude/settings.json` の hooks）

| 穴 | 機械 | 実体 |
|---|---|---|
| ① 作業の瞬間に思い出さない | **PreToolUse** | `~/.vivid-relay/hook_inject_memory.py` |
| ② 指摘されるまで記録しない | **UserPromptSubmit** | `~/.vivid-relay/hook_catch_correction.py` |
| ③ 誰も棚卸ししない | 毎朝ロビンが前日を読む | `~/.vivid-relay/memory_sweep.py` |
| （付） 承認待ちが本人に見えない | **PermissionRequest** | `~/.vivid-relay/hook_permission_slack.py` |

**①が本体。** Sheets／Notion／cron／削除／Slack を触ろうとした瞬間に、
**その作業で実際に踏んだ地雷だけ**を `additionalContext` で文脈へ割り込ませる。
★一般論は書かない。実際に踏んだものだけ。書くと読まれなくなる。

**②は作り直した。** 最初の版は「怒り」を検出する作りで、
> 「怒った時だけやりますってなっとるやろうが、それが一番おかしいねん」
と指摘された。いまは「新しい事実・制約・やり方が示された合図」を拾う。
**怒っているかどうかは関係ない。**

  判定は「★差し戻した」「通した」の2値。3分岐すべて実測でログ着弾を確認済み。
  **★例外は握りつぶす。ログの失敗でセッションを止めない。**
- **確かめ方（次に同じ質問が来たらこれを出す）** ── `tail ~/.vivid-relay/hook_writeback.log`
- **★残**：⚙️自動処理レジスタへの行と稼働盤への表示は未着手。
  ログは「見に行かないと分からない場所」＝ [[reference_delivered_but_unread]] の型に当たる。
  **ログを足しただけでは、有璽氏側の観測手段としてはまだ弱い。**

**★一般化 ── 「消えてる気がする」は仕様の指摘ではなく、観測の欠落の指摘。**
まず実測で在否を確定させる。そのうえで、**在ったなら「なぜ見えなかったか」を直す**。

## ★誤爆源の1つを特定した ── バックアップが git 管理下に落ちる（2026-09-03 実測）

**「他セッションの置き土産」の正体の一部は、担当が規範どおり取ったバックアップだった。**

```
規範        「AIが自律で書くなら ①バックアップ → ②実行 → ③実物で照合」（fukuchi-core）
実際の置き場  bin/hooks/findings_tracker.py.bak_pitagorasu_20260903
              bin/hooks/self_audit.py.bak_pitagorasu_20260903
              ＝ ★git 管理下のディレクトリ。untracked のまま残る

実測  .gitignore に .bak 系の除外        0 件
      過去に commit された .bak_ ファイル  0 件
      ＝ 誰も commit しないし、誰も ignore していない。毎回 Stop フックが鳴る
```

**Why:** 規範が「バックアップを取れ」と命じ、フックが「未コミットを片づけろ」と命じる。
**2つの規範が同じファイルに対して逆を要求している。** 担当は両方に従えない。

**How to apply:**

- **★バックアップの置き場を git 管理外に決める。** `~/.vivid-relay/` や `_archive/` など。
  規範で「取れ」と言うなら、**どこへ置くかまで規範が決める**。決めないと毎回ここで詰まる。
- **★あるいは `.gitignore` へ `*.bak_*` を足す。** 1行で慢性の誤爆が1種類減る。
- **★「誰も commit せず、誰も ignore していない」ものが在ったら、それは規範の穴。**
  個人の不注意ではない。**同じ場所に同じものが繰り返し現れるかで見分ける。**

**★決着（2026-09-03 同日中に実行済み）** ── 上の2案のうち**前者を採った**。
`bin/hooks/` 配下でAIが取る控えは全て `~/.vivid-relay/_backups/` へ置く。
`.gitignore` 案は不採用（git 管理下に一時ファイルが恒久的に残る設計を避けた）。
**規則の本体と置き場の一覧は [[reference_backups_in_volatile_places]] にある。ここには二重に書かない。**
★この決着は当日 `WORKING.md` にしか書かれておらず、**このファイルは翌朝まで「2案が未決」の
まま置かれていた。**直した側は直したつもりでも、**読む側には未決に見える**
→ [[reference_verify_outcome_not_mechanism]]（「記録は書かれたが直っていない」の裏返し）。

## ★担当が黙って止まるのを、機械で見張る（2026-09-03 有璽氏の指示）

> 「**私が確認しなくても動き続けるように**指示を出してください。**止まっていたら確認チェックが入る**ようにもしてください」

**★止まる原因は担当ではなく、窓口が作った往復だった。**
```
ビビの指示   「区切りごとに返してください」
起きたこと   ★担当は区切りで返して停止。次を渡すまで動かない
             ビビは「作業中」と思い込み、90分気づかなかった
             → [[feedback_stop_asking_just_do_it]]（「次に進めます」で終わった担当は止まっている）
```

**直し方は2つ。片方だけでは足りない。**
```
① 止まり方を変える   ★「区切りで返せ」をやめ、「最後までやり切れ」に変える
                     止まってよい分岐（消す/PC幅を変える/原本のデザイン/本番に触る/
                     写真の割り当て/数字が大きく食い違った）を★列挙して渡す
                     ＝それ以外は自分で決めて進む
② 止まったら鳴らす   ★規律ではなく機械。成果物ディレクトリの最終更新を見て、
                     10分間まったく更新が無ければ通知して終了するプロセスを回す
```

**★①だけだと、止まったことに気づけない。②だけだと、止まる回数が減らない。**
「動き続ける」と「止まったら気づく」は別の対策で、**両方要る。**

★実装の注意 ── **Monitor は権限で通らなかった**（don't ask mode）ので、
`Bash` の `run_in_background` で「条件が成立したら exit する」形にした。
**exit した時点で呼び出し側へ通知が返る**ので、1回の停止検知として機能する。
**★1回鳴ったら、また立て直す。** 立てっぱなしにできる形ではない。

### ★立てた見張りが即座に鳴った ── 「まだ始まっていない」と「止まった」の区別（2026-09-03）

上の停止検知を立てた**瞬間に発火した。** 実害はないが、設計が甘かった。

```
仕掛け   「直近10分に更新されたファイルがあるか」を60秒ごとに見る
起きたこと ★指示を出した直後は、当然まだ何も更新されていない → 即座に「停止」と判定
```

**★「動いていない」には2種類ある。**
```
まだ始まっていない   指示を出した直後・立ち上がり中   → ★鳴らしてはいけない
止まった            動いていたのに更新が絶えた       → ★鳴らすべき
時間の窓だけでは、この2つが同じに見える
```

**対処＝猶予（grace）を入れる。** 見張りの起動から15分は鳴らさない。
以降、12分間無更新なら鳴る。
```
START=$(date +%s) …  [ $((now-START)) -le 900 ] && continue
```
**★閾値を1つ決めただけの検知は、立ち上がりで必ず誤爆する。**
「時間が経った」と「状態が変わった」を混ぜない。
→ [[feedback_one_route_is_not_verification]]（対照実験・ノイズ床の話と同じ形。
**基準を決める前に、正常な状態がどう見えるかを見る**）

### ★「更新が止まった」と「止まっている」は違う（2026-09-03・見張りの3回目）

停止検知が3回目に鳴った。**3経路で確かめたら、食い違った。**

```
経路1  直近20分の更新件数     1件
経路2  最新の更新             21:06（いま21:24）＝★18分前
★経路3  プロセス               ★php 8750 が LISTEN ＝ 測定サーバが動いている
```

**★長い処理の最中は、ファイルを書かない。** 測り終わってから書く。
だから**「ファイルが更新されない」＝「止まっている」ではない。**

```
❌ ファイルの更新だけで判定   → ★長い処理を「停止」と誤判定する
✅ ★ファイルの更新 or プロセスの生存 のどちらかがあれば「動いている」
   両方無くなって初めて「止まっている」
```

**★見張りの3回とも、原因が違った。**
```
1回目  「まだ始まっていない」と「止まった」を区別していなかった → 猶予を入れた
2回目  ★find の書き方が壊れてエラーを空に倒していた           → -mmin へ
3回目  ★長い処理の最中を「停止」と誤判定した                   → プロセスも見る
```
**★検知の仕組みは、作った直後がいちばん誤報を出す。**
「正常な状態がどう見えるか」を、**種類ごとに**知るまで精度が上がらない。
**★誤報のたびに実物を3経路で確かめたから、毎回1つずつ穴が埋まった。**
鳴ったら止めるのではなく、**鳴るたびに確かめて直す。**

### ★停止を拾う経路は3本あった（2026-09-03・実地で判明）

担当が止まったのを**3つの別の経路が拾った。** どれも他の2つを代用できない。

```
① ★ハーネス自身の watchdog   「600秒 無進捗」で failed を返した
                            ★こちらが何も作らなくても効く。★いちばん確実
② こちらが立てた見張り        成果物の更新＋プロセスの生存を60秒ごとに見る
                            ★3回鳴いて3回とも原因が違った（＝調整が要る）
③ ★有璽氏                    「再開しておいてね。★止まってる気がするから」
                            ★人がいちばん早いことがある
```

- **★①が在ることを知らずに②を作った。** 先に数えていれば、②の設計は変わっていた
  （②は「①では拾えないもの」＝**進捗はあるが意味のある前進が無い状態**を見るべきだった）。
  → [[feedback_check_the_archive_first]]（型を作る前に数える）
- **★③が鳴るのは、①②が遅いか、届いていないということ。** 人に言われたら、
  **その前に鳴るはずだった仕組みがなぜ鳴らなかったかを見る。**
  今回は②が「プロセスが生きている」で見送っていた間に、担当は実際に止まっていた
  ＝**プロセスの生存は、前進の証拠ではない。**
- ★中断時の後始末（`finally` でサーバを止め、走査結果を出す）は**実地の中断で試されて通った。**
  「置き去りゼロ」を2経路で確認。**今日ずっと直してきたところが、本番で効いた。**
