# `OUT="$(func)"` の中で `exit` を呼んでも、スクリプト全体は止まらない

**2026-09-07 実測（`bin/kadoban_deploy.sh` に詰まり対策のタイムアウト＋リトライを入れた際）。**

## 症状

```bash
deploy() {
  ...
  if [ 2回連続でタイムアウト ]; then
    notify_stuck "..."
    RESULT="失敗"
    exit 1   # ★ここで止まるつもりだった
  fi
  ...
  echo "$url"
}

OUT="$(deploy)"   # ★コマンド置換＝サブシェルで deploy() が動く
log "deploy: ${OUT}"
sleep 8
...
```

**`deploy()` の中で `exit 1` を呼んでも、スクリプト全体は続行してしまう。**
詰まり通知（Slack）は正しく送信されるのに、その後の `sleep 8`・`probe()`・
プレースホルダ判定まで全部実行され、最終的に **rc=0 で正常終了する**。
実測：隔離環境で2秒タイムアウト×2回を発生させたところ、通知は届いたが
`rc=0, 実測経過秒=15` ── 本来 rc=1 で7秒前後に止まるはずが、最後まで完走した。

## 原因

`$(...)` は**サブシェルで実行される**。サブシェル内の `exit N` は、そのサブシェルを
終了させるだけで、`exit N` を呼び出したプロセス（＝コマンド置換を評価している親シェル）
には一切影響しない。`OUT="$(deploy)"` は「deploy() の標準出力を OUT に代入する」という
一つの式でしかなく、deploy() の中身がどう終わろうと、親シェルはその次の行へ進む。

同じ理由で、サブシェル内でのグローバル変数への代入（例: `DEPLOY_STUCK=1`）も
親シェルには伝わらない。「関数の詳細な結果をグローバル変数で受け取りつつ、
異常時は exit で止める」という設計は、その関数をコマンド置換で呼んだ瞬間に壊れる。

## 対処

**「詰まったら止める」を実現したい関数は、コマンド置換 `$(...)` で呼んではいけない。**
戻り値（`return`）で成否を伝え、値は別のグローバル変数（コマンド置換を介さない）で
受け渡す形にする。

```bash
DEPLOY_URL=""   # ★グローバル。関数はここへ代入する

deploy() {
  ...
  if [ 2回連続でタイムアウト ]; then
    notify_stuck "..."
    DEPLOY_URL=""
    return 1        # ★exitではなくreturn
  fi
  ...
  DEPLOY_URL="$url"  # ★echoではなくグローバル変数へ代入
  return 0
}

if ! deploy; then     # ★通常の関数呼び出し。ifの条件式でも$?がそのまま親に伝わる
  RESULT="失敗"
  exit 1               # ★ここは親シェルなので実際にスクリプトが止まる
fi
OUT="$DEPLOY_URL"
```

## 教訓

- **「詳細な戻り値が要る」と「異常時に exit したい」は同居できない設計がある。**
  `$(...)` で値を受け取る関数は、内部で exit しても effectively 無視される。
- 修正後は必ず「詰まりを実際に発生させて rc を見る」実測を通すこと。
  ログの文言（通知が出た・NGログが出た）だけでは「止まった」ことの証明にならない。
  今回も通知は正しく出ていたため、一見成功に見えた。**rc と実測経過秒を必ず見る。**

## 関連

- `bin/run_with_timeout.py`（macOSのbash/zshに`timeout`が無いための代替。
  `os.setsid()`+`os.killpg()`でプロセスグループごと確実に殺す）
- 同じ作業で、`vercel env ls` も `vercel deploy` と同様に詰まりうることが実測で判明した
  （依頼文は deploy のみを想定していたが、隔離テストで env ls がハングした）。
  詰まりうる外部コマンド呼び出しは、依頼で名指しされた1箇所だけでなく、
  同じ関数群の中で似た形の呼び出しを横断的に洗い出すこと。
- 隔離テストでダミーコマンドに差し替える際、**PATHの並び順に注意**。
  `kadoban_deploy.sh` は `PATH="/usr/local/bin:...:$HOME/.npm-global/bin:$PATH"` と
  再構築しており、本物の `npx` が `/usr/local/bin` に既にあると、`$HOME/.npm-global/bin`
  に置いたダミーは使われない。本物のVercel CLIが未認証状態だとdevice認証フローに入って
  ハングする（実際に2回踏んだ）。この型のテストでは、外部コマンド自体を環境変数で
  差し替え可能にしておく方が安全（`VERCEL="${KADOBAN_VERCEL_CMD:-npx --yes vercel@latest}"`）。
