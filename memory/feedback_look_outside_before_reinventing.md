**同じ種類の失敗が繰り返されたら、次の対症療法を考える前に「これは業界で名前のついた
問題か」を先に調べる。** 自社だけがぶつかっている特殊な問題だと思い込まない。

**Why:** 2026-09-08、有璽氏「お前だけで考えんな。他で同様の事例が起こってると思われる
ので、我々だけの、弊社だけの課題ではないと思う。他社がどうやってるのか、確認させろよ」。
背景：mini上の非対話AIエージェント（`claude -p`）が「完了通知を待ちます」と書いて実際には
何も待たずに終了する事故が3日間で複数回発生し、その都度「その言い回しを検知する」という
対症療法を積み重ねていた（→ [[reference_two_sessions_built_the_same_thing]] や
stall_watch.py 系のパッチの繰り返し）。言い回しを変えられるたびに再発しており、
根本設計（完了判定・冪等性・durable execution）を外部の知見と照合していなかった。

**How to apply:**
- 「同じ型の事故が2回以上起きている」「毎回パッチで塞いでいる」状態に気づいたら、
  実装を続ける前に一度立ち止まり、クローバー博士（researcher）へ外部調査を投げる。
  - 探すべき問い：この問題は業界で名前がついているか（例：agent early termination /
    durable execution / dead man's switch / idempotency）。一次資料（公式ドキュメント・
    論文・実装ソース）に当たり、又聞きのブログで断定しない。
- 自前の構造（cron・シェル・非対話AI・Slack通知）を変えずに今日から効くものと、
  作り直しが要るもの（ワークフロー基盤の導入等）を分けて提案してもらう。
- 詳細な調査結果は `~/.vivid-relay/clover_agent_supervision.md`（2026-09-08）を参照。

## 🔴2026-09-13 ★2回目 ── 会議室を自分の頭だけで組み立てていた

> 「この画面上でAIやAIエージェントの動きを把握しようっていう話をしているのに、
>  **それがちゃんと反映されてないと全く使えないよね**っていう話なんで。
>  で、実際こうやって**AI社員の会議室**とかって言ってやってる取り組みが、
>  **多分いっぱいあると思うので、それを一回確認して、あなたの頭だけで考えずに。
>  調べた上で作ってください。**」

**★1回目（2026-09-08「お前だけで考えんな」）と同じ型。★今度は画面の設計で踏んだ。**

```
こちらがやっていたこと
  外部LPのスクショを1枚見る → ★そこから自分で組み立てる → 差し戻し（9/12 見た目）
  → 直す → また差し戻し（9/13 中身が反映されない）
  ★2回とも「実装の細部」を直しただけで、★設計の出どころを外に取りに行っていない
★有璽氏の指摘の本質
  「ちゃんと反映されてないと全く使えない」＝★これは機能の優先順位の話
  ★動いているものが動いていると出ること が、他の全機能より先に来る
  （立ち絵・タブ・レイアウトは、そこが出てから）
```

**★この分野には先行事例が実在するはず、という前提で探す。**
うちの14体は珍しい規模だが、**「エージェントの稼働を人が見る画面」自体は一般的な題材**。
**★先に名前を数える。**無いと分かってから自前で組む。

- **★「実装が壊れていた」と「設計が自前だった」は別の問題。**
  今日 `ps -eo etimes` を直したのは前者。**後者はまだ手つかず**だった。
  実装の穴を直しても、**出す項目そのものが妥当かは一度も外と突き合わせていない。**
- **★調査の出口は「取り入れる点」まで。**用語の一覧を持ち帰っても設計は決まらない。
  → [[feedback_coverage_over_citation_when_asked_to_enumerate]]（網羅は件数優先・数値だけ出典必須）

### ★同じ日に、調査の投げ方そのものを直された

> 「クローバーが調べるべきは、**そもそもAI会議室をどうやって構築してんねん**っていうのを
>  調べさせて、そこも含めてかな。**今起こっている事象だけを調べさせても、根本的な解決に
>  ならない気がする**んで、今の起こっている事象も調べてもいいけど、**そもそもどう構築
>  してんのっていうところを調べて。**」

**★こちらが投げた依頼文が「症状の周り」だけだった。**

```
こちらが聞いていたこと（＝★今日壊れた場所の周辺）
  ①先行事例の名前 ②走行中をどう判定しているか ③判断待ちの見せ方 ④画面の項目
  → ★全部「画面に何を出すか」の話。★土台の作り方を1つも聞いていない
有璽氏が聞けと言ったこと
  ★そもそも、どう構築しているのか
  ＝実行基盤・状態の持ち方・エージェント間の受け渡し・記憶の置き場・人との接点の設計
```

**★いま壊れている場所を起点に調べると、いま壊れている場所しか直らない。**
今日の `ps` の件がまさにそれ ── **「走行中をどう数えるか」を上手にする**話に見えていたが、
**そもそも「外から ps で推測する」という作りが妥当か**を一度も問うていなかった。
（実行基盤が状態を持つなら、数えに行くこと自体が筋の悪い設計になる）

- **★調査は「症状」でなく「そもそも」から投げる。**症状は後半に置く。
  順番を逆にすると、**出てきた答えが今の作りを前提にしたものだけになる。**
- **★自分の設計を疑う質問を、依頼文に必ず1つ入れる。**
  「うちは○○という作りだが、外も同じ作りか。違うなら何が違うか」。
  これが無いと、**調査が今の作りの補強にしかならない。**
