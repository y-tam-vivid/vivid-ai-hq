**正本を書き換える前のバックアップを、セッションの scratchpad に置いてはいけない。**

fukuchi-core は「**★『取った』と『戻せる』は別物。取れているかを確認するまでが復帰経路**」と定める。
**消える場所に置いたバックアップは、この条件を最初から満たしていない。**

## 実際に起きたこと

```
2026-08-23   scratchpad/press-release-drafts.html を控えとして頼りにしていた
             → ★scratchpadごと存在しなかった（揮発済み）。控えのArtifactも認証壁で読めず
             → 一次資料から新規に組み立て直すことになった

2026-09-03   ナミが Notion 法人マスター（組織軸の正本）を書き換える前のバックアップを
             session の scratchpad へ保存した。読み返しての確認までは正しく行っていた
             → ★置き場だけが誤り。ビビが ~/.vivid-relay/ へ複製して復帰経路を成立させた
```

**★2026-09-03 は「手順は守られていたのに、置き場だけで無効になる」型。**
バックアップを取り、読み返して中身も確かめた。それでも消える場所にあれば復帰経路ではない。

## 置き場（両機で同じ）

```
◎ ~/.vivid-relay/          既存のバックアップはここ（backup_customer_db_*.json 等）
◎ ~/gas-backup/            GAS の本番バックアップ
◎ Google Drive             99_バックアップ（営業ワークブック）
✕ session の scratchpad    ★セッションが終われば消える。控えにならない
✕ /tmp                     同上
```

- **★scratchpad は「作業の途中の紙」であって「戻すための控え」ではない。** 用途が違う。
  下書き・中間生成物・検証用のスクリプトはここでよい。**正本の写しだけは別。**
- **★復帰経路を作れる操作（データの変更）では、置き場まで含めて1セット。**
  作れない操作（送信・公開・課金）とは扱いが違う → fukuchi-core「不可逆な操作の前は」。
- ★サブエージェントへ書き込みを頼むときは、**バックアップの置き場を指示に明記する。**
  「バックアップを取れ」だけでは scratchpad へ置かれる（2026-09-03 実測）。

## ★バックアップに入っていないものは、検査もできない（2026-09-03 つるの指摘）

同じ日、つるが検査に入って**バックアップの中身の不足**を見つけた。

```
保存していた   列の名前・型・選択肢          → ★突合できた
保存していない  ★列の並び順                  → ★「変わっていない」と断定できなかった
```

- **★「変わっていないこと」を後から言うには、変わりうるものを全部保存しておくしかない。**
  名前と型だけ保存して並び順を落とすと、並び順の事故だけ検査の外に出る。
- **Notionの formula 列は SQL経由で値が取れない**（`notAvailableInQuerySql`）。
  機械で検証する経路を作るときに踏む。**検査できない列がある**ことを前提に置く。

### ★同じ日に3回、同じ形で穴が開いた ── **足りないものを毎回1つずつ足していた**

```
v1   名前・型を保存        → ★並び順が無く、並び順を検査できなかった
v2   並び順を足した        → 並び順は検査できた
v3   名称のみ保存          → ★内部IDが無く、選択肢の作り直しを検査できなかった
```

**★「前回足りなかったものを足す」を繰り返している限り、次の回もどこかが足りない。**
穴の位置が毎回変わるだけで、構造は同じ。

- **★対処＝選んで保存しない。スキーマの応答をまるごとJSONで落とす。**
  「何が要るか」を書く側が判断した時点で、判断しなかったものが検査の外に出る。

### ★★「まるごと保存して」と指示したのに、v4でも守られなかった（同日・4回目）

上の対処を書いた直後、ビビはナミへ **「バックアップは v4 として★スキーマの応答をまるごと保存すること」**
と明示して指示した。**それでも v4 に option の内部IDは入らなかった**（name/color/description のみ）。
つるが「v3の弱点は v4 でも未解消」と実測。

```
★原因は指示の言葉。「まるごと」は抽象語で、書く側の解釈に委ねられる
  → 書く側は「見えている項目は全部書いた」と思っている。★本人には漏れが見えない
★対処＝保存してほしいものを名指しする
  ✕「スキーマをまるごと」        ◎「option の内部ID（collectionPropertyOption://…）を含めて」
```

- **★規範に書いても、抽象語のままでは次の実行で守られない。** → [[feedback_write_for_the_reader]]
  （抽象語で指示すると伝わらない）／[[reference_delivered_but_unread]]（記録はあったが効かない）。
- **★同じ日に、同じ穴を4回。**穴の位置が毎回変わるのではなく、**指示の粒度が毎回足りていない。**
- あわせて **v4 の `note` 欄に「既存9つ」と書きながら配列は10件**という数え違いもあった（実害なし）。
  **数を記憶で書いて、配列と突き合わせていない**型 → [[feedback_never_write_an_unmeasured_number]]。
- ★同日、Notion の select リネームが**内部IDを変える**（実質は作り直し）ことが分かった。
  **名称だけの控えでは、この事故を後から検出できない。**
  → [[reference_dangerous_entrypoints]]（名前から挙動を推測しない）。
