**2026-09-14〜15、★別々の案件で同じ型を2回踏んだ。**
どちらも「データは入った」を読み返しで確認できていた。**出なかったのは表示の側。**

```
入れる経路   API／スクリプト   … ★渡した値しか書かない
入れる経路   管理画面のUI      … ★渡した値＋周辺の値を一緒に書く（保存フックの副作用）
表示の側     ★後者が書いた値を条件にしている
```

## 実例1 ── オレンジワークス work 42件が一覧に1件も出ない（2026-09-15 実測）

```
真因（リリスが公式配布zipのソースで特定）
  work の一覧クエリは★無条件に meta_key=_exclude_in_works_list / meta_value=off を付ける
  （apollo13-framework-extensions post-list.php:336-340 ／ テーマ works-list.php:38-46）
  このメタはテーマの★管理画面保存（save_post＋nonce必須）でしか書かれない。register_meta も無い
  ＝ ★REST で作った work は永久に一覧から漏れる
実測で確定  14103 を管理画面で1回保存 → 公開 → /works/ にサムネイル付きで1件並んだ
            条件は「meta off」AND「公開」の2つ
```

**★画面は半分だけ正しく動いた。** 絞り込みのフィルタ欄には分類（「イラスト」）が出ていた。
`get_terms` は別系統でメタを見ないため。**「一部は出ている＝経路は生きている」と読むと真因を外す。**

## 実例2 ── LIFE STAND UP 本番21ページが崩れた（2026-09-14）

`page-setup.php` が投稿メタ `_lsu_source` を落とした。テーマはこのメタから
どの原本のページかを決めていたので、トップ以外の21ページが全部崩れた。

**★このとき通った検査**：HTTP 200 ／ リンク83本の生存 ／ 本文に固有の語が在る。
**1件も検出できなかった。** → [[reference_verify_outcome_not_mechanism]]

## 次に同じことをする人へ

- **★投入する前に、表示側のクエリを読む。** `meta_key` / `meta_query` / 条件付きの分岐が
  何を前提にしているかを数える。ここを読まずに入れると、入れ終わってから気づく。
- **★`register_meta` が無いメタは API から書けない＝UI専用**。存在を知る手がかりになる。
- **★最短の検出法は「1件だけUIで作り、APIで作った1件とメタを全部並べて差分を取る」。**
  ソースを読むより速い。差分が出たものが、UIが暗黙に書いている値。
- **★投入スクリプトの完了条件を「入った」で終わらせない。**
  「表示側の条件を満たしたか」までを1つの工程にする。
  （work の場合 ＝ ★REST で足したら、管理画面で保存し直すまでが投入）
- **★「読み返して入っている」は2経路にならない。** どちらも入れた側の経路。
  もう1経路は★出る側（未ログインで実際に一覧を開いて数える）。
  → [[feedback_one_route_is_not_verification]]

★隣の型：直した場所と配られる場所が違う → [[reference_fix_where_git_reaches]]
