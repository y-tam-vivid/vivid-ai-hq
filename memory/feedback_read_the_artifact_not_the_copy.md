**シート・DB・ファイルの存在や中身を述べる前に、その場で実物を読む。写しで代用しない。**

**Why**：2026-08-12の1セッションで3回、既に決まっていた・既に存在していたことを「無い」「未実施」と報告した。田村さんから「前に実施したことを覚えていない状態なのはすごく困る」と指摘を受けた。記録は存在していた。読まなかった、または写しを読んだのが原因。

失敗の型は3つとも同じで、**実物ではなく派生物を信じた**。

```
打ち切られた書き出し   Driveの read_file_content は1シート約86行で切れる
                      → 後半のシートが欠けたのを「存在しない」と誤認
ソースのコメント       .gs のコメントは書かれた時点のスナップショット
                      → 「未照合」と書いてあったが、同じ日に照合済みだった
自分の過去の記録       ⑥ログにもメモリにも書いてある決定に矛盾する提案をした
                      → 読んだうえで矛盾させた。注意不足
```

**How to apply**：

- 存在確認は必ず実物で。GASで `getSheets()` を回す、ファイルを直接開く。**書き出しの欠落を「無い」の証拠にしない**
- 「未実施」「無い」「されていない」と書く前に、一度立ち止まって根拠が実物かを確かめる。派生物ならそう明示する（「〜の記録では」と書く）
- 着手前に読む正本の一覧を持つ（この案件では [[project_sales_workbook_read_first]]）
- **同じルールが複数箇所にあると必ずずれる。** データで繰り返し学んだことは、ルール文書にも当てはまる。正本を1つ決め、他はリンクと差分だけにする
- 決定は経緯の文章に埋めず、1決定1行で引けるようにする

関連: [[project_sales_workbook_read_first]] [[project_notion_operating_rules]] [[reference_kintone_lookup_is_a_copy]]

## ★指摘の「出典」を確かめる ── 腐っているのは別の場所かもしれない（2026-08-20 実測）

営業へ渡す検査で、デザイン側が
「`94_営業の使い方` に『08はA/D/I/L』と書いてあるが実態と違う」と指摘した。

**★94 にその記述は無かった。** 実際に古かったのは **Skill `sheets-access` の78行目**。

```
指摘された場所   94_営業の使い方（人が読む手順書）
本当に古い場所   Skill sheets-access（★AIが読む側）
```

- **「実態と違う」と言われたら、まず**どこに**書いてあるかを grep で確かめる。**
  出典を確かめずに直すと、**腐った側が残ったまま**になる
- **★AIが読む側（Skill・memory）も腐る。** 人が読む手順書だけを直しても、
  次にAIが作業すると同じ古い前提で動く
- 今回は 08 の手入力列が「A/D/I/L」→ 実測「A/D/E/F/G/H/N」だった。
  **この古い情報のまま作業していたら、書くべき列を3つ落としていた**

## ★依頼文の「欄の名前」も写しである（2026-08-23 実測）

「**手段**の欄へ Chatwork を立てて、文章は**社内メモ**へ移す」という依頼を受け、
実物を読んだ。**その名前の欄は無かった。**

```
依頼の語        実物（2026-08-23 実測）
手段            40_活動ログ にその列は無い。近いのは「活動種別」
                90_選択肢マスタ の 活動種別＝訪問/TEL/メール/オンライン/
                フォーム返信/資料送付/その他 の7値。★Chatwork は無い
社内メモ        営業ワークブックに存在しない。40の本文欄は「内容」
                「社内メモ」は受付シート側のアラート欄として1箇所あるだけ
Chatwork        ★Notion 📨コミュニケーションログDB の「チャネル」には
                既に選択肢として在る（LINE/Messenger/メール/電話/Chatwork/Slack/その他）
```

- **欄名が一致しないまま着手すると、書き先が3通りに割れる**
  （活動種別へ足す／Notionチャネル＝既に在る／受付シートの社内メモへ移す）。
  どれを選んでも「言われたとおりにやった」と言える。**それが一番危ない形。**
- **★「無い」と言うためではなく、「どれか」を確定するために実物を読む。**
  名前のズレは誤記とは限らない。→ [[feedback_dont_call_it_a_typo]]
- 選択肢を1つ足す作業は 90_選択肢マスタ を直して終わりではない。
  読み書きする全経路の追随確認まで含めて1作業 → [[reference_hardcoded_option_lists]]

## ★★「その欄は無い」で止まると、隣の列にある実物を見落とす（2026-08-23 つる）

上の節を書いた2体は、どちらも **G列「連絡が取れる手段」だけ**を読み、
「Chatwork は0件・文章の混入も0件＝直す対象データが無い」と結論した。**誤り。**
**隣の H列「連絡先」に実物が4件あった**（受付シート・2026-08-23 実測）。

```
r19  手段=空          連絡先='チャットワーク'                    台帳登録=登録済み
r27  手段=空          連絡先='チャットワーク'                    未登録
r28  手段='電話, メール' 連絡先='チャットワーク交換予定、スラックも可能性あり'  未登録 ←★これが「文章」
r29  手段='電話'      連絡先='チャットワーク　メイン'（全角空白）  未登録
```

**有璽氏の依頼はこの4行を指していた。** 選択肢に Chatwork が無いから、
営業が**手段を連絡先欄へ書いた**。依頼文の「手段の欄」は列名ではなく**用途**を指していた。

- **★「欄名が無い」は調査の結論ではなく、調査の入口。**
  名前で一致しなかったら、**その用途の値がどこへ流れ込んでいるか**を探す。
  探し方は列名ではなく**値**（今回は "チャットワーク|hatwork" を全シート全セルへ）。
- **★対で使われている列は対で読む。** `intake_register.py:290` は
  `split_contacts(手段, 連絡先)` と**両方**を引数に取っている。
  片方だけ読んだ時点で、コードが対にしている前提を破っている。
- **サイレントに落ちている。** この4行を `split_contacts()` に通すと全件 `([], [])`。
  電話・メールに化けないのは良いが、**唯一の連絡手段が台帳へ1文字も渡らず、
  社内メモへのアラートも出ない**（r19 は登録済みなのに社内メモが空）
  → [[reference_silent_rejection_backlog]] [[reference_log_needs_an_exit]]
- 2体が独立に同じ見落としをした。**同じ写し（G列）を2回読んでも検算にならない**
  → [[feedback_one_route_is_not_verification]]

## ★「安全弁が4点ある」と数えた申告が、実物と1点ずれた（2026-08-23 ロビン・自分の誤り）

Slackの受け口を調べ「STOP_WORDS／**flock**／DMのみ／心拍の4点で守られている」と束ねて出した。
検査役の実測で **`slack_inbox.py:186-194` は pidファイル方式**、`flock(2)` は1箇所も無いと判明。

- **数えた安全弁は、1つずつ行番号を添えられるときだけ「実測」と書ける。**
  4点のうち3点を実物で見て1点を通り名で埋めると、**申告全体が実測の顔をする。**
- 同じ回に、時刻を「ログ 13:02」と書いた別の体も誤った（**ログにタイムスタンプは1行も無い**。
  実際は state.json の mtime からの推定）。**推定なら「推定」と書く**
  → [[feedback_never_write_an_unmeasured_number]]
- **★束ねる役ほど危ない。** 束ねた文は各担当の所見より上位に見えるので、
  そこへ混ざった通り名は誰の検算も受けずに決定の根拠になる。
  → [[feedback_one_route_is_not_verification]] [[reference_slack_tokens_and_socket_mode]]
