# 名前が決まっていないものは、識別子に名前を入れない

**2026-10-08 有璽氏**：「クロードAI側と話をして、設計担当側と話をして、**いまこのシステム、アプリの名称を決めています。**また後ほど共有します。」

```
★名称が未確定のあいだに、仮の名前を★識別子（機械が照合する側）へ入れると、
  決まった瞬間に「全部直す／直さないと動かない」になる。
★説明文（人が読む側）に入っているぶんは、置き換えるだけで済む。
```

## 実測 ── この案件はどうだったか（2026-10-08・仮称「家計台帳」で数えた）

| どこ | 出現 | 決まったら |
|---|---|---|
| `memory/` 18ファイル | 125回 | ★説明文だけ。経緯なので**直さない**（当時の呼び名が正） |
| Core_Brain `00_System/`（毎ターン届く） | 38回 | ★Current_Focus の生きた行だけ置き換える |
| mini の道具 5本の**説明文・docstring** | 14回 | ★置き換える |
| 道具の**ファイル名** | **0件**（`crm_*` `_crmsend.sh` 等） | ★直さなくてよい |
| **キーチェーンの項目名** | **0件**（`vivid-crm-dev-send` 等） | ★直さなくてよい |
| **環境変数名** | **0件**（`CRM_SEND_KEY` / `CRM_READ_KEY`） | ★直さなくてよい |
| **窓口のURL・JSONの項目名** | **0件**（`crm-persons` / `c_id` 等） | ★相手の持ち物・直さない |

★**たまたまではなく、結果的に正しい形になっていた。** 識別子は全部「CRM＝営業台帳側から見た役割」で付いていて、
相手のアプリ名を1つも含んでいない。**だから名称変更の費用は「説明文14回」だけ。**

## だからこうする

- **★識別子には「役割」を入れる。「相手の商品名」を入れない。**
  ファイル名・環境変数名・キーチェーンの項目名・DBの列名・JSONの項目名・cronの行・ログのファイル名
- **★人が読む文書には遠慮なく呼び名を書く。** 置き換えるだけなので安い
- **★名称が決まる前に「正式名です」と書かない。** 仮称だと分かる形（「いまの呼び名」）で書く
- **★決まったら、まず数える。** どこに何回あるかを出してから置き換える（上の表の形）

→ 同じ考え方：[[reference_sales_drive_folder_naming]]（フォルダ名の規約）／
  [[project_agent_naming]]（担当の名前）／[[reference_apps_script_name_collision]]（名前の衝突）

## ✅2026-10-08 続き ── 名前が決まった。予測どおり「表示名だけ」で済んだ

正式名称「**家計のみとおし。**」（★末尾の句点まで名前）に決定。有璽氏の指定はこうだった。

```
★変える    画面に出る表示名だけ（★1か所の定数 APP_NAME で持つ）
★変えない  リポジトリ名・コードの変数名・設計書の呼び名（家計台帳／kakei-daicho）
★変えない  招待メールの送信者名・件名・プライバシーポリシーの名称（★商標の確認が済むまで）
```

★**作り手の側から見ても同じ結論だった。** 「識別子は役割で付け、表示名は1か所に集める」形にしておけば、
名称変更は★定数1つの書き換えで終わる。**こちら側（営業台帳）の置き換えは0件で済んだ。**

- ★**数えておいたから、決まった瞬間に「直さなくてよい」と判定できた。** 数えていなければ探すところから始まる
- 🔴**末尾の句点は名前の一部。** 「株式会社ふくち。」と同じ型。★照合・検索・ファイル名で落ちやすい
- ★**商標の確認が済んでいない名前を、外へ出る場所（メールの送信者名・件名・規約）に先に入れない**
