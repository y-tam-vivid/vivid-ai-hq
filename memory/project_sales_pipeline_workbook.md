## ★人に渡すときの障害は、データの正しさではなく「入力の手数」（2026-08-20 実測）

営業へ渡す前の検査で、デザイン側から出た結論。

```
電話先を知る   09タブ → ①/⑤欄            2手
会社を引く     00タブ → Ctrl+F            2手
★記録する     40_活動ログへ切替 → 末尾行を探す
               → **社内顧客ID(B-####)を手入力**（プルダウン・入力規則ゼロ）
               → 00で事前に番号を調べる必要がある
               → 残り6列も手入力。実質5手以上。**ID誤入力への警告なし**
```

**★記録が重いと、誰も書かなくなり台帳が死ぬ。**
読む側（引く・探す）を整えても、**書く側が重ければ台帳は更新されなくなる。**

- **渡す前に「いちばん頻度の高い操作」が何手かを数える。** 見た目のきれいさより先に見る
- **手入力のキーには入力規則を付ける。** 誤入力に警告が出ない列は、必ず汚れる
- → [[reference_sheets_checkbox_format_creep]]（キーが壊れると後から入った行が全部ずれる）

## ★手順書が2つある ＝ 営業は矛盾した説明を読む（2026-08-23 実測）

```
94_営業の使い方           営業案件管理ワークブック内・49行・2026-08-18作成
受付シートの「使い方」タブ  📥営業 受付シート内（別ファイル）
```

**どちらも古く、どちらも同じこと（営業が何をするか）を説明している。**
94 は「受付フォームはマスタへの自動取込はまだ・当面は手で足す」という**5日前の実態**のまま。
受付シート側は「紫4列は当方処理欄」としか書かれておらず、
**照合結果・確認列の説明が抜けている。**

- **★説明する文書を2つに分けた時点で、二重管理が始まっている。**
  片方だけ直すと、営業は矛盾した2つを読む
- **★入口ごとに手順書を作らない。** 営業から見れば「1つの仕事」であって、
  受付シートとワークブックは実装の都合にすぎない
- 直すなら **どちらを正本にするかを先に決める**。
  もう片方は「◯◯を見てください」の1行だけにする（→ 規範「ミラー側では編集しない」）

### いまの94とのズレ（実測4件）

```
① 受付フォーム経由の照合・確認フローが丸ごと未記載
   実際は 即時1行 → 翌朝07:20 照合 → 候補がある行だけ確認 → 翌朝07:25 台帳へ
② 反映までの所要時間が書かれていない
   ★これが無いと「送っても反映されない」と誤解される
③ 名刺の入口が古い（「手で足す」→ 実際はフォームの名刺データ欄へ添付）
④ ★「確認が要る行」と「何もしなくてよい行」の見分け方が無い
   実測 28行中 要確認は3行だけ。残りは「登録済み。照合は不要」で放置してよい
```

**★営業がいちばん詰まるのは「確認」欄。** 入力規則が strict でないため
3択以外も打ててしまい、自由記述で答えると機械に拾われない。
手順書で **「○ 同じ人／× 別人（新規でよい）／保留（分からない）」の3つだけ** と明記する。

## ★営業ルールの正本は Notion の公開ページへ寄せる（2026-08-23 有璽氏）

有璽氏の方針 ── 「営業にはNotionで共有するのが望ましい。公開ページの形にして、
等しくルールが溜まっている状態を作る。間違っている場合は定例ミーティング等で指摘できるように。
NotionもしくはClaude側で生成した営業ルールのURLを作り、そこを更新していく」。

```
正本      Notion の公開ページ（1本・URLで配る）
ミラー    94_営業の使い方 ／ 受付シート「使い方」タブ
          → ★本文を持たせない。「ルールはこちら → URL」の1行だけにする
指摘の口  定例ミーティング＋ページ内コメント（＝誤りが人から戻ってくる経路）
```

- **★これは「手順書が2つある」問題への回答**（上の節）。どちらを正本にするかが決まった＝
  **シート側は2つとも降格**。片方を選ぶのではなく、両方を入口に落とす形
- **★正本をシートの外へ出せるのは、更新の頻度が違うから。** ルールは月に数回変わる。
  シートは毎日触る。同じ器に置くと、毎日触る側の都合で書き換えられて腐る
- **★URLを配った時点で消せなくなる**（→ [[reference_notion_archive_line]]）。
  公開ページは作り直さず、同じURLを更新し続ける
- **★公開ページは「誰でも閲覧」の共有設定が配下に効く。** 内部数値・顧客名を
  そのページ配下へ置かない（→ [[reference_link_sharing_inherits_everywhere]]）
- 開いた瞬間の着地点の問題（上の節）はこれで解決しない。**シートのどこにURLを置くか**を
  決めるまでは、営業はページに辿り着かない
- **★3枚目を足す形にしない。** Notionを作って94をそのまま残すと二重管理が三重になる。
  **新設と同時に旧2枚を1行へ縮めるまでが1作業**
- **「公開ページ」は Web公開とワークスペース内共有のどちらかを先に決める。**
  営業に届けるだけなら後者で足りる。Web公開が要る理由を確かめる
  （手順書には顧客名・社内顧客IDの実例・シートURL・チャンネル名が入りやすい）
- **鮮度ヘッダー（種別／最終更新／次回棚卸／責任AI）を付ける**（参照層）。
  手順書が実態から腐るのは既に2回実測済み。**更新責任者が空のままなら必ず腐る**
- **「定例で指摘できるように」は、指摘の出口を先に決めないと死ぬ。**
  コメント欄か③決定ログか ── ★指摘 → 反映 → 反映したことの通知 まで1本にする
  （→ [[reference_log_needs_an_exit]]／[[reference_delivered_but_unread]]）
