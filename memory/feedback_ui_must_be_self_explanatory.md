**2026-09-10、同じ日に2回。** 昼：可視化ツール（lsu-inspect.html）で「見方がよくわからない」。
夜：ブラウザ編集ツール（lsu-editor）で「①この1、2、3の使い方がよくわからん」。

```
こちらの対応（昼）   出口ファイルへ説明を書き足した
結果（夜）           ★別のツールで同じ種類の指摘が再発した
```

**Why**：文書（`feedback_write_for_the_reader`）と同じ型が、**触る画面**でも起きている。
文書は「実装名を出さない」で直るが、**画面は文字の説明を足しても直らない**。
画面自体が「何を押せばいいか」を語っていなければ、使う人は説明文を読みに行かない
（読ませる時点で、ツール本体の設計が負けている）。

**How to apply**：

```
✕ 説明を足す     README・出口ファイルに「①こうしてください②ああしてください」と書く
○ 画面を直す     ★開いた瞬間に「次に何をするか」が1つだけ大きく出ている状態にする
```

- **1度に1つだけ指示を出す（ウィザード型）。** 選択肢や入力欄を全部並べない。
  「①ページを選ぶ→②要素を選ぶ→③動かす」のように、**前の手順が終わるまで次が出ない**形にする
- **ラベルは実装の言葉を使わない。** 「セレクタ」「プロパティ」「diff」等の内部用語ではなく、
  日常の言葉に置き換える（例：「要素を選ぶ」→「直したいものをクリック」）
- **ボタン名は出口ファイルの説明文と1文字も違えないこと。** 説明文だけ先に書いて実装と
  ズレると、「読んでもボタンが見当たらない」という新しい迷子を作る
- **判定は自分で画面を撮って見る。** 「初めて開いた人が、次に何をすればいいか3秒で分かるか」
  を自問し、分からなければ画面を直す。説明を足して終わらせない

**同じ型で起きること** ── 社内向けの検証ツール・営業向けの入力フォーム・有璽氏が直接触る
編集画面。**渡す相手が実装を知らない画面すべて**が対象。
