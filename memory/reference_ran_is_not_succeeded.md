**★実行したことを「済んだ」の印にしない。成功したことを印にする。**

2026-08-20、日次ジョブのディスパッチャが `intake_register` を起動し、
Google Sheets API が **503 The service is currently unavailable** を返して失敗した。
**それなのに `intake_register.done` に当日の日付が書かれた。**

```
いまの挙動   実行した   → done を書く   → その日はもう走らない
あるべき     成功した   → done を書く
             失敗した   → done を書かない。次の周期で再試行する
```

503 は一時的な障害で、15分後に叩けば通る。
**たまたま503を引いた日は、その日の処理が丸ごと飛ぶ。しかも「済んだ」と記録される。**
→ [[reference_silent_rejection_backlog]]（却下＝処理済み扱いで二度と拾われない）と同じ形。

## 一時エラーと恒久エラーを分ける

```
一時（再試行する）    503 / 429 / 500 / タイムアウト / ネットワーク
恒久（即あきらめる）  認証切れ / 権限なし / スクリプトの構文エラー
```

恒久エラーを15分ごとに叩き続けても意味がない。すぐ人へ出す。

**★「諦めた」を「済んだ」と同じ印にしない。** 別の状態として持ち、Slack と心拍へ出す。
同じ印にすると、諦めたことすら分からなくなる。

## ★守りを足した方向だけ堅くなる。足していない方向は無防備のまま残る（2026-08-20 実測）

誤上書きのガードを足したあと、検査役が別のパターンで発火させたら**逆方向の穴**が出た。

```
更新は過敏      率の分母を「その列で変更が生じた社数」にしていた
                → 定常状態（全件一致）では、正当な2件の訂正でも率100%
                → **必ず遮断される。** 法人番号の一括補完のたびに同期全体が止まる
                → 併設した絶対件数15は **一度も効かない**（常に率が先に発火する）
新規は無防備    ★新規作成の経路（plan_create）には同種のガードが無かった
                → 新規20社・60社の作成は全ガードを通過し、書き込みAPI直前まで到達
                → 150社（30.9%）でようやく件数ガードに掛かる
```

- **ガードは「止めたい事故」で試すだけでは足りない。「止めてはいけない正常な運用」でも試す。**
  片方だけ試すと、厳しくなったことを安心と取り違える
- **★率で守るときは、分母が何かを必ず確かめる。** 分母が「変更が生じた件数」だと、
  変更が少ないほど率が上がる ── 平常時ほど発火しやすい、逆立ちした挙動になる
- **守りを1か所へ足したら、対になる経路（更新↔新規、追加↔削除）にも同じ検査があるかを数える**
