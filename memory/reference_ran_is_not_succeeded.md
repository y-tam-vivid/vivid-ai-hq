**★実行したことを「済んだ」の印にしない。成功したことを印にする。**

2026-08-20、日次ジョブのディスパッチャが `intake_register` を起動し、
Google Sheets API が **503 The service is currently unavailable** を返して失敗した。
**それなのに `intake_register.done` に当日の日付が書かれた。**

```
いまの挙動   実行した   → done を書く   → その日はもう走らない
あるべき     成功した   → done を書く
             失敗した   → done を書かない。次の周期で再試行する
```

503 は一時的な障害で、15分後に叩けば通る。
**たまたま503を引いた日は、その日の処理が丸ごと飛ぶ。しかも「済んだ」と記録される。**
→ [[reference_silent_rejection_backlog]]（却下＝処理済み扱いで二度と拾われない）と同じ形。

## 一時エラーと恒久エラーを分ける

```
一時（再試行する）    503 / 429 / 500 / タイムアウト / ネットワーク
恒久（即あきらめる）  認証切れ / 権限なし / スクリプトの構文エラー
```

恒久エラーを15分ごとに叩き続けても意味がない。すぐ人へ出す。

**★「諦めた」を「済んだ」と同じ印にしない。** 別の状態として持ち、Slack と心拍へ出す。
同じ印にすると、諦めたことすら分からなくなる。

## 今日この形は3回出た（2026-08-20）

| 何 | 「作った」 | 「効いていた」 |
|---|---|---|
| Notionのスナップショット | ファイルは実在した | 中身は台帳のID集合だけ。**戻せなかった** |
| 誤上書きのガード | 実装されていた | 実データで**一度も発火していない** |
| 日次ジョブの完了記録 | 書かれていた | 失敗した日も**「済んだ」になっていた** |

**共通しているのは、作った側がその仕組みを1度も発火させていないこと。**
→ [[reference_dangerous_entrypoints]]（実行の入口は実測で1回確かめる）
→ [[reference_notion_restore_path]]（復元を1度も実行していないバックアップはバックアップではない）

## ★守りを足した方向だけ堅くなる。足していない方向は無防備のまま残る（2026-08-20 実測）

誤上書きのガードを足したあと、検査役が別のパターンで発火させたら**逆方向の穴**が出た。

```
更新は過敏      率の分母を「その列で変更が生じた社数」にしていた
                → 定常状態（全件一致）では、正当な2件の訂正でも率100%
                → **必ず遮断される。** 法人番号の一括補完のたびに同期全体が止まる
                → 併設した絶対件数15は **一度も効かない**（常に率が先に発火する）
新規は無防備    ★新規作成の経路（plan_create）には同種のガードが無かった
                → 新規20社・60社の作成は全ガードを通過し、書き込みAPI直前まで到達
                → 150社（30.9%）でようやく件数ガードに掛かる
```

- **ガードは「止めたい事故」で試すだけでは足りない。「止めてはいけない正常な運用」でも試す。**
  片方だけ試すと、厳しくなったことを安心と取り違える
- **★率で守るときは、分母が何かを必ず確かめる。** 分母が「変更が生じた件数」だと、
  変更が少ないほど率が上がる ── 平常時ほど発火しやすい、逆立ちした挙動になる
- **守りを1か所へ足したら、対になる経路（更新↔新規、追加↔削除）にも同じ検査があるかを数える**

## ★閾値を「単位ごと」に置くと、割れば通る（2026-08-20 実測・3周目）

分母を直し、新規側にもガードを足したあと、検査役が別のパターンで叩いたら**また抜けた**。

```
4列にそれぞれ14件ずつ破損（各列は上限15未満）＝計56件   → 全ガード素通り
更新14件 ＋ 新規7件（どちらも単独なら通る量）           → 素通り
単一列15件破損                                          → 正しく停止
```

**ガードが (ルート×列) 単体と、新規単体しか見ていなかった。**
複数列・複数ルートへ薄く分散した破損と、更新と新規の合算に上限が無い。

- **単位ごとの閾値を並べても、全体の上限にはならない。** 攻撃でなく事故でも同じ
  （突合キーが一部壊れれば、影響は複数列へ薄く広がるのが自然）
- **★必ず「全体の合算」を1本置く。** 単位ごとの閾値は、その内側の細かい検知にすぎない
- **検査は「単位を割る」方向で試す。** 上限ちょうど・上限の1つ内側 ×
  複数単位に分散、を必ず叩く

### 3周かかった（自己申告では毎回通っていた）

| 周 | 作る側の申告 | 検査役が実測で見つけたもの |
|---|---|---|
| 1 | 復元を実装した | **PATCHを一度も送っていない**（戻せる保証なし） |
| 2 | ガードを発火させた | **分母が「変更が生じた件数」＝平常時ほど発火**／新規は無防備 |
| 3 | 両方向を実測した | **割れば通る**（分散破損・更新+新規の合算に上限なし） |

**毎回「実測しました」と申告されていた。** どれも嘘ではなく、
**試したパターンの外に穴があった**。作った本人は、自分が想定した壊し方しか思いつかない。

### ★テストで再現できない経路は、検証されないまま残る

合算ガードの検証で「4列に分散した破損」を指示したが、実装できたのは**3列まで**だった。
4列目（代表者・連絡先）は `01_顧客詳細` 由来で、テストが使う台帳データに**含まれていない**。

```
検証できた   台帳（00_企業マスタ）由来の列 ── 法人番号・URL・流入経路
検証できない 01_顧客詳細 由来の列 ── テストデータに存在しない
```

**「テストが書けなかった」は「その経路が安全」ではない。**
未検証として明示的に残し、**そもそもその列が同期対象なのか**を先に確かめる。
同期対象でないなら検証は不要。対象なら、経路が1本まるごと抜けている。

### ★「書き込みを止めた」と「副作用を全部止めた」は別（2026-08-20 実地）

検査役は本番のNotionへ1文字も書かなかった。**だがSlack通知だけは本物の有璽氏のDMへ飛んだ**
（09:30〜09:32 に8件）。有璽氏の受信箱が、検査の副産物で埋まった。

```
止めた     Notion への PATCH / POST      ← ハーネスで遮断していた
止め忘れた Slack への通知                ← notify.py をそのまま呼んでいた
           心拍（⚙️レジスタ）も同じ経路
```

**テストは本番の副作用経路を全部数えてから走らせる。**
`VIVID_NOTIFY_OFF=1` を立てれば `notify.tell/ask` は送らずに stderr へ出す（実測で確認）。

### ★新しい検査は、最初は誤検知だらけ（2026-08-20 実測）

`heartbeat_names_check.py`（PROC_NAME の重複を機械で見つける検査）を作ったとき、
**正常な状態で15件の誤検知が出た。**

```
① わざと壊す      重複を作る／レジスタに無い名前を使う → 正しく鳴った
② ★正常時        何も壊していないのに15件鳴った
                  原因3つを特定して修正 → 誤検知ゼロ
③ 後片付け後      一時ファイルを消して再実行 → クリーンに戻ることを確認
```

**②を飛ばすと、毎朝15件の嘘の警告が出る検査ができあがる。**
慢性的な警告は本物を埋もれさせる（→ [[reference_monitor_must_exclude_parked]]）。

**★検査を作ったら3つとも踏む。** ①鳴るべきときに鳴る ②鳴るべきでないときに鳴らない
③後片付けしたら元に戻る。

### ★共通部品が SystemExit を投げると、except Exception は素通りする（2026-08-22 実測）

「失敗したら心拍に『失敗』を残す」ため `main()` を `try/except Exception` で包んだ。
**★この修正は機能していなかった。**

```
共通部品 api()   エラー時に ★raise SystemExit(...) する作り
SystemExit       ★BaseException 直下。**Exception では捕まらない**
→ 例外は素通りし、心拍は打たれないまま落ちる
→ except BaseException にして初めて効いた（実測で確認）
```

**★同じ穴が別の場所にもあった。** `notion_customer_upsert.py` でも
「SystemExit が呼び出し元の `except Exception` を素通りして無言で落ちる」問題が出て、
`NotionSyncError`（Exception派生）へ変える形で直した（2026-08-20）。

- **★共通部品が何を投げるかを、包む前に確かめる。**
  `except Exception` は「全部拾う」ではない
- **★「try/except を付けた」で終えない。わざと失敗させて、心拍が残るかを見る**
  今回はそれで「付けたのに効いていない」が見つかった
- 直し方は2つ ── ①包む側を `except BaseException` にする
  ②共通部品が `SystemExit` ではなく Exception派生を投げるようにする
  **★②のほうが筋が良い。** ①は包む側ごとに忘れる

#### ★「共通部品」だと思っていたものが、コピペされた別物だった（2026-08-22 実測）

当方は「共通部品 `api()` を直せば全部に効く」と考えた。**前提が間違っていた。**

```
api() は共通モジュールではない
   notion_backfill.py / notion_customer_upsert.py /
   notion_meeting_customer_link.py / notion_memo_dedupe_20260820.py
   ★4本とも **それぞれ別々に定義されている**（コピペ）

```

**★「共通部品」と呼ぶ前に、本当に1か所にあるかを grep で数える。**
名前が同じで中身がコピーされているだけのものは、**直したつもりが1本しか直らない。**

## ★成功時だけ心拍を打つと、障害は「失敗」ではなく「沈黙」で出る（2026-08-24 実測）

`bin/manus.py:369` は **成功したときにしか `heartbeat.beat()` を呼んでいない**。
Manus の APIキーが失効し（`401 api key has been deleted or does not exist`）、
cron の `*/15` は回り続けているのに、レジスタには**1本も「失敗」が届かなかった**。

```
実際に起きたこと   15分ごとに401 → beat を通らない → レジスタの最終実行が固まる
レジスタの表示     「🔴 停止の疑い」＝ 止まっているのは cron だと読める見た目
真実               cron は動いている。死んでいるのは相手側の認証
```

- **🔴の理由が1種類しか無いと、原因の切り分けが人に押し戻される。**
  「沈黙」と「失敗」は別の事象なのに、同じ🔴になる。
- **失敗時こそ beat する。** メッセージに相手のエラー本文を載せれば、
  レジスタを見ただけで「キーを再発行すればよい」と分かる。
  → [[reference_silent_failure_kills_adoption]]

### 代理心拍が同じ値を書き戻し続けているときは、処理の方が死んでいる

`watch_external.py` は成果物の日付を拾ってレジスタへ代理で心拍を書く。
「ビビ 週次ふりかえり」は**毎朝 `2026-08-16 20:09` という同じ値を書き戻され続けていた**。

- **書き戻しが動いていること＝処理が動いていること、ではない。**
  代理心拍の値が前回と同じなら、それは心拍ではなく**遺影**。
- 外形監視で見るときは「更新されたか」を「値が変わったか」で見る。

## ★保留（着手トリガーつき）── api() を1つの共通モジュールへ統合する

いまは**各スクリプトが自前の `api()` を持っている**。同じ穴が新しいスクリプトのたびに開く。

```
やること     api() を1つのモジュールへ統合し、そこで Exception派生を投げるようにする
             → 呼び出し側の規律に依存しなくなる
やらない理由 いま営業の導線を固めている最中。★範囲が広がる
着手トリガー 営業へ渡す作業が一段落したとき
            ／または新しくNotionを叩くスクリプトを作るとき（そこで統合する）
暫定         呼び出し側を except BaseException で個別に塞ぐ
```

### ★同じ型が同じ日に2件（2026-08-24）── 常駐は「一度打って終わり」だと生死が分からない

```
bin/manus.py:369      成功時にしか beat を呼ばない
                      → 15分ごとに401なのにレジスタは沈黙。表示は「🔴 停止の疑い」
                        ＝ cron が止まったように見えるが、実際は認証だけが死んでいた
slack_socket.py       ★初回接続成功時に1回だけ beat。以降フラグが戻らず二度と打たない
                      → 切断・再接続を何度繰り返しても失敗の心拍が出ない
                      常時稼働で数日〜数週間動かす常駐に対して致命的
```

**★定期実行と常駐で、心拍の打ち方が違う。**

```
定期実行（cron・日次）  1回動くたびに1回打つ。★成功でも失敗でも
常駐（launchd）         ★一定間隔で打ち続ける（例：15分ごと）
                        ＋ 再接続を一定回数／時間失敗し続けたら「失敗」を明示的に打つ
                        「起動したときに1回」では、起動した瞬間しか分からない
```

- **常駐の生死は「最後に打った時刻」でしか測れない。** 打たなくなった＝死んだ、と読める形にする
- **★同じ型が2件出たら、個別に直さず型として止める。**
  新しく常駐を作るときは、この節を先に読む

#### ★常駐が心拍を打てないのは、書き方ではなく構造（2026-08-24 実測）

`slack_socket.py` を直すときに真因が分かった。

```
ws.recv()          Slackイベントが来るまで **ブロックし続ける**
ping/pong          ライブラリ内部で吸収され、呼び出し側に戻ってこない
→ メインループの中に心拍を置く限り、**打つ機会がそもそも来ない**
＝「起動時に1回」から抜けられない。bin/manus.py と同型
```

**直し方 ── 心拍は独立したスレッドで打つ。**

```
ConnState          接続状態を共有する
heartbeat_loop     15分間隔の別スレッド（起動直後は5秒の暖機）
   connected=True   → 「成功」
   connected=False  → 切断からの経過秒 ＋ **相手のエラー本文** を添えて「失敗」
down_since         ★再接続のリトライごとにリセットしない。
                   「直前まで繋がっていた瞬間」だけで更新する
                   （でないと、落ち続けているのに経過秒が毎回0に戻る）
```

**★受信を待つ処理と、生きていると告げる処理は、同じループに置けない。**
新しく常駐を作るときは、最初から別スレッドで心拍を設計する。
