**銀行明細CSVは、同じ楽天銀行でも個人と法人で形式が全く違う。3種類ある。**
2026-09-03 に実データで解析（ピタゴラス）。→ [[project_cfo_agent]]（予実の仕分けで使う）

```
① 楽天銀行 個人   RB-torihikimeisai_*.csv          4列・ヘッダー1行目・Shift_JIS
② りそな 個人     *.csv                            21列・ヘッダー1行目・Shift_JIS
③ 楽天銀行 法人   RB-torihikimeisai-zengin_*.csv   ★全銀協形式・ヘッダー行が無い・Shift_JIS
④ PayPay        Transactions_*.csv               13列・★UTF-8(BOM)・日付に時刻あり
⑤ American Express  americanexpress_*.csv         6列・Shift_JIS・★日付列が2つ
```

**★5社で5形式。共通の形は無い。**「銀行だから同じ」「同じ楽天だから同じ」は成り立たない
（楽天は個人と法人でまったく別物だった）。**新しい明細が来たら、必ず1回実物を読む。**

## ④ PayPay（13列・★UTF-8）

```
取引日 ／ 出金金額 ／ 入金金額 ／ 海外出金金額 ／ 通貨 ／ 変換レート ／ 利用国 ／
取引内容 ／ 取引先 ／ 取引方法 ／ 支払い区分 ／ 利用者 ／ 取引番号
```

- **★文字コードがUTF-8（BOM付き）。**銀行3種はすべて Shift_JIS。**PayPayだけ違う。**
- **★日付に時刻が入る**（`YYYY/M/D HH:MM:SS`）。銀行の日付列にはどれも時刻が無い。
- 「取引内容」で 支払い／ポイント獲得／チャージ／返金／送金 が分かれる。
  **★チャージは費用ではない**（残高の移動）。集計から外す判断が要る。

## ⑤ American Express（6列）

```
ご利用日 ／ データ処理日 ／ ご利用内容 ／ 金額 ／ 海外通貨利用金額 ／ 換算レート
```

- **★日付列が2つある。**予実で使うのは「ご利用日」（＝使った日）。
  「データ処理日」は締めの都合であって発生日ではない → [[project_cfo_agent]]（締め日は無視する）。
- 時刻は無い。区切りは `/`。

## ① 楽天銀行 個人（4列）

```
取引日(YYYYMMDD) ／ 入出金(円) ／ 取引後残高(円) ／ 入出金内容
```

## ② りそな 個人（21列）★日付が2種類混在する

```
✕ 先頭の「年/月/日/時/分」  → ★全行同じ値＝CSVを出力した日時。取引日ではない
◎ 後方の「取扱日付 年/月/日」 → ★これが取引日
```

**★取り違えると全件が同じ日付になる。** 前年12月分が期間の端に混ざること・空欄行（フッター）が
あることも実測済み。**正規化してから数える。**

## ③ 楽天銀行 法人＝全銀協形式（★3口座とも構造は完全一致）

レコード種別が同じCSV内に混在する。`1`=ヘッダー / `2`=データ / `8`=トレーラー / `9`=エンド。

```
ヘッダー(種別1・18列・1行)   3 作成年月日 ／ 6 銀行コード ／ 8 支店コード ／ 16 期首残高
データ(種別2・20列)★本体
   0  レコード区分 "2"
   2  ★取引日（和暦YYMMDD）    ← 起算日(列3)と全件一致を実測（不一致0件）
   4  ★入出金区分  "1"=入金 ／ "2"=出金   ★列は分かれていない。符号で判別
   6  ★取引金額（12桁ゼロ埋め・円）        ★列7は全行0
   14 ★摘要（相手方名・半角カナ）
   5/15/16  取引種別コード・摘要2・摘要3 → ★意味は不明（仕様書と未照合）
トレーラー(種別8・9列・1行)  1 入金件数 ／ 3 出金件数 ／ 6 期末残高 ／ 7 データ件数
エンド(種別9・4列・1行)
```

- **★データレコードに残高列が無い。**残高が付くのはヘッダー（期首）とトレーラー（期末）だけ。
  **1取引ごとの残高推移は算出できない。**①（残高あり）と根本的に違う。
- **★入出金の裏取りはトレーラーで取る。**「入金件数／出金件数」と列4の実件数を突合すると
  3口座とも完全一致した（推測ではなく実測）。**新しい銀行のCSVを読むときも同じ手で裏を取る。**

### 和暦→西暦

```python
def wareki_to_seireki(yymmdd):
    """全銀形式 YYMMDD（令和年2桁+月+日）→ YYYY-MM-DD。★令和のみ対応"""
    yy, mm, dd = int(yymmdd[0:2]), int(yymmdd[2:4]), int(yymmdd[4:6])
    return f"{2018 + yy:04d}-{mm:02d}-{dd:02d}"   # 令和1年(01)=2019
```

- **★平成が混ざると自動判別できない。** CSVに元号を示すコードが無く、年の2桁だけでは区別がつかない。
  **将来もっと古い期間のCSVが来たら、ファイル名の対象年月と突き合わせて人が元号を指定する。**
  **自動判定ロジックは組めない。**「組めない」ことを設計に織り込む。

## ⑥ 関西みらい銀行（ILIFE）＝**通帳のスキャンPDF・ただしOCR済みだった**

```
実物   CamScanner製のスキャンPDF。★OCRテキストレイヤーが埋め込まれている
       → 外部OCR（tesseract等）は不要。★この環境にOCRは入っていない（実測）
経路   Google Drive の read_file_content でテキストとして読める
期間   年単位で2本（2025年通年／2026年1-8月）。★月別ではない
```

- **★有璽氏の「通帳のスキャン」＝画像、と前提を置いたが実物は違った。**
  ピタゴラスは「誤記と決めつけず両方を並べて記載」した ＝ [[feedback_dont_call_it_a_typo]] のとおり。
  **★「スキャン」と聞いても、実物を見るまで画像と決めない。**
- **★日付は和暦。**`08-08-31` を西暦2008年と読みかけた（実際は令和8年＝2026年）。
  **ファイル名の期間と突き合わせて確定した。**→ 全銀協形式に続き**和暦は2回目**。
  **★日付を読んだら、必ず別の情報（ファイル名・期間）と突合する。**

## ⑦ 楽天カード（個人）＝ 完全なテキストPDF ★ただし今後はCSVになる

```
今回   SVF JavaPrint PDF Engine 製の請求書PDF。画像ではない。★1か月1本（14本）
```

**★2026-09-04 有璽氏「当月中であればCSVでの出力もできるようなので、今後ルーティンとしては
そのCSVを渡すようにしていきます」。**

```
★「当月中」＝期限がある。過ぎるとCSVを出せずPDFに戻る
→ ★楽天カードだけ、月が変わる前に出す必要がある
→ 毎月の依頼に「楽天カードは当月中に」を必ず添える
```

- **★2026年8月分のPDF読み取りは、この1回きりになる見込み。**次月からはCSV。
  **PDFの読み方は消さずに残す**（当月中に出し損ねた月は、またPDFになるため）。
- ★CSVが来たら形式を1回実測する。**「楽天銀行のCSVと同じ」と決めない**
  （同じ楽天でも個人と法人でまったく別だった実例がある）。

## ★★検算の型 ── 「読めた」ではなく「検算が通った」で判定する

```
通帳     ★前の残高 ＋ 入金 − 出金 ＝ 次の残高
         2026年8月19件を1件ずつ検算 → ★19/19 一致（528,578 → 42,064）
カード    ★請求額と明細の合計が一致するか
         ETC12行の合計＝ご請求金額 → ★一致
```

**★これでOCR・PDF読み取りの誤りを機械で検出できる。**通らない行は金額を推測で埋めず人へ返す。

## ★★大きなデータをLLMに手で転記させない（2026-09-04 実測）

楽天カードPDFを base64 で取得し、**担当が手で転記して2経路目の検算を試みたところ、
19,803バイト → 10,684バイトへ★静かに欠落した。**担当が気づいて方式ごと中止した。

- **★バイナリ・base64・長い数値列は、LLMの出力を経由させない。**
  ファイルはファイルのまま渡す（パスで渡す／その場で処理する）。
- ★同じ型が既にある → [[reference_unicode_escape_kanji_swap]]
  「大容量ファイルを逐語再生成してDriveへ上げ直すのも危険」。**今回はそれの実測。**
- ★結果として**楽天カードの検算は1経路のみ**（通帳側は残高の連続性という内部検算があり実質2経路）。
  **1経路であることを担当が正直に申告した。**
