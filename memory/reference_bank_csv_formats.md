**銀行明細CSVは、同じ楽天銀行でも個人と法人で形式が全く違う。3種類ある。**
2026-09-03 に実データで解析（ピタゴラス）。→ [[project_cfo_agent]]（予実の仕分けで使う）

```
① 楽天銀行 個人   RB-torihikimeisai_*.csv          4列・ヘッダー1行目・Shift_JIS
② りそな 個人     *.csv                            21列・ヘッダー1行目・Shift_JIS
③ 楽天銀行 法人   RB-torihikimeisai-zengin_*.csv   ★全銀協形式・ヘッダー行が無い・Shift_JIS
```

## ① 楽天銀行 個人（4列）

```
取引日(YYYYMMDD) ／ 入出金(円) ／ 取引後残高(円) ／ 入出金内容
```

## ② りそな 個人（21列）★日付が2種類混在する

```
✕ 先頭の「年/月/日/時/分」  → ★全行同じ値＝CSVを出力した日時。取引日ではない
◎ 後方の「取扱日付 年/月/日」 → ★これが取引日
```

**★取り違えると全件が同じ日付になる。** 前年12月分が期間の端に混ざること・空欄行（フッター）が
あることも実測済み。**正規化してから数える。**

## ③ 楽天銀行 法人＝全銀協形式（★3口座とも構造は完全一致）

レコード種別が同じCSV内に混在する。`1`=ヘッダー / `2`=データ / `8`=トレーラー / `9`=エンド。

```
ヘッダー(種別1・18列・1行)   3 作成年月日 ／ 6 銀行コード ／ 8 支店コード ／ 16 期首残高
データ(種別2・20列)★本体
   0  レコード区分 "2"
   2  ★取引日（和暦YYMMDD）    ← 起算日(列3)と全件一致を実測（不一致0件）
   4  ★入出金区分  "1"=入金 ／ "2"=出金   ★列は分かれていない。符号で判別
   6  ★取引金額（12桁ゼロ埋め・円）        ★列7は全行0
   14 ★摘要（相手方名・半角カナ）
   5/15/16  取引種別コード・摘要2・摘要3 → ★意味は不明（仕様書と未照合）
トレーラー(種別8・9列・1行)  1 入金件数 ／ 3 出金件数 ／ 6 期末残高 ／ 7 データ件数
エンド(種別9・4列・1行)
```

- **★データレコードに残高列が無い。**残高が付くのはヘッダー（期首）とトレーラー（期末）だけ。
  **1取引ごとの残高推移は算出できない。**①（残高あり）と根本的に違う。
- **★入出金の裏取りはトレーラーで取る。**「入金件数／出金件数」と列4の実件数を突合すると
  3口座とも完全一致した（推測ではなく実測）。**新しい銀行のCSVを読むときも同じ手で裏を取る。**

### 和暦→西暦

```python
def wareki_to_seireki(yymmdd):
    """全銀形式 YYMMDD（令和年2桁+月+日）→ YYYY-MM-DD。★令和のみ対応"""
    yy, mm, dd = int(yymmdd[0:2]), int(yymmdd[2:4]), int(yymmdd[4:6])
    return f"{2018 + yy:04d}-{mm:02d}-{dd:02d}"   # 令和1年(01)=2019
```

- **★平成が混ざると自動判別できない。** CSVに元号を示すコードが無く、年の2桁だけでは区別がつかない。
  **将来もっと古い期間のCSVが来たら、ファイル名の対象年月と突き合わせて人が元号を指定する。**
  **自動判定ロジックは組めない。**「組めない」ことを設計に織り込む。
