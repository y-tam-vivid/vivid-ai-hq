**★自動レポートは、間違いを1回で終わらせない。毎朝配り直す。**

2026-08-23 の自己監査で見つけた。`ledger_report.py`（毎朝08:10）が
**「法人番号は Web-API のアプリケーションID申請が要る」と毎朝出力していた。**

```
2026-08-20   この前提は否定済み ── 全件ダウンロードは申請不要。データは既にローカルに在る
                                    → [[reference_corp_number_bulk_download]]
2026-08-21〜  ★毎朝のレポートは、それを知らずに古い前提を出し続けた
起きること     読む側（人・AI）は最新の出力を現在地として受け取る
              → 「申請待ちだから動けない」が3日間、毎朝新品の顔で流通した
```

**Why:** 会話の中の訂正は、その会話にしか残らない。
**自動レポートの文面はコードの中にあり、訂正の対象に入っていない。**
しかも出力は毎日新しい日付を持つので、**古いことが外から見えない**
（腐った文書は日付で疑えるが、毎朝出る腐った文言は疑えない）。

## 守ること

```
前提をひっくり返したとき、直す先は3つある
  ① 会話・報告        その場で訂正する（これはやっている）
  ② memory / 手順書   → [[feedback_read_the_artifact_not_the_copy]]
  ③ ★毎日出力する側   cron・GAS・レポート・通知文の中のベタ書き ← ここが抜ける
```

- **★判断を覆したら、その文言を吐いている自動処理を grep する。**
  「申請」「要る」「未対応」のような**結論を断定している語**で探すのが速い
- **★自動出力に前提を書くなら、判定を毎回やり直す形にする。**
  「申請が要る」と固定文で書かず、実データの有無を見て出し分ける。
  固定文は書いた日の判断を永久に凍結する → [[reference_hardcoded_option_lists]] と同じ型
- **毎朝の出力は、人にもAIにも「必ず届く経路」である**（＝いちばん強い流通経路）。
  だからこそ、そこに古い前提が1行あると、届く力の分だけ害も大きい
- 検知 ── 自己監査（毎朝08:40 `self_audit.py`）はこの型を実際に捕まえた。
  **自動処理の出力文そのものを点検の対象にする**のが有効だと実証されている
  → [[feedback_find_holes_without_being_told]]
