### ★deleted の意味 ── 「完了で消している」ではない（2026-08-25 有璽氏が訂正）

当初「終わったら消している」と推測したが**誤り**。実際は次の運用。

```
1つの投稿を手で編集し続けている
  日付ブロック（2026/08/19 ＊… ＊…）  ＝ ★その日に「完了した」ものを日付の下へ手で移した記録
  末尾の日付なしリスト                  ＝ ★まだ終わっていないもの（これから）

完了したら 末尾 → 日付ブロックへ 手で移す。投稿を書き直すので古い投稿が [deleted] になる
```

- **★`[deleted]` は編集の痕跡であって完了の合図ではない。**差分で完了を検知する設計にしない。
- **★「＊」が付いた行は未完了ではなく完了ログ。**取り違えると、済んだ仕事が大量に起票される。
  **日付ブロックの中にあるか外にあるかで意味が180度変わる。**
- **★件数の根拠に message_num を使わない。**deleted を含んだ数字になる。

### 書き方の型は2つ混在

```
まとめ型   日付 ＋ ＊箇条書き    完了ログ。1投稿を編集し続ける
単発型     8/25 09:54  15字     「眉毛エステへ行く ⏎ 接骨院へ行く」  ＝思いついた時に1件ずつ
```

- **「＊」は項目の印であってタスクの印ではない。**マイチャット側でも資料メモの見出しに使われている
  （「＊GameBull デモアカウント」）。**＊ をタスク判定のキーにしない。**
- **私用と仕事が同じ部屋に混ざる**（眉毛エステ／119番の名刺）。オーナー区分での仕分けが要る。

**★中身はタスクだけではない。ここが設計の核心。** 直近30件の実測で4種が混在していた。

| 種類 | 実例（8月） | 割合の体感 |
|---|---|---|
| タスク | 「吉川さんへBPO資料の共有」「STAND UP研修動画の分類分けを検討」 | 2〜3割 |
| 商談・会議のメモ | 「人材・採用：中規模で20万／一人入社で50万」「MIKKEHOUSE 当日に契約を行う」 | 最多 |
| **認証情報（機微）** | **GameBull デモアカウントの URL・ID・パスワードが平文** | 数件 |
| リンク・電話番号・下書き文面 | Drive URL、PR TIMES 用の電話番号、送信前のメール文 | 常時 |

- **★「メモを全部 Notion タスクへ流す」は誤り。**タスクは少数派。全部流すと台帳が汚れる。
- **★機微が混ざっている。**認証情報をそのまま Notion へ写すと、平文の複製が1つ増える
  → [[reference_plaintext_credentials_handling]]。**回収の設計には除外の口が要る。**
- `[deleted]` が多数ある（削除済みメッセージ）。件数の根拠に使わない。

## ★★★★動機はストレスの解消（2026-08-26 有璽氏）── 設計の目的はここ

> 「やったかやってないかを**どのように見極めるか**、自分として**何パーセントやればOK**にするかとか、
> そういった部分、**理想と実際をうまく近づけていきたい**。特に、**やるべきことをやれてない
> みたいな状態、やりたいことがやれてないというのはすごく自分の中でストレス**なので。」

**★これまで「抜け漏れ防止」と呼んでいたものの、本当の動機。**

```
✕ 100%達成を求める設計   → 達成できない日にストレスが増える。逆効果
◎ 「何%でOK」を先に決める → 有璽氏自身が求めている。★基準が無いと毎日が減点法になる
```

- **★満点を定義しない型は、毎日「できなかった」を数える装置になる。**
  枠を作ったこと自体がストレス源になり得る。**達成率の基準を型とセットで持つ。**
- **★「予定通り崩す」と「事故で崩れる」は別物として扱う。**
  現場に出る日・会食の日は最初から対象外にする（下記）。

### ★崩れる日を先に除く ── 分母を動かす

> 「このルーティンを崩さずに、いかにやっていくか。**実際は現場に出ることも含めて多々ある**ので、
> そのあたりのルーティンをどう作るかが課題です。」
> （※「盤に出る」は音声入力。文脈から「現場に出る」と解釈）

```
✕ 週7日を分母にする      現場の日も会食の日も「できなかった」に数えられる
◎ ★カレンダーで判定して分母から除く
    早朝に予定がある日   → その日の朝ブロックは対象外
    夜に会食・遅い予定   → その日の夜ブロックは対象外
    ＝「崩れた」ではなく「今日は対象外」として扱える
```

**★これはAIが自動でできる。**カレンダーを見て前夜に判定し、朝のブリーフィングで
「今日は朝ブロック対象外です」と出せば、崩れてもストレスにならない。

### ★型の目的は2つ。時間の集計はその次（2026-08-25 有璽氏）

```
③ 会議（定例のみ）
```

- **★①に混ぜない。**混ぜると「毎週9.5時間 現場に入る」という型になり、
  週41.8hのうち **23%が架空の枠**になる。移譲の議論も歪む（渡す先が無い仕事を数えてしまう）。
- **★バッファーの消費量は人員リスクの指標になる。**欠員・病欠が多い月ほど消費が増える。
  型に持たせておけば「今月どれだけ現場に取られたか」が後から数えられる。
- **送迎と現場支援はルーティン上は1件に統合してよい**（有璽氏「同じでもいいかもしれません」）。
  実務上は別（送迎＝外へ出る／現場支援＝施設内に留まる）だが、**枠としては連続している**。

### ★カレンダーは実績の全体ではない（2026-08-25 有璽氏）

> 「私の感覚で伝えているものと、カレンダーに実際に入れている・入れていない、
> **空白でその作業を行っているものも一部あるのは実体**です。」

**★カレンダーの空白＝何もしていない、ではない。**予定に起こさず作業している時間がある。
だから **カレンダーだけでは所要時間の実測にならない。**
