**★「警告が出ている」と「対応された」は別。** 2026-08-29 ドーベルマンが実測で見つけた型。
[[reference_monitor_must_exclude_parked]] の裏返し ── あちらは偽陽性で埋もれる話、
こちらは**正しく鳴っているのに誰も拾わない**話。

## 実測（`~/Library/Logs/vivid-daily-jobs.log`）

```
heartbeat_names_check.py
  8/25  「登録漏れ ： intake_notify.py」
  8/26  「相乗り 外形監視／登録漏れ intake_notify.py／実体消失 地雷インデックス」
  8/27  「登録漏れ ： intake_notify.py」
  8/28  「異常なし」
        ★訂正（同日2周目の実測）── これは**実際に解消されていた**。
        intake_notify.py も slack_socket.py も 8/28 にレジスタ登録済みを確認。
        対応までに最大4日かかっていたのが事実で、「拾われなかった」ではない。
        ★1周目の所見をこちらが早合点して「放置」と報告した。**覆ったので訂正する。**
        残る問題は「4日かかったこと」と「その間ずっと同じ見た目で出ていたこと」

notion_backfill.py
  8/23〜8/28 の6実行すべて「★区分待ち 43件」＝ 1件も減っていない
        ★rc=0・心拍「成功」のまま。完全停滞が緑で報告され続けた
```

**検査は正しく動いていた。指摘も正しかった。誰も拾わなかった。**
有璽氏「改善しました言うけど結局止まってたりするやん」はこの構造の指摘。

## 二度と起こさない形

- **★同じ指摘が何日続いているかを数える。** N日を超えたら別扱いで強く出す。
  1日目と5日目を同じ見た目で出すと、慢性化した警告は背景に溶ける
  （[[reference_monitor_must_exclude_parked]]「慢性的な黄色は本物を埋もれさせる」と同根）。
- **★警告が消えたとき、「直った」のか「検査側が拾えなくなった」のかを区別する。**
  消えたことを成功の証拠にしない。直した記録と突き合わせて初めて「直った」と言える。
- **★数字が動いていないことを異常として扱う。** 「43件」が6日続くのは正常ではない。
  件数の絶対値だけでなく**前回との差**を見る。差が0の連続日数を持つ。
- **警告には持ち主と期限を付ける。** 誰が拾うか・いつまでに、が無い指摘は
  出た瞬間に消える（[[reference_log_needs_an_exit]]「出口が無い記録は形骸化する」の警告版）。


## ★もう1つの型 ── 数えているのに、警告の条件に入っていない（2026-08-29 実測）

`~/.vivid-relay/ledger_report.py` は毎朝の台帳レポート。**画面には出しているのに、
alerts（対応が要るものの一覧）へ足すロジックが無い項目が2つあった。**

```
②重複の要判断        16組   → 表示はする。alerts へは入らない（:114-119 が need を無視）
③法人番号が空        58件   → 表示はする。alerts へは入らない（:139-141 が no_hj を無視）

結果 ── 16組・58件がどれだけ積み上がっても
        「対応が要るものはありません」と出続ける
```

**★「except: pass で握りつぶす」型ではない。数えて、表示して、警告にしていない。**
コードは正常に動き、心拍も緑で、数字も画面に出ている。**それでも誰も対応しない。**

- **★画面に出す項目と、警告に入れる項目を別々に書かない。** 出すなら閾値も同時に決める。
  「表示だけして判定しない数字」は、数えていないのと同じ結果になる。
- なお 2026-08-29 の同じ検査で、`except Exception: pass` 約50箇所は精査の結果
  **成果を偽装する危険なものは実質無かった**（大半は通知・心拍の送信失敗を握りつぶす設計）。
  唯一 `chatwork_relay.py:183` が既存ブロックの削除失敗を握りつぶし重複表示を招きうる。
  ★「怪しそう」で数を挙げず、実際に読んで危険度を分けること。

## ★3つ目の型 ── 点検の探針が「被検査対象の実行条件」に依存していた（2026-08-30 実測）

`~/.vivid-relay/hook_selfcheck.py` は毎朝フック6本の生存を見る。**その探針1本が、
フックが正常でも「反応しない」と出す作りだった。**

```
実測（2026-08-30 つる）
  経路1  08:20 の cron       → 「異常 1件 / hook_session_writeback.py ： 反応しない」
                              Notion⚙️レジスタ「フックの生存点検」も🔴失敗
  経路2  08:45 に手で叩く     → 「6本とも正常」rc=0
  → 実体は同じ。★変わったのは作業ツリーの状態だけ
```

**なぜ揺れるか** ── 探針は `transcript_path` を `/nonexistent` にして呼び、
Stopフックが **git status を見て「10分以上さわっていない未コミットがある」ときだけ**出す
文言を待っていた。ツリーがきれいな朝はフックが**設計どおり黙る**。それを故障と読む。

- **★探針は自己完結させる。** 被検査対象が「たまたま発火する条件」に依存した探針は、
  正常な朝に🔴を出す ＝ 偽陽性で🔴が慢性化し、本物の🔴が埋もれる。
  今回は「gitの状態を一切見ない経路（検査2）」を突く形へ置き換えた。
- **★探針が本番のログ・数字を汚していないか見る。** hook_writeback.log は
  `dashboard_data.py` が当日行を数えている ＝ 毎朝1行の探針が稼働盤に偽データを毎日足す。
  子プロセスの `HOME` を一時ディレクトリへ差し替えて回避した。
- **★点検のログに時刻を入れる。** `hook_selfcheck.log` は時刻が無く「3本とも正常」が
  10行並んでいた。**いつ壊れたか読めない**。壊れた瞬間が分からない記録は事後検証に使えない。
- **★「正常しか出せない点検」になっていないか、壊して1回確かめる**
  （[[reference_dangerous_entrypoints]]「実測で1回確かめる」の点検版）。
  実測（2026-08-30 つるの検算）── 一時ディレクトリへフック6本を複製し、
  `hook_session_writeback.py` **だけ**を「即 exit 0 で黙る版」に差し替えて点検を回したところ、
  「異常 1件／hook_session_writeback.py ： 反応しない」と**その1本だけを名指しして rc=1**。
  他5本は正常のまま。＝壊れたときに検出でき、かつ犯人を特定できることまで確かめた。

**★直す側も同じ穴を踏んだ（2026-08-30・ピタゴラスの自己申告）。**
検証用にリポジトリを別の場所へクローンして点検を走らせたが、**スクリプトが REPO を
ハードコードしている**ため、クローン側で叩いても**本物（＝古いコード）を検証していた**。
穴Aと同じ型 ── **正本でない方を見て✓を出す**（[[reference_heartbeat_proves_life_not_results]]）。

- **★「別の場所にコピーして試す」は、それだけでは検証環境にならない。**
  対象がパスをハードコードしていれば、コピーは飾りで実体は本物を見ている。
  **試す前に「このプロセスはどのファイルを開くか」を1回実測する。**

### ★探針を直したら、こんどは「通らない経路」ができた（2026-08-30 ステラ検査）

**状態非依存にするために経路を1本に固定した。その結果、本来の主目的が点検の外に出た。**

```
hook_session_writeback.py の中身        新しい探針が通るか
  検査2（探さずに人へ投げた）             ◯ ここだけ通る
  検査3（1経路断定・観測モード）           ✗ 検査2が先に return 2 する
  ★git status の staleness 検出          ✗ 同上 ── これがこのフック本来の主目的
    （10分以上前の未コミットを差し戻す）
```

将来 `WATCH` タプルの誤記・`STALE_MIN` の計算誤り・`git status` 呼び出しの破損が起きても、
**点検は「6本とも正常」と言い続ける。**

- **★「点検が通った」は「その機能が全部生きている」ではない。探針が通る経路だけが生きている。**
  経路を固定して安定させると、安定と引き換えに**点検されない領域**ができる。
  トレードオフ自体は正しい。**書かずに済ませるのが間違い。**
- **★つるの「壊して確かめた」検算にも同じ限界があった。** ファイルを丸ごと黙る版に
  差し替えたので、確かめられたのは**全体が死んだケースだけ**。部分的な破損は捕まえられない。
  **「壊して確かめた」と書くときは、どう壊したかまで書く。** 壊し方が1種類なら1種類と書く。

## ★4つ目の型 ── memory に書いた「次に読んだ人へ」の指示は、誰にも割り当たっていない（2026-09-02 実測）

**警告ではなく、こちらが自分で書いた申し送りが同じ壊れ方をした。**

2026-08-29、[[reference_slack_tokens_and_socket_mode]] へこう書いた ──
**「★次にこれを読んだ人は、数え直す前に足がかり3つ（api_app_id / bot_id / channel）を
ログへ出す1行を入れること。それが無い限り翌朝も同じ更新が続く」**。

```
2026-09-02 実測
  経路1  slack_socket.py を grep      api_app_id ＝ 0件 ＝ 入っていない
  経路2  ログを日別に数え直す          8/31=1・9/1=6 で再燃。累計31回
  → ★予告どおり「翌朝も同じ更新」を、予告した本人が4日後に書きに来た
```

**なぜ実行されないか。** その memory を毎朝読むのは**棚卸し役（ロビン）だけ**で、
ロビンはコードを触らない役。**役割の外にある対処を、その役の読む場所に書いた。**
結果、指示は毎朝「読まれて」いるのに、毎朝「数え直して追記する」へ化ける。

```
書いた形   「次に読んだ人は◯◯すること」     ← 主語が空席。読む人＝実行できる人とは限らない
要る形     「担当＝ピタゴラス。対象＝<file>:<行>。検査＝ステラ」
```

- **★「次に読んだ人へ」は宛名ではない。** 誰でも宛先に見えて、誰の仕事にもならない。
  上の「警告には持ち主と期限を付ける」と同じ規則が、**memory の本文にも適用される。**
- **★対処を書く場所は、対処できる役が読む場所。** 記録役の読む場所へ対処を書くと、
  記録が対処の代わりになる（この型は同ファイルで 08-29 に一度書いた。**今回が2回目**）。
- **★件数が0の日を解消の証拠にしない。** 8/29・8/30 は0件だったが直っていなかった。
  ただ誰も押さなかっただけ。**0が続いたら、直した記録と突き合わせる**
  （上の「消えたことを成功の証拠にしない」と同根）。

## ★5つ目の型 ── 担当を名指ししても、投げなければ届かない（2026-09-02 実測・同日中に再発）

**4つ目の型を直した当日に、その直し方が足りないと実測で分かった。**

上の4つ目を受けて、ロビンは今朝 `INDEX_仕組み.md:42` へ正しい形で書いた ──
**「未修正・担当ピタゴラス（`slack_socket.py:664-708` の1行の位置）」**。宛名は空席でない。

```
06:29  ロビンが再接続ループを発見し、原因を特定して memory と索引へ記録（担当も名指し）
  ↓   ★誰もピタゴラスへ投げていない
08:36  同じループが再発（5連続。全て「1秒後に再接続」）
08:40  つるが独立に検出。本日の再接続 14回（前日までは1日5〜6回）
```

**名指しは「宛名の欠落」を直す。だが配達はしない。** memory は次にその役が起動されて
初めて読まれる。ピタゴラスは毎朝走る役ではない ＝ **起動されるまで記録は届かない。**

```
足りない   memory へ「担当＝ピタゴラス」と書いて終える     次の起動まで何も起きない
要る       その場で Agent tool でピタゴラスを起動して渡す   記録は控えであって配達ではない
```

- **★2時間で再発する障害に、記録の速さは間に合わない。** 障害の再発間隔より
  「次にその担当が起動する間隔」が長いなら、記録だけでは構造的に負ける。
  **見つけた回に投げる。**
- **★記録役（ロビン・つる）は実装コードを書けない**（`hook_role_guard.py` が正しくブロックする。
  2026-09-02 につるが実測）。だから**投げる以外に手が無い**。書けないことと投げないことを
  混同しない ── 検問は「書くな」と言っているのであって「放っておけ」とは言っていない。
- **★「未修正」と索引に書いた行は、投げた証拠にならない。** 投げたなら
  「ピタゴラスへ発注済み（日付）」へその場で書き換える。**未修正のまま置かれた行は毎朝読まれ、
  毎朝「まだ直っていない」とだけ確認されて終わる**（4つ目の型の再生産）。


### ★同じ型をビビ自身が踏んでいた（2026-08-31 → 09-03 実測）

上の「5つ目の型 ── 担当を名指ししても、投げなければ届かない」は 09-02 に記録された。
**その2日前、ビビが同じことをしていた。**

```
2026-08-31  Slackの投稿文に実在の顧客名「上妻央育／C-0049」が残っているのを発見
            有璽氏へ「今夜のうちにピタゴラスへ直させます」と★口頭で言った
            ★Agent tool で投げていない
2026-09-01  「該当なし」通知5件が本番投稿された ── ★5件すべてに実在名が付いていた
2026-09-03  実測：intake_notify 3件／intake_match 3件／slack_socket 1件 ＝ ★7箇所そのまま
```

**★「直させます」と人へ言うのは、担当へ投げたことにならない。**
言った先は有璽氏で、実行できる担当ではない。**宣言は配達ではない。**

- **★その場で Agent tool を叩くまでが依頼。** 報告文に「直させます」と書いた瞬間に投げる。
  ターンをまたぐと、次のターンには別の話題が来て落ちる。
- ★落ちたことは**報告に出ない**（投げていないので報告そのものが無い）。
  だから**自分が「やります」と言ったことを、指示の側から数え直す**しかない。


## ★★有璽氏が起動しないと何も動かない（2026-09-03 指示）

> 「**私が指示しなくても、自立して動けるような体制に、状況にしておいてください。**」

```
いま自動で動いているもの
  毎朝の自動処理（cron / daily_jobs）      ★動く
  検査役の自己監査（つる・ドーベルマン）    ★動く。指摘も出る
  記録（memory へ書く）                     ★動く

★人（有璽氏）の起動に依存しているもの
  ・検査役が見つけた指摘を「担当へ投げる」
  ・担当が返した成果を「束ねて次へ回す」
  ・判断が要るものを人へ出す
  ＝ 全部ビビ経由。ビビは★有璽氏がセッションを開かないと存在しない
```

**★これが「見つけているのに直らない」の構造。**
検査は毎朝動き、指摘は毎朝出て、memory にも書かれる。**投げる人が居ないだけ。**
（このファイルの「5つ目の型 ── 担当を名指ししても、投げなければ届かない」が
毎朝再生産されている状態）

- **★自立とは「見つける」ではなく「投げる」が自動で回ること。**
  検査を増やしても、投げる経路が人依存なら、指摘は溜まるだけ。
- ★設計は担当へ出す。**ここでビビが一人で作ると、また同じ型を踏む**
  （[[feedback_use_the_team_not_alone]]）。

## ★6つ目の型 ── 不整合を直したら、届いていた経路まで切れた（2026-09-03 実地）

**「混ざっているのは不整合だから直す」は正しい。だが混ざっていたおかげで届いていたものがある。**

```
これまで   self_audit.py（毎朝08:40・crontab で稼働中・実行ログ103件）が
           open_findings() を全件で呼んでいた
           ＝ 系統B（仕組みの自己点検）に系統A（業務データ）が混入していた
           ＝ 不整合だが、結果として系統Aの指摘は毎朝出ていた

今日直した  self_audit.py:217 へ category='B' を追加。混入は解消
            実測：_open_findings_summary() は「（3日以上開いたままの指摘は無い）」を返す

★その結果   系統A の担当は findings_escalate.py だが、実測4経路すべて 0 件
              crontab 0 ／ daily_jobs.conf 0 ／ launchd 0 ／ 実行ログ 0
            ＝ 重複21組・法人番号空59件・受付7日放置を毎日拾う経路が、この修正で消えた
```

**Why:** 直す側は「混入を除いた」としか見ていない。**除いた先に受け皿があるかを見ていない。**
分離のリファクタは、分けた片方が宙に浮きやすい。

**How to apply:**

- **★フィルタを足す前に「除外される側は誰が拾うのか」を実測で確かめる。**
  受け皿が「実装済み・未登録」なら、それは受け皿ではない。**登録されて初めて受け皿になる。**
- **★直す順序を逆にする。** ①受け皿を先に自動実行へ載せる ②動くことを1回見る
  ③それからフィルタを掛ける。逆にすると、その間だけ誰も見ない期間ができる。
- **★「不整合の解消」は、それ自体では改善の証拠にならない。**
  直す前と後で「人へ届く件数」を並べる。減ったなら、減ってよい理由を言えるようにする。
- ★この型は [[reference_monitor_must_exclude_parked]]（偽陽性で埋もれる）とも
  上の「正しく鳴っているのに拾われない」とも違う。**鳴る仕組みそのものを、善意で外した**型。
