**★「警告が出ている」と「対応された」は別。** 2026-08-29 ドーベルマンが実測で見つけた型。
[[reference_monitor_must_exclude_parked]] の裏返し ── あちらは偽陽性で埋もれる話、
こちらは**正しく鳴っているのに誰も拾わない**話。

## 実測（`~/Library/Logs/vivid-daily-jobs.log`）

```
heartbeat_names_check.py
  8/25  「登録漏れ ： intake_notify.py」
  8/26  「相乗り 外形監視／登録漏れ intake_notify.py／実体消失 地雷インデックス」
  8/27  「登録漏れ ： intake_notify.py」
  8/28  「異常なし」
        ★訂正（同日2周目の実測）── これは**実際に解消されていた**。
        intake_notify.py も slack_socket.py も 8/28 にレジスタ登録済みを確認。
        対応までに最大4日かかっていたのが事実で、「拾われなかった」ではない。
        ★1周目の所見をこちらが早合点して「放置」と報告した。**覆ったので訂正する。**
        残る問題は「4日かかったこと」と「その間ずっと同じ見た目で出ていたこと」

notion_backfill.py
  8/23〜8/28 の6実行すべて「★区分待ち 43件」＝ 1件も減っていない
        ★rc=0・心拍「成功」のまま。完全停滞が緑で報告され続けた
```

**検査は正しく動いていた。指摘も正しかった。誰も拾わなかった。**
有璽氏「改善しました言うけど結局止まってたりするやん」はこの構造の指摘。

## 二度と起こさない形

- **★同じ指摘が何日続いているかを数える。** N日を超えたら別扱いで強く出す。
  1日目と5日目を同じ見た目で出すと、慢性化した警告は背景に溶ける
  （[[reference_monitor_must_exclude_parked]]「慢性的な黄色は本物を埋もれさせる」と同根）。
- **★警告が消えたとき、「直った」のか「検査側が拾えなくなった」のかを区別する。**
  消えたことを成功の証拠にしない。直した記録と突き合わせて初めて「直った」と言える。
- **★数字が動いていないことを異常として扱う。** 「43件」が6日続くのは正常ではない。
  件数の絶対値だけでなく**前回との差**を見る。差が0の連続日数を持つ。
- **警告には持ち主と期限を付ける。** 誰が拾うか・いつまでに、が無い指摘は
  出た瞬間に消える（[[reference_log_needs_an_exit]]「出口が無い記録は形骸化する」の警告版）。


## ★もう1つの型 ── 数えているのに、警告の条件に入っていない（2026-08-29 実測）

`~/.vivid-relay/ledger_report.py` は毎朝の台帳レポート。**画面には出しているのに、
alerts（対応が要るものの一覧）へ足すロジックが無い項目が2つあった。**

```
②重複の要判断        16組   → 表示はする。alerts へは入らない（:114-119 が need を無視）
③法人番号が空        58件   → 表示はする。alerts へは入らない（:139-141 が no_hj を無視）

結果 ── 16組・58件がどれだけ積み上がっても
        「対応が要るものはありません」と出続ける
```

**★「except: pass で握りつぶす」型ではない。数えて、表示して、警告にしていない。**
コードは正常に動き、心拍も緑で、数字も画面に出ている。**それでも誰も対応しない。**

- **★画面に出す項目と、警告に入れる項目を別々に書かない。** 出すなら閾値も同時に決める。
  「表示だけして判定しない数字」は、数えていないのと同じ結果になる。
- なお 2026-08-29 の同じ検査で、`except Exception: pass` 約50箇所は精査の結果
  **成果を偽装する危険なものは実質無かった**（大半は通知・心拍の送信失敗を握りつぶす設計）。
  唯一 `chatwork_relay.py:183` が既存ブロックの削除失敗を握りつぶし重複表示を招きうる。
  ★「怪しそう」で数を挙げず、実際に読んで危険度を分けること。

## ★3つ目の型 ── 点検の探針が「被検査対象の実行条件」に依存していた（2026-08-30 実測）

`~/.vivid-relay/hook_selfcheck.py` は毎朝フック6本の生存を見る。**その探針1本が、
フックが正常でも「反応しない」と出す作りだった。**

```
実測（2026-08-30 つる）
  経路1  08:20 の cron       → 「異常 1件 / hook_session_writeback.py ： 反応しない」
                              Notion⚙️レジスタ「フックの生存点検」も🔴失敗
  経路2  08:45 に手で叩く     → 「6本とも正常」rc=0
  → 実体は同じ。★変わったのは作業ツリーの状態だけ
```

**なぜ揺れるか** ── 探針は `transcript_path` を `/nonexistent` にして呼び、
Stopフックが **git status を見て「10分以上さわっていない未コミットがある」ときだけ**出す
文言を待っていた。ツリーがきれいな朝はフックが**設計どおり黙る**。それを故障と読む。

- **★探針は自己完結させる。** 被検査対象が「たまたま発火する条件」に依存した探針は、
  正常な朝に🔴を出す ＝ 偽陽性で🔴が慢性化し、本物の🔴が埋もれる。
  今回は「gitの状態を一切見ない経路（検査2）」を突く形へ置き換えた。
- **★探針が本番のログ・数字を汚していないか見る。** hook_writeback.log は
  `dashboard_data.py` が当日行を数えている ＝ 毎朝1行の探針が稼働盤に偽データを毎日足す。
  子プロセスの `HOME` を一時ディレクトリへ差し替えて回避した。
- **★点検のログに時刻を入れる。** `hook_selfcheck.log` は時刻が無く「3本とも正常」が
  10行並んでいた。**いつ壊れたか読めない**。壊れた瞬間が分からない記録は事後検証に使えない。
- **★「正常しか出せない点検」になっていないか、壊して1回確かめる**
  （[[reference_dangerous_entrypoints]]「実測で1回確かめる」の点検版）。
