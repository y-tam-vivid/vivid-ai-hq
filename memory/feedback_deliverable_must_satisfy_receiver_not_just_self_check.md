**成果物を作るスクリプトの検査は、自分の出力(ファイルの有無・本数)だけでなく、
受け取り手(WordPress・ブラウザ・他社のツール等)が実際に受理できる形かまで見る。**

**Why:** 2026-09-09、LIFE STAND UP テーマzip（`migration/build_theme_zip.sh`）が
「必須5ファイルが揃っている」「page-templates本数が正しい」等、**自分の側の数え上げは
全部合格**のまま有璽氏へ渡り、**本番WordPressで実際にアップロードしたところ
「テーマにstyle.cssスタイルシートがありません」「テーマのインストールに失敗しました」で
弾かれた。**

真因はディレクトリ階層。スクリプトが `theme/` ごとzip化していたため、zip内部は
`theme/lifestandup/style.css`（2階層）になっていた。WordPressのテーマzipは
**zip直下がテーマフォルダでなければならない**（`lifestandup/style.css`＝1階層）という
仕様があり、そこだけがどの検査にも入っていなかった。

```
検査していたこと（自分側の視点）        検査していなかったこと（受け取り手の視点）
  必須ファイルが5つ揃っているか           zipの1階層目が何か
  page-templates の本数が合っているか     style.css が2階層目に実在するか
  検証ツールの混入が0件か                 style.css 冒頭に "Theme Name:" があるか
```

**How to apply:**

- **人に渡すファイル（zip・CSV・PDF等）を作るスクリプトには、自分の出力の数え上げに加えて
  「受け取り手が要求する構造」を検査として書く。** 受け取り手の仕様が分かっているなら
  （WordPressテーマzip・kintone取込CSVの列順・PDFの埋め込みフォント要否 等）、
  その仕様をコードのassertion／exit 1の条件として明示的に書く。
- **「ファイルが揃っている」ことを「使える」ことの証拠にしない。** 内容物の網羅性検査と、
  受信側のパーサが要求する構造検査は別物。前者だけでは今回のように**本番で初めて弾かれる**。
- 受け取り手の要件が分かっている場合は、要件を満たさなければ**その場でexit 1にして
  成果物を残さない**（合否不明のまま渡さない）。
- 同型のスクリプトが他にもあるか（zip・CSV・PDF等を人へ渡す処理）を一度数え、
  同じ検査が抜けていないか確認する → [[reference_dangerous_entrypoints]] の
  「④完走するのに件数だけ静かに違う」と同系統（完走はする・中身の意味が違う）。
- ★応急処置（今回は窓口がzipを手で開いて詰め直した）は一時しのぎ。
  スクリプト側の検査に組み込むまでが対応。
