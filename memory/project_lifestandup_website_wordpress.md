**どれも「エラーは出ない。数字は出る。その数字が間違っている」型。**
判定に使う道具は、判定の前に道具自身を疑うこと。

```
① 白紙でも「撮れた」になる
   症状  PC幅の画素比較で 11,802,706px の差が出た。ページ全体が別物に見えた
   真因  撮影の関数はファイルが出来たかしか見ていない。★真っ白なPNGでも通る
   なぜ白紙だったか  WordPress は siteurl を DBに持っている。8752 で立てても
         8750 へ転送し、転送先には何も無い → 白紙
   対処  ①口は 8750 に固定 ②撮る前に curl でHTMLのバイト数を見る
         ③撮った画像の色数を数え、20色未満なら止める
   ★危なかったのは「PC幅が壊れた」と報告しかけたこと。実物を見て気づいた

② PILの getbbox() は白を「中身」と数える
   症状  全ページの実高が撮影高16,000pxのまま出て、空白だけの分割が量産された
   真因  getbbox() が見るのは「黒(0,0,0)でない画素」。白は中身に見える
   対処  白を背景と決めて、白でない行を下から探す

③ 長いページは1枚で撮れない
   症状  topページだけ実高16,000pxで頭打ち＝下が切れていた
   対処  iframe を y だけ上へずらして撮り、6,000pxずつ継ぐ（lsu-view.html?y=）
```

**★共通する教訓：「取れた値」より先に「取れたことの確からしさ」を見る。**
①は存在で成否を判定していた ②は前提（背景は黒）が違った ③は上限に当たっても
エラーが出なかった。**3つとも、正常に完了して間違った数字を返している。**
→ [[reference_ran_is_not_succeeded]] ／ [[feedback_one_route_is_not_verification]]

## ★重なり（装飾が文字を隠す）── 2026-09-03 実測。20本×3幅×2系統＝120通り

**横あふれとは別の軸。** scrollWidth は1pxも増えないので、横あふれ検査は全部合格で通す。
有璽氏の指摘（「JOIN US がリクルートに重なっている」）を機械が独立に拾えた。

```

  内訳   top-page 63 ／ stand-up-top 19 ／ recruit-top 3 ／ ★他17ページは0
由来     元から重なっていた 85件（100%） ／ ★WordPress化で出た 0件
         （テーマ85件の組が、すべて元HTML側にも存在した）
元HTML   267件。多いのはテーマで外した装飾が元に残っているため
         （prog-poly 19・dc-badge 11・prog-bubble 9 等、テーマに無い5種）
         ★但し書き：元HTMLはCDNからReact等を読む。これはその条件下での状態
```

### ★判定は2つの指標を組み合わせないと間違える

```
比（コントラスト） 文字色 vs 装飾の地の色。★「前に出せば読めるか」を測る
覆う率            装飾が文字の何%を覆うか。★「見えているか」を測る
                  ★この2つは別のことを測っている。片方だけで並べると埋もれる
```
**実例**：`polaroid-b × みんなで えいご あそび` は比10.05（余裕で通る）だが**覆79%**。
比だけで並べていたら確実に見逃した。逆に `tape × 見学・お問い合わせはこちら` は覆5%だが
比1.63 の CTA で、覆う率だけで切ると落ちる。

```
比が低い(3.0未満)         → ★E不可。A/B/C          5組
比は足りるが覆う率が高い   → ★Eでは成立しない→A/B   4組
どちらも問題なし           → E で足りる            18組
```
