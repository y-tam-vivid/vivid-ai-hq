**MacBook がスリープすると、走っているサブエージェントは全部同時に止まる。**
2026-09-04 に5体が「10分無応答」で落ち、うち1体が明示的に返した ──
`API Error: Your computer went to sleep mid-response.`

**★「1体に大量に渡すと落ちる」と誤診し、分割で対処しようとして無駄にした。**
分割しても3体とも落ちた。**真因は件数でも担当でもなく、マシンの電源状態だった。**

## 有璽氏の制約（2026-09-05）

> 「MacBookをスリープにする。**持ち運ぶときにスリープになってしまう**んだけど、これは致し方ない。
> なんかその中でも動いてもらう方法はないかな。**指示はここで出している。（…）
> 裏側ではMac miniで実際は作業させているみたいなことってできないですかね。
> ★今のこのセッションの延長で**ってことです。」

**★スリープを我慢してもらう方向で直さない。**仕組みの問題を人に吸収させない。

## ★★2026-09-05 実測 ── **AIごと mini へ投げられる。「移せない」は誤りだった**

有璽氏の指摘 ──「**AIはミニ側にはないんだっけ？なんでないんだったっけ？**
GitHub側にあるような状態にできるから、それは関係ないんじゃないの？」
**★指摘が正しく、ビビの説明が不正確だった。**

```

実測2  ★非対話 `claude -p` が動く。認証も通っている
実測3  ★nohup で切り離せる。投げた瞬間に返る（rc=0）。45秒後にログへ答えが書かれていた
```

## できること・できないこと（★実測に基づく）

```
✕ ★このセッションのサブエージェントを mini のプロセスにする
   → 仕組みが無い。MacBook で動くので、スリープで止まる

◎ ★スクリプトを mini へ切り離して走らせる（ssh + nohup）
◎ ★AI（claude -p）ごと mini へ切り離して走らせる  ← ★2026-09-05 実測で確認
   → どちらも★MacBook がスリープしても走り続ける。結果はファイルに残る
   → ★セッションは MacBook のまま。新しいセッションを立てる必要は無い
```

```bash
# 投げる（即座に返る）
ssh mini 'nohup python3 ~/.vivid-relay/<script>.py > ~/.vivid-relay/<name>.log 2>&1 &'

# あとで結果を見る（別のターンでよい）
ssh mini 'tail -30 ~/.vivid-relay/<name>.log'
ssh mini 'ls -l ~/.vivid-relay/<出力ファイル>'
```

- **★`ssh mini 'python3 …'` を前面で待たない。**待つと ssh 接続がスリープで切れる。
  `nohup … &` で切り離す。**「投げる」と「結果を見る」を別のターンに分ける。**
- ★mini には Google の認証（`sheets_client.py` / サービスアカウント）が在る。
  **MacBook には無い。**Drive・スプレッドシートを触る処理は元々 mini 側でしか動かない。
- ★`~/.vivid-relay/` は git 管理外。**両機で自動同期されない。**置いたら実測で確認する。

## ★どこまでを「スクリプト」にするか

**LLMに1件ずつ判定させる作業は、たいてい機械で書ける。**

```
機械で書ける   対応表の完全一致／既知パターンの検出／コード表の引き当て／
              日付や金額の正規化／残ったものを「未判定」にする
LLMが要る      ★新しい摘要をどう分類するか＝全体のごく一部
```

**★LLMに回す件数を減らすほど、落ちにくく・速く・毎回同じ結果になる。**
→ fukuchi-core「繰り返す作業はスキル化し、どの端末でも同じ結果が出る状態にする」。

## 🔴 スリープすると「私（ビビ）も止まる」── 報告の出口を先に決める（2026-09-05）

```
                        miniのcron・常駐（slack_socket・daily_jobs）
★止まるもの             窓口（ビビ）のセッションそのもの
                        ★前面のssh（rsync等）── 接続が切れて途中で死ぬ
                        MacBookで起こしたサブエージェント（既知）
```

- **★「miniへ移したから寝てよい」は半分しか正しくない。**
  作業は続くが、**終わったことを伝える相手（窓口）が寝ている。**
- **★だから出口をSlackにする。** mini側の担当・処理が `ask_hub` / `notify.tell()` で
  直接 有璽氏のDMへ出せば、**MacBookが寝ていても届く。**
  → [[project_ask_hub_push_decisions]]。**窓口を経由しないと届かない設計にしない。**
- **★寝る前に1つだけ確かめる ── 前面で走っているsshが無いか。**
  `nohup` で切り離していない ssh は、スリープで**途中のまま死ぬ**（今回の225MBの移送が該当）。
  切り離してあるか、終わっているかを見てから寝る。
- **★「完了したら教えて」と言われた時点で、それはSlackで返すべき用件。**
  ターミナルへ書いても、寝ていれば読まれない → [[feedback_write_for_the_reader]]
  （★届くだけでは不足・押せる形にする、の前段＝**そもそも届く経路にあるか**）。

## ★Slackから返した指示は mini へ通る ── ただし30分で打ち切られる（2026-09-05 実測）

有璽氏「Slackから私が返信することで、Mac mini側にちゃんと伝わる状態になっているの？」

**★経路は全部そろっている。実測した。**

```
①DMを読む       cron */5 で slack_inbox.py（mini）── 稼働中
②ボタンを受ける  slack_socket.py 常駐（pid 90185）── 生存
③振り分け        不可逆な語→止める ／「状況」だけ→claudeを起動せず即答
                 作る・直す・実装・設計・検査 の語→★team_run.py（担当を並列で起こす）
                 それ以外→claude -p を1体
④返す            結果をそのままDMへ返す
```

- **🔴 打ち切りは30分（`TIMEOUT = 1800`）。** これが**制作をSlack経由で回すときの本当の上限。**
  30分を超える工程は、**途中まで**を返して殺される。
  → **★mini側のビビが、長い工程を自分で `nohup` へ逃がして即「着手しました」と返す**形にしないと、
  大きな制作はSlackからは完走しない。**この形はまだ入っていない。**
- **★実績があるのは「状況」の即答だけ。** ログで拾えた直近5回のうち、
  最後は「状況の問い合わせ ： claude を起動せずに答える」。
  **制作の指示がSlack経由で最後まで通った実績は 2026-09-04 の1回のみ**（08:54→08:55）。
  **＝「通るはず」であって「通した」ではない。**
- **★起動時の cwd は `~/vivid-ai-hq`。** 制作物（`~/lifestandup-wp`）ではない。
  規範・記憶は載るが、**対象の場所は指示文に書かないと届かない。**

## ★実際に効いた形 ── 担当を mini で切り離して起動する（2026-09-05・初実行）

有璽氏「この後スリープします。デモサイト側の…ブログの部分も実装させておいてください。」
**＝寝ている間に制作を進める、が初めて本番で走った回。**

```bash
# ①指示文はファイルにして送る（長い指示をコマンド行へ直接書かない）
scp <指示文> mini:~/.vivid-relay/<name>.txt
# ②★nohup と </dev/null で完全に切り離す。& の後に PID を出して掴んでおく
ssh mini 'zsh -lc "cd <作業場所> && nohup ~/.npm-global/bin/claude -p \"\$(cat ~/.vivid-relay/<name>.txt)\" \
  > ~/.vivid-relay/<name>.log 2>&1 < /dev/null & echo 起動PID=\$!"'
# ③★20秒待って生存を確認してから離れる（起動直後に落ちる型がある）
ssh mini 'pgrep -fl "claude -p"'
```

- **★`< /dev/null` を付ける。** 標準入力が ssh に繋がったままだと、切断で死ぬことがある。
- **★指示文には前提を全部書く。** mini 側は会話を持たない。
  ①誰として振る舞うか（agents定義のパス）②対象の場所 ③触らないもの
  ④確かめてから終わること ⑤**★終わったらSlackへ報告する**（ターミナルに誰もいない）
- **★30分の打ち切りは `slack_inbox.py` 経由のときだけ。** この形（窓口が直接 nohup で投げる）
  には時間の上限が無い。**長い制作はこちらで投げる。**
