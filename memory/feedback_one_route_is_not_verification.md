**1つの経路で見て断定するのをやめる。** 2026-08-20、1日で9回同じ型の誤りを出した。

```
404が返った        → 「未接続」と断定  ★実際はデータソースIDをDBのIDとして使っていた
Notionは392件      → ★実際は486件（ページングを読み違えた）
40_活動ログは2行    → ★実際は25行（A列「ログID」は空欄運用。キーはC列だった）
00は805件          → ★実際は416社（行数を件数として出した）
社内顧客ID列が無い   → ★実際はあった（古い計画書の記述をそのまま使った）
fukuchi-sales は未作成 → ★実際はあった
会社名だけで統合判断  → ★法人番号が違う別法人を統合しかけた
```

**Why:** どれも「確かめずに書いた」のではなく **「1つの経路で確かめて、それで足りると思った」**。
有璽氏の言葉：「そういう確認の甘さが多いだろ、いつも」「多面的にちゃんと調べてくれ」。

**How to apply:**

```
数を出すとき    全体読み と キー列の非空カウント の両方を出す
                ★行数と件数は別物。器の行数・空行・数式で埋まった行を数えていないか
                ★「A列＝キー」とは限らない。見出しを見て決める
存在を言うとき   API と 別のAPI（または実物の画面）の2経路
                ★片方しか無いなら「1経路のみ」と明示する
                ★打ち切られた書き出し（Drive read_file_content は各シート約88行）を根拠にしない
突合するとき     会社名だけで判断しない。人名・電話・メール・詳細シートの代表者名まで見る
古い記述        計画書・コメント・過去の要約を現状の説明として読まない。実物を見る
```

**一致しなければ報告しない。** どちらが正しいかを確定させてから出す。

**検査は別の主体に任せる。** 自分で書いたものを自分で検査しても、同じ思い込みが通る。
データの検査役は **つる（data-auditor）**。台帳やDBへ書き込む前に必ず通す。

## ★「使えない」と断じる前に、別の使い方があるかを聞く（2026-08-24 実地）

営業の手順書をどこへ置くかで、Notion を候補から外した。根拠はこれだけ ──

```
実測      Notion のメンバーは3名（有璽氏・柴田・高橋）。松本・鈴木が居ない
断じた    「Notion に置くと営業の3分の2に届かない。Notion案は使えない」
実際      有璽氏の想定は **公開設定のページ**だった。
          ★メンバーでなくても、リンクを知っていれば誰でも読める
```

**メンバー権限という1つの経路しか見ずに、置き場所を1つ潰した。**
実測そのものは正しい（メンバーは3名）。**その実測から引いた結論が飛躍だった。**

- **★道具を候補から外すときこそ、2経路で確かめる。**
  「権限が無い」は「届かない」と同じではない。共有リンク・公開設定・エクスポート・
  埋め込み ── 届け方は複数ある
- **★人が指定した道具を「使えない」と言うときは、使い方を1つしか想定していない可能性を先に疑う。**
  有璽氏が Notion と言ったなら、有璽氏の頭にある使い方がある

### 公開ページを選ぶときに増える制約

```
誰でも読める   ★競合も読める。会社名・顧客名・金額・人物情報を書かない
配下に効く     公開設定はぶら下がるページにも効く → [[reference_link_sharing_inherits_everywhere]]
書いてよい範囲  手順・入口・迷ったときの連絡先まで。
               内部の仕組みの詳細は元々書かない方針なので矛盾しない
```

## ★変種：出力先（stdout / stderr）が機械で違い、片方を捨てて判定が死んだ（2026-08-25）

**`vercel project protection ls` の結果を MacBook で確かめて `2>/dev/null` のまま mini へ配った。
mini では同じ情報が stderr に出るため、判定に使う変数が常に空だった。**

```
MacBook   Node 20   JSON が stdout に出る            → 判定できる
mini      Node 24   「> ssoProtection: {…}」が stderr → 2>/dev/null で捨てて空
結果      保護をONにしても永久に検知できず、本番の中身が載らない状態が続いていた
          （安全側には倒れていたので★誰も気づかない。壊れ方として最悪の形）
```

- **★`2>/dev/null` は「うるさい行を消す」ではなく「判定材料を捨てる」ことがある。**
  CLI の出力先は同じコマンドでも実行環境（Node やCLIの版）で変わる。
  **判定に使うなら `2>&1` で両方拾ってから絞る。**
- **★片方の機械で通った検証を、もう一方で叩かずに配らない。**
  道具を両機へ入れる規範（fukuchi-core）は「入れる」までしか言っていない。
  **入れたあと相手機で1回叩くまでが検証** → [[feedback_batch_the_checks]]。
- 安全側に倒れる設計だと、壊れても悲鳴が出ない。**判定そのものの生死を心拍で見る**
  → [[reference_ran_is_not_succeeded]]。実例の全文は [[project_ops_dashboard_artifact]]。

## ★変種：エラー文を「能力の宣告」として読んだ（2026-08-26）

**Canva のブランドテンプレート機能が `"requires a Canva paid plan"` を返したのを見て、
「このアカウントは無料プラン」と断定した。実際は有料アカウントで、画像生成は通った。**
有璽氏の「有料プランのはず」で覆り、その場で生成を1回叩いたら成功した。

```
エラー文が語ること     ★この機能が、この条件では使えない
エラー文が語らないこと  そのアカウントのプラン／他の機能が使えるか／目的が達成できるか
```

- **★目的の機能を1回叩く前に、周辺機能のエラーで結論を出さない。**
  やりたかったのは画像生成であって、ブランドテンプレートの列挙ではなかった。
  **手前で転んで、本命を叩かずに「できない」と報告した。**
- **★「◯◯が要ります」というエラーは、たいてい機能の階層を語っている。**
  Canva の場合、ブランドテンプレートは Teams 以上。Pro でも弾かれる。
  ＝**プランはあるのに機能だけ無い**という状態が普通に存在する。
- 空配列も同じ型で危ない。`list-brand-kits` が `[]` を返したのは
  「権限が無い」ではなく「まだ1つも作っていない」だった
  → [[feedback_never_write_an_unmeasured_number]] の `ok:false` を見ない変種と同根。
## ★同じ日に3回、確かめ方が足りないまま断定した（2026-08-29）

```
① 「新規6行はすべて180バイト以内」
     実際は4行が超過。★超過の行は同じ出力に出ていた。都合のいい方を採った
     → [[feedback_never_write_an_unmeasured_number]]

② 「検査2に find/grep が入っていない」
     grep のパターンを `SEARCH\|find\\b` と書いて当たらず「無い」と判定した。
     ★実物を開いたら 111-114行目に \bfind\b|\bls\b|\bgrep\b|\bcat\b|\brg\b が
     ちゃんと入っていた。**検索が0件なのは「無い」の証拠ではない**

③ 「検査後にファイルが更新されている可能性」
     更新時刻（07:30）だけを見て言った。★sha256 を照合したら検査役が見た版と
     4本とも完全一致。**更新されていなかった**
```

**★①は出力を選んだ。②は検索を間違えた。③は照合できるのに時刻で代用した。**
共通するのは「**確かめる手段が足りないまま断定した**」の一点。

- **★検索が0件なら、まず検索式を疑う。** 「無い」と言う前に、
  当たるはずの語で1回テストして検索式が生きていることを確かめる
- **★同一性は時刻でなくハッシュで見る。** 更新時刻は「触った」を示すだけで
  「中身が変わった」を示さない。sha256 なら1回で確定する
- **★申告は誰のものでも実物で確かめる。検査役の申告も例外ではない。**
  2026-08-29、検査役が「テストログは削除済み」と申告したが**実物は残っていた**。
  実装した担当の「6ケース実測」も、ログは5行・全て同一秒＝一括投入だった。
  ★悪意ではない。**申告と実物はふつうにズレる。だから実物を見る。**
