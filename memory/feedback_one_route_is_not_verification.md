**1つの経路で見て断定するのをやめる。** 2026-08-20、1日で9回同じ型の誤りを出した。

```
404が返った        → 「未接続」と断定  ★実際はデータソースIDをDBのIDとして使っていた
Notionは392件      → ★実際は486件（ページングを読み違えた）
40_活動ログは2行    → ★実際は25行（A列「ログID」は空欄運用。キーはC列だった）
00は805件          → ★実際は416社（行数を件数として出した）
社内顧客ID列が無い   → ★実際はあった（古い計画書の記述をそのまま使った）
fukuchi-sales は未作成 → ★実際はあった
会社名だけで統合判断  → ★法人番号が違う別法人を統合しかけた
```

**Why:** どれも「確かめずに書いた」のではなく **「1つの経路で確かめて、それで足りると思った」**。
有璽氏の言葉：「そういう確認の甘さが多いだろ、いつも」「多面的にちゃんと調べてくれ」。

**How to apply:**

```
数を出すとき    全体読み と キー列の非空カウント の両方を出す
                ★行数と件数は別物。器の行数・空行・数式で埋まった行を数えていないか
                ★「A列＝キー」とは限らない。見出しを見て決める
存在を言うとき   API と 別のAPI（または実物の画面）の2経路
                ★片方しか無いなら「1経路のみ」と明示する
                ★打ち切られた書き出し（Drive read_file_content は各シート約88行）を根拠にしない
突合するとき     会社名だけで判断しない。人名・電話・メール・詳細シートの代表者名まで見る
古い記述        計画書・コメント・過去の要約を現状の説明として読まない。実物を見る
```

**一致しなければ報告しない。** どちらが正しいかを確定させてから出す。

**検査は別の主体に任せる。** 自分で書いたものを自分で検査しても、同じ思い込みが通る。
データの検査役は **つる（data-auditor）**。台帳やDBへ書き込む前に必ず通す。

## ★変種：出力先（stdout / stderr）が機械で違い、片方を捨てて判定が死んだ（2026-08-25）

**`vercel project protection ls` の結果を MacBook で確かめて `2>/dev/null` のまま mini へ配った。
mini では同じ情報が stderr に出るため、判定に使う変数が常に空だった。**

```
MacBook   Node 20   JSON が stdout に出る            → 判定できる
mini      Node 24   「> ssoProtection: {…}」が stderr → 2>/dev/null で捨てて空
結果      保護をONにしても永久に検知できず、本番の中身が載らない状態が続いていた
          （安全側には倒れていたので★誰も気づかない。壊れ方として最悪の形）
```

- **★`2>/dev/null` は「うるさい行を消す」ではなく「判定材料を捨てる」ことがある。**
  CLI の出力先は同じコマンドでも実行環境（Node やCLIの版）で変わる。
  **判定に使うなら `2>&1` で両方拾ってから絞る。**
- **★片方の機械で通った検証を、もう一方で叩かずに配らない。**
  道具を両機へ入れる規範（fukuchi-core）は「入れる」までしか言っていない。
  **入れたあと相手機で1回叩くまでが検証** → [[feedback_batch_the_checks]]。
- 安全側に倒れる設計だと、壊れても悲鳴が出ない。**判定そのものの生死を心拍で見る**
  → [[reference_ran_is_not_succeeded]]。実例の全文は [[project_ops_dashboard_artifact]]。

## ★プロセスを数えるとき、自分自身が母数に入る（2026-09-03 ロビン・実地）

Slack常駐が二重起動していないかを確かめようとして、こう数えた。

```
経路1  ps aux | grep -c '[s]lack_socket.py'   → 2      ★「二重起動だ」と早合点しかけた
経路2  ps -o pid,lstart,command -p <各pid>    → 1本は自分（claude -p ...）だった
結論   実際は1本。二重起動はしていない
```

**★`[s]` の角括弧トリックは「grep 自身」しか除外しない。**
**そのプロセス名を本文に含む別のプロセスは、そのまま数に入る。**
ここでは**自分（エージェント）の起動コマンドにログ抜粋が丸ごと載っており**、
その中に `slack_socket.py` の文字列があったため、自分で自分を数えていた。

- **★この環境では特に踏みやすい。** 毎朝のエージェントは、材料としてログ本文を
  プロンプトへ埋め込んで起動される。**`ps` の出力にログの中身がそのまま現れる。**
  何を grep しても自分がヒットしうる。
- **対処**：数えたら **pid を1つずつ開いて実体を見る**（`ps -o pid,lstart,command -p <pid>`）。
  件数だけ見ない。`pgrep -f 'slack_socket\.py --run'` のように
  **そのプロセスにしか無い引数まで含める**のも有効。
- **★「2件あった」は、2件が何であるかを見るまで結論ではない。**
  これは「0件だから無い」の裏返し。**多い側にも同じ罠がある。**
  数が増える方向の誤りは「見つかった」ので安心してしまい、かえって止まりにくい。

## ★経路を増やす前に、その経路が差を検出できるかを測る（2026-09-03 リリス実測）

**2経路そろえても、片方がノイズに埋もれていれば1経路と同じ。**

LIFE STAND UP サイトのHTMLをWordPressテーマへ分解し、見た目が変わっていないかを
画素比較で確かめようとした。

```
原本 vs 分解後   3,222px 差（0.0112%）  ← 「ほぼ一致」と書きたくなる
★対照実験       同じものを2回撮っただけで 2,827px 差
                （.bridge-variant の animation:fade 等で描画が毎回ゆれる）
→ 差はノイズ床と同じ桁。★この経路では「差が有るか無いか」を判定できない
```

- **★「0.01%だから一致」と書かない。** 0.01%が小さいかどうかは、**同じものを2回測った差**と
  比べて初めて分かる。比較対象を持たない割合はただの数字。
- **★対照実験を1回入れる。** 測る前に「同じものを2回測る」。そこで出た差が**その経路のノイズ床**。
  実測値がノイズ床を超えないなら、その経路は判定に使えない。**使えないと書く。**
- 今回の判定は残る2経路で出した ── ②JS実行後のDOM突合（差は意図した2点のみ）／
  ③`getComputedStyle` の計算後スタイル（cmp 0バイト差・sha256一致）。
  **画素は捨てた。捨てたことを報告に書いた。** これが正しい形。

前段で「ノイズ床を測れ」を学び、実行し、**その直後にもう一段の穴を踏んだ。**

```

              → 「ノイズ床0だから、この差は本物」と結論し、有璽氏へもそう報告した

  画像の撮影時刻と写り込みで新しい画像だと確かめたのは**正しい形**。

## ★画像に写ったものを、実装の欠陥だと断定した（2026-09-03・撮り方の産物だった疑い）

有璽氏が「スマホ幅で右が切れている」と指摘し、**ビビが画像を開いて確認し、
「ページ全体が390pxより広く、右端が全域で切れています」と断定して報告した。**

```
実測（そのあとリリスが機械で測った）
  Chrome のヘッドレスは★ビューポート幅を500px未満にできない
    --window-size=320 / 360 / 390  → いずれも clientWidth = 500
    --window-size=768 / 1440       → 正しく効く
  ＝ SP画像は「500pxで組んだページを、390pxの窓で切り取った画像」
  → 右が110px切れて当然。★見切れは撮り方が作った像である疑いが強い
  参考：3ページ×5幅の全15通りで scrollWidth == clientWidth（ただし390以下は実質500px）
