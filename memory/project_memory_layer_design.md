**有璽氏の方針（2026-08-24・原文の要点）**

> メモリのMDファイルと他のMDファイルの使い分けをうまくできないか。メモリMDの役割・位置づけを
> 明確にし、**派生的に別のMDファイルも作っていく設計**にできないか。
> 例えば **全体のルール・AIとしてのルールはメモリに帰属**するが、**それぞれの役割や担当は
> 別のファイルで管理**していく。**そうでないと、ファイル上限になったらずっとそうなる。**
> 過去のものは**完全に削除せずアーカイブとして保存**し、**履歴を追えるように**しておきたい。

**★これは「MEMORY.mdを小さくする」話ではない。「増え続けても壊れない形にする」話。**
行を短くする対策は毎回効くが、3日で戻る（[[feedback_memory_index_hygiene]] に実測あり）。

## 設計案（未承認・2026-08-24 時点）

**軸は有璽氏の言葉どおり「全体のルール」と「役割・担当」。** これは frontmatter の `type` とほぼ一致する。

```
毎ターン届く ── ★予算制。ここは増やさない
  規範    fukuchi-core/SKILL.md     AIとしてのルール（全員・全領域に効く）
  記憶    memory/MEMORY.md          ★feedback / user だけ（36本 ≒ 7KB）
                                     ＋「この分野を触るならこれを読む」の入口 6行
  現在地  WORKING.md                いま進行中だけ（★履歴を置かない）

呼ばれたら読む ── ★上限なし。いくらでも増えてよい
  memory/INDEX_営業.md        顧客台帳・kintone・名刺・受付フォーム
  memory/INDEX_仕組み.md      cron・同期・レジスタ・シェル・フック
  memory/INDEX_notion.md      Notion運用・各DB・Drive
  memory/INDEX_発信.md        広報・SNS・Manus・デザイン
  memory/INDEX_エージェント.md 10体の定義・組織・名鑑
  memory/*.md                 実体146本（そのまま。移動しない）

追えるようにする ── ★消さない
  memory/_archive/INDEX_過去.md  索引から降ろしたものを1行ずつ、降ろした日付つきで
  memory/_archive/               過去の版（MEMORY_full_20260821.md が既にある）
```

**見積り: MEMORY.md 23,850 → 約7,000バイト。**新規メモリを100本足しても毎ターンの予算は動かない。

### ★この案の最大の穴と、その塞ぎ方

**分野別索引は「読みに行かないと来ない」。** 規範2-2 が明言している ──
**「着手前に必ず読む」は対策にならない。読む規律に依存する対策は、規律が切れた回にだけ効かない。**
分野別に分けた瞬間、この穴が開く。だから**分けるだけでは劣化**する。

塞ぎ方は「規律」ではなく「入口が自動で連れてくる」形にすること。

```
営業の仕事に着手      → Skill `fukuchi-sales` が発火 → その冒頭で INDEX_営業.md を読む
Notionを読み書き      → Skill `notion運用`（新設 or 既存へ相乗り）→ INDEX_notion.md
エージェントを呼ぶ    → agents/*.md の frontmatter skills: に分野索引を紐づける
                        ★エージェントは MEMORY.md を読んでいない（grep 0件・実測済み）
                          ＝ いまは記憶が届いていない。この設計で初めて届くようになる
最後の砦              → MEMORY.md 本体に「この分野ならこれを読む」を6行だけ残す
```

## ★配り方は2層（2026-08-25 有璽氏・承認とあわせて示された）

> 「大元のメモリは**全エージェント・全AIが閲覧はする**。その上で、いまビビが窓口なので、
> **ビビがエージェント側に、メモリ以外のどのMDファイルを確認しないといけないかを振ってくれたら良い**。
> 一方で、**エージェントごとに基本的に見るべきMDファイルのベースは生まれる**のではないか。
> 都度はビビから、基本はエージェント側に**あらかじめ渡しておく**形が望ましい。」

**目的は「抜け漏れない体制をAI側でも構築すること」。**分けること自体が目的ではない。

```
常設（あらかじめ渡す）    担当ごとの「基本これは必ず見る」セット
                          置き場 = agents/*.md（そのエージェントが起動した時点で必ず届く）
                          例: 営業担当 → INDEX_営業 ／ 開発ライン → INDEX_仕組み
                              ロビン   → INDEX_notion ／ モルガンズ → INDEX_発信

都度（ビビが振る）        案件ごとの「これも見て」
                          ビビが担当を選ぶとき、読むべきMDを一緒に渡す
                          ★ビビ側に対応表が無いと振れない
```

### 二重管理を作らない置き方（★ここを間違えると設計が腐る）

対応表と agents/*.md の両方に「読むもの」を書くと**必ずズレる**（規範2「どれが正本か先に決める」）。

```
正本      memory/INDEX_担当別.md      担当 × 常設で読むMD の対応表。★ここだけが正本
                                      ビビはこの1枚を持って振る

各体      agents/*.md に1行だけ       「あなたの常設セットは INDEX_担当別.md の自分の行」
          ★内容を写さない。写した瞬間に二重管理になる
```

### ★「抜け漏れない」は検査で担保する（設計の要）

分野別に分けると、**どの索引にも載っていないメモリ**が生まれる。いまの `check.sh` 項目4は
**MEMORY.md しか見ていない**ので、層分けした瞬間にこの検査は用をなさなくなる。

```
いま      memory/*.md が MEMORY.md に載っているか       ← 1枚だけ見ている
これから  memory/*.md が MEMORY.md か INDEX_*.md の
          いずれか1つ以上に載っているか                 ← 載っていなければ孤児として赤
          ＋ 担当別対応表に出てくる INDEX_* が実在するか
          ＋ 各 agents/*.md が対応表の自分の行を指しているか
```

**★分ける作業と、check.sh を直す作業は同じ1作業。**検査を後回しにすると、
「分けたつもりで届いていない」が静かに発生する → [[reference_reference_audit_false_negative]]。

## 🔴 実測 ── 同じ棚卸しを2機が別々にやっていた（2026-08-25）

```
このMacBook   8/24 に MEMORY.md を 25,063 → 23,850 へ棚卸し（未push・ahead 6）
Mac mini      8/23・8/25 に「記録の棚卸し」を2回実施（origin/main）
origin/main の MEMORY.md   26,987バイト・146行・180超44行 ＝ ★上限超過のまま
```

- **こちらの棚卸しは向こうに1バイトも届いていない。**向こうは追記を続けている。
- 原因は着手宣言（WORKING.md）を書かずに始めたこと ── **こちらの手順違反**。
  → [[reference_two_sessions_built_the_same_thing]]
- **★この事故そのものが「抜け漏れない体制」の必要性を示している。**
  記憶の構造を触る作業は、必ず WORKING.md に宣言してから着手する。

**★つまり「分ける」と「入口へ結線する」は同じ1作業。片方だけやると事故る。**

### アーカイブの扱い（有璽氏の指示）

- **ファイル本体は動かさない。** `memory/` から出すと `[[リンク]]` と `check.sh` の
  索引整合チェックが壊れる。**移すのは索引行だけ。**
- 索引から降ろすときは `memory/_archive/INDEX_過去.md` へ
  `2026-08-24 | [名前](file.md) — 降ろした理由` の形で1行足す。**履歴はここで追える。**
- **★索引から降りた瞬間、そのメモリは事実上存在しなくなる。**
  だから **どれを降ろすかは必ず有璽氏に一覧で出す**（AIが独断で降ろさない）。

## いまここ（2026-08-25）

**★承認は出た**（2026-08-25 有璽氏「このやり方が最善であれば問題ないので進めてください」）。
**ただし着手はしていない。** 同期🔴かつ Mac mini 側が memory/ を触っている最中のため、
いま作ると3例目の二重作業になる。**先に同期を通す。**

着手の順序（一度に全部作らない → [[feedback_let_it_settle_before_adding]]）

```
0  WORKING.md へ着手宣言 ＋ origin/main を取り込む   ← ★これを飛ばしたのが今回の事故
1  memory/_archive/INDEX_過去.md            器1つ。降ろした索引を日付つきで1行
2  memory/INDEX_担当別.md                   担当 × 常設セットの対応表（正本）
3  INDEX_営業.md を1本だけ作り fukuchi-sales と営業担当エージェントへ結線
   ★ここで「本当に届くか」を肯定形で実測する（→ [[reference_mac_mini_execution_env]]）
4  check.sh 項目4を「MEMORY.md か INDEX_* のいずれかに載っているか」へ拡張
5  効いたら 仕組み／notion／発信／エージェント へ展開
6  MEMORY.md を feedback/user だけに絞る    ★降ろす一覧を有璽氏に出して承認を得る
```

**3で届かなければこの設計は採用しない。** 分けただけで届かなければ、いまより悪くなる。

**★あわせて出す残件**: WORKING.md 45,652バイトは「進行中だけ・履歴を溜めない」という
自分たちのルールに反している。畳んだ完了ログが残っている。**ここを削るのが単独で最も効く。**
