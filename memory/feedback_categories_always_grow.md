**★選択肢を決めたら、その場で「その他」と「増やし方」を用意する。**
有璽氏から**同じ日に2件**出た指摘。案件が違っても同じことを言われている。

```
2026-09-09 LSU            「カテゴリーは今後増えることも想定し設計して」
2026-09-09 かわちばなし    「地域について、その他も選択肢に入れられるようにしておいて。
                            基本は4市ですが★例外も発生すると思われるので」
```

## なぜ毎回これを言われるか

**★こちらが「いま分かっている分」で選択肢を閉じるから。**
4市／6カテゴリ／3区分と決めた瞬間、それ以外が来たときに**入れる場所が無くなる**。
現場では例外が必ず出る。**出たときに器が無いと、人は空欄にするか、無理に近い値へ押し込む。**
どちらも後から見分けがつかない。

## 決めるときに必ずやる3つ

```
① ★「その他」を入れる       どの区分にも当てはまらないものの居場所を作る
② ★選択肢を1か所に置く      ベタ書きしない。マスタ（選択肢タブ・定数）を1つ作り、全部そこを見る
                            → 増やすときに1か所を直せば全部に反映される
③ ★色・見た目も「その他」を用意  4市に色を割り当てたなら、その他の色も先に決める
                            決めておかないと、増えた瞬間に見た目が崩れる
```

## 「その他」を入れるときの注意

- **★「その他」が増えたら、それは新しい区分になりかけている合図。**
  件数を数える仕組みを持ち、**一定数を超えたら独立させるかを人が判断する。**
- **★「その他」に何が入ったかを書く欄も要る。** 「その他」だけでは後から分からない。

## ★同じ日に3件目（2026-09-09・かわちばなし SPOT／SPECIAL）

**★1つの案件の中でも、区分は面ごとに増えていく。**

```
2026-09-09 LSU            「カテゴリーは今後増えることも想定し設計して」
2026-09-09 かわちばなし①  市＝4市＋その他        → 選択肢タブと taxonomy へ集約・済
2026-09-09 かわちばなし②  提供元リンクの種類7つ  → taxonomy へ集約・済（★向こうが note を追加）
2026-09-09 かわちばなし③  ★SPOT の区分 食べる/遊ぶ/観る ・ SPECIAL の区分 特集/グルメ/コラム
                          ＝ どちらも .dc.html に★ベタ書き。「その他」も無い
```

- **★先に集約した区分の隣に、まだ集約していない区分が残る。**
  市とカテゴリを1か所へ寄せた時点で「済んだ」と思ったが、
  同じファイルの中に `cat:` と `tag:` がベタ書きで並んでいた。
  **★「集約した」と言えるのは、そのファイルの区分を全部数えたときだけ。**
- **★数え方**：`grep -o "cat: '[^']*'"` のように**キー名で拾って値を一覧にする**。
  見出しやラベルを目で追っても、データ側のベタ書きは見つからない。
- **★新しい面を作るときが、いちばん安く直せる。** 実データが入る前なら列も定数も動かせる。
  → [[project_kawachibanashi_portal]]（実データ0件のうちに列を挿入した実例）

## ★相手のツールへ「1か所にまとめろ」と言ったときに残るもの

**★相手は自分の側の1か所にまとめる。こちらの器との整合は、こちらが取りにいく。**
2026-09-09、リンクの種類はサイト側 `kawachi-taxonomy.js` に集約されたが、
**こちらのスプレッドシートの選択肢とは別の1か所**。片方だけ増えると食い違う。
役割が違う（人が選ぶ用／画面を描く用）ので統合はしないが、
**種類を足すときは両方**、と決めておく。**指示した側に残る仕事がある。**

## ★増えるのは区分だけではない。件数も増える ── 本文の日本語に埋めた数が古くなる（2026-09-11）

LSU の職員インタビューを **4名 → 5名** にしたとき、選択肢もタクソノミーも正しく増えたのに、
**画面の日本語が3箇所とも4名のまま**だった（リリス／mini が実装中に発見・修正）。

```
★ベタ書きされていた   「4名の言葉には共通する姿勢がありました」
                      「4名のスタッフ」「話を聞いた4名」
直し方                count( lsu_staff_slot_order() ) で出す＝データの数から文を作る
```

- **★「増える想定で設計した」は、たいてい器（選択肢・taxonomy・配列）までしか見ていない。
  文章の中の数字は器の外にある。** grep でしか見つからない。
- **★1件足すときの数え方**：`grep -nE "[0-9]+名|[0-9]+件|[0-9]+つ"` を対象一式へかけ、
  出た数字が**データから出ているか、手で書いてあるか**を1つずつ見る。
  → [[feedback_never_write_an_unmeasured_number]]（数える部品を1か所へ集約して読むだけにする）
- ★同じ形は見出し・メタ説明・OGP・PDFの表紙・メール文面にも出る。**画面だけ直すと残る。**

関連 → [[feedback_dont_call_it_a_typo]]（既存の器を「足りない」と決めつけない）／
[[project_kawachibanashi_portal]] ／ [[project_lifestandup_website_wordpress]]

## ★2026-09-14 区分の軸は「内容」でなく「時間の向き」だった

有璽氏：
> 「**イベントそのものはお知らせ等の意味合いで、今後のイベントのような形で出していた**と思います。
>  あくまで今出しているやつは、活動風景として出しているやつは、**終わったものの報告に近い**ような
>  要素のものだと思います。なので、**ちょっとイベントとは違う**と思われます。」

```
★正しい軸        これから（予告・告知）        終わったこと（報告）
                 ├ お知らせ                    └ 活動
                 └ イベント ← ★これから開く催しの告知
★こちらが使った軸  催しかどうか（内容）        ← ★誤り
```

こちらは「夏祭り」「母の日イベント」「職業体験イベント」という**題名の語**を見て
イベント候補に挙げた。**中身はどれも終わったことの報告**なので、有璽氏の判定は「除外」。

**★区分の名前が内容を指しているように見えても、運用上の軸は別のことがある。**
「イベント」は催しの記事ではなく、**まだ来ていない催しを知らせる枠**だった。

**★だから機械のキーワード判定は、この軸では原理的に当たらない。**
題名に「夏祭り」と書いてあっても、過去か未来かは題名からは決まらない。
→ **区分を機械で振り分ける前に、その区分が何の軸で切られているかを人に1問聞く。**

```
聞くこと   この区分は★何で分けていますか（内容／時間／相手／出どころ）
           ★1つの例を挙げて「これはどちらですか」まで確かめる
やらない   題名の語で当たりを付けて候補を出す（軸が違えば全部空振りになる）
```
→ [[feedback_dont_call_it_a_typo]]（既存の器を自分の解釈で決めつけない）

## ★区分は「現場が実際に書いているもの」の範囲でしか成立しない（2026-09-14 同日）

有璽氏：
> 「逆に**ルールとして、このイベントの活用方法を明確にすべき**だと思います。
>  今、**現状はちゃんと定まってない**し、**現場側はあくまで実施報告の方をブログとして
>  掲載してきた**というのが今までです。」

```
デザイン側が用意した区分   お知らせ ／ 活動 ／ ★イベント
★現場が実際に書いてきたもの  実施報告（終わったこと）だけ
                            ＝「これから」の告知を書く運用が★そもそも無い
結果                       イベントタブは在るのに★中身が永久に0件
```

**★区分を足すと、その区分を埋める仕事が現場に増える。**
誰が・いつ・何を書くかが決まっていない区分は、**器だけ残って空になる**。
→ [[reference_mockup_values_survive_as_real]]（空の器も、作り物と同じく画面を壊す）

**★区分を提案するときに一緒に決めること（これが無いなら足さない）**

```
① 誰が書くか      現場か・事務か・代表か
② いつ書くか      催しの何日前か／終わった直後か
③ 書かれなかったら  タブを隠すのか・空のまま出すのか
④ 既存との境目    「お知らせ」との違いを1文で言えるか
```

**★「定まっていない」と言われたら、決めるのは人。こちらは案を選択肢で出す。**
勝手に消さない・勝手に定義しない。ただし**案を出さずに聞き返すだけにもしない。**

## ★2026-09-14 有璽氏の決定 ── イベントは案A・書くのは本部事務

> 「**イベント区分は案Aでやる。本部事務側が更新できる形を作っていきたい。**」
> 「④ お客様の声2本 → **案1（一覧から外す）**」

```
イベント   ＝ ★これから開く催しの告知（予告）。終わったら活動へ報告を別に書く
書く人     ★本部事務（現場ではない）
           ＝ 現場の運用（実施報告だけ書く）は★変えない。ここが決め手だった
お客様の声  一覧から外し、専用ページ /testimonials/ にだけ出す
```

**★「本部事務側が更新できる形」＝ 画面と手順の設計まで含めてこちらの仕事。**
区分を足すだけでは終わらない。**押す場所を特定した手順書までが1セット。**
→ [[feedback_ui_must_be_self_explanatory]]（説明を足すのでなく画面自体で伝える）

## ★2026-09-15 書く人を決めても、一次情報が無ければ動かない

有璽氏：
> 「イベント情報については、本部事務でやると伝えたが、**一次情報がない中で本部側で作ることは
>  不可能**なので、**現場から吸い上がる仕組みを構築**し、その情報を元に**本部事務がAIを活用**し、
>  イベント情報として掲載できるような、そういうプロセスを考えている。」

**★昨日こちらが決めたのは「誰が書くか」だけだった。**
本部事務は**催しの中身（日時・場所・対象・申込み）を持っていない**。
＝ 書く人を指名しても、材料が無いので**手順書は机上で止まる**。

```
★区分を運用に載せるには4つが要る（1つでも欠けたら動かない）
  ① 一次情報を★誰が持っているか    現場（催しを企画・実施する人）
  ② それを★どう渡すか              ★吸い上げる仕組み ← ★ここが空いていた
  ③ ★誰がどう文章にするか          本部事務 ＋ ★AI
  ④ ★どこに出るか                  イベント区分（作成済み・0本）
```

**★「①を持つ人」と「③書く人」が違うとき、②が設計の本体になる。**
昨日の手順書は③④しか書いていなかった。**①②が無い手順書は、読めても実行できない。**

**★渡すときの検算**：手順書を読んだ人が、**その場で最初の1件を書き始められるか。**
「情報を集めてから書いてください」と書いた時点で、②が未設計だと分かる。
→ [[feedback_ui_must_be_self_explanatory]]／[[feedback_break_down_to_the_work_level]]
