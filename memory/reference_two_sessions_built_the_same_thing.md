**別のマシンで動いているセッションとは、直接やり取りできない。** `ListAgents` に出るのは
**同じマシンのセッションだけ**で、`SendMessage` もそこへしか届かない。
相手が動いていることは `ssh <機械> 'ls /tmp/cc-socks/'` で分かるが、**話しかける手段は無い。**

**Why:** 2026-08-20、MacBook と Mac mini が **同じ「00_企業マスタ → Notion🏢顧客DB の upsert」を
別々に実装した。** どちらも着手宣言を先に書いていなかった。

```
00:09  MacBook  upsert を実行  382件 → 486件（補完309・新規104）
02:42  mini     notion_customer_upsert.py を本実行  → 更新0・新規0
                （＝MacBookが先に書き終えていたので、書くものが無かった）
```

**実害はゼロだった。冪等に作ってあったから助かっただけで、設計で防いだのではない。**
片方が「全部消してから作り直す」型だったら、もう片方の結果は消えていた。

**How to apply:**

```
連携の経路（上から順に試す。★1つで足りると思わない）
  ① WORKING.md へ着手宣言 → commit      正規の経路。ただし相手が pull 停止中だと届かない
  ② 相手のローカルへ直接ファイルを置く    確実。~/.vivid-relay/HANDOFF_*.md など
  ③ Notion（⑥／③）                     両者が見る場所。非同期でよいならここ
  ✕ SendMessage                        ★別マシンには届かない
```

- **相手が `git pull` 停止中なら ①も届かない。** 未コミットがあると ff-only が止まるため。
  こういうときは②を使う。**「commit したから伝わったはず」は成立しない。**
- **書くものは冪等に作る。** 2回走っても壊れないなら、二重実装は事故にならず「無駄」で済む。
  `update` は空欄補完のみ、`create` は突合してから、`clear`→`rebuild` は避ける。
- **着手宣言は「相手のため」ではなく「自分が後で誤解しないため」でもある。**
  2026-08-20 は両セッションとも宣言なしで走り、あとから WORKING.md を見て初めて
  同じものを作っていたと分かった。
- 機械側の補強 → `bin/vivid-sync.sh` が未コミットのファイル名を `SYNC_STATUS.md` へ書き出す
  （宣言を忘れても、触っている実態は見える）。関連 → [[reference_silent_sync_failure]]

## ★別の面で作られたファイルは、このマシンには存在しない（2026-08-28 実地）

claude.ai のチャットが `event-skills-for-claude-code.tar.gz` を「アーカイブにしました」と告げ、
有璽氏がその展開コマンドをこちらへ貼った。**そのファイルは MacBook にも Mac mini にも無かった。**
Downloads・Desktop・/tmp・Drive のどこにも無く、**チャットの添付としてしか存在しなかった。**

```
チャットが「作った」        添付リンクとして存在する（そのチャットの中だけ）
このマシンに「在る」        ~/Downloads へ人が保存して初めて成立する
                           ★この2つの間に自動の橋は無い
```

- **★「作った」「アーカイブにした」は受け渡しの完了ではない。** 面が違えば、
  作った側は自分のマシンへ置けない。**人が1回ダウンロードするまで、実体はゼロ。**
- **★コマンドを貼られても、その前提（ファイルの実在）を先に確かめる。** 2026-08-28 は
  `tar xzf` を打つ前に `ls` で確かめたので、`cp -r` が既存スキルへ何かする前に止まった。
  **貼られた手順は「実在の証拠」ではない。**
- **★受け渡しの正解は git。** ファイルを人が置く → こちらが `vivid-ai-hq` へ commit →
  もう一方の機は `bin/vivid-sync.sh`（15分ごと）で自動的に受け取る。
  **手で mini へ scp すると、以降の改訂のたびに二重管理になる**（有璽氏の指摘・2026-08-28）。
  → [[reference_fix_where_git_reaches]]
- **★base64 で Drive へ流すのは採らない。** バイナリは1バイト崩れると展開できず、
  失敗が「壊れたファイル」として静かに残る。テキストへばらすのも写経＝転記事故を増やす。
  **人が1回ダウンロードするのがいちばん確実で速い。**
## ★同名の untracked ファイルが、同期を永久に止める（2026-08-29 実測）

**2つのセッションが同じファイルを作ると、git の同期がその瞬間から止まる。**
しかも `vivid-sync.sh` の自動処理では解けない。

```
起きたこと
  MacBook 側が bin/setup_ffmpeg.sh を作って push
  mini 側でも同じものが作られた（★untracked のまま・commit していない）
  → merge しようとすると
     error: The following untracked working tree files would be overwritten by merge:
            bin/setup_ffmpeg.sh
  → ★未取込 9件のまま固定。SYNC_STATUS.md が🔴になり
     「いま読んでいる WORKING.md / MEMORY.md は古い」状態が続く
```

**★`vivid-sync.sh` は枝分かれ（behind>0 かつ ahead>0）には対処済み**（過去に
behind=11/ahead=1 で孤立した事故を踏んで `git merge --no-edit` を入れてある）。
**だが untracked の同名衝突は、その merge も弾く。** 自動では絶対に解けない。

### 直し方（可逆・消さない）

```
1  退避する（消さない・移動のみ）   mv して scratchpad へ
2  git merge --no-edit origin/main
3  ★退避した版とリモート版を diff で比較する
   2026-08-29 の実測では **完全に同一**だった（＝両セッションが同じものを作っていた）
4  違っていたら、退避した版の中身を確認してから判断する
```

### ここで一度、誤った断定をしかけた

担当が「`vivid-sync.sh` の自動処理に委ねます」と報告したのに対し、こちらは
**「それは成立しません」と断定しかけた**。実物（`bin/vivid-sync.sh` 90-105行目）を読んだら
枝分かれは既に扱えていた。**担当の判断のほうが正しかった。**
本当の原因は別（untracked の同名衝突）で、**それは読むまで分からなかった**。
→ [[feedback_one_route_is_not_verification]]

**★🔴 が出ている間に現在地を答えない。** 今日、🔴 が出ている状態で有璽氏へ報告を続けていた。
規範（fukuchi-core「届いたものがいつの版か」）に「先に取り込む」と書いてある。


## ★発行と受信が別の機械だと、押しても「見つかりません」になる（2026-09-03）

プッシュ型の判断経路（Slackのボタン）を作ったとき、**運用の決まりが1つ増えた。**

```
★発行は必ず mini から
理由  受付番号の台帳（ask_hub_queue.json）は★出した機械のディスクにできる
      MacBook から出すと、受信側（mini の slack_socket.py）から台帳が見えない
      → ★押しても「受付番号が見つかりません」になる
```

**★「両機に同じ道具を入れる」だけでは足りない。** 道具は両方に在っても、
**状態（台帳）が片方にしかできない**なら、**動く機械は1つに決まる。**
```
道具（コード）   両機に入れてよい。★入れた
状態（台帳）     ★片方にしかできない → ★発行する機械を1つに決める
受信（常駐）     mini にしか無い（MacBook に SLACK_APP_TOKEN が無く原理的に動かない）
```

**★この決まりは「気をつける」では守れない。** MacBookから出した回に必ず壊れる。
**機械で止める仕組みが要る**（発行時に受信側の常駐と同じ機械かを確かめて、違えば止める）。
→ [[reference_hooks_enforce_what_discipline_cannot]]
★いまは決まりだけ。**止める仕組みは未実装**と、そう書いておく。

## ★同じ機械でも二重になる ── DM 1通が2つのビビを起こす（2026-09-04・実害あり）

**別マシンの話だと思っていた。同じ機械の中でも起きる。**

```
有璽氏がSlack DMへ1通書く
   ├─▶ ターミナルで動いているビビ（このセッション）が受ける
   └─▶ slack_inbox.py（cron */5）が拾い、claude -p でビビを**もう1つ起動**する
        実測：ps に PID 15936 `claude -p 「あなたは「ビビ」…」`＋同じDM本文が丸ごと
        08:55 起動・09:17 時点で22分以上走行中
```

**実害（2026-09-04）** ── 2つのビビが同じ `~/.vivid-relay/notify.py` を触った。

```
09:03  こちら側のピタゴラスが改修（ask()をask_hub委譲＝ボタン化）
09:15  ★notify.py が改修前と完全一致する内容へ巻き戻る（こちらの操作ではない）
       実測2経路 ＝ ①sha256 が _backups/notify.py.bak_…0901 と完全一致
                    ②grep で ask_hub 0件・「番号だけでOK」の旧文言が復活
       ＝ 有璽氏がその朝に指摘した記述式が、そのまま戻った
```

- **★着手宣言（WORKING.md）は、相手が読まない経路で起動されていると効かない。**
  `claude -p` で起動された側は WORKING.md を読むが、**こちらが書く前に走り出している。**
- **★同じ依頼を2つの窓口で受けない。** 受け口が2つある構造そのものが原因。
  直すならどちらかに寄せる（例：ターミナルで対応中は slack_inbox の起動を抑止する）。
  **これは設計の分岐＝有璽氏の判断が要る。勝手に片方を止めない。**
- **★巻き戻りは「壊れた」より見つけにくい。** 動くし、エラーも出ない。
  **版を固定して sha256 を取る**運用だけが検知できた → [[reference_freeze_the_version_under_review]]。
- **★検査役が「対象が消えた」と言ってきたら、まず自分で数え直す。**
  今回はステラの申告どおりだった（こちらも独立に2経路で確認して一致）。

## ★1日で5回起きた。MacBook側だけ。miniは無事（2026-09-04 実測）

同じ `notify.py` が **09:15 ／ 10:45頃 ／ 10:53頃 ／（作業終了後にもう1回）** と巻き戻った。

```
実測（ピタゴラスの作業直後にビビが独立に確認）
  MacBook  grep -c ask_hub = ★0      sha256 5c3de558…
  mini     grep -c ask_hub = 27      sha256 d0a23d0d…
→ ★不一致。ピタゴラスの「両機で一致をsha256で確認済み」は、その後にまた戻った
  稼働中の claude プロセス ★20個
```

- **★実害は今のところ無い。定期実行はすべて mini が持つ**（fukuchi-core「定期実行は片方だけ」）。
  MacBook 側の `~/.vivid-relay/` は**誰も実行していない写し**。ここが戻っても Slack の挙動は変わらない。
  **だが「両機を同じ環境にする」原則は破れている。** 片方を正、片方を写しと呼び分けるまで直らない。
- **★原因は特定できていない。** claude プロセスが20個走っており、どれが書いたか追えなかった。
  **着手宣言（WORKING.md）にも該当の宣言は無かった** ＝ 宣言に頼る仕組みが効いていない。
- **★対処は「検知」であって「復元」ではない。** `self_audit.py` に
  `_notify_ask_hub_check()` を新設し、notify.py を実読して委譲の実在を見る。
  無ければ「★人が要る」へ回す。**機械が勝手に書き戻さない**
  （書き戻す側が増えると、巻き戻りと区別がつかなくなる）。
- **★「両機で一致を確認した」は、確認した瞬間の事実でしかない。**
  巻き戻る環境では、**報告を読んだ側がもう一度数える**しかない。

## ★`git add -A` は他人の作業中の変更を巻き込む（2026-09-04・軽微）

ビビが memory を書いてコミットしようとしたら **「nothing to commit」**。
担当が着手宣言を書いた際の `git add -A` が、**ビビの未コミットの追記ごと拾っていた。**

```
実測  grep で追記は実在（内容は無事）
      git log -1 -- <そのファイル> → ★別人のコミット e37d546 に含まれていた
```
- **実害は無い**（消えたのではなく、別のコミットに入っただけ）。
  ただし**履歴を追う人は、そのコミットメッセージからこの変更を見つけられない。**
- **★同じリポジトリを複数が同時に触る前提では、`git add -A` は安全ではない。**
  自分が触ったファイルを名指しで add する方が正確。
  ★ただし全員に徹底させるのは規律依存なので、**「巻き込まれることがある」と知っておく**方を採る。
- **★「nothing to commit」を見たら、消えたと思う前に grep で中身を確かめる。**

## ⛔⛔2026-09-05 夜 再訂正 ── 真因は「2セッション」ではなかった（ピタゴラス実測）

**上の 9/4「ビビが2体走っていた」という説明は、notify.py の巻き戻りの原因としては誤り。**

```
実測（2026-09-05 18時台・2経路）
  経路1  bin/vivid-sync.sh:194 が */15 で bin/setup_hooks.sh を★無条件に呼ぶ
         setup_hooks.sh:38-47 が bin/hooks/*.py を ~/.vivid-relay/ へ★上書きコピーする
  経路2  同じ日に直した bin/hooks/self_audit.py は★生きている
         （_notify_ask_hub_check が実在し、走らせると正しく判定を返す）
  ＝ 消えたのは「~/.vivid-relay 側だけを直した」ファイルだけ。セッション数と無関係
```

- **★このファイルの型（2セッションが同じものを作る）自体は実在する。** 消さない。
  ただし **notify.py の巻き戻りはこの型ではない。** 犯人を取り違えたまま索引に載せると、
  正しい対処（正本を `bin/hooks/` 側にする）に永久に辿り着かない。
- **★「原因を1つ見つけた」で止めない。** 9/4 は ps で2プロセスを見つけた時点で確定させた。
  **同じ日に別のファイルが生き残っていた**という反証を数えていれば、その場で否定できた
  → [[feedback_one_route_is_not_verification]]
- 対処と見分け方は [[reference_fix_where_git_reaches]] の末尾に集約した（本文はそちらが正本）。
