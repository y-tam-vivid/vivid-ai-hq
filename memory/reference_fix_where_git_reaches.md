**★修正を入れる前に「このファイルは配られる場所にあるか」を見る。**

2026-08-21、つるが**同じ日に同じ種類の穴を2つ**直した。**片方は両機へ届き、片方は届いていない。**

```
直したもの                                     置き場所        相手機へ
bin/daily_jobs.sh（実行機ガード）              vivid-ai-hq/    ★自動で届いた
                                               ＝git配下       vivid-sync.sh（*/15）
~/.vivid-relay/automation_inventory_check.py   git管理外       ★届いていない
（daily_jobs.conf を3本目の経路として数える）                  MacBook は毎朝
                                                               偽陽性6件を出し続ける
```

## 置き場所ごとの配布経路

```
~/vivid-ai-hq/ 配下       git → vivid-sync.sh（両機・*/15）→ 自動で届く
                          ★配られる＝置いただけで相手機の cron にも載る
                            → 実行機ガードが要る（心拍の取り合いになる）
~/.vivid-relay/           git管理外。手で入れるまで届かない
                          フック・検査スクリプト・心拍部品の実体はここ
~/.claude/settings.json   git管理外・機械ローカル（絶対パスを含むので配れない）
```

## ★「届かない」は「止まる」ではない

止まっていれば心拍が古くなって🔴が立つ。**届かない場合は古い版が元気に動き続ける。**
つまり **🟢のまま、直したはずの誤検知を出し続ける。** 気づく手がかりが一切残らない。

```
配られなかった      MacBook の automation_inventory_check.py は旧版のまま
                    → 毎朝きちんと動いている7本を「申告倒れ」と報告し続ける
                    → 本物の申告倒れ2件が偽陽性6件に埋もれる
```

## 直すときの手順

1. **git 配下か外かを最初に見る**
2. **git配下なら** ── 相手機でも走ることを前提に、実行機ガードを同時に入れる
   （目印ファイル方式。無ければ心拍も打たずに黙って抜ける）
3. **git外なら** ── 直したその瞬間に「相手機は古いまま」という残件が生まれる。
   **その場で残件として書き出す。**「あとで入れる」は消える
4. **mini から相手機の `~/.vivid-relay/` へは触らない**（ssh で入れると、相手機が
   閉じている日に検査が働かない）→ 相手機での実行＝人の手が要る

**★fukuchi-core「両機を同じ環境にする」は、置き場所によって自動では守られない。**
git 配下だけが自動。それ以外は毎回、人の手を数に入れる。

## ★★ 成果物も同じ構造で消える ── `scratchpad/` を commit しないと相手機に無い（2026-08-23）

**スクリプトだけの話ではない。作った成果物そのものが片方の機械にしか無い。**

```
2026-08-21  MacBook でプレスリリース2本のドラフト scratchpad/press-release-drafts.html を作った
2026-08-23  mini で続きをやろうとしたら **scratchpad フォルダごと存在しない**
            控えの Artifact URL も認証壁で開けず、一次資料PDFも mini の Downloads に無い
            → 文言を引き継げず、memory の確定事実から組み直すことになった
```

- **`scratchpad/` は `.gitignore` に入っていない。** つまり **commit すれば配られる。**
  消えたのは仕組みの制約ではなく、**commit しなかったから**。
- **★「あとで清書するから」で commit を飛ばさない。** 下書きこそ相手機で続きをやる。
  `vivid-sync.sh` はコミット済みだけを push する＝**書きかけは1バイトも飛ばない。**
- **★Artifact のURLを控えとして数えない。** 別セッション・別マシンからは認証で開けない。
  控えとして機能するのは **git に載ったファイルだけ**。→ [[reference_artifact_embed_local_images]]

### ★保留（着手トリガーつき）── どちらかへ寄せる

```
案A  ~/.vivid-relay のスクリプトを ~/vivid-ai-hq/bin/ へ移し、git で配る
     ★認証・ログ・状態ファイルは git に載せない（分離が要る）
案B  同期の仕組みを作る（vivid-sync.sh が bin/hooks/ を配っているのと同じ形）
     ★フックは既にこの形で両機へ自動導入されている。前例がある

やらない理由   いま営業の導線を固めている最中
着手トリガー   営業への引き渡しが一段落したとき
              ／または「片方でしか動かない」事故が実際に起きたとき
暫定           ★直したら、その場で MacBook にも入れる（手作業）
```

**★案Bに前例がある。** `bin/setup_hooks.sh` を `vivid-sync.sh` が15分ごとに呼び、
フックを両機へ自動導入している（2026-08-20 に作った）。同じ形が使える。

## ★「1回やれば済む」で終わらせない ── 配る仕組みごと作る（2026-08-26 有璽氏）

> 「Stopフックを mini にも進めるにはどうしましょうか？ **ただ、これを毎回するのが手間なので、
>   どのようにしていけばそれぞれが自動で入るようになっていきますか？一度やれば問題ないですか？**」

**答え ── いまのままなら「毎回要る」。仕組みを1段足せば「以後ずっと自動」になる。**

```
git で配れるもの      bin/ ・ memory/ ・ .claude/agents,skills ・ WORKING.md
                      → 15分ごとの vivid-sync.sh が両機へ届ける。人の操作は要らない

git で配れないもの    ~/.claude/settings.json（機械ローカル・フックの登録先）
                      ~/.vivid-relay/*.py（git管理外・フックの実体）
                      → ★ここが手作業として残っていた
```

- **★`bin/setup_hooks.sh` は 2026-08-20 から在った。**冪等で、`bin/hooks/*.py` を
  `~/.vivid-relay/` へ複製し `settings.json` へ登録する。
  **2026-08-25 に Stop フックを入れたとき、これを使わず手で settings.json を書いた。**
  ＝ **仕組みが在るのに使わず、mini へ配る経路を自分で塞いだ。**
- **直し（2026-08-26）**: SPEC へ Stop を追加し、**`setup_hooks.sh` を `vivid-sync.sh` から
  15分ごとに呼ぶ**ようにした。以後は **`bin/hooks/` に置いて SPEC へ1行足すだけで、
  15分以内に両機へ自動で入る。**
- **★機械ローカルの設定を触る仕組みは、壊れると Claude Code が起動しなくなる。**
  だから setup 側に3つ入れた ── ①書く前にバックアップ ②JSONとして読めなければ触らない
  ③**変更が無ければ1バイトも書かない**（15分ごとに mtime を動かさない）。
- **一般化 ── 「新しい機械で1回だけ実行する」と書いた手順は、必ず忘れられる。**
  手順書に書くのではなく、**定期実行から呼ぶ**。呼べない性質のものだけを人へ渡す。
