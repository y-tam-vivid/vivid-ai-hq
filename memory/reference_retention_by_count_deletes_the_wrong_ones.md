**2026-08-20 実地。** `cron_apply.sh` が15分ごとに crontab を退避しており、
同じ内容のバックアップが1日24本たまっていた。つるが「20世代で頭打ち」に直した結果 ──

```
消えたもの   crontab_backup_20260818.txt / 20260819.txt  ← その日ただ1本の版
残ったもの   20260820-*.txt を20本                        ← 全部が同一内容の重複
```

**新しい順に本数で切ると、重複が多い日が枠を食い尽くし、1本しか無い日から消える。**
頻度が高い時期ほど保護され、頻度が低い＝希少な版ほど落ちる。逆になっている。

**How to apply:**

| 残す単位 | いつ使うか |
|---|---|
| **日ごとに最新1本** | 定期退避（crontab・設定ファイル）。頻度がばらつくもの |
| **内容が変わったときだけ取る** | 入口側で重複を作らない。これが第一の対策 |
| 本数（N世代） | 1回の実行につき1本しか作らないものに限る |

- **消す前に「何種類あるか」を数える。** 20本あっても中身が1種類なら世代は1つ。
  ファイル数は世代数ではない。
- ★営業ワークブックの `weekly_backup.gs`（8世代・あふれは `_旧世代` へ**移動**）は
  週1回＝1実行1本なので本数で正しい。**移動であって削除でないのも正しい。**
  定期退避に本数制限を入れるなら、まずこの形（消さずに移す）を検討する。
