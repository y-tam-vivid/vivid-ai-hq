# Slack通知の作法 ── 宛先・手段・条件・書式

**2026-09-03、別セッション（予実を扱うビビ）から「通知ルールを教えてほしい」と聞かれ、
探したところ①〜③は3つのファイルに散っており、④は どこにも書かれていなかった。**
同じ問いが次に来たときに探し直さなくて済むよう、1枚に集める。

## ① 宛先 ── DM固定。チャンネルへ投げない

```
DM = 'D0AT4NQ6X7D'    有璽氏とのDM（notify.py:26）
```

**★チャンネルへは投げない**（notify.py:15 に明記・2026-08-20 有璽氏「他のメンバーの
邪魔になる」）。例外は既に運用されている業務チャンネル
（`#01_営業部門-ai確認依頼` の承認ボタン、`#09_事務-議事録管理bot` の議事録通知）だけで、
**新しく人へ判断を仰ぐものはDMへ出す。**

## ② 手段 ── notify.py を必ず通す

```
~/.vivid-relay/notify.py   ask(topic, options, detail='', link='')
                           ★MacBook・mini の両方に実在（2026-09-03 実測）
```

生の `chat.postMessage` を自分で叩かない。共通部品を通す。

**★検査・ドライランでは環境変数 `VIVID_NOTIFY_OFF=1` を必ず立てる。**
立て忘れて**本物の有璽氏のDMへ8件誤送信した事故が実際に起きている**（notify.py:37）。

## ③ 条件 ── 判断が要ることだけ

「判断が要ることは必ずここを通してDMへ出す」（notify.py:4）。
裏を返せば**判断が要らない報告は送らない**。変化が無ければ黙る。

既知の欠陥2つ（次に触る人へ）：

- `slack_pending.json` に古い未回答pendingが残ると `notify.pending()` が
  永久に「判断待ちあり」と誤判定する。**呼び出し側で鮮度チェック（24h）を持つ**
- PENDINGは単一ファイル制約のため、**1回の実行で送れるのは実質1件**

## ④ 書式と機微 ── ★ここだけ当方の解釈。承認は未取得

### 書式（これは明文あり → [[feedback_cannot_copy_from_terminal]]）

- **★有璽氏はターミナルからテキストをコピーできない。** 本文に数字や手順を書いても
  「渡した」ことにならない。`link=` でクリックできるリンクを渡す
- **報告と判断依頼を混ぜない。** 報告なら「返信は要りません」を明記する
- 「◯◯を探して」ではなく、押す場所まで特定して渡す

### 機微（★明文が無い。fukuchi-core の情報ファイアウォールから導いた）

```
書いてよい   何が起きたか／判断が要るという事実／件数の桁／Notionへのリンク
書かない     ★具体的な金額・口座・個人名・個人の支出の内訳
```

根拠は2つ。

1. fukuchi-core「機微本体は正本側に留置し、中間ミラーと分ける」
   → **金額の本体はNotion側に置き、Slackは通知と導線だけにする**
2. **★Slackはスマホのロック画面に通知プレビューが出る。** DMなので本人しか開けないが、
   金額を本文に書くと、画面を伏せていない場面で他人の目に入る

```
NG  「9月の予実：売上◯◯万円・着地見込み△△万円で未達です。どうしますか」
OK  「9月の予実で判断が要る項目が2件あります。数字はこちら → <Notionリンク>」
```

**★この④は当方（オレンジワークス案件のセッション）が2026-09-03 に導出したもので、
有璽氏の承認を得ていない。** 予実・給与・請求など機微度の高いものをSlackへ出す前に、
1度「これでよいか」を確認すること。確認が済んだらこの注記を消す。
