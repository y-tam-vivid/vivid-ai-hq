# Slack通知の作法 ── 宛先・手段・条件・書式

**2026-09-03、別セッション（予実を扱うビビ）から「通知ルールを教えてほしい」と聞かれ、
探したところ①〜③は3つのファイルに散っており、④は どこにも書かれていなかった。**
同じ問いが次に来たときに探し直さなくて済むよう、1枚に集める。

## ① 宛先 ── DM固定。チャンネルへ投げない

```
DM = 'D0AT4NQ6X7D'    有璽氏とのDM（notify.py:26）
```

**★チャンネルへは投げない**（notify.py:15 に明記・2026-08-20 有璽氏「他のメンバーの
邪魔になる」）。例外は既に運用されている業務チャンネル
（`#01_営業部門-ai確認依頼` の承認ボタン、`#09_事務-議事録管理bot` の議事録通知）だけで、
**新しく人へ判断を仰ぐものはDMへ出す。**

## ② 手段 ── notify.py を必ず通す。★経路は2つある

```
~/.vivid-relay/notify.py    ★MacBook・mini の両方に実在。sha256 一致（2026-09-03 実測）
  tell(title, body='', link='')          報告用。返事は要らない
  ask(topic, options, detail='', link='') 判断依頼用
  pending()                              未回答が残っているかを見る
```

生の `chat.postMessage` を自分で叩かない。共通部品を通す。

| | tell() | ask() |
|---|---|---|
| 用途 | 報告 | 判断を仰ぐ |
| 1回に送れる数 | **制約なし** | **実質1件**（PENDINGが単一ファイルのため） |
| 冒頭 | `📋 *題名* （報告です。返信は要りません）` を**自動で付ける** | 選択肢つきで出る |

**★「返信は要りません」を本文へ手で書かない。`tell()` が自動で付ける。** 手で書くと二重になる
（2026-08-20、付けないと有璽氏が「これは答えないといけないのか」と迷った実地が根拠）。

**★検査・ドライランでは環境変数 `VIVID_NOTIFY_OFF=1` を必ず立てる。**
立て忘れて**本物の有璽氏のDMへ8件誤送信した事故が実際に起きている**（notify.py:37）。
`tell()` `ask()` とも先頭で `_muted()` を見るので、立てれば両方止まる。

## ③ 条件 ── 経路で条件が違う

```
判断が要る  → ask()    「判断が要ることは必ずここを通してDMへ出す」（notify.py:4）
報告        → tell()   ★ただし濫発しない。変化があったときだけ
```

**★「判断が要らないなら送らない」は ask() の話。報告には tell() という別経路がある。**
2026-09-03、当方はこれを取り違えてビビへ「報告は送らない」と伝え、訂正を受けた。

既知の欠陥2つ ── **直すのはピタゴラス／検査はステラ**（当方の領域外）：

- `slack_pending.json` に2026-08-20付の古い未回答が残り、`notify.pending()` が
  永久に「判断待ちあり」と誤判定する。**呼び出し側で鮮度チェック（24h）を持つのが暫定対処**
  → 同型の事故が [[reference_pending_decision_does_not_pause_the_pipeline]] にある
- `ask()` は1回の実行で実質1件しか送れない

## ④ 書式と機微 ── ★ここだけ当方の解釈。承認は未取得

### 書式（これは明文あり → [[feedback_cannot_copy_from_terminal]]）

- **★有璽氏はターミナルからテキストをコピーできない。** 本文に数字や手順を書いても
  「渡した」ことにならない。`link=` でクリックできるリンクを渡す
- **報告と判断依頼を混ぜない。** ＝ 経路で分ける（`tell()` と `ask()`）。
  ★「返信は要りません」は `tell()` が自動で付けるので手で書かない
- 「◯◯を探して」ではなく、押す場所まで特定して渡す

### 機微（★明文が無い。fukuchi-core の情報ファイアウォールから導いた）

```
書いてよい   何が起きたか／判断が要るという事実／件数の桁／Notionへのリンク
書かない     ★具体的な金額・口座・個人名・個人の支出の内訳
```

根拠は2つ。

1. fukuchi-core「機微本体は正本側に留置し、中間ミラーと分ける」
   → **金額の本体はNotion側に置き、Slackは通知と導線だけにする**
2. **★Slackはスマホのロック画面に通知プレビューが出る。** DMなので本人しか開けないが、
   金額を本文に書くと、画面を伏せていない場面で他人の目に入る

```
NG  「9月の予実：売上◯◯万円・着地見込み△△万円で未達です。どうしますか」
OK  「9月の予実で判断が要る項目が2件あります。数字はこちら → <Notionリンク>」
```

**🔴 この④は有璽氏の承認が未取得。** 2026-09-03 に当方（オレンジワークス案件のセッション）が
規範から導いたもので、本人の発言ではない。

```
確認する人   ビビ（予実のセッション）★分担として合意済み。当方からは聞かない
確認する中身 「Slackの本文に金額・口座・個人の支出内訳を書かない。
              数字はNotionのリンクで渡す」──この線引きでよいか、の1点
承認後       ビビから当方へ連絡が来る。★来たらこの🔴ブロックを消して「承認済」に書き換える
```

それまでは、予実・給与・請求など機微度の高いものをSlackへ出す前に、この線引きが
未承認であることを踏まえて判断する。
